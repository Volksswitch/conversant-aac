### Test-suite Pass 1 — filler timing + TTS-echo feedback loop (Ken, June 16 2026), v0.3.4

Two defects Ken found running the live conversation-engine test suite, with **Ken's chosen approach** for the second:

1. **Placeholders started/repeated too soon — now driven by the Settings values.** The §6 filler ladder used fixed constants (rung 1 at 0.8 s, rung 2 at +1.7 s) and ignored the user's two Settings: "Initial Placeholder Statement Delay" (`initialDelay`, default 4 s) and "Subsequent Placeholder Statement Delay" (`subsequentDelay`, default 10 s) — exactly the controls whose hint says they govern this. Rewrote `placeholders.js`:
   - **First placeholder lands `initialDelay` seconds after the partner *finishes* speaking** (matching the Settings hint). Because the silence checkpoint that triggers the ladder already consumed `silencePeriod` (`loadSilenceThreshold()`) seconds of that wait, rung 1 waits the remainder: `max(MIN_RUNG1_DELAY=500ms, (initialDelay − silencePeriod) × 1000)`. Defaults → 2 s after the checkpoint = **4 s after the partner stops**.
   - **Subsequent placeholders re-fill every `subsequentDelay` seconds** (rung 1 → next filler is now one `subsequentDelay`, not 1.7 s; the old `rung2`/`rung3` collapsed into one recurring `refill()`/`scheduleRefill()`). Rung 1 is still the inline ACK token (no fetch); rung 2+ are the projection fillers from `placeholders.json`, never the same twice in a row.

2. **App's own TTS was captured by the mic as partner speech (the feedback loop).** While the filler ladder spoke, the mic stayed live (`listeningIntent` true), so SpeechRecognition transcribed the placeholder audio, appended it to `accumulatedText`, reset the silence timer, and **re-fired `handleSilencePeriod`** — which restarted the ladder at rung 1 ("begin/repeat too soon") and bumped `generationToken`, **delaying and even abandoning the already-generated responses** in favor of a regeneration from `partner statement + filler comments`. **Ken's approach (chosen over muting the mic): the app knows exactly what it spoke, so discard only that content — the mic stays on so a partner talking over the filler is still heard; only *unique* content renews the partner's turn.** Implemented as content-based echo filtering, not mic gating:
   - **`tts.js`** broadcasts speaking-state with the spoken text: `onSpeakingChange(cb)` fires `cb(true, text)` on each `speak()` start and `cb(false, null)` on end; a monotonic `speakToken` stops a superseded utterance's late `onend` from reporting a spurious end. `cancel()` also reports the end. Added `isSpeaking()`.
   - **`app.js`** wires it: `tts.onSpeakingChange((speaking, text) => speaking ? stt.noteSpokenStart(text) : stt.noteSpokenEnd())`.
   - **`stt.js`** keeps a list of `activePhrases` the app is currently speaking (each stays matchable for `ECHO_TAIL_MS = 1500 ms` past end-of-speech, to cover recognition lag/trailing audio). `onresult` runs each captured segment through `isEcho()` and **drops matches** (doesn't accumulate, and — crucially — only calls `resetSilenceTimer()` when a *non-echo* segment was heard, so pure echo never renews the turn or re-fires generation). `isEcho` matching (normalized lowercase, punctuation→spaces): **exact** (segment is the phrase), **prefix** (segment is a leading slice — the recognizer's interim builds up as a growing prefix), and **embed** (phrase appears inside the segment — recognizer padding/merging) but **embed is restricted to multi-word phrases** so a short common ACK token ("Okay.", "Right.") can't swallow real partner speech that merely contains that word (e.g. "okay so what do you think"). Empty-after-normalize segments (pure punctuation/noise) count as echo.
   - **Accepted tradeoff:** if the recognizer merges a multi-word filler verbatim with the partner's resumed words into one segment, the whole segment is dropped (the filler is far more likely to be our echo the recognizer extended than the partner reciting our 4-word filler). In practice the filler and the partner's resumed speech are separated by a pause and arrive as different segments.

CACHE_VERSION/APP_VERSION → **`0.3.4`**. **Verified in preview** (no mic/speaker — the acoustic loop itself needs the tablet): app boots clean, no console errors; `tts.onSpeakingChange` broadcasts the spoken text; the `isEcho` matching table passes for all echo cases (exact/prefix/padded filler, ACK token, noise) **and** all genuine-partner cases pass through (including "okay so what do you think" and "right after lunch we left"). *Still to confirm on the test tablet with the mic on: that real placeholder TTS is no longer transcribed back into the partner turn, and that the first placeholder now lands at the user's `initialDelay`.*

**Acknowledgment-token cleanup (Ken, June 16 2026), v0.3.5.** Ken flagged that "Okay." is a poor rung-1 token — it's a common *real* response to a greeting, so a partner hears it as the user's actual reply, not a stall (and being a short common word it also makes TTS-echo filtering fragile). Removed the response-like tokens from `ACK_TOKENS` ("Okay.", "Right.", "I see."); kept only clearly-stalling ones ("Hmm.", "Ah.", "Good question.", "Let me think.", "Oh.", "Mm.", "Well…"). **Design principle for fillers going forward: a placeholder must read as floor-holding "I'm thinking," never as a substantive answer.** The filler set is user-owned/configurable later (Configuration Model); this is just a better default.

### Conversation Engine observations Pass 1 (Ken, June 18 2026), v0.3.9

Five observations from live engine testing; four built this pass (one of the five — the multi-party note — was already future-scoped). Decisions via AskUserQuestion are recorded inline.

1. **Placeholders now cover the *choosing* window, not the AI-latency gap, and only fire for questions (obs 1 + 3, DECIDED: "only while choosing, questions only").** Ken's obs 1 ("start the placeholder timer with the arrival of suggested responses") and obs 3 ("placeholders are inappropriate for STATEMENT, and during pre-closing/closing — they fit QUESTION") are the same problem: the old flow started the filler ladder at the partner-silence checkpoint, *before* the classification came back, so it couldn't gate on action/phase and it fired during pure AI latency. **New model:** `app.js` `handleSilencePeriod` no longer calls `placeholders.start()`; the ladder is started inside `generateOptions` **after** `ingestClassification`, gated by `shouldPlayFiller(snap)` — fires only when `turn_status === COMPLETE`, not a repair-initiator, mode ≠ PRE_CLOSING_CLOSING, phase ∉ {PRE_CLOSING, CLOSING}, and `partner_action ∈ {QUESTION, INVITATION, REQUEST}` (`FILLER_WORTHY_ACTIONS`). `placeholders.js` rewritten to a **single neutral pool** (no rungs): first phrase lands `initialDelay` seconds **after the options appear** (so a quick pick cancels it via `stop()` → **no placeholder at all when not needed**), then re-fills every `subsequentDelay`. The old rung-1 ACK-token concept and the `initialDelay − silencePeriod` math are gone. **Accepted tradeoff (Ken's call):** no floor-holding during the AI-latency wait before options arrive — a brief natural pause before answering a question, deemed fine; fillers earn their keep on the long *choosing* interval.
2. **Filler phrases must be neutral/reflective, never imperative (obs 2a, + Ken's correction).** My first replacement set included "Let me think." / "Give me a second." — Ken corrected: with the flat inflection of the built-in voices, anything **imperative or directed at the partner** ("Let me think", "Give me a second", "Hold on") reads as **curt/annoyed**. New default pool (`placeholders.json`, fallback mirrored inline in `placeholders.js`): **"Good question." / "That's a good question." / "Hmm, interesting." / "That's interesting." / "Oh, interesting." / "I'm thinking about that."** — all non-imperative, multi-word/intelligible, and question-appropriate (safe since we only fire on questions). Also softened the **"Hold on" override button** text from `"Hold on, let me think."` → `"Hmm, let me think about that."`. **Principle:** fillers must read as warm engaged interest, not impatience. *(Ken, June 18 2026: these placeholder statements will eventually need to be **user-editable** — the JSON pool is the seam for that.)*
3. **Response options no longer lead with empty interjections (obs 2b, DECIDED: "strip empty interjections, keep real softeners").** The generation prompt (`llm.js`) literally told the DISPREFERRED slot to open with "Well…"/"Ah…". Changed: DISPREFERRED now opens with a **meaningful** softener that carries content ("I'd love to, but…", "I wish I could —"), not a bare interjection; added a global rule — **no move may begin with** "Ah/Oh/Um/Er/Well/So/Hmm/You know" — "get to the point." User-preferred verbosity will come from the worldview questionnaire later.
4. **TTS-echo feedback loop fixed at the trigger, not just by content match (obs 4, the Pass-6 bug).** Symptom: a placeholder ("I'll have to think about that…") showed up in the *partner* box, pushed away the displayed options, pushed a QUESTION onto the stack though nobody spoke, and options regenerated repeatedly — i.e. repeated AI round-trips. Root cause: the v0.3.4 **content** echo filter (`stt.isEcho`) drops captured segments that *match* our playback, but the recognizer mis-hears its own audio (drops/adds a word), the echo slips past, **renews the silence timer and re-fires generation** → runaway loop. Content matching can't be made robust to mis-transcription, so we added a **trigger-level guard**: `stt.js` tracks `appSpeaking` (set in `noteSpokenStart`/`noteSpokenEnd`, with the existing `ECHO_TAIL_MS` tail → `speechActive()`); while the app is speaking (or within the tail), captured audio does **not** reset the silence timer (`onresult`: `if (heardPartner && !speechActive()) resetSilenceTimer()`) and the checkpoint does **not** fire (`fireSilenceCheckpoint` re-checks every 200 ms until quiet). The mic stays on and non-echo content still accumulates (Ken's v0.3.4 "don't mute the mic" decision preserved) — our own playback just can't drive a generation checkpoint. **Residual (noted):** a mis-transcribed echo can still leave a brief cosmetic flash in the transcript and pollute the *one* next checkpoint's text, but the runaway *loop* (stack growth, option flicker, repeated round-trips) is gone. The eventual robust solution remains Phase-2 partner voice recognition.
5. **Hard-terminate control (obs 5): "End conversation" button.** New persistent override (`index.html` `#endConversationBtn`, `ui.onEndConversationClick`, `app.handleEndConversation`): stops the filler ladder, cancels TTS, stops listening (clears `manualListenArmed`), invalidates in-flight generation (`generationToken++`), drops the uncommitted partner turn, clears palette/transcript, and `engine.reset()`s to STANDBY (empty stack, floor OPEN). **No danger-confirm** (Ken's recommendation accepted) — it's the "hang up" control and committed exchanges are already logged; only the current unselected turn is discarded.

CACHE_VERSION/APP_VERSION → **`0.3.9`**. **Verified in preview** (no API key / mic — the live filler-gating, echo loop, and prompt change need Ken's key + the tablet mic): app boots clean, no console errors; version 0.3.9 in About; the End-conversation button is wired and resets status to standby with no throw; `placeholders.json` carries the neutral set with no single-syllable tokens. *Still to confirm on the test tablet:* that placeholders now fire only on questions and only while choosing, that the neutral phrasing reads better, and that real placeholder TTS no longer re-fires generation.

**Role-differentiated placeholders + per-turn cap (Ken, June 18 2026), v0.3.10 — fixes sequential-filler repetition.** Ken's follow-up on the v0.3.9 neutral set: it was semantically clustered ("Hmm, interesting." / "That's interesting." / "Oh, interesting."), so two fillers in one choosing window sound stupid even without an exact repeat — and a bigger flat pool only papers over it. **Chosen fix (my recommendation C + D, with B folded in): role-differentiated pools by position + a cap.** `placeholders.json` is now a `{ acknowledgment:[], thinking:[] }` object. ### Proportional, two-axis layout (June 21 2026), v0.4.1–v0.4.2

**Design intent (Ken): the conversation layout is sized as a predictable FRACTION of the screen's pixel capacity** — the same share on every tablet, so an element is physically larger on a 13" and smaller on a 10" but always the same proportion. Elements need NOT be the same physical size across devices, only the same share of the pixel box. **Two independent multipliers (Ken's refinement over a single `vmin` basis):** horizontal sizes scale with screen **width** (`vw`), vertical sizes with screen **height** (`vh`), each axis using its own pixel capacity so an off-3:2 window (split-screen/portrait/resized) doesn't collapse both axes to the smaller one. **Font-size is the one exception** — a glyph is a single scalar (can't scale W and H independently), so type picks one basis, `vmin` (keeps text fitting the squeezed axis = height in landscape). All wrapped in `clamp()` with bounds OUTSIDE the real fleet (~1280–1465 wide × ~853–976 tall) so within the fleet everything scales linearly. **What the platform can/can't tell us drives this:** the CSS pixel box (`innerWidth/Height`, `screen`, `devicePixelRatio`, `visualViewport`) is fully knowable and reactive; **physical size (inches) and true density (real PPI) are NOT exposed by any web API** — `devicePixelRatio` is the Windows *scaling* factor, not density. So we anchor to pixels, never millimeters; the doc's "20 mm touch target" is unenforceable and becomes the user-scalable target-size profile knob instead.
- **v0.4.1 — `app/js/viewport.js`:** logs the full platform-knowable metric set (layout viewport, full screen, available area, `devicePixelRatio`, recovered native resolution = `screen × dpr`, visual viewport) at startup and, debounced, on every resize/orientation/keyboard change — so beta testers can report their real pixel box. Physical size deliberately absent (unknowable).
- **v0.4.2 — `styles.css`:** the conversation UI sized on the two axes (vertical→vh, horizontal→vw, font→vmin); replaced the fixed `max-width:1100px` (which pinned the column to identical pixels on every device) with a width-proportional cap `min(96vw,1600px)`. Verified at 1280×853 and 1465×976: vertical metrics track height, horizontal track width, independently; no console errors.

## Auto-update on launch / Start (June 14 2026), v0.2.10

**Problem (Ken):** the app didn't pick up new deployments on launch or when Start was pressed — the old "Ctrl+Shift+R dance." Two causes: (a) the network-first worker's `fetch(request)` still hit the **browser HTTP cache** (GitHub Pages serves `Cache-Control: max-age=600`), so a launch within 10 min of a deploy got stale assets; (b) the registration never rolled a redeployed worker into the running page — a new `sw.js` installed but the page kept the version it launched with.

**Fix (three parts):**
1. **`sw.js` revalidates.** Runtime fetch is `fetch(new Request(request, { cache: 'no-cache' }))` (ETag revalidation — can't serve stale within the max-age window). Precache `addAll` uses `new Request(u, { cache: 'reload' })` so the precached shell is fresh too. (`self.skipWaiting()` on install + `clients.claim()` on activate were already there.)
2. **Auto-reload on new worker (`index.html`).** A `controllerchange` listener reloads the page once when a freshly-activated worker takes control. Guarded with `hadController` (skip the first-ever install, which has no prior controller) and a `reloading` flag (no loop). `reg.update()` is called on `load` to check for a new worker every launch.
3. **Update check on Start (`app.js` `handleStart`).** `navigator.serviceWorker.getRegistration().then(r => r && r.update())` — a cheap no-op when nothing's new; if a new worker is found it activates and the `controllerchange` handler reloads. Covers the "left open, redeploy, press Start" case.

APP_VERSION / CACHE_VERSION → `0.2.10`. **Verified in preview:** worker registers + activates + controls the page, version 0.2.10 in About, no console errors, **no reload loop** on localhost (controllerchange doesn't fire after the first claim when nothing's new). *The redeploy→auto-reload path itself can't be exercised in the preview (needs a real new deployment) — confirm on the test tablet that a fresh deploy now appears on relaunch without a hard refresh.*

## Settings Panel — usability pass (June 14 2026), v0.2.8

Six Settings-panel improvements shipped (Ken's list), modeled on the Keyguard Designer web app's settings panel (`keyguard-designer-web/app.html`, the second working directory). *(Superseded in v0.2.16: the **Save button was removed** — every control now applies AND persists immediately; the "Save persists / Close keeps for the session" wording in items 1 and 3 below is historical.)*

1. **"Cancel" → "Close".** Footer button relabeled (`index.html`). Behavior unchanged — it dismisses without persisting; **Save** persists.
2. **Draggable modal.** Added a dark title-bar `#settingsHeader` ("Settings" + faint "drag to move" hint) as the drag handle. `initSettingsDrag()` in `app.js` (adapted from Keyguard's `mousedown` drag, but using **pointer events** + `setPointerCapture`): on first drag it converts the native `<dialog>`'s UA centering to pixel `left/top` with `margin:0`, then tracks the pointer clamped to the viewport. Stays modal — the backdrop still blocks the app behind it — but can be moved aside. Position persists for the session.
3. **Live-apply of UI/behavior settings while the modal is open.** Settings that change app behavior now take effect on `change`, not only on Save, so (with the panel dragged aside) the effect is visible/audible immediately — the pattern Keyguard uses. Wired in `openSettings()` via `.onchange`: voice (`tts.setVoice`), silence threshold (`stt.setSilenceThreshold`), keyboard mode (`keyboard.setMode`). Save persists to storage; Close keeps the live changes for the session. This is the **foundation for future UI-customization settings** Ken flagged as coming.
4. **Point-release version in About.** `APP_VERSION` constant in `app.js` (currently `0.2.8`) injected into `#aboutVersion`; About now reads "Version 0.2.8 — Phase 1 Proof of Concept". **Bump `APP_VERSION` alongside `sw.js` CACHE_VERSION every release** — crucial for beta-tester bug reports.
5. **Scrolling panel.** Dialog is a flex **column** (header + footer pinned via `flex-shrink:0`, `#settingsContent` scrolling via `flex:1; min-height:0` on `#settingsLayout`, `max-height:calc(100vh - 3rem)`). **Two gotchas (the v0.2.8→0.2.9 fix below):** (a) `display:flex` on a `<dialog>` **drops the UA's auto-centering** (computed margin → 0, pins top-left) — restored with `inset:0; margin:auto` on the base `dialog`. (b) Putting `display:flex` on the *base* `dialog` selector also **overrode the UA's `dialog:not([open]) { display:none }`** (author origin beats UA regardless of specificity), so the panel was CSS-visible at all times — it showed at startup *and* "Close" appeared to do nothing (the button handlers are wired in `openSettings()`, which never ran, and `.close()` is a no-op on a not-truly-open dialog). **Fix:** scope the flex layout to **`dialog[open]`** so a closed dialog stays `display:none`.
6. **General tab shortened (Ken's call: "add Speech + Conversation tabs").** Tabs are now **General** (API Key, About You pointer, Data Folder) / **Speech & Input** (Voice, Keyboard for typing) / **Conversation** (silence period, auto-resume, + the former Placeholders delays folded in) / **About**. The standalone Placeholders tab is gone. Tab-switching JS is generic (`data-tab`), so no handler changes were needed.

**Touch drag:** `#settingsHeader` has `touch-action: none` so the browser doesn't claim the touch gesture for scroll/pan (without it a touch drag moved the panel only a few mm).

CACHE_VERSION → `aac-v0.2.9`; APP_VERSION → `0.2.9`. **Verified in preview:** panel hidden at startup (`display:none`, not in DOM box); opens to `display:flex` via the button; **Close actually closes** (`open:false`, `display:none`); tabs distribute correctly; version 0.2.9 in About; drag moves precisely and clamps to viewport edges; centered on default open; long (Conversation) tab scrolls on a short viewport with footer pinned; no console errors. *Note:* drag + `touch-action` tested via synthetic PointerEvents (harness window isn't OS-focused and synthetic events bypass `touch-action`) — **confirm real touch drag on the test tablet.**

### Conversation-pane layout fixes: cross-region scrollbar, wide scrollbar, bubble width (Ken, July 17 2026)
