# CR-001: Ending or restarting a conversation overwrites the saved conversation file with "null" or with the next conversation's data

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** critical
- **Category:** data-loss
- **Verdict:** confirmed (skeptic: confirmed; reproducer: reproduced)
- **Location:** `app/js/storage.js:2473`
- **Also affects:** `app/js/storage.js:2074-2088 (resetConversationId)`; `app/js/storage.js:2338-2346 (finalizeOffer)`; `app/js/storage.js:2197-2207 (logEvent)`; `app/js/app.js:2777 (stt.stopListening -> logEvent 'listen off')`; `app/js/app.js:2807 (clearPalette -> finalizeOffer, not awaited)`; `app/js/app.js:2823 (storage.resetConversationId)`; `app/js/app.js:3010, 3036, 2981 (unawaited finalizeOffer)`; `app/js/storage.js:2470 (merged duplicate: Conversation-file writes are not serialized, so an older snapshot can be the last one saved)`
- **Source:** storage-01, x-async-15

**What a user notices.** When a person ends a conversation (or picks an opener to start a new one) while suggestion cards are on screen or the microphone is on, the whole saved record of the conversation they just had can be wiped or replaced. It then disappears from Conversation Review and from the usage reports.

**What is wrong.** flushLog() reads the module variable currentLogData AFTER its first await. terminateConversation() fires several log writes without awaiting them (clearPalette -> finalizeOffer, stt.stopListening -> logEvent('listen off'), the command-bar noteUserAction -> finalizeOffer) and then, when the partner has no pending words, calls storage.resetConversationId() synchronously in the same tick. resetConversationId sets currentLogData = null while those flushes are suspended inside createWritable(). When they resume they serialize the CURRENT value: JSON.stringify(null) -> the file becomes the 4 bytes "null". If the next conversation has already begun (choosing an opener after Start conversation runs terminateConversation then immediately logs the opener, which lazily creates a new currentLogData), the suspended flush writes the NEW conversation's object into the OLD conversation's file handle, destroying the old record. Concurrent flushes are also not serialized, so a burst of writes can land out of order (an older snapshot closing last). Reproduced in real headless Chrome (OPFS backend) by driving storage.js directly: the old file read back as "null", and in the second variant as the new conversation's {"id": <new id>, "exchanges": []}.

**Evidence.**

```
app/js/storage.js:2470-2476:
  async function flushLog() {
      if (!currentLogHandle || !currentLogData) return;
      try {
          const writable = await currentLogHandle.createWritable();
          await writable.write(JSON.stringify(currentLogData, null, 2));   // read AFTER the await
          await writable.close();
app/js/storage.js:2083: currentLogData = null; (in resetConversationId)
app/js/app.js:2807: clearPalette();   // -> storage.finalizeOffer({ outcome: 'cleared' }) not awaited (app.js:3010)
app/js/app.js:2820-2823:
    if (finalRaw) { await storage.finalizePartnerTurn(...); }
    storage.resetConversationId();
```

**How it happens.** 1) Hold a conversation with a data folder connected; after saying goodbye the goodbye cards are on screen (a pending offer). 2) Press End conversation. 3) finalizeOffer's flush and the 'listen off' event flush are suspended in createWritable; finalRaw is empty so resetConversationId() runs at once. 4) Both flushes resume and write "null" into conversations/<id>.json. Variant: Start conversation, pick an opener -> terminateConversation then logUserResponse creates the new log; the suspended flush writes the new conversation's JSON into the previous conversation's file. Verified in headless Chrome: content read back was "null" / {"id":"<new id>",...,"exchanges":[]}.

**Suggested fix.** In storage.js make flushLog snapshot synchronously and serialize writes: add `let logWriteChain = Promise.resolve();` and rewrite flushLog as a non-async function that captures `const handle = currentLogHandle; const data = currentLogData;` returns if either is null, computes `const text = JSON.stringify(data, null, 2);` BEFORE any await, then sets `logWriteChain = logWriteChain.then(async () => { try { const w = await handle.createWritable(); await w.write(text); await w.close(); } catch { /* silent */ } });` and returns logWriteChain. Because the text and handle are captured at call time, a later reset or a new conversation can no longer redirect the bytes, and the chain guarantees the newest snapshot is written last. Also export `export function whenLogWritten() { return logWriteChain; }` and in app.js terminateConversation call `await storage.whenLogWritten();` just before storage.resetConversationId() so End conversation finishes its writes first.

> **Verifier correction to the fix (takes precedence):** The suggested fix is right. Also check every other read of currentLogData that sits after an await (finalizePartnerTurn reads it after nothing, so it is fine, but logErrorToConversation and startConversationLog push into currentLogData after awaits; with the snapshot-in-flushLog change those pushes can still land in a new conversation's object if a reset happened mid-await - acceptable, but worth a comment). Keep the whenLogWritten() await in terminateConversation before resetConversationId.

**How to verify the fix.** Add a test to tests/storage-transcript.test.mjs whose fake createWritable awaits a setTimeout(5) before resolving: startConversationLog, logOffer, then call finalizeOffer({outcome:'cleared'}) WITHOUT awaiting and resetConversationId() synchronously; wait 50 ms and assert the file parses to an object whose last offer has outcome 'cleared' (not null). Second test: after reset immediately call logUserResponse (new conversation, wait >1 s first so ids differ) and assert the OLD file still holds the old exchanges. Both fail on current code (reproduced).

**Do not break.** Keep the write fire-and-forget from callers' point of view (they must never throw); keep the 'Don't save' gates in the callers. Do not make flushLog re-read currentLogData after an await anywhere. The conversation file must still mirror the pane after every event.

**Design reference.** CLAUDE.md 'Transcript mirrors the conversation pane — incremental partner writes' and 'THE STANDARD FOR THE RECORD IS CAN IT BE RECREATED TO THE SECOND'

The common trigger is real: after a goodbye the closings palette is on screen as a pending offer, and End conversation runs clearPalette. Nothing in TODO.md or the Security Review tracks it.

<details><summary>Merged duplicate x-async-15: Conversation-file writes are not serialized, so an older snapshot can be the last one saved</summary>

Every log mutation calls flushLog(), which awaits createWritable(), writes JSON.stringify(currentLogData) and awaits close(). Many mutations happen back to back without awaiting each other (fire-and-forget calls). With File System Access each writable commits on close, so the last close wins; if an earlier flush's close completes after a later one, the file holds the older snapshot. It is corrected by the next flush, except when the racing flushes are the conversation's last. Separately, startConversationLog checks currentLogData before an await, so two concurrent first callers both create the log object (the second overwrites the first and both push a 'start' context entry).

Fix as proposed by that reviewer: Serialize writes and coalesce: `let flushChain = Promise.resolve(); let flushQueued = false; function flushLog() { if (flushQueued) return flushChain; flushQueued = true; flushChain = flushChain.then(async () => { flushQueued = false; /* existing body */ }); return flushChain; }` (capture currentLogHandle/currentLogData inside the queued function). For startConversationLog keep a module-level `let startingLog = null;` promise and return it to concurrent callers.

</details>
