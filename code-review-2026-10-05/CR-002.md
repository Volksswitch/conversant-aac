# CR-002: After a restart, OpenAI, Google Cloud and ElevenLabs hearing are silently replaced by the browser's own recognizer

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** high
- **Category:** bug
- **Verdict:** confirmed (skeptic: already_tracked; reproducer: reproduced)
- **Location:** `app/js/app.js:485`
- **Also affects:** `app/js/app.js:488`; `app/js/app.js:490`; `app/js/app.js:514`; `app/js/app.js:518`; `app/js/app.js:524`; `app/js/diagnostics.js:99`; `app/js/app.js:7170`; `app/js/app.js:485 (merged duplicate: After any relaunch, OpenAI / Google Cloud / ElevenLabs hearing silently reverts to the browser recognizer)`
- **Source:** x-providers-01, x-contracts-02
- **Already in TODO.md as an unconfirmed suspicion:** TODO.md: "Check that OpenAI, Google Cloud and ElevenLabs hearing are really used where hearing must be paid for" (raised 2026-09-21, marked 'Not confirmed'). This review confirms it from the code; close that TODO entry when this item is fixed.

**What a user notices.** Someone who chose OpenAI, Google Cloud or ElevenLabs to hear the other person is quietly switched back to the free browser listening every time the app is reopened, while Settings still shows their paid choice. On an iPad installed to the Home Screen or on Android, that means the app hears nothing at all.

**What is wrong.** At startup initApp decides whether a paid hearing service is usable by looking up its key, but the lookup only knows two of the five paid services. For 'openai', 'google' and 'elevenlabs' paidSttKey is null, so usingPaidStt is false and stt.init is called with source 'builtin'; storage.setSttBackend records 'browser'. The Settings radio still reads the stored choice, so nothing on screen disagrees. Live switching via stt.setSource (added Sept 30 2026 for exactly this symptom) only runs when the radio is changed, so every reload - including the reload after Load profile (app.js:7170) - reverts to the browser recognizer. On iPad Home Screen the listeningUnavailable warning is also raised because usingPaidStt is false. The same gap exists for a key entered AFTER startup for the already-selected service (Deepgram/Azure included): startup fell back to builtin because the key was empty, and saving the key never calls stt.setSource, so hearing stays on the browser until the radio is toggled or the app reloads. Diagnostics report the stored setting (storage.loadSttProvider) rather than stt.currentSource(), which is why a problem report cannot reveal the mismatch. This is the same 'else-branch knows two services' shape CLAUDE.md warns about in 'A TWO-SERVICE if/else MET FIVE SERVICES'.

**Evidence.**

```
app/js/app.js:485-488:
    const paidSttKey = sttProvider === 'deepgram' ? storage.loadDeepgramKey()
                     : sttProvider === 'azure'    ? storage.loadAzureKey()
                     : null;
    const usingPaidStt = !!(paidSttKey || '').trim();
app/js/app.js:518: storage.setSttBackend(usingPaidStt ? sttProvider : 'browser');
app/js/app.js:524: source: usingPaidStt ? sttProvider : 'builtin',
app/js/diagnostics.js:99: info.speech.sttProvider = storage.loadSttProvider ? storage.loadSttProvider() : '(n/a)';
```

**How it happens.** 1) Settings > Speech, paste an OpenAI key, choose 'OpenAI transcription (paid)'. Status reads 'Saved, and in use now.' 2) Close and reopen the app (or Load a settings profile, which reloads). 3) Settings still shows OpenAI selected, but stt.currentSource() is 'browser' and every partner turn is stamped stt:'browser'. On an iPad Home Screen app the Listen button lights and nothing is ever transcribed; the pre-start screen also warns that listening may not work. Second path: select Azure with no key, restart, then paste the Azure key - hearing stays on the browser recognizer until the radio is changed.

**Suggested fix.** Add a helper in app.js next to serviceKeyFor: `function sttKeyFor(provider) { if (provider === 'deepgram') return (storage.loadDeepgramKey() || '').trim(); if (provider === 'azure') return (storage.loadAzureKey() || '').trim(); if (STT_PROVIDERS[provider]) return (storage.loadServiceKey(provider) || '').trim(); return ''; }` and replace lines 485-488 with `const usingPaidStt = sttProvider !== 'builtin' && !!sttKeyFor(sttProvider);`. Reuse the same helper for `haveKey` at app.js:7382-7385. Then, in each key field's save/onChange (Deepgram 7346, Azure 7429, catalog loop 7917), add: `if (storage.loadSttProvider() === <service> && stt.currentSource() !== <service> && sttKeyFor(<service>)) { stt.setSource(<service>); storage.setSttBackend(stt.currentSource()); }`. In diagnostics.collectSystemInfo add `info.speech.sttInUse = stt.currentSource();` beside sttProvider.

**How to verify the fix.** Manual: choose OpenAI hearing with a key, reload, open Settings > Troubleshooting > System information and confirm sttInUse reads 'openai'; start a conversation and confirm the saved partner turn's `stt` field is 'openai'. Add a source-level guard in tests/stt.test.mjs (or a new tests/provider-wiring.test.mjs) that reads app.js and asserts the startup paid-key decision references STT_PROVIDERS / loadServiceKey (strip comments first, as CLAUDE.md requires for source-level asserts).

**Do not break.** Keep the 'only WITH ITS KEY IN HAND' rule: a keyless paid source must still fall back to the browser recognizer at startup (storage.loadSttProvider and app.js:480-484 explain why). Do not change the Android default in storage.loadSttProvider. stt.setSource tears down any running capture - only call it from the key handlers when the service actually differs from currentSource().

**Design reference.** CLAUDE.md: 'HEARING COULD FAIL FOREVER IN SILENCE, AND THE SERVICE COULD NOT BE CHANGED WITHOUT A RESTART' and 'A TWO-SERVICE if/else MET FIVE SERVICES'

**Verification notes.** The TODO item describes exactly this startup gap and says it is unconfirmed. Reading the code confirms it. app.js:485-488 looks up a key only for 'deepgram' and 'azure', so for openai/google/elevenlabs usingPaidStt is false, stt.init gets source 'builtin' and setSttBackend records 'browser'. stt.setSource is called only from the radio onchange (app.js:7368), so nothing corrects this after a reload. The TODO can be closed as confirmed and fixed. The finding's second path is NOT in the TODO: a paid service chosen at startup with no key falls back to builtin, and pasting the key later never calls setSource. That path also affects Deepgram and Azure, and the fix should cover it. A sttKeyFor helper can reuse the existing serviceKeyFor (app.js:1076), which already covers all five services.

**Reproduction (reproduced).** Method: Ran the real storage.js and stt.js modules in node (scratchpad repro.mjs, with localStorage/window/navigator/document shims as in tests/env.mjs). Saved an OpenAI key with storage.saveServiceKey('openai', ...) and the choice with storage.saveSttProvider('openai'), as Settings does. Then read the exact startup decision text from app/js/app.js lines 479-488, ran it as a function against the real storage module, passed the resulting source to the real stt.init(), and read stt.currentSource(). Repeated the decision for 'google' and 'elevenlabs'. Also grepped every stt.setSource call site and read the key-field handlers and the Load-profile path. The startup decision returned {sttProvider:'openai', paidSttKey:null, usingPaidStt:false}, even though an OpenAI key was stored. 'google' and 'elevenlabs' gave the same result. So app.js line 524 passes source 'builtin', and line 518 stamps 'browser'. After stt.init, storage.loadSttProvider() returned 'openai', which is what the Settings radio and diagnostics.js line 99 report. stt.currentSource() returned 'browser'. As a control, calling stt.setSource('openai') (the radio-change path) switched it to 'openai', so the backend itself works and only the startup lookup is wrong. grep shows the only stt.setSource call in the app is at app.js:7368, inside the sttProvider radio onchange handler. None of the key-field handlers call it: Deepgram's onChange (around 7346) only refreshes voices, Azure's onChange clears the voice catalog, and the catalog loop's onChange/paste (7917+) only refreshes voices. That confirms the second path: a key entered after a keyless startup is not picked up until the radio is changed or the app reloads. The Load profile handler (app.js 7165-7170) calls location.reload(), so it goes back through the same broken startup decision. Because usingPaidStt is false, listeningUnavailable at line 490 is also raised wherever the platform verdict is unusable, for example an iPad Home Screen app. That last consequence was confirmed by tracing the code, not by running it.

<details><summary>Merged duplicate x-contracts-02: After any relaunch, OpenAI / Google Cloud / ElevenLabs hearing silently reverts to the browser recognizer</summary>

initApp decides whether a paid hearing service is in use with a two-way test that only knows Deepgram and Azure. For any catalog service (STT_PROVIDERS: openai, google, elevenlabs) paidSttKey is null, so usingPaidStt is false, stt.init is called with source 'builtin', storage.setSttBackend('browser') stamps every turn as browser, and listeningUnavailable is computed from the browser verdict. stt.setSource() is only called from the Settings radio onchange, so nothing ever corrects this until the user re-clicks the radio. Where the Web Speech API is absent, stt.init is never called at all, so even a later radio change cannot help (setSource returns false when initOpts is null). This is the same 'switch by exclusion' shape CLAUDE.md warns about ('A TWO-SERVICE if/else MET FIVE SERVICES'). The same block also means that a user who picks Deepgram/Azure first and pastes the key later stays on the browser recognizer until reload, because key-field onChange handlers never re-evaluate the source.

Fix as proposed by that reviewer: In initApp replace lines 485-487 with a lookup that names every service:
  const paidSttKey = sttProvider === 'deepgram' ? storage.loadDeepgramKey()
                   : sttProvider === 'azure'    ? storage.loadAzureKey()
                   : STT_PROVIDERS[sttProvider] ? storage.loadServiceKey(sttProvider)
                   : null;
(STT_PROVIDERS is already imported at line 44.) Secondary, same root: in the key-field onChange handlers for Deepgram (line ~7352), Azure (~7432) and the catalog loop (~7924), when storage.loadSttProvider() equals that service and stt.currentSource() !== that service, call stt.setSource(service), storage.setSttBackend(stt.currentSource()), recompute `listeningUnavailable` and call applyListenAvailability(). Also consider reporting stt.currentSource() alongside the stored setting in diagnostics.collectSystemInfo (diagnostics.js:99).
