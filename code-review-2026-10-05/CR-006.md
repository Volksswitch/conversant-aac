# CR-006: Deepgram hearing drops the partner's first words whenever they start talking before the connection finishes opening

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** high
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed; reproducer: reproduced)
- **Location:** `app/js/stt-deepgram.js:193`
- **Also affects:** `app/js/stt-deepgram.js:213-219`; `app/js/stt-deepgram.js:225-231`; `app/js/stt-deepgram.js:295-334`; `app/js/stt-deepgram.js:338-353`; `app/js/app.js:1311 (handleSttStatus comment: 'the gate can open on the first syllable before the socket has finished connecting ... Measured: it does')`; `app/js/vad.js:44-60 (pre-roll raised to 1200ms for Ken's Android report 'it still loses about the first second of speech')`; `app/js/app.js:2064 and app/js/app.js:2143 (listening is stopped and restarted around every exchange, so a new socket is opened each time)`
- **Source:** g-stt-overflow-01

**What a user notices.** With Deepgram doing the hearing, if the other person starts talking the moment listening turns on - which is normal right after the user's reply is spoken - the first half-second or more of what they say never appears on screen and never reaches the AI. Their sentence shows up with its opening words missing.

**What is wrong.** start() creates a fresh WebSocket and then immediately starts the ScriptProcessor (running = true). Audio frames flow from the first ~85 ms while the socket is still in readyState CONNECTING (DNS + TCP + TLS + WebSocket upgrade to api.deepgram.com, typically a few hundred ms and often over a second on cellular). send() silently discards anything sent while the socket is not OPEN. When the voice gate opens during that window, handleFrame flushes the pre-roll ring through send() - discarded - empties the ring, and then sends every subsequent gate-open frame through send() - also discarded - until ws.onopen fires. Frames are only kept in the pre-roll while the gate is CLOSED, so nothing that arrives with the gate open during CONNECTING is ever retained. The pre-roll exists exactly to protect the opening syllables, and in this window it is thrown away. Because app.js stops listening when a response is chosen and restarts it on auto-resume, a new socket (and a new CONNECTING window) occurs at the start of EVERY partner turn, which is precisely when the partner begins speaking. The billing counter also counts the discarded time (openedAt set on the dropped 'open' edge). handleSttStatus already records that the gate is measured to open before the socket connects; nothing buffers for it. Reproduced in a Node harness with a fake WebSocket that stays CONNECTING: 8 loud frames (about 680 ms of speech) captured before onopen produced 0 sent frames; after onopen only the 4 later frames were sent.

**How it happens.** 1. Settings -> Speech: hear with Deepgram, valid key; auto-resume listening on. 2. Start a conversation; partner says something; user taps a card - app speaks it and listening restarts (stt.startListening -> deepgram start() -> new WebSocket). 3. Partner replies immediately, 'Sure, I can do Tuesday at three.' 4. The voice gate opens on 'Sure' while the socket is still CONNECTING; the pre-roll and every frame until onopen are discarded by send(). 5. Transcript shows 'Tuesday at three.' (or 'can do Tuesday at three.'); the AI receives the truncated turn. Same on first Listen tap if the partner is already talking, and on the visibility-guard resume.

> **Verifier correction to the trigger:** The gate needs only one frame above the open level, so any sound at that level during the handshake (the partner, or room noise) opens it and starts losing audio. This most likely explains the August 31 2026 Android report of the first second being lost. Raising pre-roll could not fix that symptom while the socket is still connecting.

**Suggested fix.** In createSource add `let pending = [];` and a cap `let pendingMax = 0;` (set in start(): `pendingMax = Math.ceil(10 * rate / FRAME_SAMPLES);` - about 10 s). Change send() to:
    function send(buf) {
        if (!ws) return;
        if (ws.readyState === WebSocket.OPEN) { ws.send(buf); return; }
        if (ws.readyState === WebSocket.CONNECTING) {
            pending.push(buf);
            while (pending.length > pendingMax) pending.shift();
        }
    }
In ws.onopen, FIRST flush: `for (const b of pending) ws.send(b); pending = [];` then report 'listening' and start the KeepAlive timer as now. Clear `pending = []` in start() (next to `preRoll = []`), in ws.onerror, in ws.onclose, and in stop(). Leave the billing arithmetic alone (the time is already counted, and now it is genuinely sent). Do not move `running = true` later and do not delay the processor - capturing during the handshake is what makes this recoverable.

**How to verify the fix.** Add tests/stt-deepgram.test.mjs: stub globalThis.WebSocket with a fake whose readyState starts at CONNECTING and records send(); stub window.AudioContext (createMediaStreamSource, createScriptProcessor capturing the processor, createGain, close) and navigator.mediaDevices.getUserMedia (define navigator with Object.defineProperty - it is getter-only in Node 21+). Call start(), drive processor.onaudioprocess with 8 frames of Float32Array(4096).fill(0.1), assert 0 frames sent; set readyState=OPEN and call ws.onopen(); assert all 8 frames are sent before any later frame. Call stop() in an after() hook so the KeepAlive setInterval cannot hang the test run (CLAUDE.md warns about this). Manually: Deepgram on a tablet over cellular, have the partner speak the instant the chime sounds, confirm the first word appears.

**Do not break.** Keep the queue bounded so a socket that never opens cannot grow memory without limit. Drop the queue on error/close so a failed socket cannot replay old audio into a later one. Do not change vad.js thresholds or pre-roll (CLAUDE.md: raising pre-roll, not lowering openLevel, is deliberate). Do not report 'listening' before onopen (stt-deepgram.js:318-326 records why). Billing/usage display is a separate reported issue; do not double-count.

**Design reference.** vad.js header ('Pre-roll ... Without it every utterance loses its opening consonant'); CLAUDE.md 'Paid speech-to-text — Deepgram' (VAD gate, pre-roll); vad.js DEFAULTS.preRollMs note (Ken, Android, Aug 31 2026: 'it still loses about the first second of speech')

**Verification notes.** Traced in app/js/stt-deepgram.js. start() opens a new WebSocket and sets running=true at once, so frames reach handleFrame while readyState is CONNECTING. send() (line 193) drops anything not OPEN, and nothing queues it. The gate in vad.js opens on a single frame at or above openLevel. On that 'open' edge the pre-roll is flushed through send() and emptied, so it is dropped. Every later frame while the gate stays open also goes through send() and is dropped. Frames are only kept in the pre-roll while the gate is closed. stt.startListening/resumeListening -> openSource -> externalSource.start() builds a new socket every time. app.js stops listening on a response and restarts it on auto-resume (around app.js:2143 and in startFreshListening), so a fresh handshake comes at the start of each partner turn. The handleSttStatus comment (app.js ~1309) says the gate was measured to open before the socket connects. The suggested fix (a bounded queue flushed in onopen, cleared on error, close, stop and start) is correct. It is also a likely cause of the Android report that raised preRollMs to 1200 ('still loses about the first second'): a bigger pre-roll cannot help when the pre-roll itself is thrown away during CONNECTING.

**Reproduction (reproduced).** Method: Ran the real app/js/stt-deepgram.js in Node (scratchpad repro.mjs) with a fake WebSocket whose readyState stays CONNECTING (0), a fake AudioContext capturing the ScriptProcessor, and a stubbed getUserMedia (navigator defined via Object.defineProperty). Called createSource(...).start(), drove processor.onaudioprocess with 8 loud frames (Float32Array(4096).fill(0.1), RMS 0.1 > openLevel 0.02) before the socket opened, then set readyState=OPEN, called ws.onopen(), and drove 4 more loud frames. Also traced stt.js: stopListening/startListening call externalSource.stop()/start() (stt.js:594, 674, 685, 730), and stop() sets ws=null, so each restart opens a new socket. Output: 'readyState during first 8 loud frames: 0 -> frames sent: 0 statuses: capturing' and 'after onopen + 4 more loud frames: sent = 4 statuses: capturing,listening'. So the gate opened ('capturing') on the first loud frame while CONNECTING; handleFrame (stt-deepgram.js:213-219) flushed the pre-roll through send(), which (line 193-195) silently drops anything when readyState !== OPEN, then emptied preRoll; every subsequent gate-open frame also went to send() (line 225-226) and was dropped, because frames are only retained in preRoll while the gate is closed (line 227-231). After onopen only the 4 later frames were sent; the 8 earlier frames (~680 ms at 48 kHz) were never sent and are unrecoverable. The billing counter still counted the open span (openedAt set on the dropped 'open' edge). Because stop() nulls ws and start() creates a new WebSocket each time listening restarts (every auto-resume after a spoken reply), a fresh CONNECTING window opens at the start of each partner turn. app.js:1309-1311 comment confirms the gate is measured to open before the socket connects. Suggested fix (bounded pending queue flushed in onopen, cleared on start/error/close/stop) is consistent with what was observed.
