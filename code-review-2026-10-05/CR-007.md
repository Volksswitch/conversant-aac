# CR-007: After a paid hearing service fails, it keeps running, and the next Listen tap lights the button on a dead connection

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** high
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed; reproducer: reproduced)
- **Location:** `app/js/stt.js:660`
- **Also affects:** `app/js/stt-deepgram.js:303`; `app/js/stt-deepgram.js:312`; `app/js/stt-deepgram.js:250`; `app/js/stt-rest.js:208`; `app/js/stt-azure.js:333`; `app/js/app.js:1304`; `app/js/stt.js:660 (merged duplicate: Paid hearing services keep the microphone open (and Azure/REST keep uploading audio) after a fatal error; the next Listen tap then reports listening while deaf)`
- **Source:** stt-02, x-async-01

**What a user notices.** If the internet drops for a moment while a paid hearing service is in use, listening switches off; tapping Listen again lights the button but the app never hears anything again until the user turns listening off and on once more. Meanwhile the microphone stays on in the background.

**What is wrong.** handleSourceError() only clears listeningIntent and reports 'error'; it never stops the external source. The sources do not stop themselves on a fatal error either: Deepgram's ws.onerror/ws.onclose report 'error' but leave `running === true`, the MediaStream, AudioContext and ScriptProcessor alive, and `ws` pointing at a closed socket; stt-rest reports a fatal 'error' (401/403 or 3 consecutive failures) and keeps capturing and submitting every later phrase; Azure reports 'error' on any HTTP failure and keeps going. app.js handleSttStatus sets isListening=false on 'error', so the next Listen tap takes the START branch -> stt.openSource() -> externalSource.start(), which hits `if (running) { onStatus('listening'); return true; }` and returns. The button lights, but for Deepgram `send()` silently drops every frame because `ws.readyState !== OPEN`. For REST/Azure, results that do succeed after the 'error' are still delivered through onText and drive silence checkpoints while the button shows listening OFF. Additionally stt-rest's `failures` counter is only reset in start(), which returns early, so the next single hiccup is immediately fatal again.

**Evidence.**

**How it happens.** iPad Home Screen app with Deepgram (the one setup where it is required). Wi-Fi blips; the socket closes; the app logs 'closed (code 1006)' and the Listen button goes dark. User taps Listen: button turns red ('listening'), partner talks, nothing appears, no error is logged. Only tapping Listen off and on again (which calls stop() then start()) recovers.

**Suggested fix.** In stt.js handleSourceError(), stop the paid source before reporting: `if (externalSource) { try { externalSource.stop(); } catch { /* already stopped */ } }` placed BEFORE `onStatusChange('error', detail)`, so the final status the app sees is 'error' (stop() emits 'stopped'/'idle' first, which handleSttStatus treats the same way). Also clear the silence timer there (`clearSilenceTimer()`). Optionally, in stt-deepgram.js start(), treat `running && (!ws || ws.readyState > WebSocket.OPEN)` as not running (call stop() then continue) so a dead socket can never be re-reported as listening.

**How to verify the fix.** Add a test in tests/stt.test.mjs (or a new tests/stt-deepgram.test.mjs with fake WebSocket/getUserMedia): start the Deepgram source via stt.init({source:'deepgram'}) + startListening, fire ws.onclose({code:1006}) while open, assert the fake MediaStream track was stopped and that a subsequent stt.startListening() opens a NEW WebSocket. For stt-rest, make fetch reject 3 times and assert the track is stopped after the third.

**Do not break.** Do not make single REST/Azure 'warning' failures fatal - CLAUDE.md requires a run of three. The browser recognizer path must keep working: handleSourceError is also called from recognition.onerror, where externalSource is null.

**Design reference.** CLAUDE.md 'HEARING COULD FAIL FOREVER IN SILENCE ...' (worst failure: microphone lit while nothing is heard)

**Verification notes.** Traced. handleSourceError (stt.js) only clears listeningIntent and reports 'error'. Deepgram's ws.onerror/onclose never set running=false and never release the stream, context or processor. handleSttStatus sets isListening=false on 'error', so the next tap takes the start branch: openSource() calls externalSource.start(), which hits `if (running) { onStatus('listening'); return true; }`. The button lights, and send() drops every frame because the socket is not OPEN. The microphone track also stays live. stt-rest (after its fatal 401/403 or third failure) and Azure (any HTTP error) also keep capturing after an 'error'. Later successes still reach onText/afterIngest, which do not check listeningIntent, so checkpoints can fire while the button shows off. stt-rest's failure counter resets only in start(), which returns early in this state.

**Reproduction (reproduced).** Method: Ran the real stt.js with stt.init({source:'deepgram'}) in node (scratchpad exp2.mjs), fake getUserMedia/AudioContext/WebSocket, and an onStatus that applies app.js handleSttStatus's isListening mapping (stopped/idle/error -> false, listening -> true). Opened the socket, fired ws.onclose({code:1006}), then called stt.startListening() as the app's start branch would. After open: isListening true. After onclose(1006): statuses ['listening','error:closed (code 1006)'], isListening false, but tracksStopped 0 and ctxClosed 0 - the source is still running with the mic and AudioContext alive. Re-tap (stt.startListening -> openSource -> externalSource.start): statuses add 'listening', isListening true, sockets created still 1 and streams still 1 - start() returned through the `if (running)` guard without reconnecting. Feeding 5 audio frames afterwards: 0 open sockets and 0 frames sent (send() drops because ws.readyState is CLOSED). So the button shows listening on a dead connection and nothing is ever heard; only a stop (which calls externalSource.stop()) then start recovers. handleSourceError (stt.js:660-663) only clears listeningIntent and reports; it does not stop the source. The REST/Azure 'keeps capturing after a fatal error' part was confirmed by reading (stt-rest.js submit reports 'error' with no teardown; start() resets `failures` only after the running guard), not executed.

<details><summary>Merged duplicate x-async-01: Paid hearing services keep the microphone open (and Azure/REST keep uploading audio) after a fatal error; the next Listen tap then reports listening while deaf</summary>

When a paid source reports status 'error', stt.js handleSourceError only clears listeningIntent and forwards the status; it never calls externalSource.stop(). The source's own `running` flag stays true, so its getUserMedia stream, AudioContext and ScriptProcessor keep running. Azure and the REST services keep closing spans and POSTing audio to the provider after the UI says listening is off (each failure logs another error). Deepgram's socket is closed, so on the next Listen tap externalSource.start() sees `running === true`, re-reports 'listening' and returns: the app shows listening while send() silently drops every frame because ws.readyState is CLOSED. The state only clears when something else calls stt.stopListening() (a card, End conversation).

Fix as proposed by that reviewer: In stt.js handleSourceError, stop the external source BEFORE reporting the error:
```js
function handleSourceError(detail) {
    listeningIntent = false;
    if (externalSource) { try { externalSource.stop(); } catch { /* already stopped */ } }
    if (onStatusChange) onStatusChange('error', detail);
}
```
Stopping first means the source's own 'stopped'/'idle' status arrives before the 'error', so the error is the last status the app sees. Because Deepgram's stop() sets running=false and nulls ws before the socket's onclose fires, this also removes the duplicate 'error' (onerror followed by onclose) that currently writes two error-log entries per failure. Leave the 'warning' path untouched (non-fatal by design).

</details>
