# CR-008: Choosing a data folder from the About Me banner reconciles only About Me answers, so other stores later overwrite the folder's files

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** high
- **Category:** data-loss
- **Verdict:** confirmed (skeptic: confirmed; reproducer: reproduced)
- **Location:** `app/js/worldview-ui.js:151`
- **Also affects:** `app/js/worldview-ui.js:106-130 (open(): restoreDataFolder may newly connect a folder, then syncs only worldview, relationships, places, voice)`; `app/js/app.js:5925 (adoptDataFolder - the shared post-connect function this banner bypasses)`; `app/js/app.js:7004-7012 (Settings pickFolderBtn, which correctly calls adoptDataFolder)`; `app/js/app.js:741 (worldviewUI.init() takes no arguments, so the UI has no route to adoptDataFolder)`; `app/js/relationships.js:99-103 (save writes the whole in-memory graph over relationships.json)`
- **Source:** worldview-01

**What a user notices.** Someone who copies their data folder from another computer and connects it using the banner on the About Me page sees no people, places or Express Panel phrases from that folder, and the first edit they make writes over the copied files, so the people and phrases from the other computer are lost.

**What is wrong.** renderFolderPrompt's button calls storage.pickDataFolder() and then only wv.syncToFolder(). Every other user-owned store (relationships, places, voice, practice library, Express Panel, control phrases, placeholder phrases) keeps its in-memory/localStorage-cache copy. The project rule (v0.2.25, restated for all stores) is that a file already in the connected folder always wins. Because those modules were never reconciled, their next save() writes the stale cache over the folder's file. app.js already has adoptDataFolder() precisely because 'the cost of an omission is silent' (CLAUDE.md, Android section: 'the failure of an eight-item list is always the item somebody forgot'); this second pick path re-creates that omission. It also skips updateFolderDisplay(), renderSettingsProfiles() and renderBackupList(), so Settings > General still says 'No folder selected' and the profile/backup lists stay empty until Settings is reopened. The banner is shown exactly when no folder is connected (new machine, cleared browser data), which is the cross-machine copy case the rule exists for. open() has the same gap in a narrower form: restoreDataFolder() at line 109 can newly connect a folder and only four stores are then synced.

**Evidence.**

```

    try {
        await storage.pickDataFolder();
        // File-in-folder wins (v0.2.25): adopt an existing

        renderHome();

        try { await expressPanel.syncToFolder(); } catch {}

app/js/relationships.js:99-103: async function save() { graph.updated = ...; writeCache(graph); await writeFile(FILE, JSON.stringify(graph, null, 2)); }
```

**How it happens.** 1. On PC1 add three people and customize the Express Panel; data folder holds relationships.json and express-panel.json. 2. Copy the folder to PC2, where the app has never had a folder. 3. On PC2 open Settings > About Me; the 'Choose data folder' banner shows; pick the copied folder. 4. Open 'People in Your Life': the list is empty (in-memory graph is PC2's empty cache). 5. Add one person. rel.addPerson -> save() writes a one-person relationships.json over the copied three-person file. The three people are gone from the folder. Same for any Express Panel edit made before the next app restart.

**Suggested fix.** Give worldview-ui a way to run the shared post-connect routine. In worldview-ui.js change `export function init()` to `export function init(opts = {})` and store `onFolderConnected = opts.onFolderConnected || null`. In app.js line 741 call `worldviewUI.init({ onFolderConnected: adoptDataFolder })`. In renderFolderPrompt replace `try { await wv.syncToFolder(); } catch {}` with `if (onFolderConnected) { try { await onFolderConnected(); } catch {} } else { try { await wv.syncToFolder(); } catch {} }`, then `renderHome()`. In open(), capture `const hadFolder = storage.hasDataFolder();` before restoreDataFolder(), and if `!hadFolder && storage.hasDataFolder() && onFolderConnected` call it (in addition to the existing loads), so a folder newly restored there is also reconciled for every store.

**How to verify the fix.** Manual: with no folder connected and a populated folder from another profile on disk, open About Me, use the banner to pick it, then open People and Settings > Express Panel: both must show the folder's contents, and Settings > General must name the folder. Add a person and confirm relationships.json still contains the original people. A source-level guard can go in tests/placeholders.test.mjs style: assert renderFolderPrompt does not call wv.syncToFolder() alone without the onFolderConnected path.

**Do not break.** adoptDataFolder lives in app.js, which worldview-ui cannot import (circular); pass it in, do not import it. Keep the button a fresh user gesture (pickDataFolder must still be the first await). Do not change the 'file in the folder wins' rule itself.

**Design reference.** CLAUDE.md Worldview Questionnaire: 'Cross-PC copy of worldview.json — the file in the folder is the source of truth'; CLAUDE.md Android section: 'connecting a folder reconciled seven data stores and did not redraw the settings-profile list... Both now go through one shared post-connect function'.

**Verification notes.** renderFolderPrompt (worldview-ui.js:148-158) calls storage.pickDataFolder() then only wv.syncToFolder(). pickDataFolder just sets the root and creates subfolders; it dispatches nothing that app.js listens for. The in-memory relationships graph stays whatever rel.load() read from the cache in open() before the folder existed, and renderPeople never reloads it. rel.addPerson -> save() writes the whole graph over relationships.json. The Express Panel and the other stores behave the same way. adoptDataFolder (app.js:5925) syncs all nine stores and redraws the folder name, profile list and backup list; the banner bypasses it. worldviewUI.init() takes no arguments. Switching tabs and returning would rerun open(), and rel.load reads the file first, which would rescue people and places. The direct path (banner, then People, then add) has no such rescue. The trigger is narrow (banner pick plus a pre-populated folder), but the data loss is real.

**Reproduction (reproduced).** Method: Ran the real app/js/storage.js, relationships.js and worldview.js in node (scratchpad repro-worldview/r1.mjs), shimming localStorage, window and navigator.storage.getDirectory as tests/storage-transcript.test.mjs does. That sends pickDataFolder down the device-storage path, which uses the same readFile/writeFile code. I pre-populated the folder root with a relationships.json holding three people (Alice, Bob, Carol), standing in for the folder copied from PC1. Then I replayed the exact sequence: open() with no folder (rel.load + rel.syncToFolder), then the banner's handler (storage.pickDataFolder() followed ONLY by wv.syncToFolder()), then the People screen's read (rel.listPeople()), then one edit (rel.addPerson({name:'Dave'})). Finally I read the bytes back from the folder. Output: 'before pick, people: []' / 'folder connected: true' / 'People screen shows: []' / 'relationships.json on disk now: [ 'Dave' ]'. The copied three-person file was overwritten by a one-person file on the first edit.

Why it happens:
- relationships.save() (relationships.js:99-103) writes the in-memory graph whole.
- That graph was loaded from the empty browser cache when there was no folder.
- The banner (worldview-ui.js:150-155) reconciles only worldview, never relationships.

The Settings pick path (app.js:7004-7012) calls adoptDataFolder (app.js:5925), which reconciles every store, and worldviewUI.init() (app.js:741) has no route to it.

By code reading, without running it: Express Panel, control phrases, placeholders, places, voice and the practice library are exposed the same way. The folder name, profile list and backup list are not redrawn either.

One mitigation narrows the window but does not close it. Re-entering the About Me tab re-runs open(), and rel.load() would then read the folder. A user who goes straight from the banner into People in the same visit loses the data, as shown.
