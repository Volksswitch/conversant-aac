# CR-009: People, Places and general-goal edits auto-save on the 'change' event, which never fires for text typed with the on-screen keyboard

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** high
- **Category:** data-loss
- **Verdict:** confirmed (skeptic: confirmed; reproducer: reproduced)
- **Location:** `app/js/worldview-ui.js:1209`
- **Also affects:** `app/js/worldview-ui.js:1208-1213 (person edit path: name, nickname, about, relationship 'Other' text, both pronunciations, both topic boxes)`; `app/js/worldview-ui.js:967 and 983 (partner-profile note and the three phrase textareas)`; `app/js/worldview-ui.js:891 (typed goal's button label, all three goal editors)`; `app/js/worldview-ui.js:1452 (place fact key/value)`; `app/js/worldview-ui.js:1519-1522 (place name, pronunciation, topic boxes)`; `app/js/worldview-ui.js:1287-1308 (general goals screen has no Done button, so nothing rescues an uncommitted label)`; `app/js/keyboard.js:140-149 (insert sets f.value and dispatches only 'input')`; `app/js/keyboard.js:743-786 (focusout handler dispatches no change)`
- **Source:** worldview-02

**What a user notices.** A user who types with the app's own on-screen keyboard can edit a person's name or notes, a place's facts, or a goal's button label, go back to the list, and find the change was never kept. On the general goals screen a typed button label is never kept at all.

**What is wrong.** The September 10 2026 decision removed Save/Cancel on the edit paths and commits 'typed fields when they are left' via addEventListener('change', ...). The app's on-screen keyboard (keyboard.js, which owns every '.wv-text' field) inserts text by assigning field.value and dispatching a synthetic 'input' event. Browsers only fire 'change' on blur for user-edited values; a programmatic value assignment resets the 'last change' baseline, so no 'change' event is ever dispatched. Measured in headless Chromium (puppeteer, scratchpad change.cjs): focus input, set value + dispatch input, focus another field -> zero change events; the same flow with real keystrokes fires one. So in on-screen keyboard mode (the target user's normal mode) typed edits are committed only if a discrete control (select/checkbox/goal button) changes afterwards or Done is pressed. Leaving via '‹ All topics', tapping Edit on another person, switching Settings tab, or closing Settings discards them silently. On renderGeneralGoals there is no Done at all, so a typed goal label (kept only in memory via the 'input' handler) is lost unless a goal is later added/moved/removed. The comment at 1206-1207 ('Done commits again, so nothing typed and never blurred is lost either way') assumes blur commits, which is false here.

**How it happens.** Settings > Buttons: keyboard mode 'On-screen keyboard'. About Me > People in Your Life > Edit 'Tyler'. Tap the 'Anything worth knowing' field and type 'plays chess' with the on-screen keyboard. Tap '‹ All topics', then reopen People: Tyler's note is unchanged. Same with a place fact. On 'Goals For Any Conversation', add 'Something else…' goal, type a button label with the on-screen keyboard, leave the screen: label is gone.

> **Verifier correction to the trigger:** Applies only when Settings > keyboard is set to the app's own on-screen keyboard. The default is 'physical', and real keystrokes, including from the OS touch keyboard, do fire change on blur.

**Suggested fix.** Preferred (one place, covers every editor): in keyboard.js remember the field's value when it gains focus (in the focusin handler, `focusValue.set(e.target, e.target.value)` with a WeakMap), and in the focusout handler, before any early return, if `isScoped(e.target)` and `e.target.value !== focusValue.get(e.target)` dispatch `e.target.dispatchEvent(new Event('change', { bubbles: true }))`. Alternatively, local fix in worldview-ui: replace each `addEventListener('change', fn)` on typed fields with a helper `commitOnLeave(box, fn)` that sets a `dirty` flag on 'input' and calls fn on 'blur' (and on 'change') when dirty, then clears the flag.

**How to verify the fix.** Puppeteer or browser check: in on-screen mode, focus a person-form field, type via the keyboard keys (or set value + dispatch input as keyboard.js does), blur, and assert rel.listPeople() shows the new value without pressing Done. Repeat for a place fact and for a general-goal label. If the keyboard.js route is taken, add a jsdom-free unit-style check is not possible; add a source guard in tests/ asserting the focusout handler dispatches 'change'.

**Do not break.** A synthetic change may now also reach handlers elsewhere that listen for 'change' on in-scope fields (Express editor, Controls editor, Settings inputs) - check each is idempotent. Do not commit per keystroke (CLAUDE.md: a file write per character). Keep the 'a name can never be blanked' guard.

**Design reference.** CLAUDE.md 'A LIST THAT SHOWS AN ITEM AS ADDED HAS PROMISED IT IS SAVED (Ken, September 10 2026)': 'anything typed commits when the field is LEFT'.

**Verification notes.** Person, place and goal-label editors on the edit path commit only on 'change' (worldview-ui.js:1209-1212, 891, 1452, 1519-1522). keyboard.js insert() assigns f.value and dispatches only 'input', and its focusout handler dispatches nothing. Headless Chromium in the scratchpad confirmed that a programmatic value plus an 'input' event, followed by moving focus to another field, produces zero change events. In on-screen keyboard mode, typed edits are therefore saved only by Done or by a later discrete-control commit. Leaving via '‹ All topics' discards them. The general-goals screen has no Done, so a typed label lives only in memory until another add, move or remove. In physical-keyboard mode, and with the OS touch keyboard, real keystrokes do fire change, so the trigger is limited to the app's on-screen keyboard. That is the keyboard designed for the target users.

**Reproduction (reproduced).** Method: Two parts.
1. Browser check: headless Chromium via puppeteer, loaded with createRequire from the project (scratchpad r2.cjs). I reproduced keyboard.js insert() (lines 140-148) exactly: assign field.value, setSelectionRange, dispatch a synthetic 'input' event. Then I moved focus away and counted 'change' events. As a control, I ran the same flow with real keystrokes (page.keyboard.type) and clicked away.
2. Code trace: I followed the listeners in worldview-ui.js and the keyboard's focusout handler. Results: the on-screen-keyboard-style insertion produced log ['input','input'] and NO 'change' event on blur. The real-keystroke control produced ['change: chessold'].

Why that loses the edit:
- On the edit path every typed person field commits only through addEventListener('change', commitNow) (worldview-ui.js:1208-1210). The same applies to the goal label (891) and place facts (1452).
- keyboard.js contains no 'change' dispatch (grep finds none). Its focusout handler (743-786) only manages showing and hiding the keyboard.
- The '‹ All topics' button (renderPeople at line 684) calls renderHome with no commit.
- So text typed with the app's on-screen keyboard is written only if Done is pressed or a discrete control (select or checkbox) changes afterwards.

A typed goal label is held only in memory via the 'input' handler (line 884), so it is lost the same way. On renderGeneralGoals (1287-1308) there is no Done button to rescue it.

All the affected fields are '.wv-text', which is inside the keyboard's IN_SCOPE (keyboard.js:38), so they are typed with the on-screen keyboard whenever on-screen mode is on.
