# CR-010: Report endpoint permanently refuses any report with a cell over 50,000 characters (most problem reports, some weekly reports), and the stuck report then blocks every later report

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** high
- **Category:** data-loss
- **Verdict:** confirmed (skeptic: confirmed; reproducer: reproduced)
- **Location:** `scripts/weekly-report-endpoint.gs:100`
- **Also affects:** `scripts/weekly-report-endpoint.gs:174`; `scripts/weekly-report-endpoint.gs:197`; `app/js/weekly-send.js:380`; `app/js/weekly-send.js:295`; `app/js/app.js:6430`; `app/js/diagnostics.js:138`; `app/js/app.js:6832`; `app/js/weekly-send.js:380 (merged duplicate: An oversized report is refused by the Sheet forever and blocks every later weekly report while telling the tester it will send)`; `scripts/weekly-report-endpoint.gs:108 (merged duplicate: A report too large for one spreadsheet cell is refused forever and blocks every later report in the queue)`
- **Source:** reporting-platform-01, x-security-02, x-contracts-06

**What a user notices.** A tester who presses Send on a problem report is told it is saved and will go by itself, but it never arrives, and from then on their weekly reports stop arriving too, for weeks. The team hears nothing from exactly the tester who tried to tell them about a problem.

**What is wrong.** Google Sheets refuses any single cell longer than 50,000 characters; appendRow throws 'Your input contains more than the maximum of 50000 characters in a single cell'. doPost writes the whole problem report text into one cell (p.report, column 'full report') and the whole weekly payload JSON into one cell (_raw(p), column 'raw'). The problem report embeds the full transcript of every conversation that had an error (buildErrorReport, now including every offered card set as an [offered ...] line), up to 200 'recent events' lines and up to 80 voice lines, so a tester with errors in two or three normal-length conversations easily exceeds 50,000 characters. The weekly raw JSON carries 60 days of per-day event counts (metrics byDay), up to 200 new errors, and systemInfo.speech.voices with the ENTIRE voice list (no cap; Edge exposes hundreds of 'Online (Natural)' voices). When the throw happens doPost catches it and answers 'error: Exception: ...'. post() turns that into 'refused: ...', flush() keeps it at the head of the queue and returns, so every later payload (weekly or problem) waits behind it until enqueue() evicts the head after 8 more enqueues (about 8 weeks at one report a week - longer than the beta). The weekly error mark and weeklySendLastAt were already advanced when it was queued, so the errors it carried never reach the Sheet. The refusal is permanent: the same oversized text is retried every launch.

**How it happens.** 1) Tester has two 20-minute conversations that each hit an AI error (about 30 offered card sets each, ~300 characters per [offered] line). 2) They open Settings > Troubleshooting and press Send, confirm. 3) The report text is ~60,000 characters; appendRow throws; endpoint answers 'error: Exception: Your input contains more than the maximum of 50000 characters in a single cell'. 4) App shows 'Not sent yet - it is saved and will go by itself next time'. 5) Every later launch retries it and fails; the next 7 weekly reports queue behind it and are never posted. Same outcome for a weekly report on Edge whose systemInfo voice list plus 60 days of byDay counts passes 50,000 characters.

**Suggested fix.** Endpoint (primary): add `var CELL_MAX = 49000; function _clip(s) { s = String(s == null ? '' : s); return s.length > CELL_MAX ? s.slice(0, CELL_MAX - 60) + '\n[...truncated ' + (s.length - CELL_MAX + 60) + ' chars]' : s; }` and wrap every free-text value: `_clip(p.note)`, `_clip(_raw(p))`. For the problem report, keep the whole text by splitting it across columns appended at the END of PROBLEM_HEADER ('full report', 'full report (2)' ... 'full report (6)'): `var parts = []; for (var i = 0; i < 6; i++) parts.push(String(p.report || '').slice(i*CELL_MAX, (i+1)*CELL_MAX));` and append `parts` in place of the single value, keeping row length equal to PROBLEM_HEADER.length. Bump SCRIPT_VERSION and redeploy via Manage deployments. App (defense in depth): in diagnostics.collectSystemInfo cap the voice list (e.g. `voices.slice(0, 80)` plus `voiceCount`), matching what formatSystemInfo already prints.

> **Verifier correction to the fix (takes precedence):** The endpoint fix as described is right: clip or split the cells, keep each row exactly as long as its header, add new columns only at the END, bump SCRIPT_VERSION and redeploy through Manage deployments. Add two things on the app side as defence in depth: cap info.speech.voices in collectSystemInfo (for example the first 80, keeping voiceCount), and fix finding 03 so systemInfo is not re-sent every week.

**How to verify the fix.** Add a case to tests/weekly-send-delivery.test.mjs (or a new tests/weekly-endpoint.test.mjs that loads the .gs file in a vm with stubbed SpreadsheetApp whose appendRow throws when any cell > 50000 chars) posting a problem payload with a 120,000-char report and a weekly payload with a 2,000-entry voices list; assert the response is 'ok' and the row length equals the header length. Manually: run a probe POST with a 60,000-char report to the redeployed /exec URL and confirm 'ok' and the split columns in the problems tab.

**Do not break.** Rows must stay exactly as long as their header and new columns may only be added at the END (endpoint _fit rule). Do not drop transcripts from the problem report; they are the permitted, previewed exception. Keep the client's 'only remove on ok' queue rule intact.

**Verification notes.** Traced end to end. doPost writes p.report (problems tab) and _raw(p) (reports tab) each into a single cell with no length limit (weekly-report-endpoint.gs:100-109, 174, _raw at 353). A Google Sheets cell holds at most 50,000 characters and appendRow throws past that; the outer catch (197-198) returns 'error: ...'. post() maps any non-'ok' body to 'refused: ...', and flush() (weekly-send.js ~375-383) leaves the payload at the head and returns, so every later payload waits behind it. enqueue() only evicts the head after the queue passes QUEUE_MAX = 8. The weekly path's error mark and weeklySendLastAt are advanced when the payload is built or queued (weekly-send.js:295, 413-417). Size check: the one real problem report in Reports/ is 13,884 characters, but buildErrorReport embeds the full transcript, including every [offered ...] line, of every conversation that logged an error, from a 200-entry ring buffer, so 50k is reachable. diagnostics.collectSystemInfo puts the whole getVoices() list into info.speech.voices with no cap. block() caps the problem-report text at 80 voices, but the weekly raw JSON carries all of them. Because of finding 03, systemInfo rides in every weekly report, so an Edge device with a long voice list can be refused every week, not just once.

**Reproduction (reproduced).** Method: I ran the real scripts/weekly-report-endpoint.gs in a node vm. Its SpreadsheetApp stub's appendRow throws Google's documented message ('Your input contains more than the maximum of 50000 characters in a single cell.') when any cell is longer than 50,000 characters. I did NOT post to the live endpoint, so the Sheets limit itself is simulated from its documented behavior. A fetch stub routed the real app/js/weekly-send.js (sendProblemReport, flush, enqueue, maybeSend) into that doPost. Browser globals were shimmed the way tests/storage-transcript.test.mjs does it. Script: scratchpad/repro-reporting-platform/e2e.mjs. To size the payloads I captured Edge's real voice roster by launching the installed msedge.exe through puppeteer (non-headless, default args off): voices.mjs gave 324 voices. I measured transcript sizes from Ken's real conversation files (size.mjs) and a real problem report from Reports/...problems.csv. QUEUE BLOCKING, reproduced end to end. sendProblemReport with a 60,000-character report returned {sent:0, queued:1}. The send log reads 'refused: error: Error: Your input contains more than the maximum of 50000 characters in a single cell.' That comes from doPost's catch at gs:197-198 turning into post()'s 'refused: ...'. Eight more reports followed and each one queued behind the stuck head: results {sent:0, queued:2} through {sent:0, queued:8}, the head still the 'it stopped working' note, and 0 rows in the problems tab. Only the 8th later enqueue made enqueue() (weekly-send.js:194-199, QUEUE_MAX 8) drop the stuck head; then {sent:8} went through at once. At one weekly report a week, that is about 8 weeks of blocked reports, as the finding claims. The oversized report is lost permanently, never delivered.

WEEKLY PATH, reproduced. Real maybeSend on the made-up test-data-folder (17 conversations, systemInfo included) produced a raw JSON cell of 5,079 characters. Replacing systemInfo.speech.voices with Edge's real 324-voice list (39,202 characters on its own; diagnostics.js:138 has no cap) made it 44,281, which the endpoint accepted. Adding 120 redacted errors (redactErrors allows up to 200; the first report after a backlog can carry that many) made it 71,410, and the endpoint answered 'error: Error: Your input contains more than the maximum of 50000 characters...'. So a weekly report on Edge needs a sizeable error batch, or larger metrics byDay than the empty set in my run, to cross the limit. It does not happen on every Edge report.

SIZE CLAIM, partly overstated. 'Most problem reports' is too strong. The one real problem report in the Sheet export is 13,884 characters (Sep 6, before offered card sets were logged). Ken's 17 real errored conversations together give only 10,912 characters of transcript. On Edge, a problem report's fixed part already holds about 9.7k characters of voice lines (80 voices x ~120), up to 200 recent-event lines (roughly 10k), plus usage text and settings, so about 25k before any transcript. Offered-set lines in real logs average 174 characters (max 403), so one 20-minute conversation with about 32 offered sets is roughly 8-10k. Two or three such conversations with errors push a report past 50k. That is plausible for a struggling tester, but it is not the common case.

The mechanism and its consequence are real: no clipping at the endpoint, a permanent refusal, and the head-of-queue block that only clears after 8 more enqueues. The weekly error mark advancing on enqueue (weekly-send.js:295) means errors carried in a lost payload never reach the Sheet.

<details><summary>Merged duplicate x-security-02: An oversized report is refused by the Sheet forever and blocks every later weekly report while telling the tester it will send</summary>

Google Sheets refuses any cell longer than 50,000 characters, so appendRow throws, doPost catches it and answers 'error: Exception: Your input contains more than the maximum of 50000 characters in a single cell'. Two cells can exceed that: the problem tab's 'full report' (p.report, which embeds the full transcript of every conversation that hit one of up to 200 logged errors, plus system info and the voice list) and the reports tab's 'raw' column (_raw(p): up to 200 redacted errors x ~250 chars plus systemInfo). post() turns any non-'ok' body into a refusal and flush() stops at the first refusal, leaving the payload at the head of the queue. Because the refusal is permanent, every later launch retries the same payload, fails, and stops; all weekly payloads queued behind it are stuck until enqueue() shifts the head out after 8 more enqueues (about 8 weeks). Meanwhile sendProblemReport's caller shows 'Not sent yet - it is saved and will go by itself next time you open the app', which is false. Separately, saveWeeklyQueue swallows a localStorage quota error, so a very large problem report can be dropped from the queue entirely while the status line still says it is saved.

Fix as proposed by that reviewer: Endpoint (scripts/weekly-report-endpoint.gs): add `function _cell(s) { s = String(s == null ? '' : s); return s.length > 49000 ? s.slice(0, 48900) + '\n[truncated - ' + s.length + ' chars]' : s; }` and wrap p.note, p.report and _raw(p) with it; bump SCRIPT_VERSION and redeploy via Manage deployments. App (weekly-send.js flush): distinguish a permanent refusal from a transient one - when the body starts with 'error:' or equals 'bad secret', move that payload out of the queue into the send log (outcome 'refused permanently: ...') and continue with the next item instead of returning; keep the current stop-and-retry behavior only for a rejected fetch. In sendProblemReport, cap `report` client-side (for example 45,000 characters with a truncation note) before enqueuing, and in app.js show a different status when the result's last log outcome is a refusal rather than 'waiting for a connection'.


Verifier correction: Truncating at the endpoint (_cell on note/report/raw) is the most robust fix since it needs no app release. On the app side, prefer capping the report text before enqueue over dropping 'error:' payloads automatically: an 'error:' reply can also be transient (a mail-quota throw, a Sheets outage), and dropping those would lose reports. If a permanent/transient split is added, treat only the specific too-long message (or 'bad secret') as permanent.

<details><summary>Merged duplicate x-contracts-06: A report too large for one spreadsheet cell is refused forever and blocks every later report in the queue</summary>

Google Sheets rejects any single cell longer than 50,000 characters. The endpoint writes the whole problem report text (`p.report`) into one cell and the whole weekly payload (`_raw(p)`) into one cell, with no truncation. A problem report contains complete transcripts of every conversation that logged an error plus the error list; a weekly payload can contain up to 200 redacted errors (~300 chars each in JSON) and, when systemInfo changed, the full voice roster (Edge exposes hundreds of voices) - both can exceed 50,000. appendRow throws, doPost returns 'error: ...', post() returns 'refused: error: ...', and flush() keeps the payload at the head and stops (lines 380-383). Every launch retries the same oversized payload; later payloads (including a newly sent problem report, appended at the end) are stuck behind it until enqueue() evicts it after 8 more entries (~8 weeks of weekly reports).

Fix as proposed by that reviewer: Endpoint: add a helper `function _cell(s) { s = String(s || ''); return s.length > 49000 ? s.slice(0, 49000) + '\n[truncated: ' + s.length + ' chars]' : s; }` and use it for `p.note`, `p.report` and `_raw(p)`; bump SCRIPT_VERSION and redeploy via Manage deployments (same URL). App side (belt and braces): in weekly-send.flush, if the head has been refused (outcome starts with 'refused') on N consecutive attempts (store an attempt count on the queued payload, e.g. payload._attempts), drop it, log it via appendWeeklySendLog, and continue with the next item instead of returning.


Verifier correction: Truncating on the endpoint requires a redeploy (Manage deployments, same URL) to take effect. For the app-side cap, store the attempt count somewhere that survives (on the queued payload or a separate key) and only count 'refused' outcomes, never fetch rejections; also consider moving a stuck head to the back rather than dropping so a problem report queued behind it is sent first.
