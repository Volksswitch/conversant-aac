# CR-011: In a 'Don't save this conversation' conversation, the partner's words are still written to the About Me file

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** high
- **Category:** privacy
- **Verdict:** confirmed (skeptic: confirmed; reproducer: reproduced)
- **Location:** `app/js/app.js:1923`
- **Also affects:** `app/js/app.js:1931 recordExtraGaps(result.missingOther, partnerText)`; `app/js/worldview.js:329-331 gaps[].partnerText`; `app/js/worldview.js:411 extras[].partnerText`; `app/js/storage.js:2007 isConversationSaving`; `app/js/app.js:1923 (merged duplicate: 'Don't save this conversation' still writes the partner's exact words into worldview.json (gaps and new questions))`
- **Source:** app-b-03, x-contracts-04

**What a user notices.** If the user marks a conversation as not to be saved, what the other person said can still end up stored on the device (and in backups and the data folder, which may be cloud-synced) as part of the user's About Me information.

**What is wrong.** After every successful generation, generateOptions calls worldview.recordGaps(result.missingFacts, partnerText) and worldview.recordExtraGaps(result.missingOther, partnerText) unconditionally. Both store the verbatim partner text (`existing.partnerText = partnerText` / `partnerText: partnerText || ''`) in the worldview profile and then `await save()`, which writes worldview.json to the data folder and the localStorage cache. Nothing checks storage.isConversationSaving(). Every other partner-speech write (logPartnerInterim, finalizePartnerTurn, logUserResponse, logError's extra.partner) honors the private flag; this one does not. worldview.json is included in Export/backups.

**Evidence.**

```
app/js/app.js:1922-1924 `if (result.missingFacts && result.missingFacts.length) {\n            worldview.recordGaps(result.missingFacts, partnerText).catch(() => { /* non-fatal */ });`
app/js/app.js:1930-1931 `worldview.recordExtraGaps(result.missingOther, partnerText)`
app/js/worldview.js:329 `if (partnerText) existing.partnerText = partnerText;`
app/js/worldview.js:331 `profile.gaps.push({ key, partnerText: partnerText || '', count: 1, lastSeen: now });`
app/js/worldview.js:411 `count: 1, lastSeen: now, partnerText: partnerText || '',`
app/js/storage.js:2168 `if (!conversationSaving) return; // private conversation — nothing is written` (the rule every other writer follows)
```

**How it happens.** Tap the 'Don't save this conversation' toggle. Partner asks "What's your address? I need it for the form." With the address field unanswered, the model returns missing_facts containing the address key. worldview.json now contains gaps[{key:'address', partnerText:'What\'s your address? I need it for the form.'}], persisted to disk and included in the next backup.

**Suggested fix.** In generateOptions, pass the partner text only when saving is on: `const gapContext = storage.isConversationSaving() ? partnerText : '';` and use gapContext in both recordGaps and recordExtraGaps calls. Recording that the gap exists (key, count) carries no conversation content and can stay.

**How to verify the fix.** Add a test in tests/worldview.test.mjs is not enough because the decision is in app.js; add a source-level guard in tests/placeholders.test.mjs asserting the generateOptions body passes a value derived from isConversationSaving to recordGaps/recordExtraGaps. Manual: with a fixture profile missing a field, toggle Don't save, have the partner ask about it, then inspect localStorage aac_worldview / worldview.json and confirm no partnerText text is present.

**Do not break.** Do not stop recording the gap itself (the 'suggested next' / extras features depend on it). Keep the behavior for saved conversations unchanged.

**Design reference.** CLAUDE.md SEC-2 ('Don't save this conversation' no longer leaks partner speech); both User Manuals' privacy wording (a private conversation leaves only a technical error note).

**Verification notes.** generateOptions (app.js ~1921-1931) calls worldview.recordGaps(result.missingFacts, partnerText) and recordExtraGaps(result.missingOther, partnerText) with no isConversationSaving check. worldview.js:329/331/411 store the verbatim partner text in profile.gaps / profile.extras and then await save(), which persists worldview.json (data folder) and the localStorage cache. Every conversation-log writer in storage.js returns early on !conversationSaving; this path does not. Not listed in TODO.md or the Security Review document.

**Reproduction (reproduced).** Method: Ran the real app/js/storage.js and app/js/worldview.js in node (tests/env.mjs localStorage shim + mockFetchFromDisk for the registry). Set storage.setConversationSaving(false), then made the same two calls generateOptions makes at app.js 1922-1931: worldview.recordGaps(['home_city'], partnerText) and worldview.recordExtraGaps([{name:'insurance_provider',question:...}], partnerText). Read back localStorage 'aac_worldview'. Also checked generateOptions (1743-1935) for any isConversationSaving guard and data-transfer.js for whether worldview.json is backed up. isConversationSaving() = false, yet aac_worldview now contains gaps:[{key:'home_city', partnerText:'Where do you live now? I need it for the intake form.', count:1}] and extras:[{name:'insurance_provider', ..., partnerText:'Where do you live now? I need it for the intake form.'}]. worldview.save() (166-170) writes both the localStorage cache and worldview.json in the data folder. generateOptions contains zero references to isConversationSaving; the calls are unconditional. data-transfer.js:102 includes worldview.json ('About Me answers') in Export/backups, so the verbatim partner speech from a 'Don't save' conversation travels into backups.

generateOptions passes the raw partner turn (partnerText) to worldview.recordGaps and worldview.recordExtraGaps on every generation that returns missing_facts / missing_other. Both store it verbatim (`partnerText`) in the profile and save() writes worldview.json to the data folder and the localStorage cache. Neither call checks storage.isConversationSaving(). For a private conversation every other store is gated (logUserResponse, logPartnerInterim, logEvent, logOffer, logError strips extra.partner, recordSteer is gated by its caller), so this is the one place third-party speech from a private conversation lands on disk. worldview.json is also exported in backups (data-transfer DATA_FILES) and synced if the folder is on OneDrive/Drive. The privacy documents promise that nothing said in a private conversation is written down (only a technical error note).

Fix as proposed by that reviewer: In generateOptions (app/js/app.js ~1920-1932) compute `const gapContext = storage.isConversationSaving() ? partnerText : '';` and pass gapContext instead of partnerText to both worldview.recordGaps and worldview.recordExtraGaps. Keep recording the gap keys/questions themselves (they are about the user, not the partner's words). Optionally also gate in worldview.js by accepting partnerText only when provided.


Verifier correction: Gate partnerText as suggested (pass '' when !storage.isConversationSaving()). Also note recordGaps keeps an existing gap's earlier partnerText when given '' (line 329 only overwrites if truthy), which is fine. Consider whether the model-written extras `question` should also be skipped for private conversations, since it is derived from what the partner asked; decide with Ken.
