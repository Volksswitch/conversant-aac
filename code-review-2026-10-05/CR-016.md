# CR-016: Keyboard focus is thrown back to the top of the page whenever the panel, the cards or an About Me card redraws, or the composer closes

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** accessibility
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/ui.js:536`
- **Also affects:** `app/js/ui.js:345`; `app/js/ui.js:1254`; `app/js/app.js:4573`; `app/js/app.js:4587`; `app/js/app.js:4619`; `app/js/app.js:4632`; `app/js/worldview-ui.js:1588`; `app/js/worldview-ui.js:839`; `app/js/express-editor.js:174`; `app/js/app.js:1661`
- **Source:** x-a11y-04

**What a user notices.** A keyboard or switch user who switches on a partner, place, feeling or goal, picks a suggestion, closes 'In my own words', or answers an About Me question loses their place: the next Tab starts again from the very top of the screen, so every action costs many extra presses.

**What is wrong.** Several surfaces rebuild their DOM with innerHTML='' or replaceWith() and never move focus to the equivalent new element, so document.activeElement falls to <body>. ui.renderExpressPanel clears epGrid (ui.js:536) and every Express toggle handler calls renderExpressPanel (app.js:4573/4587/4619/4632), destroying the button that was just activated. showResponses/clearResponseOptions clear #responseOptions (ui.js:345/404) on every selection and every reprompt, so a focused card disappears. hideComposerOverlay blurs the textarea (ui.js:1257) without returning focus to the 'In my own words' button. About Me's refreshCard replaces the whole card after each chip/Save (worldview-ui.js:1588-1590); buildGoalEditor's renderGoals rebuilds rows after Move up/down/remove (worldview-ui.js:839-863); the Express editor's move() calls render() (express-editor.js:174). The pre-start chain hides the focused Start/Close button (app.js:1615, 1646, 1661) without focusing the next step's control.

**Evidence.**

ui.js:345 `responseOptions.innerHTML = '';`

express-editor.js:172-174 `[list[i], list[j]] = [list[j], list[i]]; saveBand(band, list); render();`

**How it happens.** 1. Settings > Express Panel and Keyboard > 'My physical keyboard'. 2. Start a conversation. 3. Tab to a partner button in the Express Panel and press Enter. 4. Press Tab once: focus lands on the first control at the top of the document (Start report link / Listen) rather than the next panel button. Same after pressing Enter on a response card, after Cancel in 'In my own words', and after pressing Enter on an About Me answer chip.

**Suggested fix.** Add focus preservation at each rebuild. (a) In ui.renderExpressPanel: before `epGrid.innerHTML = ''`, record `const hadFocus = epGrid.contains(document.activeElement)` and the focused cell's ordinal (index of the button among `epGrid.querySelectorAll('button')`); after the grid is rebuilt, if hadFocus, focus the button at the same ordinal (`{preventScroll:true}`). Cell ordinals are fixed by the layout, so the same position is the right target. (b) In showResponses/clearResponseOptions: if a card had focus, focus the card with the same data-index after rebuild, or #regenerateBtn when the palette is cleared. (c) ui.showComposerOverlay should remember `document.activeElement` and hideComposerOverlay should restore it (falling back to `#epGrid .ep-imow`) instead of only blurring. (d) worldview-ui refreshCard: after replaceWith, focus the new card's element matching the previously focused element's text/class (e.g. the chip with the same text), else the card's first chip/input. (e) buildGoalEditor and express-editor move(): after re-render, focus the same action button on the moved row. (f) In the pre-start chain, focus the visible step's primary button (folderReconnectBtn, apiKeyContinueBtn, the What's-new Close) when it is shown.

**How to verify the fix.** Add Puppeteer cases (tests/ui-standards.test.mjs already drives the real app): focus an Express partner button, press Enter, assert document.activeElement is an .ep-btn at the same ordinal; open and cancel the composer via keyboard and assert focus returns to .ep-imow. Unit-level: a jsdom-free check is not possible for ui.js, so the browser test is the verification.

**Do not break.** Do not call focus() on text fields as a side effect (focusing a text field raises the on-screen keyboard over the panel - see revealSetting and openSettings comments); only restore focus when the element that was focused before the rebuild was inside the rebuilt region, so touch users (whose taps do not leave keyboard focus) are unaffected. Use preventScroll to avoid moving the transcript. No geometry change.

**Design reference.** CLAUDE.md Worldview Questionnaire 'Keyboard / field tabbing - shipped' (physical-keyboard users supported); ui.js composerTabTrap comment

**Verification notes.** I verified each rebuild point. ui.renderExpressPanel sets `epGrid.innerHTML = ''` (ui.js:536), and every toggle handler calls renderExpressPanel (app.js:4573, 4587, 4619, 4632). hideComposerOverlay only blurs the textarea and never restores focus (ui.js:1254-1260). worldview-ui refreshCard replaces the whole card (1588-1590), and the code only refocuses when a module is first rendered. No focus-restoration code exists in ui.js beyond the composer's tab trap. This affects keyboard and switch users only, but physical-keyboard use is an explicitly supported mode.
