# CR-017: Before Start, a physical keyboard can operate the whole conversation screen and skip the start-up sequence

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/css/styles.css:1103`
- **Also affects:** `app/index.html:44`; `app/js/app.js:1475`; `app/js/app.js:1657`
- **Source:** x-a11y-02

**What a user notices.** Someone using a physical keyboard or a switch that acts like a keyboard can press Tab past the Start button and use Listen, the Express Panel or Settings on the dimmed screen. If they do, the app never reconnects their data folder for that session, so conversations and changes are kept only in the browser, and on an iPad the voice may stay silent.

**What is wrong.** Pre-start blocking is done only with `main.disabled { pointer-events: none; }`. pointer-events blocks mouse/touch but not keyboard focus or keyboard activation. The Start button sits inside <main> (#transcriptSection > #startBlock), so Tab from Start moves straight into #listenControls, #regenerateBtn and the Express Panel buttons, all of which act on Enter/Space. No handler checks `main.disabled`. Activating any of them bypasses handleStart(), which is where the data-folder permission is requested and storage warmed up (storage.requestFolderPermissionNow, warmUpStorage), the audio contexts are unlocked (chime.unlock, tts.unlockAudio), fullscreen is requested, the weekly report is scheduled, and the What's-new / reconnect / API-key steps run.

**Evidence.**

```
styles.css:1103-1105 `main.disabled { pointer-events: none; }`
index.html:44 `<main class="disabled" id="conversationMain">` (Start button is inside it at index.html:111)
app.js:1475-1505 handleStart: `chime.unlock(); ... tts.unlockAudio(); ... storage.requestFolderPermissionNow(); requestAppFullscreen(); ... await withTimeout(warmUpStorage(), ...)`
grep of app.js finds no `classList.contains('disabled')` guard in any Command Bar/Express handler.
Measured in headless Chrome before Start: focusable elements in main, in Tab order: startBtn, startReportBtn, listenBtn, initiateBtn, endConversationBtn, sayAgainBtn, holdOnBtn, pardonBtn, windDownBtn, privacyBtn, settingsBtn, regenerateBtn, ... plus Express Panel buttons.
```

**How it happens.** 1. Launch the app with a data folder previously chosen (Android or Windows) and a physical keyboard. 2. On the launch screen press Tab three times (Start, the report link, then Listen) and press Enter, or Tab to an Express Panel phrase and press Enter. 3. The app starts listening / speaks the phrase while the screen is still dimmed; the folder was never reconnected, so the conversation log and any About Me edits go to the localStorage cache only; on iOS the paid voice may be silent because audio was never unlocked.

> **Verifier correction to the trigger:** "Never reconnects for that session" is too strong. Pressing Start later still runs handleStart and reconnects the folder. The real exposure is the window before Start: conversation turns are not written to the folder, and About Me answers typed then go to the browser cache only. When a worldview.json already exists in the folder, the file wins at the next sync and those cache-only answers are dropped.

**Suggested fix.** Make the regions behind the start overlay inert rather than only pointer-blocked. In finishStart() (app.js ~1657) remove `inert` from #listenControls, #responsesSection, #dockArea and #transcriptLog (and the composer overlay); add a small helper `setPreStartInert(on)` that sets/removes the `inert` attribute on those four elements, call `setPreStartInert(true)` once early in initApp (or put `inert` on those elements in index.html), and `setPreStartInert(false)` in finishStart(). Do not make <main> itself inert, because #startBlock lives inside it. Keep the existing `main.disabled` dimming CSS.

**How to verify the fix.** Manual: reload, press Tab from Start - focus must go to the report link and then leave the page (or cycle back), never to Listen or Express buttons; after Start, all controls are Tab-reachable again. Automated: add a Puppeteer case to tests/ui-standards.test.mjs (it already drives the real app) asserting that before Start no element inside #listenControls/#dockArea/#responsesSection is reachable (`el.closest('[inert]')` true) and that after clicking Start none is inert.

**Do not break.** #startBlock (Start, the reconnect/API-key/What's-new cards and the report button) must stay operable - it is the only route when Settings is unreachable. Conversation Review and Settings re-open paths call restoreConversationScreen/finishStart-like code; make sure nothing re-adds inert after Start. Paint-only - no geometry change (Rule 1).

**Design reference.** CLAUDE.md 'Android' section (folder permission must be requested on the Start tap) and 'Beta instrumentation' (Settings unreachable before Start by design); index.html comments at lines 112-128

**Verification notes.** `main.disabled` sets only `pointer-events: none` (styles.css:1103). Start lives inside <main> at index.html:111. #listenControls (136), #responsesSection (157) and #dockArea (189) follow it in document order, and nothing makes them inert or removes them from the tab order. No handler checks the disabled class (grep finds only finishStart's remove at app.js:1662). toggleListening runs straight into startFreshListening. The folder reconnect, storage warm-up and audio unlock all happen only in handleStart.
