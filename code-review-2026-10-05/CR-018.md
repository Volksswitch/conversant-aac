# CR-018: "In my own words" text-size setting has no effect

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/css/styles.css:2019`
- **Also affects:** `app/css/styles.css:3069-3078 (#composerInput rule that reads --composer-font-scale)`; `app/js/app.js:5139 (sets --composer-font-scale)`; `app/js/app.js:8413 (composerFontSelect onchange)`; `app/index.html:430-431 (the Settings control)`
- **Source:** css-02

**What a user notices.** Changing the text size for "In my own words" in Settings does nothing: the typing box always uses the same small text, which matters for someone with low vision who needs to read what they are typing.

**What is wrong.** The composer textarea only exists inside the overlay (index.html line 166-167). The rule that applies the user's scale, `#composerInput { font-size: calc(1.1rem * var(--composer-font-scale, 1)) }` (specificity 1,0,0, line 3076), is overridden by `.composer-overlay #composerInput { font-size: 1.1rem; }` (specificity 1,1,0, line 2019), which hard-codes the size. So --composer-font-scale, set by applyFontScales() from the composerFontSelect setting, is never used. Measured in headless Chrome with --composer-font-scale:1.6 on body: the textarea computed font-size 16.06px (= 1.1rem) instead of ~25.7px.

**Evidence.**

```
styles.css:2006-2019 `.composer-overlay #composerInput { ... font-family: inherit; font-size: 1.1rem; resize: none; }`
styles.css:3069-3076 `#composerInput { ... /* User-settable "In my own words" text size (Settings → Speech & Input). */ font-size: calc(1.1rem * var(--composer-font-scale, 1));`
app.js:5139 `root.setProperty('--composer-font-scale', String(storage.loadComposerFontScale()));`
```

**How it happens.** Settings > Text & Color > text size for "In my own words" = the largest option. Close Settings, open the composer from the Express Panel, type: the text is the same size as at the default setting.

**Suggested fix.** In the `.composer-overlay #composerInput` rule (line 2019) replace `font-size: 1.1rem;` with `font-size: calc(1.1rem * var(--composer-font-scale, 1));`, and remove the now-unreachable font-size line from the plain `#composerInput` rule at line 3076 (or leave it - it is harmless) so there is a single source.

**How to verify the fix.** Manual: set the composer text size to the largest value, open the composer, confirm the typed text is visibly larger; confirm the prediction ghost still lines up with the typed text (keyboard.js copies the field's computed font, so it should). Add an assertion to tests/styles.test.mjs that every rule whose selector targets #composerInput and sets font-size uses var(--composer-font-scale).

**Do not break.** The composer overlay is a fixed footprint over the response region; a larger font must not change the overlay's size (it does not - the textarea is flex 1 1 auto and scrolls). Speak/Reframe/Cancel must stay aligned with the card and New 4 holes.

**Design reference.** CLAUDE.md UI Layout Rule 13 (text size is a per-surface user setting, which is why zoom can be disabled)

**Verification notes.** #composerInput exists only inside #composerOverlay (index.html:166-167). .composer-overlay #composerInput (1,1,0) at styles.css:2006-2019 sets font-size: 1.1rem and outranks #composerInput (1,0,0) at 3069-3078, which is the only rule reading --composer-font-scale. app.js:5139 sets the variable and 8413 wires the select, so the setting is saved and applied to a property nothing uses.
