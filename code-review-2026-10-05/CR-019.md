# CR-019: Paid transcription time is under-counted: the running total is never reset when listening restarts

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:1274`
- **Also affects:** `app/js/app.js:176-179`; `app/js/stt-deepgram.js:293`; `app/js/stt-azure.js:447`; `app/js/stt-rest.js:314`; `app/js/app.js:1276 (merged duplicate: The paid-transcription usage total drops the first speech burst of every listening session)`; `app/js/app.js:1274 (merged duplicate: Paid hearing time is under-counted: the first phrase of every listening run is dropped from the cost)`
- **Source:** app-a-01, stt-07, x-providers-03

**What a user notices.** The cost of paid transcription shown in Settings reads far lower than what the service actually bills, because most of the audio heard after the first listening session is never counted. A user budgeting by that figure will be surprised by the real bill.

**What is wrong.** Every paid STT source reports a CUMULATIVE total for the current listening session (billedMs), and every source resets that total to 0 each time it starts (stt-deepgram.js:293, stt-azure.js:447, stt-rest.js:314). handleSttBilled stores only the increment over the last value seen, held in the module-level sttBilledThisSession, which is never reset anywhere (grep: only lines 179, 1276, 1277). After the first listening session, the next session's first report is smaller than the stale total, so delta is negative and ignored while the baseline is lowered; that whole first burst of audio is lost. With auto-resume on, the source is stopped and restarted on every exchange, and a typical partner turn is one burst, so most transcription after the first exchange is never added to usageSttSeconds. CLAUDE.md (prompt-caching section) states a cost display that reads low is worse than none, since the whole funding model is 'you pay only for what you use'.

**Evidence.**

```
app/js/app.js:176-179
// Cumulative audio (seconds) the paid transcription backend has uploaded since it
// was last started ...
let sttBilledThisSession = 0;

app/js/app.js:1274-1279
function handleSttBilled(seconds) {
    // The source reports its cumulative total for the session; store the delta.
    const delta = seconds - sttBilledThisSession;
    sttBilledThisSession = seconds;
    if (delta > 0) storage.addSttSeconds(delta);
}

app/js/stt-deepgram.js:293  billedMs = 0;   (inside start)
app/js/stt-azure.js:447    billedMs = 0;
app/js/stt-rest.js:314     billedMs = 0;
```

**How it happens.** Deepgram (or any paid) hearing, auto-resume on. Exchange 1: partner speaks 6 s -> onBilled(6) -> +6 counted, baseline 6. User picks a card; listening restarts (billedMs reset to 0). Exchange 2: partner speaks 4 s in one burst -> onBilled(4) -> delta -2, nothing added, baseline 4. Exchange 3: 3 s -> onBilled(3) -> delta -1, nothing added. Settings shows 6 s while 13 s were billed.

**Suggested fix.** Make every source tell the app when its running total restarts. In each of the three source files, immediately after the line `billedMs = 0;` in the start path, add `if (onBilled) onBilled(0);`. handleSttBilled then sees 0, computes a negative delta (ignored) and sets sttBilledThisSession = 0, so the next real report is counted in full. Alternatively, inside handleSttBilled treat a decrease as a new session: `const delta = seconds >= sttBilledThisSession ? seconds - sttBilledThisSession : seconds;` - but that still under-counts when a new session's first report exceeds the old total, so the onBilled(0) reset is the correct fix.

**How to verify the fix.** Add a test in tests/stt-rest.test.mjs (or the deepgram/azure source tests) that starts a source, captures onBilled calls, stops and starts again, and asserts onBilled(0) is reported at the second start. Manual: with a paid key and auto-resume on, hold three exchanges of ~5 s each and confirm Settings -> About transcription seconds grows by roughly 15, not 5.

**Do not break.** Do not change the cumulative-report contract in a way that double-counts (do not switch the sources to per-burst increments while also leaving the app's delta logic). The VAD gating that bills only speech must be untouched.

**Design reference.** CLAUDE.md 'Prompt caching' (cost display must not under-report) and 'Paid speech-to-text - Deepgram' (usage counted in seconds because transcription bills while nobody is doing anything deliberate)

**Verification notes.** Traced end to end. All three paid sources keep a cumulative billedMs that is zeroed in their start path (stt-deepgram.js:293, stt-azure.js:447, stt-rest.js:314) and report the running total through onBilled (stt.js passes the app's handleSttBilled straight through at stt.js:420). handleSttBilled (app.js:1274-1279) stores only seconds - sttBilledThisSession, and sttBilledThisSession is assigned only at its declaration (179) and at 1277 - nothing resets it when a source restarts. Every exchange stops the source (handleResponseSelected -> stt.stopListening) and a resume calls openSource -> externalSource.start(), which zeroes billedMs. So the first report of each later session is compared against the previous session's larger total, the delta is negative and dropped, and the baseline is lowered. The reviewer's 6+4+3 scenario reproduces exactly (6 counted of 13). Also applies to a Settings service switch, which builds a fresh source starting at 0. No test covers it and TODO.md does not track it.

<details><summary>Merged duplicate stt-07: The paid-transcription usage total drops the first speech burst of every listening session</summary>

Each paid source reports a CUMULATIVE total via onBilled and resets that total to 0 on every start() (billedMs = 0). app.js handleSttBilled() converts it to a delta against `sttBilledThisSession`, which is a page-lifetime variable never reset when a new listening session starts. On the first report of a new session, `seconds` is small and `sttBilledThisSession` holds the previous session's total, so `delta` is negative and dropped, and the variable is then overwritten with the new small value. The microphone is stopped and restarted on every exchange (stopListening on each response; auto-resume restarts it), so for a partner who speaks one burst per turn most billed audio is never added to usageSttSeconds.

Fix as proposed by that reviewer: In handleSttBilled treat a decrease as a new session: `const delta = seconds >= sttBilledThisSession ? seconds - sttBilledThisSession : seconds;` then `sttBilledThisSession = seconds; if (delta > 0) storage.addSttSeconds(delta);`. (Alternatively change the sources to report per-burst increments, but that touches three files.)


Verifier correction: The suggested `seconds >= prev ? seconds - prev : seconds` is still wrong when the new session's first report exceeds the previous session's total: it counts the difference instead of the full value. Make the sources report increments instead. At each `billedMs += x` in stt-deepgram.js, stt-azure.js and stt-rest.js, call `onBilled(x / 1000)`, and have handleSttBilled simply `storage.addSttSeconds(seconds)`. The alternative is a session token or reset hook that zeroes sttBilledThisSession whenever a source's start() resets billedMs. Keep Azure's billedSeconds() accessor working.

</details>

<details><summary>Merged duplicate x-providers-03: Paid hearing time is under-counted: the first phrase of every listening run is dropped from the cost</summary>

Each paid capture source reports a cumulative billed total for the current run via onBilled(billedMs/1000), and resets billedMs = 0 at every start(). handleSttBilled converts that into a delta against the module-level sttBilledThisSession, which is never reset when a new run starts (it is only ever assigned inside handleSttBilled). After the first run, the first report of the next run is smaller than the stored baseline, so the delta is negative and discarded, and the baseline is then lowered to that value - the first span of every subsequent run is lost. With auto-resume on, every exchange is a new run. Simulated: runs of spans [5,10],[4,3],[6] (28 s real) store 18 s.

Fix as proposed by that reviewer: Make the sources report deltas instead of totals, or reset the baseline per run. Smallest change: in each source's start() (stt-deepgram.js, stt-azure.js, stt-rest.js) call `if (onBilled) onBilled(0);` immediately after `billedMs = 0;`, and in handleSttBilled treat a value lower than the baseline as a new run: `const delta = seconds >= sttBilledThisSession ? seconds - sttBilledThisSession : seconds; sttBilledThisSession = seconds; if (delta > 0) storage.addSttSeconds(delta);`. The second line alone fixes it (a drop in the cumulative total can only mean a new run started).


Verifier correction: The 'second line alone' fix (treat a value below the baseline as a new run) is incomplete. If a new run's first report is at or above the old baseline (old baseline 5, new run's first span 8), it still records 3 instead of 8. Reset the baseline at each run start: emit onBilled(0) right after billedMs = 0 in each source's start(), or have handleSttBilled's caller reset sttBilledThisSession when a source reports 'listening'. Better still, have the sources report per-span deltas. Note that Deepgram's stop() also reports a final cumulative value, so any reset must happen on start, not on stop.

</details>
