# CR-024: Practice Mode is switched on/off on the wrong side of the conversation teardown, so real conversations get labeled practice (and vice versa)

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:2546`
- **Also affects:** `app/js/app.js:2554`; `app/js/app.js:2632`; `app/js/app.js:2640`; `app/js/app.js:2783-2784`; `app/js/app.js:2821`; `app/js/app.js:4409-4415`; `app/js/transcript-log.js:115`; `app/js/usage-summary.js:113`; `app/js/review-model.js:35-47`
- **Source:** app-c-01

**What a user notices.** If the other person said something that was never answered and the user then starts a practice scenario, the real conversation is filed as a practice conversation and disappears from the real conversations list in Conversation Review and from the usage counts. Ending a short practice can do the reverse and file a rehearsal as a real conversation with the person the scenario was about.

**What is wrong.** terminateConversation() commits the partner's pending (unanswered) turn with partnerStamp(), and also emits metrics.conversationBoundary({practice: practiceMode}). partnerStamp() returns {label: 'Practice: <title>'} whenever practiceMode && practiceScenario. startPractice() sets practiceMode=true and practiceScenario BEFORE awaiting terminateConversation(), so the REAL conversation's last partner turn is stamped 'Practice: X' (finalizePartner overwrites handle.partner when a stamp is given) and its end event is tagged practice:true. usage-summary.isPractice() and review-model.isPractice() classify a whole conversation as practice if ANY exchange carries a 'Practice:' label, so the entire real conversation is reclassified. handleEndConversation() has the mirror fault: it sets practiceMode=false and practiceScenario=null before terminateConversation(), so the practice conversation's pending partner turn is stamped with activePartner (for a scenario started from a person in About Me, that is the real person, e.g. 'Mom'), overwriting the 'Practice:' label written at the pause; a practice conversation whose only partner line was never answered then contains no practice label at all and is counted as a real conversation with that person. The comment at 2548-2549 ('Set before terminateConversation, which clears the tour') is stale: terminateConversation no longer touches the tour.

**How it happens.** 1) Real conversation: press Listen, partner says 'See you Tuesday', user does not reply. 2) Open Settings > Practice, start 'Ordering coffee'. 3) Open Settings > Conversation Review, real conversations: the real conversation is missing; it appears under practice titled 'Ordering coffee'. Reverse: start a practice scenario created from a person in About Me (e.g. Mom), tap Listen, let the AI partner speak one line, then End conversation without answering: Review lists it as a real conversation with Mom.

> **Verifier correction to the trigger:** Only the forward direction happens (unanswered real partner turn + starting practice reclassifies the real conversation as practice). The reverse case is refuted: every practice conversation's 'start' context entry carries the 'Practice: <title>' partner label, so it is still classified as practice even when End conversation restamps the pending partner turn with the person.

**Suggested fix.** In startPractice, call `await terminateConversation();` FIRST, then set `practiceMode = true; practiceScenario = scenario;` (keep computing isTour from `scenario` before, and delete the stale comment about the tour). In handleEndConversation, capture `wasPractice`, then call `await terminateConversation();` BEFORE setting `practiceMode = false; practiceScenario = null; practiceOpeners = [];` and before `applyListenAvailability()`; keep `tour = null; ui.setCoachLine(null);` where they are (before teardown is fine). Check that nothing in terminateConversation depends on practiceMode being false (it only reads it for the metrics flag and partnerStamp, which is exactly what should now be correct).

> **Verifier correction to the fix (takes precedence):** The startPractice reorder (terminateConversation first, then set practiceMode/practiceScenario) is the needed fix. The handleEndConversation reorder is optional (it would make the pending turn's stamp consistent) but is not required to fix a misclassification; if done, keep applyListenAvailability after practiceMode is cleared.

**How to verify the fix.** Add a source-level guard in tests/placeholders.test.mjs (where app.js source guards live): assert that in startPractice the `await terminateConversation()` appears before `practiceMode = true`, and in handleEndConversation before `practiceMode = false`. Manual: run the two scenarios above with a data folder; open the saved JSON and confirm the real conversation's last partner turn has its real partner stamp and the practice one keeps 'Practice: ...'.

**Do not break.** terminateConversation must keep committing the pending partner turn (Ken, July 12 2026). handleEndConversation's comment says practice must be exited before teardown 'so the paths (resumeOrIdle, stamps) revert' - resumeOrIdle is not called by terminateConversation, so moving the flag after is safe; re-check applyListenAvailability ordering still re-enables/disables Listen correctly.

**Design reference.** CLAUDE.md, Practice Mode - full plan ('Save practice conversations, flagged as practice ... Practice: <scenario>'); Conversation Review - first build ('real or practice conversations, never both')

**Verification notes.** Forward direction traced end to end: startPractice sets practiceMode=true and practiceScenario before awaiting terminateConversation(); terminateConversation captures pendingStamp = partnerStamp() which then returns {label:'Practice: <title>'}; finalizePartnerTurn -> transcript-log.finalizePartner overwrites handle.partner when a stamp is given; usage-summary.isPractice and review-model.isPractice use 'any exchange carries a Practice: label', so the real conversation is reclassified. metrics.conversationBoundary also gets practice:true. The reverse direction (handleEndConversation) does NOT produce the claimed result: a practice conversation's log is created lazily by the partner line's logPartnerInterim, and startConversationLog pushes a 'start' context entry built from contextSnapshot() -> partnerStamp(), which in practice is the 'Practice: X' label. So even if the pending partner turn is restamped with the person, the context entry keeps the practice label and isPractice stays true.
