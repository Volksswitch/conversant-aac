# CR-030: Ending Practice while the practice partner's turn is up leaves the Listen button stuck 'on' when hearing is a paid service

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:3628`
- **Also affects:** `app/js/app.js:2602-2607 (advancePracticePartner sets isListening = true)`; `app/js/app.js:2776-2777 (terminateConversation relies on stt.stopListening to reset the state)`; `app/js/stt.js:730 (stopListening for a paid source just calls externalSource.stop())`; `app/js/stt-deepgram.js:357-358, app/js/stt-azure.js:476-477, app/js/stt-rest.js:327-328 (stop() returns silently when not running)`; `app/js/app.js:2579-2581 (startPractice resets isListening explicitly - the missing counterpart)`; `app/js/app.js:1675-1678 (toggleListening takes the stop branch while isListening is true)`
- **Source:** x-async-07

**What a user notices.** On a device that hears through a paid service (for example an iPad Home Screen app with Deepgram), ending a practice session while the other person's reply is showing leaves the Listen button lit red. Tapping it does nothing, again and again, until the user speaks something.

**What is wrong.** In practice mode advancePracticePartner sets isListening = true and lights the button; it stays true while the cards are up. handleEndConversation sets practiceMode = false and terminateConversation calls stt.stopListening(). For the built-in recognizer that reports 'stopped' synchronously, but for a paid source stopListening returns externalSource.stop(), which returns without any status because the source was never started in practice. Nothing else resets isListening, so the Listen button stays lit, conversationInProgress() stays true (layout borders locked) and every Listen tap takes the stop branch, which again does nothing.

**Evidence.**

```
app.js:2606-2607 `isListening = true;
    ui.setListenButtonState(true);`
stt.js:730 `if (externalSource) return externalSource.stop();`
stt-deepgram.js:357-358 `stop() {
            if (!running) return;`
app.js:1675-1678 `if (isListening) { manualListenArmed = false; stt.stopListening(); } else {...}`
```

**How it happens.** iPad Home Screen app with Deepgram hearing. Settings -> Practice -> pick a scenario -> tap Listen (partner speaks, cards appear) -> Settings -> Practice -> End practice. Back on the normal screen the Listen button is red. Tapping it never starts listening.

**Suggested fix.** In handleEndConversation, after `await terminateConversation();`, add:
```js
if (wasPractice) { isListening = false; ui.setListenButtonState(false); }
```
(mirrors startPractice lines 2579-2581). Alternatively make stt.stopListening report 'stopped' for an external source that was not running: `if (externalSource) { const wasRunning = externalSource.isRunning && externalSource.isRunning(); externalSource.stop(); if (!wasRunning && onStatusChange) onStatusChange('stopped'); return; }`.

**How to verify the fix.** Manual on desktop: Settings -> Speech, choose Deepgram (any key), start a practice scenario, tap Listen, wait for cards, end practice; the Listen button must be off and a tap must start listening. Unit-test the stt.js alternative in tests/stt.test.mjs with a stub external source whose stop() is silent when not running.

**Do not break.** Do not emit the chime or log 'listen on/off' spuriously; setListenButtonState(false) is a false edge and does not chime.

**Design reference.** CLAUDE.md Practice Mode (Start Listening is the partner cue) and the August 3 2026 Listen-button entry ('a silent state change is what made this cost an evening')

**Verification notes.** advancePracticePartner sets isListening=true (app.js:2606-2607) and it stays true while the partner's cards are up. handleEndConversation -> terminateConversation -> stt.stopListening(); for a paid source that is `return externalSource.stop()`, and each source's stop() returns silently when !running (it was never started in practice), so no status reaches handleSttStatus. Nothing else resets isListening, so toggleListening keeps taking the stop branch. For the built-in recognizer stopListening emits 'stopped' synchronously, so only paid-hearing configurations are affected, as described.
