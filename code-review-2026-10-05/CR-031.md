# CR-031: More button is a dead tap while the partner's choices are on offer

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:4249`
- **Also affects:** `app/js/app.js:4080-4086 (handleExpressMore sets paging then re-renders)`; `app/js/app.js:3394-3409 (setOfferedChoices / setOfferedRange - where choices actually arrive)`; `app/js/app.js:669-678 (global reset listener skips .ep-more)`
- **Source:** app-d-03

**What a user notices.** When the other person has just offered a choice (like 'coffee or tea?'), tapping More on the Express Panel does nothing at all, so phrases behind More cannot be reached until the turn is over.

**What is wrong.** The design says choices arriving from the partner PUT BACK a paged panel because they cover the Context band's More button - i.e. reset on arrival. drawExpressPanel instead resets paging on EVERY draw for as long as currentPartnerText is set and choices/range exist. So handleExpressMore sets expressPaging = {band, page: 1}, calls renderExpressPanel -> drawExpressPanel, which immediately calls resetExpressPaging() before composing. The Always and Flex bands' More buttons are not covered by the chips (choiceSlots are the last four Context cells) and remain visible labelled 'More', but every tap is undone in the same render.

**Evidence.**

```
app/js/app.js:4247-4250
  // The partner's choices cover the Context band's More button, so a paged panel goes
  // back to its first set the moment they arrive (Ken, September 14 2026).
  if (currentPartnerText && (offeredChoices.length || offeredRange)) resetExpressPaging();
  const composed = composedPanel();
app/js/app.js:4083-4085
  else expressPaging = { band: m.band, page: 1 };
  renderExpressPanel();
```

**How it happens.** Size the Always band so it overflows (a More button appears). In a conversation, have the partner ask 'Would you like coffee or tea?' so Coffee/Tea chips appear. Tap the Always band's More: the panel does not change and the button still says More.

**Suggested fix.** Reset only when choices ARRIVE. Remove the reset line from drawExpressPanel and instead, in setOfferedChoices (after `offeredChoices = next;`) add `if (next.length) resetExpressPaging();`, and in setOfferedRange (after `offeredRange = range || null;`) add `if (range) resetExpressPaging();`. If you also want a paged Context band or a whole-panel page never to sit under the chips, keep a narrower guard in drawExpressPanel: `if (currentPartnerText && (offeredChoices.length || offeredRange) && expressPaging && (expressPaging.band === expressBands.BAND.CONTEXT || storage.loadExpressMoreScope() === 'panel')) resetExpressPaging();`.

**How to verify the fix.** Manual: with an overflowing Always band, trigger a closed-set question in Practice Mode; confirm the panel resets to page 0 when the chips appear, and that tapping the Always band's More then pages normally and Close returns. Confirm the chips stay visible throughout.

**Do not break.** The chips must still never be covered by a whole-panel page or a paged Context band (they sit in the last four Context cells). Keep the global capture-phase reset listener unchanged.

**Design reference.** CLAUDE.md 'A band that overflows gets a MORE button' (choices arriving reset any paging)

**Verification notes.** Traced. handleExpressMore (app.js:4080) sets expressPaging and calls renderExpressPanel, which calls drawExpressPanel. drawExpressPanel (line 4249) calls resetExpressPaging() on every draw while currentPartnerText is set and choices or a range are on offer. The page request is wiped before composedPanel runs, so the Always or Flex band's More button, which the chips do not cover, does nothing for as long as the choices are showing. The recorded design is that choices arriving reset the paging, not that the panel is held on page 0 for the whole turn.
