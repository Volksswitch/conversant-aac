# CR-033: With the layout unlocked, taps inside Settings are hijacked to drag hidden layout borders

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed; reproducer: reproduced)
- **Location:** `app/js/app.js:4852`
- **Also affects:** `app/js/app.js:4910-4936 (borderUnder)`; `app/js/app.js:5061-5079 (onLayoutPointerDown, capture phase on document)`; `app/js/app.js:5083-5087 (onLayoutHover sets row-resize cursor over Settings)`; `app/js/app.js:699-700 (listeners armed once at startup)`; `app/js/app.js:8356-8362 (the unlock checkbox lives in Settings)`; `app/css/styles.css:1392 (handles hidden while Settings is open, but the proximity grab is not)`
- **Source:** app-d-01

**What a user notices.** After someone unlocks the screen layout in Settings, some taps on Settings controls do nothing, and instead the conversation screen hidden behind the panel quietly changes shape - which moves every keyguard hole without anyone seeing it happen.

**What is wrong.** The proximity border-drag path is a capture-phase pointerdown listener on document. Its gate, layoutDraggable(), checks only the unlock setting and realConversationInProgress(); it never checks whether a modal (the Settings dialog, a confirmDanger card) is open. borderUnder() measures #transcriptSection/#listenControls/#responsesSection/#dockArea, which still have real rects behind the dialog, so any pointerdown whose coordinates fall within GRIP_PX/2 (10px) of a border's y (or the side dock's x) and inside the column span is claimed: preventDefault + stopPropagation in the capture phase means the Settings control under the finger never receives the press, and onLayoutDrag then rewrites the stored layout and re-solves it. The CSS rule `body:has(#settingsDialog[open]) .layout-handle { display: none; }` hides the circles while Settings is open precisely because the panel covers the screen being adjusted - but the invisible proximity grab was not given the same rule. On a bottom dock the Settings panel is the full-width top region matching the conversation main area (UI Rule 11), so the command-bar and response-panel borders both run straight across it; the on-screen keyboard reparented into Settings sits exactly on the dock border. The unlock checkbox itself is in Settings, so the exposed state is reached the moment a user unlocks and keeps working in the panel. onLayoutHover likewise shows a row-resize cursor in horizontal stripes across Settings.

**How it happens.** Bottom dock, default layout. Open Settings, check 'unlock the layout' (layoutUnlockToggle). Stay in Settings and tap any control whose vertical position is within 10px of the y-coordinate of the top of the Command Bar (or the top of the Response Panel, or the top of the dock where the on-screen keyboard's top row sits). The control does not respond; the body gets class layout-dragging (all pointer events dead) and moving the finger resizes the command bar behind the dialog. Close Settings: the layout has changed.

**Suggested fix.** Make the drag gate refuse while any modal is open. In layoutDraggable() add a check: `if (document.querySelector('dialog[open]')) return false;` (this covers #settingsDialog and the confirmDanger danger dialog), i.e. `return storage.loadLayoutUnlocked() && !realConversationInProgress() && !document.querySelector('dialog[open]');`. Because borderUnder(), onHandlePointerDown(), positionLayoutHandles() and onLayoutHover all route through layoutDraggable(), this one change covers every path. Also clear any stale cursor: in onLayoutHover the existing `border ? ... : ''` already resets it once borderUnder returns null.

> **Verifier correction to the fix (takes precedence):** The suggested gate change is right: add `&& !document.querySelector('dialog[open]')` to layoutDraggable(). It also affects refreshLayoutMode(), which toggles body.layout-unlocked from the same gate, so that class drops while a dialog is open. Settings closing must then re-run refreshLayoutMode(), or the circles stay hidden after Settings closes. applyButtonSizing() normally runs on close and calls it, but verify that on every close path (X, Escape, starting a Practice scenario).

**How to verify the fix.** Manual: unlock the layout in Settings, then tap Settings controls lying on the command-bar and response-panel border lines and the top row of the on-screen keyboard while Settings is open - each control must respond and the layout must be unchanged after closing Settings. Then close Settings and confirm the borders are still draggable on the conversation screen. Also open the 'Put the layout back?' confirmation and tap its buttons near a border line.

**Do not break.** Do not hide or disable the drag on the conversation screen itself (Practice Mode must stay draggable - see realConversationInProgress). Keep the check in layoutDraggable so the visible circles and the invisible grab zone keep using the same gate.
