# CR-034: Dragging a border uses the un-normalized stored layout, so other borders jump

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:5098`
- **Also affects:** `app/js/app.js:4788-4789 (applyButtonSizing normalizes before solving)`; `app/js/conv-layout.js:115-131 (setRegion budget uses the stored values of the other regions)`; `app/js/conv-layout.js:142-158 (normalize)`
- **Source:** app-d-04

**What a user notices.** On a screen where the saved layout no longer quite fits (for example after switching to eight cards, increasing the gaps, or loading a profile from a bigger tablet), dragging the command bar's edge makes the response area and keyboard change size too, and the edge does not end up under the finger.

**What is wrong.** applyButtonSizing displays convLayout.solve(convLayout.normalize(stored, ctx), ctx), but onLayoutDrag computes the drag against convLayout.solve(stored, ctx) on the RAW stored layout and calls setRegion(stored, ...) on it. Normalized values are never written back, so whenever the stored layout is out of bounds for the current screen (cards 4->8 raises the response floor, a bigger gap, a smaller window, a larger screen edge margin, a profile from another device - all things conv-layout.js names as the reason normalize exists), the drag's notion of the far edges differs from what is on screen. Measured with conv-layout.js in node: bottom dock, ctx {height:500, rem:16, gap:0, cards:8}, stored {command:.10, response:.30, dock:.60}; shown = {transcript:.096, command:.10, response:.204, dock:.60}. Dragging the transcript/command border down to 0.15 yields {command:.064, response:.30, dock:.54} - the command bar SHRINKS while being dragged to grow and the response panel and keyboard both move, exactly the 'border moving while a different one is being dragged' fault conv-layout.js says must never happen. Using the normalized layout in the drag gives a stable result.

**Evidence.**

```
app/js/app.js:5098-5099
  const stored = storage.loadConvLayout(dock);
  const solved = convLayout.solve(stored, ctx);
app/js/app.js:5114  const next = convLayout.setRegion(stored, layoutDrag.resizes, value, ctx);
app/js/app.js:4788-4789
  const stored = convLayout.normalize(storage.loadConvLayout(dock), ctx);
  const r = convLayout.solve(stored, ctx);
```

**How it happens.** Bottom dock: drag the keyboard border up to near its cap and the response panel up, then in Settings switch to 8 cards per category (or raise Button spacing). The screen re-normalizes for display only. Unlock and drag the top of the command bar down a little: the command bar shrinks to its minimum and the response panel/keyboard heights change.

> **Verifier correction to the trigger:** The reviewer's figures are off. For that example normalize trims the DOCK (to .504), not the response panel; the response panel stays at .30. The observed fault is that any drag of the top command-bar border snaps the command bar to its minimum (.064), whichever way it is dragged, while the keyboard grows from .504 to .54.

**Suggested fix.** In onLayoutDrag replace line 5098 with `const stored = convLayout.normalize(storage.loadConvLayout(dock), ctx);` so the drag, the solver and the display share one budget (the layoutContext comment says they must not disagree). setRegion then starts from what is on screen and the saved result is already in bounds.

**How to verify the fix.** Add a test in tests/conv-layout.test.mjs (or the existing conv-layout test file) that builds an out-of-bounds stored layout, normalizes it, simulates valueForDrag + setRegion for 'transcriptCommand' on the normalized layout, and asserts response and dock are unchanged after solve(normalize(next)). Manually repeat the failure scenario and confirm only the dragged border moves.

**Do not break.** Keep next.last = layoutDrag.resizes so normalize still trims the most recently touched region last. Do not persist a normalized layout outside a drag (normalize is intentionally display-only for non-drag changes).

**Design reference.** app/js/conv-layout.js header ('A DRAG IS STOPPED ON THE WAY IN, NEVER CORRECTED AFTERWARDS'); layoutContext comment at app/js/app.js:4822-4823

**Verification notes.** Reproduced in node against conv-layout.js. Context: bottom dock, height 500, rem 16, gap 0, 8 cards; stored layout {command .10, response .30, dock .60}. The screen shows {transcript .096, command .10, response .30, dock .504}, because normalize trims the dock first. onLayoutDrag solves and calls setRegion on the RAW stored layout. Dragging the transcript/command border to any position (0.08, 0.12 or 0.20) collapses the command bar to its floor (.064) and grows the keyboard from .504 to .54. That is true even when the border is dragged UP to make the command bar bigger. Normalizing first, as applyButtonSizing does, keeps the dock at .504 and puts the border under the pointer.
