# CR-035: Visiting the Express Panel tab leaves 'hide keyboard on blur' switched on for About Me and the composer

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:5685`
- **Also affects:** `app/js/app.js:5697 (keyboard.setHideOnBlur(true) on the Express tab)`; `app/js/app.js:5701 (the only setHideOnBlur(false), after the aboutme early return)`; `app/js/app.js:8418-8437 (Close button: does not reset it)`; `app/js/app.js:760-770 (Escape cancel listener: does not reset it)`; `app/js/app.js:876-880 (review closeSettings: does not reset it)`; `app/js/app.js:6980-6992 (openSettings switches to General without handleSettingsTab, so it is not reset on reopen)`; `app/js/keyboard.js:762-781 (focusout: servingPanelOpen && hideOnBlur -> hide on next tick)`; `app/js/app.js:5685 (merged duplicate: Leaving the Express tab leaves 'hide keyboard on blur' switched on for About Me and for the next Settings visit)`; `app/js/keyboard.js:763 (merged duplicate: Express-tab 'hide on blur' leaks past Settings and breaks the composer's Speak (pending completion lost))`
- **Source:** app-f-02, app-e-04, keyboard-02

**What a user notices.** After someone has been on the Express Panel tab, the on-screen keyboard starts disappearing at the wrong moments: tapping Save on an About Me answer can drop the keyboard and make the Save tap miss, and in 'In my own words' the keyboard can vanish right after it appears, before the user can type.

**What is wrong.** keyboard.setHideOnBlur(true) is turned on only for the Express tab (handleSettingsTab, 5697) and turned off at 5701, but (a) the About Me tab returns at 5685 before reaching 5701, so going Express -> About Me keeps it on; and (b) no close path (Close button, Escape, review's closeSettings) and not openSettings resets it, so it stays on after Settings is closed and on the General tab of the next open. In keyboard.js the focusout handler, when a serving panel is open (Settings OR the composer overlay) and hideOnBlur is true, hides the keyboard on the next tick whenever focus has left a text field. That reintroduces two bugs the keep-open rule was written to prevent: the July 2026 'keyboard doesn't display' bug in the composer (a stray focusout after the composer opens) and Ken's bugs 2/3 in About Me (tapping Save blurs the field, the keyboard hides, the Settings panel reflows and the tap is stolen).

**How it happens.** On-screen keyboard mode. 1. Open Settings, tap the Express Panel tab. 2. Tap the About Me tab, open a topic, tap an answer field (keyboard rises), type, tap the card's Save: focus moves to the button, the keyboard hides on the next tick, the panel resizes, and the click can land on something else. Or: 1. Open Settings, Express tab, Close. 2. Open 'In my own words': any focusout that leaves focus on the page body (the documented reflow/mic re-render case) now hides the keyboard.

**Suggested fix.** Make hostExpressPanel the single choke point, since every close path and every tab switch already calls it: inside hostExpressPanel(inSettings) add `keyboard.setHideOnBlur(!!inSettings);`. Then the call at 5697 becomes redundant (keep or remove), and the aboutme early return, Close, Escape, review close and openSettings (which calls hostExpressPanel(false) at 6984) all reset it automatically.

> **Verifier correction to the fix (takes precedence):** Putting keyboard.setHideOnBlur(!!inSettings) inside hostExpressPanel is correct, because every tab switch and close path already passes through it. Also check that the calls at 2528 and 2552 (hostExpressPanel(false)) are paths where turning hide-on-blur off is wanted. They are close paths, so it is.

**How to verify the fix.** Add a source-level guard in tests/settings-wiring.test.mjs (or tests/keyboard.test.mjs) asserting hostExpressPanel calls keyboard.setHideOnBlur. Manual: on-screen keyboard mode, visit Express tab, switch to About Me, edit an answer and tap Save - keyboard stays up and Save works on the first tap; close Settings, open 'In my own words', type - keyboard stays up.

**Do not break.** The Express tab must still hide the keyboard when focus leaves a phrase box (Ken, August 23 2026); setting it true when hostExpressPanel(true) preserves that. Do not change the keep-open rule itself in keyboard.js.

**Design reference.** keyboard.js comments at 611-632 (keep-open rule and the Express-tab opt-out); CLAUDE.md 'Hiding the keyboard on pointerdown reflows the page' and Ken's bugs 2/3 in About Me.

**Verification notes.** keyboard.setHideOnBlur is called in only two places: setHideOnBlur(true) on the Express tab (app.js:5697) and setHideOnBlur(false) at 5701, which the 'aboutme' early return at 5685 skips. None of these calls hostExpressPanel(false) and reset the flag: the Close button (8431-8436), Escape (769), the review close (878), the paths at 2528 and 2552, or openSettings (6984). hideOnBlur is a module-level flag in keyboard.js (636), so it survives closing Settings. In the focusout handler (keyboard.js 762-779), when servingPanelOpen() is true (the Settings dialog is open, which covers About Me, or the composer overlay is visible) and hideOnBlur is true, the keyboard hides on the next tick whenever focus has left a scoped field. That branch also returns before the KEEP_OPEN_CONTROLS check, so tapping the composer's Speak or Reframe button would also hide the keyboard. Both reported sequences are reachable after a single visit to the Express tab.

<details><summary>Merged duplicate app-e-04: Leaving the Express tab leaves 'hide keyboard on blur' switched on for About Me and for the next Settings visit</summary>

handleSettingsTab sets keyboard.setHideOnBlur(true) for the Express tab and resets it with setHideOnBlur(false) only on the code path AFTER the `aboutme` early return. So switching Express -> About Me leaves hideOnBlur true. Separately, openSettings shows the General tab directly (it toggles classes and calls makeGroupsCollapsible) without going through handleSettingsTab, so closing Settings while on the Express tab and reopening it leaves hideOnBlur true on General too. With hideOnBlur true, keyboard.js's focusout handler hides the keyboard on the next tick whenever focus leaves a field inside Settings - exactly what the keep-open rule exists to prevent ('it must not hide on Save (Ken's bug 2)' and 'must not reflow the layout out from under the tap, which steals the first click (Ken's bug 3)').

Fix as proposed by that reviewer: In handleSettingsTab, set the flag before any early return: replace the two existing calls with a single `keyboard.setHideOnBlur(tabName === 'express');` placed immediately after `hostExpressPanel(tabName === 'express');` (line 5684), and delete the later `keyboard.setHideOnBlur(true)` / `keyboard.setHideOnBlur(false)` lines. In openSettings, next to `hostExpressPanel(false);` (around line 6984), add `keyboard.setHideOnBlur(false);` since that path bypasses handleSettingsTab. Optionally also call it in the closeSettingsBtn handler.

</details>

<details><summary>Merged duplicate keyboard-02: Express-tab 'hide on blur' leaks past Settings and breaks the composer's Speak (pending completion lost)</summary>

setHideOnBlur(true) is set when the Express tab is activated and only reset when ANOTHER Settings tab is activated. None of the Settings close paths (Close button, Escape 'cancel' listener, review closeSettings, startPractice) reset it. keyboard.js consults hideOnBlur for any 'serving panel', which includes the composer overlay (servingPanelOpen checks `composer && !composer.hidden`). So in the composer, any blur (including the tap on Speak, whose focusout fires on pointer-down before the click) schedules hide() on the next tick. hide() clears activeField and the ghost before Speak's click handler runs keyboard.acceptPendingGhost(), so the completion is dropped. It also re-opens the July 2026 'keyboard vanishes on a stray focusout' bug that the composer keep-open rule exists to prevent, and the KEEP_OPEN_CONTROLS check is bypassed because the servingPanelOpen branch returns first. Verified in a puppeteer harness with real mouse down/up: without the leak Speak spoke 'Yesterday' (accepted=true); with hideOnBlur left true the keyboard was hidden during the press and Speak got 'Yest' (accepted=false).

Fix as proposed by that reviewer: Make hideOnBlur apply only while Settings is actually open on the Express tab. Simplest robust change in keyboard.js focusout: replace `if (!hideOnBlur) return;` with `const dlg = document.getElementById('settingsDialog'); if (!hideOnBlur || !(dlg && dlg.open && e.target instanceof Element && dlg.contains(e.target))) return;`. Additionally (belt and braces) call `keyboard.setHideOnBlur(false)` in each Settings close path in app.js (the Close button handler near line 8431, the 'cancel' listener near 768, reviewUI closeSettings near 877, startPractice near 2551).

</details>
