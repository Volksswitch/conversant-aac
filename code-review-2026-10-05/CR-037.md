# CR-037: Changing the hearing service in a browser without built-in recognition either does nothing or throws

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:7368`
- **Also affects:** `app/js/app.js:490 (listeningUnavailable computed once at startup)`; `app/js/app.js:514 (stt.init skipped when no API and no paid service)`; `app/js/stt.js:585 (setSource returns false when init never ran)`; `app/js/stt.js:446-447 (new SpeechRecognition() with no API)`; `app/js/app.js:514 (merged duplicate: Choosing a paid hearing service in a browser without built-in recognition never takes effect)`; `app/js/app.js:7368 (merged duplicate: Changing the hearing service says 'in use now' when it cannot take effect, and can throw on browsers with no built-in recognizer)`
- **Source:** app-f-08, app-a-03, x-providers-08

**What a user notices.** On a browser that cannot listen by itself, choosing a paid listening service in Settings says 'Saved, and in use now' but the Listen button stays disabled until the app is restarted; switching back to 'This device' can break listening entirely.

**What is wrong.** (1) If the app started with the free recognizer on a browser lacking SpeechRecognition, stt.init never ran (514) and listeningUnavailable has apiPresent false, so Listen is disabled. Selecting a paid service calls stt.setSource, which returns false because initOpts is null; the status still says 'in use now', storage.setSttBackend records 'browser', and applyListenAvailability is never re-run. (2) If the app started on a paid service there, switching to 'builtin' calls init({source:'builtin'}), which runs `new SpeechRecognition()` with SpeechRecognition undefined and throws inside the change handler, after the old source was already torn down.

**Evidence.**

```
app/js/app.js:7368-7373 stt.setSource(radio.value); storage.setSttBackend(stt.currentSource());
app/js/stt.js:584-587 export function setSource(source) { if (!initOpts) return false; ...
app/js/stt.js:446-447 const SpeechRecognition = window.SpeechRecognition || window.webkitSpeechRecognition; recognition = new SpeechRecognition();
```

**How it happens.** Firefox (no SpeechRecognition): start with 'This device', Listen is disabled. Settings > hearing: Deepgram with a key. Status: 'Saved, and in use now.' Listen remains disabled until reload.

**Suggested fix.** In the sttProvider onchange: if stt.setSource returns false and the source changed, call stt.init with the same options used at startup (factor the init options at 519-535 into a function sttInitOptions(source) and reuse it). Recompute `listeningUnavailable = (radio.value !== 'builtin' || speechSupport.usable) ? null : speechSupport` (keep speechSupport in module scope) and call applyListenAvailability(). Before switching to 'builtin', check platform.speechRecognitionSupport().apiPresent; if false, refuse with a warn status and keep the current source.

> **Verifier correction to the fix (takes precedence):** Factor the startup init options into one function, sttInitOptions(source), shared by startup and the radio handler. When it builds the key check, include the catalog services (loadServiceKey) so the TODO.md startup gap closes at the same time. Guard the builtin switch on platform.speechRecognitionSupport().apiPresent, and recompute listeningUnavailable and call applyListenAvailability after any source change.

**How to verify the fix.** Unit test in tests/stt.test.mjs: setSource('builtin') with no window.SpeechRecognition does not throw and leaves the previous backend. Manual on Firefox as above.

**Do not break.** Keep the warn-don't-block rule (only an absent API disables Listen). Do not break Practice Mode's exemption in applyListenAvailability.

**Design reference.** CLAUDE.md 'THE CAPABILITY VERDICT WARNS, IT NEVER BLOCKS' and 'HEARING COULD FAIL FOREVER IN SILENCE... THE SERVICE COULD NOT BE CHANGED WITHOUT A RESTART'.

**Verification notes.** Traced both paths. (1) With no SpeechRecognition API and the free recognizer chosen at startup, stt.init is skipped (app.js:513), so initOpts stays null and stt.setSource returns false at stt.js:585. The radio handler still prints 'Saved, and in use now', setSttBackend records 'browser', and listeningUnavailable/applyListenAvailability are never recomputed, so Listen stays disabled. (2) If the app started on a paid service with that API absent, switching to builtin runs stopListening and teardown first, then init({source:'builtin'}), which reaches `new SpeechRecognition()` at stt.js:446-447 with the constructor undefined and throws. The trigger requires a browser that has no SpeechRecognition at all (for example Firefox). Every supported platform exposes the API (it is present even in an iPad Home Screen app), so reachability is narrow. Related and more serious: startup decides 'paid' only from a Deepgram or Azure key (app.js:485-488), so a saved OpenAI, Google or ElevenLabs hearing choice silently starts as the free recognizer after every reload. That gap is already tracked in TODO.md under 'Check that OpenAI, Google Cloud and ElevenLabs hearing are really used where hearing must be paid for'.

<details><summary>Merged duplicate app-a-03: Choosing a paid hearing service in a browser without built-in recognition never takes effect</summary>

initApp only calls stt.init when `speechSupport.apiPresent || usingPaidStt`. In a browser with no SpeechRecognition (e.g. Firefox) and no paid key at launch, stt.init never runs, so stt's initOpts stays null. The Settings radio handler later calls stt.setSource(value), which returns false immediately when initOpts is null, yet the handler unconditionally reports 'Saved, and in use now.' listeningUnavailable is computed once in initApp and never recomputed, so applyListenAvailability keeps the Listen button disabled. Conversely, if the app started on a paid source in such a browser and the user switches to 'builtin', setSource tears the paid source down and calls init with source 'builtin', which runs `new SpeechRecognition()` with an undefined constructor and throws a TypeError inside the radio handler, leaving no working source.

Fix as proposed by that reviewer: 1) Move the stt.init options object in initApp into a module-level function, e.g. `function sttInitOptions(source) { return { onResult: handleSpeechResult, ..., source, ... }; }`, and use it at line 519. 2) In the Settings radio handler, when stt.setSource returns false because stt was never initialised (add `export function isInitialized() { return !!initOpts; }` to stt.js), call `stt.init(sttInitOptions(value))` for a paid value. 3) After any change, recompute `listeningUnavailable` the same way initApp does (paid source with a key, or speechSupport.usable) and call applyListenAvailability(). 4) In stt.init's builtin branch, guard `if (!SpeechRecognition) { recognition = null; backend = 'browser'; return; }` so switching to builtin in such a browser cannot throw. 5) Only print 'in use now' when stt.currentSource() equals the chosen value; otherwise say it takes effect after a restart.


Verifier correction: Fix the launch logic FIRST, before (and as the basis of) the reviewer's steps: in initApp replace the two-service ternary with one that covers every paid source, e.g. `const paidSttKey = sttProvider === 'deepgram' ? storage.loadDeepgramKey() : sttProvider === 'azure' ? storage.loadAzureKey() : STT_PROVIDERS[sttProvider] ? storage.loadServiceKey(sttProvider) : null;` (Azure also needs a region; mirror whatever the radio handler's haveKey check uses). Put this in one helper, e.g. `paidSttReady(provider)`, and use it in initApp, in the radio handler's haveKey line, and in the recompute of listeningUnavailable the reviewer proposes in step 3 - otherwise step 3 reproduces the same omission. Add a test in tests/ (source-level guard on initApp, comments stripped) or extract the helper into a testable module and assert it returns true for 'openai' with a stored key. The reviewer's steps 1-5 are otherwise correct; for step 2 note setSource also returns false when wanted === backend, so 'not initialised' must be checked separately (the proposed isInitialized export does that).

<details><summary>Merged duplicate x-providers-08: Changing the hearing service says 'in use now' when it cannot take effect, and can throw on browsers with no built-in recognizer</summary>

stt.setSource() returns false without doing anything when init() never ran (initOpts null). init() is skipped at startup when the recognition API is absent and no paid key was usable (app.js:514), so a later radio change cannot build the paid source; the handler ignores the return value and prints 'Saved, and in use now.' Listen also stays disabled because listeningUnavailable/applyListenAvailability are never recomputed. In the opposite direction, if the app started on a paid source in such a browser and the user picks 'This browser's own', setSource calls init({source:'builtin'}), which runs `new SpeechRecognition()` with an undefined constructor and throws a TypeError out of the radio onchange handler, after the old source has already been torn down.

Fix as proposed by that reviewer: In stt.init, before constructing the recognizer, add `if (!isSupported()) { backend = 'browser'; return; }`. Make setSource work without a prior init: store initOpts in app.js's startup call even when skipping capture (always call stt.init with source 'builtin' only if supported; otherwise keep the opts via a new exported `stt.configure(opts)`), or simpler: in the radio handler, if `stt.setSource(radio.value)` returns false and `stt.currentSource() !== normalized choice`, show 'Saved — restart the app to use it.' and, when a paid key is present, set `listeningUnavailable = null; applyListenAvailability();` after a successful switch.

</details>
