# CR-038: "User is leading" context is lost after the first pause of the partner's go-ahead, and on New N / Reframe / chip / context refresh

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/engine.js:322`
- **Also affects:** `app/js/engine.js:243-252 (buildRequestContext)`; `app/js/engine.js:328-337`; `app/js/app.js:3354 (handleRegenerate)`; `app/js/app.js:3451 (handleChoiceChip)`; `app/js/app.js:3546 (handleReframe)`; `app/js/app.js:4527 (refreshForContextChange)`; `app/js/llm.js:592 (User is leading prompt rule)`
- **Source:** llm-engine-02

**What a user notices.** When the user opens a conversation ("Can I ask you something?") and the other person says "Sure... go ahead" with a small pause, or when the user asks for different options, the suggestions switch from helping the user say what they wanted to treating the other person's "go ahead" as something to answer.

**What is wrong.** user_holds_floor_to_lead is derived only from the top of the sequence stack (a USER-opened, non-REPAIR entry). The first ingestClassification after the user's opener POPS that entry (engine.js:322-327), so from then on buildRequestContext returns user_holds_floor_to_lead=false. Two consequences: (a) continuous capture re-ingests every silence checkpoint of the SAME partner turn (0.5s default), and on the second checkpoint the stack is empty, so the else-branch pushes a fresh PARTNER FPP and the request context says the partner is owed an answer - contradicting the comment that later pauses of the same turn must update in place rather than create a new obligation; (b) every refresh path (New N, choice chip, Reframe, context-change refresh) calls engine.buildRequestContext() after that pop, so a regenerate of a lead palette is generated as replies to the partner.

**Evidence.**

```
engine.js:243-244:
    const top = state.sequenceStack[state.sequenceStack.length - 1];
    const userHoldsFloorToLead = !!(top && top.openedBy === 'USER' && top.action !== 'REPAIR');
engine.js:322-337:
    } else if (top && top.openedBy === 'USER' && top.action !== 'REPAIR') {
        ...
        state.sequenceStack.pop();
    } else {
        // A new partner turn ...
        state.sequenceStack.push({ action: ..., openedBy: 'PARTNER', ... });
Experiment (scratchpad lead.mjs): initiate -> selectResponse(OPENER) -> ingest('Sure') -> buildRequestContext().user_holds_floor_to_lead === false and sequence_stack === [] at the second checkpoint; after ingest('Sure, go ahead') the stack holds a PARTNER STATEMENT FPP.
```

**How it happens.** User taps Start conversation, picks "Can I ask you something?". Partner: "Sure" [0.6s pause] "go ahead". Checkpoint 1 gets lead responses. Checkpoint 2 sends user_holds_floor_to_lead:false with a PARTNER FPP on the stack, so the replacement palette answers the partner instead of letting the user ask their question. Same result if, after checkpoint 1, the user presses New N, taps a Feeling, or taps a choice chip.

**Suggested fix.** Add `userLeading: false` to engine state (and reset it in reset()). In ingestClassification's USER-opened branch set `state.userLeading = true` when popping the user's FPP. Add a branch before the final else: `else if (state.userLeading) { /* same partner reply refining; push nothing */ }`. In buildRequestContext use `const userHoldsFloorToLead = state.userLeading || !!(top && top.openedBy === 'USER' && top.action !== 'REPAIR');`. Clear `state.userLeading = false` in selectResponse (both branches), deferAnswer is fine to leave, pardon(), windDown(), initiate(), resumeConversation(), completeRepairOfSelf(), and when ingestClassification takes the CLOSING or repair-initiator branch.

**How to verify the fix.** Add to tests/engine.test.mjs: initiate; selectResponse({slot:'OPENER',text:'Can I ask you something?'}); ingestClassification(STATEMENT,'Sure'); assert buildRequestContext().user_holds_floor_to_lead === true and stack length 0; ingestClassification(STATEMENT,'Sure, go ahead'); assert still true and no PARTNER entry pushed; selectResponse({slot:'PREFERRED',text:'x'}); ingest a new partner QUESTION; assert user_holds_floor_to_lead false and a PARTNER FPP is on the stack.

**Do not break.** Do not reintroduce any turn_status gating (Ken, July 10 2026). The flag must clear on the user's next spoken turn or a genuinely new partner turn would be mis-tagged as a go-ahead. Keep refreshPalette's no-reingest behavior.

**Design reference.** CLAUDE.md 'No turn-completion gate' (later pause updates the same partner turn in place); llm.js 'User is leading' rule; Conversation-Engine-Design.docx sequence stack.

**Verification notes.** I ran engine.js in node. After initiate() and selectResponse(OPENER), buildRequestContext() reports user_holds_floor_to_lead=true. After the first ingestClassification('Sure'), it is false and the stack is []. A second ingest of the same partner turn ('Sure go ahead') then pushes a PARTNER STATEMENT FPP. This contradicts the in-place-update intent. generateOptions builds the context before ingesting (app.js:1817), so checkpoint 2 sends lead=false. Every refresh path (handleRegenerate 3354, handleChoiceChip 3451, handleReframe 3546, refreshForContextChange 4527) calls buildRequestContext() after the pop, so a New N on a lead palette always loses the flag. The mechanism is deterministic. How badly the model's output suffers is less certain, because the history still shows the user's opener.
