# CR-039: Engine phase never returns to BODY: OPENING lasts the whole conversation and PRE_CLOSING sticks after the partner reopens

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/engine.js:341`
- **Also affects:** `app/js/engine.js:669-675 (initiate sets OPENING)`; `app/js/engine.js:648-665 (windDown/showClosings set PRE_CLOSING)`; `app/js/engine.js:245-251 (phase sent to the model)`; `app/js/app.js:1757-1774 (closing fast path keyed on phase)`; `app/js/conversation-logic.js:58-83 (looksLikeClosing)`
- **Source:** llm-engine-04

**What a user notices.** After the user starts a conversation with an opener, or after a wrap-up that the other person talks past, the app keeps treating the conversation as just starting or as ending. Later, an ordinary short remark like "We should go see it sometime" or "You too, honestly" can make the suggestions suddenly switch to goodbyes while the conversation is still going.

**What is wrong.** state.phase is set to OPENING by initiate() and to PRE_CLOSING by windDown()/showClosings()/a CLOSING classification, but nothing except reset() and resumeConversation() ever sets it back to BODY. ingestClassification's non-CLOSING branch sets mode = RESPONDING and leaves phase alone; selectResponse never touches phase. Effects: (1) buildRequestContext sends phase:'OPENING' to the model for every turn of a user-opened conversation, and phase:'PRE_CLOSING' for the rest of a conversation after any wind-down or after the partner's first-checkpoint "Well…" was classified CLOSING (the prompt itself names "Well…" as a closing opener, and at a 0.5s silence period that is a likely first checkpoint); this biases classification toward CLOSING. (2) generateOptions' closing fast path is gated on `phase === 'PRE_CLOSING'`, so for the rest of the conversation any partner reply of 6 words or fewer matching a farewell pattern skips the AI and replaces the cards with goodbyes. The CLAUDE.md closing-decline entry already identified 'stuck in pre-closing ... next partner turn still read through the closing fast-path' as a defect, but fixed it only for the decline card.

```
Experiment (scratchpad phase.mjs): after initiate+opener+two partner turns, buildRequestContext().phase === 'OPENING'; after windDown -> partner QUESTION -> three more exchanges, mode LISTENING but phase 'PRE_CLOSING'; looksLikeClosing returns true for 'We should go see it sometime', 'You too, honestly', 'Nice talking about this stuff', 'I have to go check'.
```

**How it happens.** User taps Wrap up, says "I should get going." Partner: "Oh wait, did you hear about Sam?" The conversation carries on for several exchanges. Partner later says "We should go see it sometime." generateOptions takes the fast path, ingests a synthetic CLOSING and shows the goodbye palette instead of replies.

**Suggested fix.** In engine.ingestClassification's non-CLOSING else-branch add: `if (state.phase !== 'BODY') state.phase = 'BODY';` (a partner turn that is not a closing means the conversation is in its body - this covers both OPENING after the user's opener has been answered and PRE_CLOSING after the partner reopens). Keep the CLOSING branch as is. Leave selectResponse unchanged so a user's own wind-down still holds PRE_CLOSING until the partner replies.

**How to verify the fix.** tests/engine.test.mjs: (a) initiate; selectResponse(OPENER); ingest STATEMENT -> assert getSnapshot().phase === 'BODY'. (b) windDown; selectResponse(WIND_DOWN); ingest QUESTION -> assert phase 'BODY' and mode 'RESPONDING'. (c) ingest CLOSING -> phase 'PRE_CLOSING' still. Manually: wrap up, have the partner (Practice Mode) continue talking, then say a short 'You too' mid-conversation; the AI path (not goodbyes) must run.

**Do not break.** Do not widen or narrow looksLikeClosing - its precision trade is a recorded decision. The CLOSING_DECLINE path (reopenFromClosing) must keep working. Phase 'OPENING' should still be sent to the model for the partner's first reply to an opener (the change happens on ingest, after the context for that request was built).

**Design reference.** CLAUDE.md 'Closing detection: CLOSING defined in the prompt, and a decline-the-closing card' and 'Wind-down and closing are two distinct steps'; conversation-logic.js fast-path decision note.

**Verification notes.** Node experiment: after initiate, an opener and two partner turns, phase stays 'OPENING'. After windDown, a WIND_DOWN selection and a partner QUESTION, mode is RESPONDING but phase is still 'PRE_CLOSING'. The only code that resets phase is reset() (called at Start and in terminateConversation) and resumeConversation()/reopenFromClosing() (overlay cancel, decline card); ingestClassification's non-CLOSING branch and selectResponse never touch phase. generateOptions' fast path (app.js:1757-1760) keys on phase === 'PRE_CLOSING'. looksLikeClosing('We should go see it sometime') is true: it has 6 words and matches the 'should go' pattern. So once the partner reopens after a wind-down, any short farewell-like line later in the same conversation skips the AI and brings up the goodbyes. The suggested fix (set phase BODY on a non-CLOSING ingest) is correct and leaves the decline path intact.
