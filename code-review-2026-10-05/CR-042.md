# CR-042: Tapping a Context or Flex button in the Settings-hosted Express Panel leaves its editor section closed when another band's section was open

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/express-editor.js:728`
- **Also affects:** `app/js/express-editor.js:80-96 (focusItem sets openAfterRender)`; `app/js/express-editor.js:726 (makeCollapsible restores remembered open state)`; `app/js/sections.js:124-128 (details.open restored, toggle listener calls closeSiblings)`; `app/js/app.js:3968-3972 (editedInSettings -> expressEditor.focusItem)`
- **Source:** live-visual-01

**What a user notices.** On the Express Panel tab of Settings, tapping a button such as "Mom" or a Flex phrase marks it as being edited on the panel, but its editing row never appears: the section for a different band stays open and the right one stays shut, so it looks as if the tap did nothing.

**What is wrong.** focusItem() records openAfterRender = 'context'|'flex'|'always' and calls render(). render() rebuilds the three band sections and calls makeCollapsible(container,'expressBands'), which (sections.js:124) restores each <details>.open from the remembered openSections set BEFORE the toggle listener is attached; that restore queues a 'toggle' event for the previously open band (e.g. Always). render() then synchronously sets the target band's details.open = true (line 731), which queues a second toggle. The toggle events run afterwards in order: the restored band's handler sees itself open and calls closeSiblings(), which closes the target band that was just opened; the target's own toggle then fires with open=false and does nothing. Net result: the previously open band stays open and the band holding the picked row is closed. It only works when no band section was open beforehand.

**Evidence.**

```
app/js/express-editor.js:726-732:
    makeCollapsible(container, 'expressBands');
    if (openAfterRender) {
        const det = container.querySelector(`.setting-group[data-band="${openAfterRender}"] details`);
        openAfterRender = null;
        if (det && !det.open) det.open = true;   // fires toggle, which closes the others
    }
app/js/sections.js:124-128:
        details.open = openSections.has(key);
        details.addEventListener('toggle', () => {
            if (details.open) openSections.add(key); else openSections.delete(key);
            if (details.open) closeSiblings(details);
        });
Measured in headless Chrome (seeded test data): after tapping "Yes" then "Mom", open sections = ["Always — the words that never move"], picked row = the partner row inside the closed Context section. Same after tapping "Pumped", "Pulp Comics", and the Flex phrase "Do not finish my sentence" while Context was open.
```

**How it happens.** 1. Start, open Settings > Express Panel and Keyboard. 2. Tap "Yes" on the hosted Express Panel (the Always section opens with Yes selected). 3. Tap "Mom" (a Context partner button). Expected: the Context section opens with Mom's row selected. Actual: Mom's cell gets the 'picked' ring on the panel, the Always section stays open, the Context section stays collapsed, and no editor for Mom is visible. Reverse also fails (Context open, tap an Always phrase).

**Suggested fix.** In express-editor.js render(), when openAfterRender is set, close every OTHER band section synchronously before opening the target, so no queued toggle from the restore can re-close it:
    if (openAfterRender) {
        const det = container.querySelector(`.setting-group[data-band="${openAfterRender}"] details`);
        openAfterRender = null;
        if (det) {
            for (const other of container.querySelectorAll('.setting-group[data-band] > details')) {
                if (other !== det && other.open) other.open = false;
            }
            if (!det.open) det.open = true;
        }
    }
The restored band's queued toggle then fires with open=false (it just removes its key), and the target's toggle fires with open=true and runs closeSiblings normally. After opening, scroll the picked row into view after the toggle has settled (e.g. requestAnimationFrame) because focusItem's scrollIntoView currently runs while the row is still inside a closed section.

**How to verify the fix.** Manual: steps in failure_scenario now show the Context section open with Mom's row highlighted and scrolled into view; repeat for an Always phrase while Context is open, and a Flex phrase while Always is open. Automated: add a browser case to tests/ui-standards.test.mjs (it already launches puppeteer) that opens the Express tab, clicks an Always cell, then a Context cell, and asserts the details inside .setting-group[data-band="context"] is open and contains .ee-row-picked.

**Do not break.** Do not change sections.js closeSiblings semantics (one section open per tab is a recorded decision, Rule 18). The keyboard/panel dock swap (syncExpressTabDock) listens to these toggles; confirm the panel, not the keyboard, stays in the dock after the fix.

**Design reference.** CLAUDE.md 'An editor for a grid edits ONE cell at a time, with the grid itself as the list' and 'AS BUILT (August 8 2026) — tap-to-define'; Rule 18 (one section open at a time).

**Verification notes.** render() calls makeCollapsible(container,'expressBands'), which sets details.open from the remembered openSections set before attaching the toggle listener (sections.js:124-128). It then sets the target band's details.open=true (express-editor.js:731). Toggle events are dispatched later, so both handlers run in the order queued. The restored band runs first, sees itself open and calls closeSiblings (scoped to the whole .tab-panel), which closes the target band. I reproduced the exact sequence in headless Chrome with a minimal page using the same restore-then-attach-then-open order: result d0:true, d1:false (the previously open section stays open, the target ends up closed). focusItem's scrollIntoView also runs while the row is inside a closed section. The suggested fix works: closing the other bands synchronously first leaves the restored band's queued toggle with open=false, so it only removes its key.
