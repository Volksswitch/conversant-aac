# CR-043: Spoken help in Settings breaks after any scroll: the "?" goes dead for one tap, and scrolling while armed speaks the wrong setting

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/help-mode.js:221`
- **Also affects:** `app/js/help-mode.js:268`; `app/js/help-mode.js:270`; `app/js/help-mode.js:246`
- **Source:** ui-shell-01

**What a user notices.** After the user scrolls the Settings panel, the first tap on the "?" help button does nothing. And if help is switched on and the user scrolls to find a setting, the app immediately explains whatever setting their finger landed on to start the scroll and switches help off.

**What is wrong.** handle() makes ONE decision per gesture and records it in gestureDecided/gesturePrevented, but those flags are only reset in the 'click' listener. A touch scroll (pan) on a tablet raises pointerdown and then pointercancel with NO click, so the flags stay set and the NEXT tap's pointerdown/mousedown/click are treated as the tail of the old gesture: they are never decided, only re-prevented (or not). Separately, the SPEAK decision is taken on pointerdown, which also starts every touch scroll, so when help is armed a scroll that begins on a control speaks that control's phrase and disarms help (say() sets armed=false). Reproduced in a node harness with a fake dialog: a pointerdown with no click, followed by a full tap on the "?", leaves help unarmed; a pointerdown on the API key field while armed speaks the API-key phrase and disarms. If the stale gesture had been a SWALLOW (armed, pointerdown on padding), gesturePrevented stays true and the whole next tap is silently eaten.

**How it happens.** On a tablet: open Settings, General tab. Swipe up to scroll the panel (finger starts on the API Key box). Tap the "?" once: it does not arm. Tap it again: it arms. Now swipe to scroll again, starting the swipe on the Data Folder row: the app immediately speaks the Data Folder explanation and help disarms, although the user only wanted to scroll.

**Suggested fix.** In help-mode.js init(): (1) treat every pointerdown as the START of a new gesture - wrap the pointerdown listener as `(e) => { gestureDecided = false; gesturePrevented = false; pendingSpeak = null; handle(e); }`. (2) Add `dialog.addEventListener('pointercancel', () => { gestureDecided = false; gesturePrevented = false; pendingSpeak = null; }, true);`. (3) Defer the actual speech to the click: in case ACTION.SPEAK, keep `stop()` (so a select does not open and a range does not jump) but if e.type !== 'click' store `pendingSpeak = { key, groupEl: tap.groupEl }` instead of calling say(); in the click listener, before resetting the flags, `if (pendingSpeak) { const p = pendingSpeak; pendingSpeak = null; say(p.key, p.groupEl); }`. A keyboard-initiated click (no pointerdown) still decides SPEAK on the click itself and should call say() directly. Leave decideTap/resolveTap unchanged.

> **Verifier correction to the fix (takes precedence):** The suggested fix is sound. Two details: (a) when pointerdown has been preventDefault'ed, the browser suppresses the compatibility mousedown but still fires click, so deferring the speech to the click works; (b) keep the TOGGLE decision on pointerdown as now (only SPEAK needs deferring), and clear pendingSpeak in reset() too.

**How to verify the fix.** Add a test to tests/settings-help.test.mjs that drives init() with a fake dialog (addEventListener collecting handlers) as in the reproduction: fire pointerdown on a control, then a pointerdown/mousedown/click on the help button, and assert isArmed() is true; then fire pointerdown + pointercancel on a control while armed and assert nothing was spoken and isArmed() is still true; then a full tap on the control speaks once. Manually on a touch tablet: scroll the Settings panel, then tap "?" once - it must arm.

**Do not break.** Must keep the load-bearing safety property (an armed tap never changes a control): preventDefault must still happen on pointerdown for SPEAK/SWALLOW so a select does not open and a range does not jump. Must keep one decision per pointerdown/mousedown/click triple (the bug recorded in UI Layout Rule 17 where the "?" armed and disarmed itself).

**Design reference.** CLAUDE.md UI Layout Rule 17 (spoken help: safety property, one-shot, 'one tap fires pointerdown AND mousedown AND click')

**Verification notes.** help-mode.js handle() sets gestureDecided=true on the first event and the flags are reset only in the click listener (lines 268-275); there is no pointercancel listener anywhere in help-mode.js. A touch pan raises pointerdown then pointercancel and no click, so the flags carry into the next tap: that tap's pointerdown/mousedown/click are all treated as the tail of the old gesture, so a tap on the "?" never reaches the TOGGLE branch (the button has no click handler of its own; arming happens only in handle()). If the stale decision was a SWALLOW, gesturePrevented stays true and the whole next tap is eaten. Separately, SPEAK is decided and say() called on pointerdown, and preventDefault on pointerdown does not stop a touch pan, so a scroll that starts on a control while armed speaks it and disarms (say() sets armed=false).
