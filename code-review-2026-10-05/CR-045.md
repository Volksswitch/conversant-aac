# CR-045: On-screen keyboard keeps typing into a field that has been removed or that the user has left

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/keyboard.js:762`
- **Also affects:** `app/js/keyboard.js:140`; `app/js/keyboard.js:154`; `app/js/keyboard.js:297`; `app/js/control-phrases-editor.js:81`; `app/js/control-phrases-editor.js:102`; `app/index.html:555`; `app/index.html:1160`
- **Source:** keyboard-01

**What a user notices.** In Settings, after moving or deleting a phrase, or after tapping a box the app keyboard does not serve (an OpenAI key, the tester name), the keyboard stays up but the letters go somewhere invisible or into the previous box. The person types and nothing appears where they are looking.

**What is wrong.** keyboard.js holds a module-level `activeField` and never re-validates it. While the Settings dialog (or the composer) is open, the focusout handler returns early (servingPanelOpen) and keeps the keyboard up bound to the old field. Two consequences: (a) when an editor re-renders (Commands editor reorder/delete, About Me goal/person lists, etc.) the focused input is removed from the DOM, but activeField still points at the detached node, so insert()/backspace() write into an element nobody can see; for the control-phrases editor the input listener closes over the OLD data copy (getPhrases returns copies), so the typed text is silently discarded. (b) When focus moves to a text field that is not in IN_SCOPE (e.g. #openaiKeyInput, #testerNameInput, #placeholderEditor inputs), no focusin show() happens, so the keyboard keeps typing into the previously focused scoped field. Verified in a puppeteer harness: after a re-render the new field stayed empty while 'b','c' were typed; with focus in the OpenAI key field, tapping 'x' appended to the Deepgram key field ('Dx').

**Evidence.**

```
keyboard.js:762-763 `if (servingPanelOpen()) { if (!hideOnBlur) return;` ; keyboard.js:140-148 `function insert(text) { const f = activeField; if (!f) return; ... f.value = ...; f.dispatchEvent(new Event('input', ...))` (no isConnected / focus check); control-phrases-editor.js:81 `up.addEventListener('click', () => { ...; commit(true); });` -> render() -> `container.innerHTML = '';` (line 102); control-phrases-editor.js:76 `row.appendChild(textInput(text, 'Card text', (v) => { arr[i] = v; commit(false); }));` where `arr` belongs to the replaced `data` copy.
```

**How it happens.** On-screen keyboard mode. Settings > Commands. Tap an opener text box, type a letter (keyboard shows). Tap the down-arrow next to it. The list redraws; the keyboard stays up. Type 'hello' - nothing appears in any box and nothing is saved. Second scenario: Settings > Speech, tap the Deepgram key box (app keyboard appears), then tap the OpenAI key box and type on the app keyboard - the characters are appended to the (re-redacted) Deepgram field instead.

**Suggested fix.** 1) At the top of handleKey() (and handleTool()), re-validate: `if (activeField && !activeField.isConnected) { const now = document.activeElement; if (isScoped(now)) show(now); else { hide(); return; } }`. Also guard renderGhost() with `if (!f.isConnected) { clearGhost(); return; }`. 2) In the focusout handler, before the `if (previewing) return;` line, add: if `next` is an editable text control that is not in scope (`next instanceof HTMLTextAreaElement || (next instanceof HTMLInputElement && /^(text|search|email|url|tel|password|number)$/.test(next.type))` and `!isScoped(next)`), call `hide()` and return - the keyboard must never type into a field the user has left. (Bringing the missing fields into IN_SCOPE is a separate finding.)

**How to verify the fix.** Manual: repeat both scenarios; after the reorder the keyboard should either hide or attach to the newly focused box, and in the OpenAI case the app keyboard should hide (or type into OpenAI once it is in scope). A browser harness like the one used here: dialog#settingsDialog open, #controlEditor with an input and a button that replaces container.innerHTML; focus input, click button, dispatch pointerdown on .kbd-key[data-char=b]; assert the keyboard is hidden or the new input receives 'b'.

**Do not break.** Do not break the deliberate keep-open behaviour: tapping Save or another non-text button inside a Settings panel must still leave the keyboard up (CLAUDE.md, keyboard Save bugs 2/3). Do not break the composer's Speak/Reframe/Cancel keep-open, nor Conversation Review, whose word input is focused programmatically.

**Design reference.** CLAUDE.md 'In My Own Words' keyboard-selection spec; keyboard.js focusout comments; UI Layout Rule 18 (Controls editor re-renders on add/reorder/delete)

**Verification notes.** Read keyboard.js insert()/backspace()/focusout and control-phrases-editor.js. insert() writes to the module-level activeField with no isConnected/focus check. In Settings the focusout handler returns at `if (servingPanelOpen()) { if (!hideOnBlur) return; ...` (hideOnBlur is false on every tab but Express), so tapping the ↑/↓/✕ button leaves activeField pointing at the input that render() then destroys (`container.innerHTML = ''`). Only the '+ Add' path re-focuses (pendingFocus). Typed text lands in the detached node; its input listener writes into the OLD `arr` and then commit(false) calls model.setPhrases(data) with the NEW module-level `data`, so the edit is discarded. Case (b) also holds: #openaiKeyInput etc. are not in IN_SCOPE, so focusing one triggers no show(); the focusout from the Deepgram field returns early for the same servingPanelOpen reason, and app-keyboard key presses preventDefault so focus stays on the OpenAI box while insert() appends to the Deepgram field.
