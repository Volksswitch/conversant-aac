# CR-046: Finishing a suggestion request cuts off the user's own "Hold on" or "Repeat what I said" mid-sentence

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed; reproducer: reproduced)
- **Location:** `app/js/placeholders.js:252`
- **Also affects:** `app/js/app.js:1904-1908`; `app/js/app.js:1948`; `app/js/app.js:3225`; `app/js/app.js:3236`; `app/js/app.js:265-270`; `app/js/tts.js:401-412`; `app/js/placeholders.js:245 (merged duplicate: placeholders.stop() cancels ALL speech, so a returning AI request or the partner talking cuts off the user's own 'Repeat what I said' / 'Hold on' / 'Ask them to repeat' mid-sentence)`
- **Source:** phrases-practice-01, x-async-02

**What a user notices.** If the user taps "Hold on" or "Repeat what I said" while the app is still fetching suggestions, the sentence is often chopped off partway through the moment the suggestions arrive. The other person hears half a sentence in the user's voice.

**What is wrong.** placeholders.stop() unconditionally calls tts.cancel(), which cancels ANY speech in progress, not only a placeholder the ladder is speaking. "Hold on" and "Repeat what I said" call abortPlaceholders(), which bumps placeholderEpoch but deliberately does NOT bump generationToken, so an in-flight generateOptions() keeps running. When it completes, the epoch check sends it to the else-branch, which calls placeholders.stop() -> tts.cancel(), killing the user's statement that is still being spoken. The catch branch (generation failed) does the same. Hold on is pressed precisely during the 4-8 s round trip (that is its purpose), and its phrase plus a Say-again re-speak take 1.5-5 s, so the collision is common. The July 2026 fix meant to stop a placeholder restarting after a speaking button; it now does the opposite harm by cancelling the button's speech.

**Evidence.**

```
placeholders.js:245-253 `export function stop() { active = false; armed = false; if (timer) {...} tts.cancel(); }`
app.js:1904-1908 `if (pEpoch === placeholderEpoch && convLogic.shouldPlayPlaceholder(snap)) { placeholders.start(); } else { placeholders.stop(); }`
app.js:1933-1948 catch: `if (token !== generationToken) return; ... placeholders.stop();`
app.js:181-184 `function abortPlaceholders() { placeholders.stop(); placeholderEpoch++; }` (no generationToken++)
app.js:3236 handleHoldOn: `abortPlaceholders(); ... await speakUserStatement(text, { announce: true });`
tts.js:401-403 `export function cancel() { speakToken++; synth.cancel(); ...`
```

**How it happens.** 1. Real conversation, partner says something and pauses; generation starts (takes ~4-8 s).
2. At ~2 s the user taps Hold on; the app starts saying "I'm taking a little longer with this one."
3. The suggestions return while that phrase is still playing; generateOptions sees pEpoch !== placeholderEpoch and calls placeholders.stop().
4. stop() calls tts.cancel(); the user's phrase stops mid-word. Same with Repeat what I said (a longer sentence), and with any generation failure (catch branch).

**Suggested fix.** Make stop() cancel only the ladder's OWN speech. In placeholders.js add `let speakingOwn = false;` and in speakNext wrap the speak: `speakingOwn = true; try { await tts.speak(phrase); } finally { speakingOwn = false; }`. In stop() replace the bare `tts.cancel();` with `if (speakingOwn) tts.cancel();`. Callers that genuinely need all speech stopped (terminateConversation, togglePracticeCue) already call tts.cancel() themselves. Optionally also, in app.js generateOptions, skip the else-branch stop() when `pEpoch !== placeholderEpoch` because abortPlaceholders already stopped the ladder.

> **Verifier correction to the fix (takes precedence):** The speakingOwn flag works, but it must also be cleared inside stop() right after the cancel (`if (speakingOwn) { speakingOwn = false; tts.cancel(); }`). The ladder's own `finally` only runs once the superseded tts.speak promise settles, which happens asynchronously, so a later stop() could still see speakingOwn true while the user's statement is already playing. A token comparison against the ladder's own utterance is the more robust option. Also skip the else-branch stop() in generateOptions when pEpoch !== placeholderEpoch, since abortPlaceholders already stopped the ladder. The catch-branch stop() is covered by finding 04.

**How to verify the fix.** Add to tests/placeholders.test.mjs: stub tts so speak() returns a pending promise and cancel() records a call; call placeholders.stop() with no ladder phrase playing and assert cancel was NOT called; then arm(), advance timers so a placeholder is speaking, call stop() and assert cancel WAS called. Manual: start a conversation with a real key, after the partner pauses tap Hold on immediately, and confirm the full phrase is heard when the cards arrive mid-phrase; repeat with Repeat what I said.

**Do not break.** A placeholder that IS playing must still be cut off by stop() when the partner resumes (handlePartnerResumed), when a card is chosen, and on a repair-initiator. Do not touch the separate TODO.md item about New N / Reframe / choice chips cutting a placeholder; this fix is about the user's own statements and must not let a placeholder start over them.

**Design reference.** CLAUDE.md 'Transcript mirrors the conversation pane' Follow-up 3 (pressing any button that can speak must abort placeholders, never be interrupted by them); 'PLACEHOLDERS ARE PART OF THIS SAME FLOW'.

**Verification notes.** placeholders.stop() (placeholders.js:245-253) ends with an unconditional tts.cancel(), and tts.cancel() (tts.js:401-411) bumps speakToken and cancels synth and every paid backend, which cuts whatever is playing. handleHoldOn and handleSayAgain call abortPlaceholders() (app.js:181-184), which bumps placeholderEpoch but not generationToken, and then await speakUserStatement(). An in-flight generateOptions captured pEpoch before the press. On success it sees pEpoch !== placeholderEpoch and calls placeholders.stop() (app.js:1904-1908). On failure the catch also calls stop() (app.js:1948). Either way the user's own statement is cut off. Nothing guards against this: the user-speaking gate only defers speakNext and is never checked in stop(). TODO.md:40 tracks silent buttons cutting a placeholder, which is a different defect. Severity lowered to medium: the trigger is a timing window during the round trip (about 3 s on the current model), and the user can tap the button again.

**Reproduction (reproduced).** Method: I traced the code in app.js, then ran the real placeholders.js and tts.js modules in node. The script is scratchpad/repro-phrases-practice/repro.mjs. It installs a speechSynthesis shim in which an utterance keeps playing until cancel() is called, and imports tests/env.mjs, tts.js and placeholders.js by file URL. It copies app.js's speakUserStatement, the speaking gate, abortPlaceholders (stop() plus placeholderEpoch++, with no generationToken bump) and the epoch check at line 1904. How the code gets there:
1. generateOptions (app.js:1744-1746) records token = ++generationToken and pEpoch = placeholderEpoch.
2. handleHoldOn (3236) and handleSayAgain (3225) call abortPlaceholders() (181-184). That bumps placeholderEpoch but never generationToken.
3. Neither button bumps generationToken, so the in-flight generation still passes its own guard when it returns (`if (token !== generationToken) return` at about line 1819).
4. It then reaches line 1904. Because pEpoch !== placeholderEpoch, it takes the else branch and calls placeholders.stop().
5. stop() (placeholders.js:245-253) ends with an unconditional tts.cancel(). That function (tts.js:401-412) bumps speakToken, calls synth.cancel(), and cancels every paid backend.
6. The catch branch at app.js:1948 calls placeholders.stop() in the same unguarded way.

Node output:
- While the Hold on phrase was playing: isSpeaking=true, synth.speaking=true, statement promise not yet resolved.
- The else branch then called placeholders.stop() with no placeholder playing.
- Afterwards: isSpeaking=false, synth.speaking=false, and the statement promise had resolved early.
- Event log: ['synth.cancel', "speak:I'm taking a little longer with this one.", 'synth.cancel'].

The second synth.cancel is the generation's stop() killing the user's own statement mid-sentence. The speaking gate (setUserSpeakingGate) does not prevent this: it only stops a placeholder from STARTING over the user, not stop() from cancelling the user. The paid voices are hit the same way, because tts.cancel() cancels every backend.

When that generation returns, generateOptions sees pEpoch !== placeholderEpoch and takes the else branch `placeholders.stop()` -> tts.cancel() -> the user's statement is cancelled mid-word. The same happens on the catch path, and when the partner interjects during a Say-again (Say again does not stop the mic, so handlePartnerResumed fires stop()). The cancelled speakUserStatement promise resolves normally, so logSpokenUserTurn records the full text as spoken. This is the July 13 2026 'placeholder interrupted Repeat what I said' bug arriving by a different route: the epoch was added to stop the generation from STARTING a placeholder, but its else branch now cancels the user's speech instead.

Fix as proposed by that reviewer: Make stop() cancel speech only when the ladder itself is speaking. In placeholders.js add `let speakingPlaceholder = false;`, wrap the ladder's own speech in speakNext: `speakingPlaceholder = true; try { await tts.speak(phrase); } finally { speakingPlaceholder = false; }`, and change stop() to `if (speakingPlaceholder) { speakingPlaceholder = false; tts.cancel(); }`. Callers that must silence whatever is playing before their own speech (handleResponseSelected etc.) still work: tts.speak of the new statement supersedes the old one, and terminateConversation calls tts.cancel() directly.
