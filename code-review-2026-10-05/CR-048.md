# CR-048: An error logged outside a conversation creates a fake conversation file that then swallows the next real conversation

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/storage.js:2690`
- **Also affects:** `app/js/storage.js:2661 (ensureConversationId in logError)`; `app/js/storage.js:2120-2133 (startConversationLog reuses the id and returns early)`; `app/js/review-model.js:239-251 (started/duration taken from data.started)`; `app/js/usage-summary.js:222-249 (every file counts as a conversation, context timestamps count as active days)`; `app/js/app.js:6553, 6667, 798, 6407 (logError calls made from Settings / outside a conversation)`
- **Source:** storage-02

**What a user notices.** If something goes wrong while the person is in Settings (an import or export problem, a paid voice failing during a voice test, a problem report that would not send), the app quietly starts a saved 'conversation' containing only that error. The next real conversation is then filed under that earlier time, so Conversation Review shows the wrong start time and a much longer length, and usage reports count an extra conversation and active day.

**What is wrong.** logError() calls ensureConversationId() unconditionally, minting a conversation id whenever no conversation is active, and logErrorToConversation() calls startConversationLog() lazily whenever a data folder exists. So an error raised between conversations creates conversations/<error time>.json with a 'context start' entry and the error. currentLogData then stays set, so when the user later presses Listen or Start conversation, startConversationLog() returns early and the real conversation is appended to that file: its id, file name and `started` are the error's time. review-model computes started/duration from data.started, and listConversationLogs' `since` cutoff uses the file-name date, so a conversation can be mis-dated (or hidden by the last-week filter if the app sat open) and its 'How long' inflated. A file that never gets a real conversation is counted by usage-summary as a conversation (and its context entry as an active day), inflating the beta adoption figure. Reproduced in Node against the real storage.js: logError('export',...) created a conversation file, and a later startConversationLog() returned the SAME file name and appended the partner turn to it.

**How it happens.** 1) With a data folder connected and no conversation running, open Settings and trigger an error (e.g. Import a malformed backup -> app.js:6553 logError('import', ...), or a paid voice preview failing offline -> logError('voice', ...)). 2) conversations/<10:00>.json is created holding a context entry and the error. 3) An hour later press Listen and talk. 4) The conversation is written into the 10:00 file; Conversation Review lists it as starting at 10:00 and lasting over an hour.

**Suggested fix.** In logErrorToConversation replace `if (!currentLogData) await startConversationLog(); if (!currentLogData) return;` with `if (!currentLogData) return;` - an error only joins a conversation file that already exists (Listen and Start create the file eagerly, so in-conversation errors are still captured). In logError use `conversation: currentConversationId || null` instead of `ensureConversationId()` so an error between conversations does not mint the next conversation's id; startConversationLog already mints the id when a conversation actually starts.

> **Verifier correction to the fix (takes precedence):** Removing the lazy startConversationLog from logErrorToConversation is right. Changing the ring-buffer id to currentConversationId || null has one side effect to handle: an error raised at the very start of a conversation before any log write (for example a TTS failure while the first Express phrase is being spoken, before logUserResponse runs) would then carry conversation null and never reach the file. Either accept that (state it in a comment) or keep minting the id only when a conversation is actually in progress (e.g. let app.js tell storage a conversation has begun).

**How to verify the fix.** Add to tests/storage-transcript.test.mjs: with device storage active and no conversation started, call logError('export','x'); assert the conversations folder has no files and getConversationId() is null; then startConversationLog() and assert the new file's id is at or after the moment of that call and contains no 'error' entry.

**Do not break.** Errors raised during a live conversation must still be interleaved into that conversation's file and carry its id (CLAUDE.md error-reporting section). Keep the 'Don't save' gate. errors.log and the ring buffer must still record the error (with conversation null).

**Design reference.** CLAUDE.md 'Error reporting — audited against expectation' and storage.js comment at 2058-2065 (one id per conversation)

**Verification notes.** logError always calls ensureConversationId() (storage.js:2661) and logErrorToConversation lazily calls startConversationLog() when a data folder exists and saving is on (storage.js:2690). Reproduced in Node against the real storage.js: logError('import', ...) with no conversation created conversations/<error time>.json; a second later startConversationLog() returned that SAME file name and id, and the later partner turn was appended after the error, so the file's id/started are the error's time. Saving is on between conversations by default, and Settings actions (import, export, voice test) run logError outside a conversation. The storage.js comment says the id is created lazily on the first turn or first error, but it does not record the side effect of a file being created and the next conversation being misdated, so this is not a recorded accepted cost.
