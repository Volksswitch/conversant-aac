# CR-049: Stopping Deepgram while it is still connecting reports a false error and can switch listening off for good

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/stt-deepgram.js:303`
- **Also affects:** `app/js/stt-deepgram.js:304`; `app/js/stt-deepgram.js:367`; `app/js/stt.js:673`; `app/js/stt.js:660`
- **Source:** stt-09

**What a user notices.** Ending a conversation, or switching away from the app, just after tapping Listen with Deepgram can mark the transcript with the red 'something went wrong' wash for no reason, and after returning to the app listening may not come back on.

**What is wrong.** ws.onerror reports `onStatus('error', 'network')` unconditionally; only onclose is gated on `running`. stop() sets running=false and calls ws.close() but leaves the socket's handlers attached. Calling close() on a socket in CONNECTING state makes the browser fire an 'error' event, so a stop during the handshake produces 'error' -> stt.js handleSourceError -> listeningIntent=false + error logged (red wash). When the stop came from the visibility guard's suspendSource(), clearing listeningIntent means the guard's `if (listeningIntent) openSource()` never reopens capture on return. Also, while running, any socket failure fires onerror AND onclose, logging two errors for one event. Separately, stop() sends CloseStream and then immediately calls ws.close(); per the WebSocket spec messages arriving while CLOSING are discarded, so the 'flush pending transcript' the comment promises cannot happen.

**Evidence.**

```
stt-deepgram.js:303 `ws.onerror = () => { if (onStatus) onStatus('error', 'network'); };`
stt-deepgram.js:312 `if (running && onStatus) {` (onclose only)
stt-deepgram.js:367-375 `if (ws) { try { if (ws.readyState === WebSocket.OPEN) ws.send(JSON.stringify({ type: 'CloseStream' })); } catch {} try { ws.close(); } catch {} ws = null; }`
stt.js:536-538 `} else if (suspendedForHidden) { suspendedForHidden = false; if (listeningIntent) openSource(); }`
```

**How it happens.** Deepgram on cellular. Tap Listen, then within a second tap End conversation (or press Home). stopListening -> source.stop() -> ws.close() while CONNECTING -> onerror -> 'error'/'network' logged; the transcript washes red; if it was the Home press, on return listening stays off.

**Suggested fix.** Change line 303 to `ws.onerror = () => { if (running && onStatus) onStatus('error', 'network'); };` and, to avoid double reporting, let only onclose report while running (onerror can just record nothing). In stop(), before closing, detach handlers: `ws.onmessage = null; ws.onerror = null; ws.onclose = null; ws.onopen = null;` (also prevents a late onopen from starting a KeepAlive interval on a stopped source). Either remove the misleading CloseStream comment or delay ws.close() until a short timeout after CloseStream while ignoring results (results after a deliberate stop must not reach the transcript).

**How to verify the fix.** New tests/stt-deepgram.test.mjs with a fake WebSocket whose close() in CONNECTING fires onerror then onclose: start(), stop() before open -> assert no 'error' status emitted. Fire an abnormal close while OPEN -> exactly one 'error'.

**Do not break.** Keep carrying the close code in the onclose error (CLAUDE.md, Ken's iPad August 3 2026). Keep 'listening' reported from ws.onopen only.

**Design reference.** CLAUDE.md 'Paid speech-to-text — Deepgram' and the Listen-button 'capturing' fix in the August 3 2026 handoff

**Verification notes.** ws.onerror reports `onStatus('error','network')` without checking `running`, and stop() calls ws.close() without detaching the handlers. Under the WebSocket spec, close() on a CONNECTING socket fails the connection and fires an error event (Chrome logs 'closed before the connection is established'). So a stop during the handshake becomes handleSourceError → an error logged and the red wash, for a deliberate stop. If the stop came from suspendSource(), listeningIntent is cleared and the guard does not reopen on return. Note that the guard currently is not even registered when the app launches on Deepgram (see stt-03). While running, one failure fires both onerror and onclose, so two errors are logged. Messages that arrive after close() while the socket is CLOSING are discarded, so the CloseStream 'flush' comment is wrong.
