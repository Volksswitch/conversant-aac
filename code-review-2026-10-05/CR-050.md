# CR-050: Words the partner says while the app is speaking a placeholder never get fresh suggestions

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/stt.js:360`
- **Also affects:** `app/js/stt.js:179`; `app/js/stt.js:636`; `app/js/stt.js:360 (merged duplicate: A partner reply heard within 1.5 s after the app stops talking never triggers suggestions - the app sits listening with no cards and no error)`
- **Source:** stt-05, live-runtime-05

**What a user notices.** If the other person adds something while the app is saying 'I'm thinking about that', the suggestions stay based on what they said before, so the user may answer the wrong question. The app also keeps playing holding phrases over them.

**What is wrong.** afterIngest() renews the silence checkpoint and fires onPartnerActivity only when `heardPartner && !speechActive()`. Genuine (non-echo) partner speech that arrives while the app is speaking or within the 1.5 s tail is accumulated into the transcript but arms no timer. The previous checkpoint has already fired, so when the app falls quiet nothing ever re-checks: no checkpoint fires for the added words unless the partner speaks AGAIN after the tail. CLAUDE.md accepts that a partner cutting in mid-placeholder 'isn't aborted until it ends'; here it is never handled at all.

**Evidence.**

```
stt.js:360-367 `if (heardPartner && !speechActive()) { resetSilenceTimer(sawFinal); if (onPartnerActivity) onPartnerActivity(); }`
stt.js:179-186 noteSpokenEnd only sets `speechSettleUntil` and phrase expiry; it schedules nothing.
Experiment (scratchpad exp3.mjs, threshold 0.5 s): final 'Do you want coffee?' -> checkpoint; noteSpokenStart(placeholder); final 'Or maybe some tea instead.'; noteSpokenEnd(); after 3 s silences = ['Do you want coffee?'] only, buffer = 'Do you want coffee? Or maybe some tea instead.'
```

**How it happens.** Partner: 'Do you want coffee?' (pause) -> cards generated, placeholder starts 2 s later. Partner, over the placeholder: 'Or maybe some tea instead.' then waits. No new cards; the coffee cards remain; a second placeholder plays 10 s later.

> **Verifier correction to the trigger:** This only happens when the recognizer delivers the final result for the added words before the app's speech ends plus 1.5 s. A result that arrives later (recognizer lag, or a longer addition) does renew the timer and is handled normally. So it bites on short additions spoken over the placeholder.

**Suggested fix.** In stt.js keep `let heardDuringSpeech = false;`. In afterIngest, when `heardPartner && speechActive()`, set `heardDuringSpeech = true`. In noteSpokenEnd(), schedule `setTimeout(() => { if (heardDuringSpeech && listeningIntent && !speechActive()) { heardDuringSpeech = false; resetSilenceTimer(false); if (onPartnerActivity) onPartnerActivity(); } }, ECHO_TAIL_MS + 10)`. To avoid re-creating the v0.3.4/v0.3.9 echo runaway loop, only set heardDuringSpeech when the ingested text has at least two tokens that appear in none of the active phrases (a 'novel token' test using the existing normalizeForEcho/tokens), and allow at most one such deferred checkpoint per app utterance. Clear heardDuringSpeech in resetTranscript().

**How to verify the fix.** Add to tests/stt.test.mjs a test reproducing exp3: after the placeholder ends and the tail elapses, a second checkpoint must fire carrying both sentences. Add a negative test: a mis-heard echo of the placeholder ('steel mulling that over') captured during speech must NOT produce a deferred checkpoint.

**Do not break.** The trigger-level echo guard exists to stop a runaway loop (CLAUDE.md 'The TTS-echo defense is TWO layers'); placeholders.arm() resets the per-turn count on every checkpoint, so an unguarded deferred checkpoint fed by mis-heard echo would loop. Keep the novel-token test and the once-per-utterance limit.

**Design reference.** CLAUDE.md 'Standing findings — The TTS-echo defense is TWO layers' and 'No turn-completion gate' (known limitation about mid-placeholder resumption)

**Verification notes.** afterIngest renews the silence timer and calls onPartnerActivity only when `heardPartner && !speechActive()`. noteSpokenEnd() sets the settle deadline and phrase expiry but schedules nothing. So genuine partner text ingested while the app is speaking, or within the 1.5 s tail, is added to the buffer but never re-checkpointed, unless another result arrives after the tail. The checkpoint for the earlier words has already fired, so no timer is pending. CLAUDE.md accepts only that a partner cutting in mid-placeholder 'isn't aborted until it ends'. That implies it is handled afterwards, so this gap is not covered by the accepted limitation.

<details><summary>Merged duplicate live-runtime-05: A partner reply heard within 1.5 s after the app stops talking never triggers suggestions - the app sits listening with no cards and no error</summary>

afterIngest only (re)starts the silence timer when `heardPartner && !speechActive()`. speechActive() stays true for ECHO_TAIL_MS (1500 ms) after the app's speech ends. If every recognizer result for a short partner utterance is delivered inside that window, the content is accumulated (it passed the echo content filter and is shown) but no timer is ever armed; nothing later re-arms it, so fireSilenceCheckpoint never runs, no generation happens and the placeholder ladder (armed by the checkpoint) never starts. The trigger guard was meant to stop echo from RENEWING a turn, but it also drops the first real partner content entirely. With auto-resume on, the mic reopens immediately after the user's statement, which is exactly when a quick reply lands in the tail.

Fix as proposed by that reviewer: In afterIngest add an else branch so genuine content heard during the tail still schedules (but does not renew) a checkpoint: `else if (heardPartner && !silenceTimer) { silenceTimer = setTimeout(fireSilenceCheckpoint, Math.max(silenceThreshold, speechSettleUntil - Date.now())); }`. fireSilenceCheckpoint already defers while speechActive(), so the checkpoint cannot fire during the app's own speech. Do not call onPartnerActivity in that branch.


Verifier correction: The suggested else-branch would arm a checkpoint for ANY content heard during the tail. That includes mis-heard echo of the app's own speech that slipped past the content filter, which is exactly what the v0.3.4/v0.3.9 trigger-level guard exists to stop. A placeholder's mis-heard echo would then fire a generation, which arms more placeholders: the runaway loop comes back. Instead, re-evaluate once when the tail ends. For example, noteSpokenEnd schedules a single check at speechSettleUntil: if no timer is pending and content was ingested since appSpeaking became false, arm one checkpoint. Allow at most one tail-originated checkpoint per app utterance, and extend the echo-loop tests to cover mis-heard echo in the tail.
