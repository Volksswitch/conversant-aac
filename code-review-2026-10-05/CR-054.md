# CR-054: Fact labels sent to the AI come from the first placeholder synonym and misdescribe several answers

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/worldview.js:539`
- **Also affects:** `app/js/worldview.js:784-788 (facts/privateKnown lines use labelFor)`; `app/js/worldview.js:763-765 (declined phrase-around list also uses labelFor, and the Set merges the two 'place' labels)`; `app/data/worldview-questions.json:171-180 (work_school fills[0] 'school')`; `app/data/worldview-questions.json:183-192 (grade_role fills[0] 'grade')`; `app/data/worldview-questions.json:154-168 (occupation fills[0] 'job')`; `app/data/worldview-questions.json:206-215 and 440-449 (regular_places and fav_places both fills[0] 'place')`; `app/data/worldview-questions.json:392-402 (fav_music fills[0] 'artist' though genres are allowed)`; `app/data/worldview-questions.json:195-204 (typical_week fills[0] 'activity')`
- **Source:** worldview-04

**What a user notices.** The app can tell the AI wrong things about the user, for example that they attend a school called the name of the store where they work, or it lists their favorite places and their regular hangouts under the same word, so suggested replies can state things that are not true.

**What is wrong.** labelFor(key) uses meta.fills[0] as the fact label. fills is a list of placeholder synonyms (for bracket-filling), not a field label, and for several fields the first synonym is a narrower or wrong description of the answer. Running buildBlock with occupation='I work', work_school='Acme Hardware', grade_role='Store manager', regular_places=['the gym','church'], fav_places=['Paris'], fav_music=['jazz','The Beatles'] produced: '- Job: I work', '- School: Acme Hardware', '- Grade: Store manager', '- Place: the gym, church', '- Artist: jazz, The Beatles', '- Place: Paris'. A worker's employer is labeled 'School'; two different questions produce identical 'Place' lines with no way for the model to tell regular haunts from favorite destinations; declining both collapses to one 'place' in the phrase-around Set. This is exactly the fabrication risk the anti-fabrication rule guards against, introduced by the profile itself.

**Evidence.**

```
app/js/worldview.js:539-547:
    function labelFor(key) {
        const meta = fieldMeta(key);
        if (!meta) return key;
        // The canonical placeholder name reads as a clean fact label
        if (meta.fills && meta.fills.length) {
            const f = meta.fills[0];
            return f.charAt(0).toUpperCase() + f.slice(1);
        }
Registry: "key": "work_school", "q": "Where — the name of the company, school, or program?", "fills": ["school", "company"]; "key": "regular_places" ... "fills": ["place"]; "key": "fav_places" ... "fills": ["place"].
Observed output: '- School: Acme Hardware' and '- Place: the gym, church' ... '- Place: Paris'.
```

**How it happens.** User answers 'I work' and 'Acme Hardware'. The partner asks 'Where do you go to school?' The model, told 'School: Acme Hardware', offers 'I go to Acme Hardware.' as a preferred response.

**Suggested fix.** Add an optional `label` property to registry fields and have labelFor prefer it: `if (meta.label) return meta.label;` before the fills fallback. Author labels at least for occupation ('What I do during the day'), work_school ('Where I work or study'), grade_role ('My grade or role there'), typical_week ('A typical week'), regular_places ('Places I go regularly'), fav_places ('Favorite places'), fav_music ('Favorite music'), fav_screen ('Favorite shows or movies'), fav_reading ('Favorite reading'), home_region ('State/province and country'). Keep fills unchanged (they serve placeholder matching).

**How to verify the fix.** Add to tests/worldview.test.mjs: set work_school='Acme Hardware' and assert buildBlock() contains no 'School: Acme Hardware'; set both regular_places and fav_places and assert the two lines have different labels. Also assert every registry field's label (label or fills[0]) is unique.

**Do not break.** Labels sit in the CACHED prompt prefix; changing them invalidates the cache once, which is fine. Do not change `fills` (used for placeholder synonyms) or field keys (gaps and saved profiles depend on them). A test asserts trait/humor strings match the registry; do not alter those options.

**Design reference.** CLAUDE.md 'No fabricated autobiography' (Further Design Thoughts #2a); Worldview Questionnaire Build Step 1 (buildBlock labels from fills[0]).

**Verification notes.** labelFor (worldview.js:539-547) returns fills[0] capitalized, and buildBlock uses it for fact lines and the declined phrase-around set. The registry confirms the bad labels: work_school fills ['school','company'] gives 'School'; grade_role gives 'Grade'; occupation gives 'Job'; typical_week gives 'Activity'; fav_music gives 'Artist'. regular_places and fav_places both give 'Place', so two different answers carry identical labels, and declining both collapses them into one entry in the Set. No field has a 'label' property today. The mechanism is certain; how far it misleads the model is less certain, since the model also sees other context.
