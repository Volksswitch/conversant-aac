# CR-058: Restoring a backup while the remembered data folder is not reconnected is silently undone on the next launch (and an export made then omits every conversation)

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** data-loss
- **Verdict:** confirmed (skeptic: confirmed; reproducer: reproduced)
- **Location:** `app/js/data-transfer.js:393`
- **Also affects:** `app/js/data-transfer.js:154-157 (buildPackage reads conversations/audio/profiles from the folder only)`; `app/js/data-transfer.js:441-445 (conversations skipped with no folder)`; `app/js/app.js:6514-6561 (importPackageText - no folder check)`; `app/js/app.js:6612-6675 (export - no folder check)`; `app/js/storage.js:136 (hasRememberedFolder exists and is unused here)`; `app/js/express-panel.js:248-261, worldview.js:142-158, relationships.js:84-92 (folder file wins on load/sync)`
- **Source:** review-backup-01

**What a user notices.** On a computer or Android tablet where the person tapped "Not now" on the reconnect-folder card, restoring a backup appears to work, but the next time the folder is reconnected the app quietly puts the old answers, people, places and buttons back and the restore is gone. A backup made in the same state contains no saved conversations, sounds or profiles.

**What is wrong.** applyPackage writes each data file to the localStorage cache and then calls storage.writeFile, which is a silent no-op when dirHandle is null. On Android (permission is asked every launch) and on Windows after a declined prompt, the folder handle is KEPT in IndexedDB while dirHandle stays null until the user reconnects (CLAUDE.md, Android section: 'the handle is now KEPT on any failure'). So the import lands only in the cache. On the next launch the user reconnects the folder, and every model's load()/syncToFolder() follows the v0.2.25 'file in the folder wins' rule: it reads the folder's OLD worldview.json/relationships.json/express-panel.json/... and overwrites the imported cache. Conversations and sounds are not restored at all (writeConversationLog returns false, writeAudioFile throws) and nothing tells the user (see separate finding about the restart card). The export side has the mirror defect: buildPackage reads conversations, audio and profiles only from the folder, so a backup made while the folder is remembered-but-disconnected silently contains 0 conversations and stale cache copies of the data files, and is saved via the download path because hasVisibleDataFolder() is false.

**How it happens.** 1) Android tablet, data folder chosen earlier, Settings has edits. 2) Relaunch, tap Start, tap "Not now" on the Reconnect my folder card. 3) Settings > Backup, import a backup containing different About Me answers and Express buttons; confirm. 4) Restart now - the imported data shows (read from cache). 5) Next launch, reconnect the folder: syncToFolder adopts the folder's old files; the imported answers and buttons are gone. Conversations from the backup were never written.

> **Verifier correction to the trigger:** The export half is not fully silent: buildPackage gets 0 conversations and 0 sounds, and the 'Backup finished' card lists the counts from summarize(), so a 0 is visible if the user reads it. It also goes down the download path because hasVisibleDataFolder() is false.

**Suggested fix.** In app.js importPackageText (before confirmDanger) and in the exportDataBtn handler (before building), add: `if (!storage.hasDataFolder() && await storage.hasRememberedFolder()) { setBackupStatus('Reconnect your data folder first (General tab), then try again - otherwise the backup cannot reach it.'); return; }`. Optionally offer to run the existing reconnect (storage.restoreDataFolder) from that button tap. Keep the no-folder-ever case (hasRememberedFolder false) working as today.

**How to verify the fix.** Manual: on Chromium with a folder chosen, reload and skip the reconnect; try Import and Export - both must refuse with the message and change nothing. Reconnect and import - data persists across a second reload. Unit test in tests/storage-transcript.test.mjs style is hard because hasRememberedFolder needs IndexedDB; a source-level guard test in tests/ (like the placeholders source guards) asserting importPackageText calls hasRememberedFolder is acceptable.

**Do not break.** Do not block the iPad (OPFS, supportsFolderPicker false, hasRememberedFolder returns false) or a user who never chose a folder. The confirmation must still be confirmDanger, not window.confirm.

**Design reference.** CLAUDE.md 'Cross-PC copy of worldview.json - the file in the folder is the source of truth'; CLAUDE.md 'Android - MEASURED' (handle kept on failure, Reconnect my folder card); data-transfer.js header 'WHAT TRAVELS: everything'

**Verification notes.** Traced. afterFolderNotice (app.js ~1586) offers the reconnect card only when !hasDataFolder() && hasRememberedFolder(), and dismissFolderNotice lets the session continue on the cache. In that state applyPackage (data-transfer.js 393-408) writes localStorage then storage.writeFile, which returns immediately when dirHandle is null (storage.js 380). importPackageText and the export handler never check for a remembered-but-disconnected folder. On the next launch with the folder reconnected, worldview.load/express-panel.syncToFolder/voice.load read the folder file first and overwrite the cache, so the import is undone. writeConversationLog returns false with no conversations dir, so conversations from the backup are dropped, and offerRestart says nothing about it. The general loss of edits made while disconnected is a recorded accepted trade-off (worldview.syncToFolder comment), but an import that reports success and is then reverted is a larger, unannounced case and the backup file still exists, so severity is medium rather than high (narrow trigger: the user tapped past the reconnect card; recoverable by re-importing after reconnecting).

**Reproduction (reproduced).** Method: Ran the real app/js/storage.js, data-transfer.js, worldview.js and relationships.js in node (scratchpad repro-review-backup/repro.mjs). The shims were the ones tests/storage-transcript.test.mjs uses: an in-memory directory handle as the folder root, a localStorage map, and no showDirectoryPicker. The folder was seeded with OLD worldview.json and relationships.json (person 'OLD-PERSON') plus one saved conversation. The 'Not now' state was reproduced by never calling restoreDataFolder, so dirHandle stayed null. I then ran buildPackage and applyPackage with a backup carrying NEW data (person 'NEW-PERSON' and two conversations). For the next launch I called storage.restoreDataFolder() and then the same load()/syncToFolder() sequence app.js:1449-1471 runs after connecting. I also traced app.js importPackageText (6514-6561) and the exportDataBtn handler (6612-6675): neither checks hasDataFolder or hasRememberedFolder. hasRememberedFolder is used only by the reconnect card at app.js:1602. Output from the run:
- hasDataFolder (disconnected): false
- EXPORT while disconnected: conversations 0, although the folder holds 1. buildPackage reads them via listConversationLogs, and getConversationsDir returns null with no dirHandle. The export handler then takes the download path because hasVisibleDataFolder() is false.
- applyPackage result: files ['About Me answers', 'People and relationships'], conversations 0, failed []. The restart card is therefore told the data files were restored. The conversations were silently not written: writeConversationLog returned false and nothing went into failed[].
- After the import, the worldview cache said NEW-NAME while the folder's worldview.json still said OLD-NAME. writeFile is a no-op at storage.js:380-381. The folder's conversations directory still held only the old file.
- Next launch: restoreDataFolder returned true, and worldview.syncToFolder and relationships.syncToFolder both returned 'adopted'.
- After reconnect, the relationships cache was ['OLD-PERSON'] and NEW-PERSON was gone. The worldview cache was replaced by the folder file: it carries the old file's 'updated: 2026-01-01' and NEW-NAME is absent.

The imported data is silently reverted on reconnect, and no imported conversation reached the folder. express-panel.js syncToFolder (248-261) has the same 'if (disk) adopt' shape, so Express items revert the same way.

The only part not run in a browser is the Android/Windows picker path. There, restoreDataFolderInner keeps the IndexedDB handle and leaves dirHandle null when permission is refused or the card is dismissed (storage.js 237-290), which is exactly the state simulated here. The reconnect then goes through setRoot(stored, FOLDER), which is the same reconcile the node run exercised through the device-storage root.
