# CR-060: Deepgram stop() closes the socket right after CloseStream, so the promised flush of the partner's last words never arrives, and unsettled words are lost on resume

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** data-loss
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/stt-deepgram.js:367`
- **Also affects:** `app/js/stt.js:724-731 (stopListening returns externalSource.stop() without committing currentInterim)`; `app/js/stt.js:673-676 (suspendSource, same)`; `app/js/stt.js:474-488 (the built-in path DOES flush currentInterim before a restart - the paid path has no equivalent)`; `app/js/app.js:1678 (manual Listen off)`; `app/js/app.js:1703-1705 (resumePartnerCapture)`; `app/js/app.js:5282 (sound-button mute stops and then resumes listening)`
- **Source:** g-stt-overflow-02

**What a user notices.** With Deepgram hearing, if listening is paused in the middle of the other person's sentence (tapping Listen off and on, playing a sound button, or switching away from the app and back), the words that were on screen but not yet settled disappear when listening comes back, and the last fraction of a second they said before the pause is never transcribed at all.

**What is wrong.** stop() sends {type:'CloseStream'} - whose purpose (per its own comment and Deepgram's docs) is to make the server finish transcribing buffered audio, send the final results, then close - and then immediately calls ws.close() and nulls ws. Calling close() puts the socket into CLOSING at once, and the WebSocket standard discards any message received when readyState is not OPEN ('When a WebSocket message has been received ... If ready state is not OPEN, then return'). So the flushed final results Deepgram sends in reply to CloseStream can never be delivered; the comment's promise is false. Two concrete losses follow: (a) audio sent in roughly the last 0.3-1 s before the stop, for which no interim has yet come back, is never transcribed; (b) words that arrived only as an INTERIM (is_final=false) sit in stt.js currentInterim. Nothing commits them on a paid-source stop (stopListening/suspendSource just call externalSource.stop()). On resumeListening a new socket opens and its first interim message overwrites currentInterim in ingest(), so the previously visible unsettled words are silently dropped from the turn. The built-in recognizer path guards exactly this case (stt.js:474-488 commits currentInterim before restarting); the Deepgram path does not. This contradicts the 'Listen stop/start is a PAUSE' decision, whose whole point is that a mid-turn stop/start loses nothing.

**How it happens.** 1. Deepgram hearing. 2. Partner: 'I wanted to ask whether you could come on Thursday' - the screen shows 'I wanted to ask whether you could come' as an interim; 'on Thursday' has been sent but not yet transcribed. 3. User taps Listen off (or plays a sound button, or the tablet is backgrounded). 4. CloseStream is sent and the socket closed at once; Deepgram's final for the span is discarded; 'on Thursday' is never transcribed. 5. User taps Listen on (resume, buffer kept); the partner continues 'or Friday'. 6. The new socket's first interim replaces currentInterim, so the saved turn reads only 'or Friday.' - the earlier half shown on screen is gone.

> **Verifier correction to the trigger:** The sound-button path (app.js ~5282) only resumes listening when playback FAILS. On a successful play it takes the floor, and heardPartnerText() (which includes the interim) is captured before the stop, so a successful sound play loses nothing. The real triggers are a manual Listen off and then on mid-sentence, and the visibility guard's suspend and resume on platforms that guard visibility.

**Suggested fix.** Two parts. (A, required, small) In stt.js add
    function commitPendingInterim() {
        if (currentInterim.trim()) commitSegment(currentInterim);
        currentInterim = '';
    }
and call it for EXTERNAL sources only, before stopping them: in stopListening() change `if (externalSource) return externalSource.stop();` to `if (externalSource) { commitPendingInterim(); return externalSource.stop(); }`, and in suspendSource() do the same before `externalSource.stop()`. (Built-in stop() delivers its own final, so do not add it there or the words would be recorded twice.) This keeps exactly what the user saw. (B, Deepgram drain) In stt-deepgram.js stop(), do not call ws.close() immediately after CloseStream. Keep the old socket in a local `const draining = ws; ws = null;`, replace its handlers with a drain handler that accepts only is_final messages and passes them to a new optional callback `onLateFinal(text)` (do NOT route them through the normal onText, which arms the silence timer and would fire a checkpoint after listening stopped - see the already-reported late-result issue), set `draining.onclose = null; draining.onerror = null;` so a late close cannot report an error into a NEW session, and call `draining.close(1000)` from `setTimeout(..., 1500)` or when the server closes first. In stt.js, onLateFinal should replace the last segment only if the transcript has not been reset since the stop (keep a counter bumped in resetTranscript and compare). If (B) is judged not worth it, at minimum delete the false comment and close with `ws.close(1000)`; part (A) alone fixes the visible loss.

**How to verify the fix.** Part A: in tests/stt.test.mjs, init with `source: 'openai'` is not drivable, so add to the new tests/stt-deepgram.test.mjs (fake WebSocket/AudioContext as in the first-words finding) or test via a fake external source: start listening, deliver onText('I wanted to ask', false), call stt.stopListening(), then stt.resumeListening() and deliver onText('or Friday', false); assert getCurrentTranscript() === 'I wanted to ask or Friday'. Part B: with the fake socket, call stop(), then deliver a message {is_final:true, channel:{alternatives:[{transcript:'on Thursday'}]}} to the draining socket's onmessage and assert onLateFinal received it, and that a later onclose on the old socket produces no 'error' status. Manually on a tablet: Deepgram, partner mid-sentence, tap Listen off/on, confirm the earlier words survive.

**Do not break.** Do not let late finals arm the silence timer or call onSilencePeriod after the user stopped listening. Do not let the old socket's onclose/onerror fire into a newer session (the module-level `running` flag would be true again). The 'Listen stop/start is a PAUSE' decision (CLAUDE.md) must still hold: resume keeps the buffer, only floor changes reset it. Committing the interim for the built-in recognizer would duplicate words.

**Design reference.** CLAUDE.md 'DECIDED + BUILT (Ken, August 5 2026) — Listen stop/start mid-turn is a PAUSE, not a turn boundary'; stt.js comments at 474-486 (Ken, July 12 2026, interim lost on restart)

**Verification notes.** stop() sends CloseStream and then calls ws.close() straight away and nulls ws. After close() the socket is CLOSING, and the HTML WebSocket spec drops any message received when readyState is not OPEN. So the flushed final Deepgram sends in reply to CloseStream can never be delivered, and the comment's promise is false. On the interim half: ingest() overwrites currentInterim with each new interim. stopListening() and suspendSource() call externalSource.stop() without committing currentInterim. Only the built-in onend path commits it (stt.js ~487). toggleListening resumes when heardPartnerText() is non-empty, which includes the interim. resumePartnerCapture -> resumeListening opens a new socket, and its first interim replaces the old interim, so those words vanish. This goes against the recorded 'Listen stop/start is a PAUSE' decision. The same applies to the visibility guard, which calls suspendSource on external sources. The trigger needs a stop while words are still unsettled, so medium is right.
