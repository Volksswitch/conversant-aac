# CR-066: Credential and other Settings text fields are handled by hand-maintained id lists; five newer key fields, the Azure region, the tester name and the placeholder editor are outside the keyboard's scope, and key fields get auto-capitalized

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** design-violation
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/keyboard.js:38`
- **Also affects:** `app/js/keyboard.js:353`; `app/js/keyboard.js:653`; `app/index.html:517`; `app/index.html:527`; `app/index.html:555`; `app/index.html:565`; `app/index.html:588`; `app/index.html:1160`; `app/js/placeholder-editor.js:58`; `app/js/keyboard.js:38 (merged duplicate: The app's own keyboard covers only two of the six key fields and skips the placeholder editor and tester name)`; `app/js/keyboard.js:38 (merged duplicate: On-screen keyboard does not serve five of the Settings key/region fields (Azure, OpenAI, Google, ElevenLabs, region, tester name))`; `app/js/keyboard.js:38 (merged duplicate: On-screen keyboard mode skips the newer Settings text fields, so they pop the system keyboard instead)`
- **Source:** keyboard-04, x-contracts-09, x-rules-01, x-a11y-10

**What a user notices.** With the app's own keyboard chosen, some Settings boxes (OpenAI, Google, ElevenLabs and Azure keys, the Azure region, the tester name, the placeholder phrases) bring up the device's keyboard instead, or none, while the boxes beside them use the app's. Typing a Deepgram key on the app keyboard capitalizes its first letter, so a typed key is rejected.

**What is wrong.** IN_SCOPE lists #apiKeyInput and #deepgramKeyInput but none of the key fields added with the five-provider work (#azureKeyInput, #azureRegionInput, #openaiKeyInput, #googleKeyInput, #elevenlabsKeyInput), nor #testerNameInput (same tab as #problemNoteInput, which is in scope) nor the #placeholderEditor inputs. CLAUDE.md records the decision that Settings key fields use the app keyboard (Ken, June 14 2026) and the Sep 8 2026 lesson that listing providers by id silently misses the next one. Two further id lists encode credential handling: predictionOff() exempts only apiKeyInput/deepgramKeyInput from word completion and LEARNING, and show() exempts only apiKeyInput from the one-shot capital. So simply adding the new key ids to IN_SCOPE would start suggesting dictionary words in key fields and learning letter runs from secret keys into localStorage. Verified: typing 'd' first into #deepgramKeyInput produced 'D' (Deepgram keys are lowercase hex).

**Evidence.**

```
keyboard.js:38 `const IN_SCOPE = '#composerInput, #reviewWordInput, .wv-text, #apiKeyInput, #deepgramKeyInput, #controlEditor input, #expressEditor input, #settingsProfileNameInput, #problemNoteInput, #practicePanel input[type="text"], #practicePanel textarea';`; keyboard.js:353-357 `return !f || f.id === 'apiKeyInput' || f.id === 'deepgramKeyInput' || (f.dataset && f.dataset.noPredict !== undefined);`; keyboard.js:653 `shiftState = field.id === 'apiKeyInput' ? 'off' : 'shift';`; index.html:555 `<input type="text" id="openaiKeyInput" ...>` (also 517, 527, 565, 588, 1160); placeholder-editor.js:58-64 builds plain inputs inside #placeholderEditor.
```

**How it happens.** On-screen keyboard mode on a Windows tablet with the cover folded back. Settings > Speech: tap the OpenAI key box - Windows' own keyboard pops up (inputmode not 'none') and the app keyboard does not serve the field. Tap the Deepgram key box and type 'a1b2...' on the app keyboard - the field reads 'A1b2...'.

**Suggested fix.** Mark fields by attribute instead of id. In index.html add `data-no-predict` and a new `data-no-autocap` attribute to every credential input (apiKeyInput, deepgramKeyInput, azureKeyInput, azureRegionInput, openaiKeyInput, googleKeyInput, elevenlabsKeyInput). In keyboard.js: add those ids or (better) a class such as `.key-input` / `#settingsDialog input.kb-scope` to IN_SCOPE, plus `#testerNameInput` and `#placeholderEditor input`; change predictionOff() to `return !f || (f.dataset && f.dataset.noPredict !== undefined);` and show() to `shiftState = (field.dataset && field.dataset.noAutocap !== undefined) ? 'off' : 'shift';`. Keep the two id checks only if the attributes are added in the same change.

**How to verify the fix.** Extend tests/no-predict.test.mjs with a source-level check that every `id="...KeyInput"` in app/index.html carries data-no-predict, and that predictionOff no longer names ids. Manual: in on-screen mode each key field raises the app keyboard, shows no completion, and the first typed letter stays lowercase.

**Do not break.** tests/no-predict.test.mjs asserts the predictionOff structure (`dataset && f.dataset.noPredict !== undefined` and no inline `f.id === 'apiKeyInput'` exclusion of the old form) - keep it passing. API keys must never reach the learned word list (SEC-6). Text boxes of type=number (band sizes, title bar height) can stay on the device keyboard.

**Design reference.** CLAUDE.md 'In My Own Words' keyboard-selection spec (app keyboard used for Settings key fields); CLAUDE.md 'Five paid speech services' ('Styling a row by its id is the same bug as listing providers by name')

**Verification notes.** IN_SCOPE (keyboard.js:38) lists #apiKeyInput and #deepgramKeyInput but not #azureKeyInput, #azureRegionInput, #openaiKeyInput, #googleKeyInput, #elevenlabsKeyInput (index.html 517/527/555/565/588), #testerNameInput (1160, beside the in-scope #problemNoteInput), or the plain text inputs placeholder-editor.js builds inside #placeholderEditor. predictionOff() exempts only apiKeyInput/deepgramKeyInput by id, and show() suppresses the one-shot capital only for apiKeyInput, so the first typed letter in #deepgramKeyInput is capitalized. Deepgram keys are lowercase hex, so a hand-typed key is wrong. The reviewer's warning holds: adding the new ids to IN_SCOPE alone would turn on prediction and learning in secret fields, so the attribute change has to come with it.

<details><summary>Merged duplicate x-contracts-09: The app's own keyboard covers only two of the six key fields and skips the placeholder editor and tester name</summary>

keyboard.IN_SCOPE decides which fields get inputmode='none' (suppressing the OS keyboard) and summon the app keyboard. It lists #apiKeyInput and #deepgramKeyInput and the Controls/Express editors, but none of the fields added later: azureKeyInput, azureRegionInput, openaiKeyInput, googleKeyInput, elevenlabsKeyInput, testerNameInput, and the inputs of #placeholderEditor (a sibling of #controlEditor, which is in scope). The recorded decision (commit be94177, v0.2.14) is that Settings fields use the app keyboard, not the OS keyboard.

Fix as proposed by that reviewer: Extend IN_SCOPE to include '#azureKeyInput, #azureRegionInput, #openaiKeyInput, #googleKeyInput, #elevenlabsKeyInput, #testerNameInput, #placeholderEditor input'. Better, to stop it drifting again, replace the per-id key entries with a class: add class="key-input" (or reuse the existing `.key-row input`) and list '.key-row input' in IN_SCOPE.

</details>

<details><summary>Merged duplicate x-rules-01: On-screen keyboard does not serve five of the Settings key/region fields (Azure, OpenAI, Google, ElevenLabs, region, tester name)</summary>

The keyboard decides which fields it serves from a hard-coded selector list, IN_SCOPE. It names #apiKeyInput and #deepgramKeyInput but none of the speech-key fields added later (#azureKeyInput, #azureRegionInput, #openaiKeyInput, #googleKeyInput, #elevenlabsKeyInput), and it does not name #testerNameInput. In on-screen mode, applyInputMode() sets inputmode="none" only on in-scope fields, and the focusin handler calls show() only for isScoped() targets. So those fields keep their normal inputmode, the Windows or iPad system keyboard is summoned, and the app keyboard does not dock. CLAUDE.md records the opposite decision for Settings fields: the app keyboard serves them so the OS keyboard is suppressed (June 14 2026). This is the same 'listed by name, so a new service was forgotten' defect that CLAUDE.md records for the credential-row CSS (Rule 18b).

Fix as proposed by that reviewer: Stop listing key fields one by one. Add a shared class to every Settings credential and region input in index.html (for example class="key-input"; the region input already has class region-input) and to #testerNameInput. Replace '#apiKeyInput, #deepgramKeyInput' in IN_SCOPE with '.key-row input[type="text"], .region-input, #testerNameInput'. All five key rows already carry class key-row, and #apiKeyRow and #deepgramKeyRow are .key-row too, so that selector covers the existing two as well. Keep the rest of the list unchanged. A key field should not get the prediction ghost; if prediction is applied, add data-no-predict to the key inputs the way express-editor does for respellings.

</details>

<details><summary>Merged duplicate x-a11y-10: On-screen keyboard mode skips the newer Settings text fields, so they pop the system keyboard instead</summary>

IN_SCOPE lists only #apiKeyInput and #deepgramKeyInput among the credential fields; the fields added later (azureKeyInput, azureRegionInput, openaiKeyInput, googleKeyInput, elevenlabsKeyInput), #testerNameInput, and the Placeholders editor inputs (#placeholderEditor) are absent, so in 'onscreen' mode they keep inputmode='' (OS keyboard pops) and the app keyboard never shows. predictionOff likewise names only the two old key ids, contradicting its own comment that fields opt out with data-no-predict.

Fix as proposed by that reviewer: Add `#azureKeyInput, #azureRegionInput, #openaiKeyInput, #googleKeyInput, #elevenlabsKeyInput, #testerNameInput, #placeholderEditor input` to IN_SCOPE. Add `data-no-predict` to all six credential inputs and the region input in index.html, then simplify predictionOff to rely on the data attribute (keep the two id checks only if removing them is judged risky). In show(), extend the shift-off case (`field.id === 'apiKeyInput'`) to any field carrying data-no-predict so keys do not start with a capital.

</details>
