# CR-067: Loading a settings profile that came from another device applies its device-bound settings, bypassing the backup's hold-back rule

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** design-violation
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/storage.js:574`
- **Also affects:** `app/js/data-transfer.js:73-94 (OS_BOUND / SCREEN_BOUND)`; `app/js/data-transfer.js:304-319 (settingsForThisDevice used only for the package's current settings)`; `app/js/data-transfer.js:431-439 (profiles from another device written as files, unfiltered)`; `app/js/storage.js:617-633, 648-680 (export/import of profiles carry no device signature)`
- **Source:** x-contracts-08

**What a user notices.** After restoring a backup from a different device, loading one of its saved settings profiles brings over things that should stay with the old device - how the app hears, the keyboard type, full screen, and the keyguard edge margin - which can leave an iPad unable to hear anyone or move every keyguard opening.

**What is wrong.** Import deliberately holds back OS_BOUND (keyboardMode, sttProvider, fullscreen) and SCREEN_BOUND (appMarginPos) keys when the backup came from a different OS/screen, because those values would be WRONG on this device (e.g. 'use the browser's own listening' on an iPad Home Screen app hears nothing). But the same backup also writes every saved profile into settings/<name>.json untouched, and those files carry no device signature. applySettingsProfile then replaces every portable key with the profile's values, so the user's first 'Load' of an imported profile reintroduces exactly the values the import was designed to hold back. The import even marks the source device's active profile as current, inviting the Load.

**How it happens.** 1. On a Windows laptop (sttProvider 'builtin', appMarginPos for a tight case) save profile 'Home'. 2. Export a backup and import it on an iPad Home Screen app: current settings correctly hold back sttProvider/appMarginPos. 3. Settings -> profiles shows 'Home' (marked current); tap Load. 4. sttProvider becomes 'builtin' (browser listening, which delivers nothing in a Home Screen app) and the screen-edge margin of the laptop's case is applied.

**Suggested fix.** Stamp profiles with the device they were saved on and apply the same hold-back when loading: (1) in saveSettingsProfile add `device: platform.deviceSignature()` to the payload; (2) carry `device` through exportSettingsProfiles/importSettingsProfiles; (3) move OS_BOUND/SCREEN_BOUND into a module both storage.js and data-transfer.js can import (e.g. platform.js or a new device-bound.js) to avoid a circular import; (4) in applySettingsProfile, if payload.device exists and platform.compareDevice(payload.device, platform.deviceSignature()) says sameOs/sameScreen is false, keep the current value for those keys (as applyPackage does at data-transfer.js:420-423). A profile with no device field (older) should be treated as 'unknown device' - decide with Ken whether to hold back or apply.

> **Verifier correction to the fix (takes precedence):** Avoid a storage.js <-> data-transfer.js circular import by moving OS_BOUND/SCREEN_BOUND to platform.js or a small new module. Profiles already on disk have no device stamp; treat them as 'unknown' and ask Ken whether to hold back or apply (holding back on unknown would change same-device behavior for every existing profile, which conflicts with 'reproduce the profile exactly').

**How to verify the fix.** Add a test in tests/storage-transcript.test.mjs (it already drives profiles through a fake folder): save a profile with a fake foreign device signature and sttProvider 'builtin', set current sttProvider 'deepgram', apply the profile, assert sttProvider is still 'deepgram' and a non-bound key (e.g. colorScheme) changed.

**Do not break.** Profiles saved and loaded on the same device must keep their exact full-replace behavior (Ken's 'reproduce the profile exactly'). Do not touch PROFILE_EXCLUDE (secrets, testerName stay excluded).

**Design reference.** data-transfer.js header 'ONE FILE, FILTERED AT IMPORT' and OS_BOUND/SCREEN_BOUND notes; CLAUDE.md 'Profiles in a settings backup' (Ken, September 9 2026)

**Verification notes.** applyPackage filters OS_BOUND/SCREEN_BOUND keys only for the package's current settings (settingsForThisDevice, data-transfer.js:304-319, 410-423), then writes every profile via storage.importSettingsProfiles unfiltered (431) and marks the source's active profile current (437-438). applySettingsProfile (storage.js:574-596) replaces every non-excluded key with the profile's values and profile files carry no device signature, so loading an imported profile brings back sttProvider, keyboardMode, fullscreen and appMarginPos from the other device. No recorded decision addresses profiles crossing devices (the Sept 9 2026 note covers only including them in the backup). Trigger requires the user to tap Load on the imported profile, which the import invites by marking it current.
