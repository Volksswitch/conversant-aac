# CR-068: Azure hearing: one busy or server error switches listening off, a lost connection never does, and the helpful key-refusal message is never shown

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** design-violation
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/stt-azure.js:333`
- **Also affects:** `app/js/stt-azure.js:344`; `app/js/stt-azure.js:167`; `app/js/stt-azure.js:361`; `app/js/stt-rest.js:208`; `app/js/stt-rest.js:251`; `app/js/stt-azure.js:333 (merged duplicate: Azure hearing turns listening off after one server hiccup, yet never gives up when every phrase fails)`
- **Source:** stt-08, x-providers-05

**What a user notices.** With Azure, a single 'too busy' answer from Microsoft turns listening off in the middle of a conversation, while a connection that is completely down leaves the microphone lit and hearing nothing forever. When the key is refused, the error log just says 'http 401' instead of explaining that the service may have been deleted or the free trial ended.

**What is wrong.** The REST path (stt-rest.js) implements the September 30 2026 rule: a 401/403 is fatal immediately, any other failure is a 'warning' unless three in a row fail. Azure's live submit() does the opposite on both sides: (a) any non-OK HTTP status (including 429 and 5xx) is reported as 'error', which stt.js handleSourceError treats as fatal for the session; (b) a rejected fetch (offline, DNS, timeout) is always a 'warning' with no counter, so an Azure user with no connectivity listens forever and transcribes nothing - the 'worst failure' the rule exists to prevent. The live error text is `http ${res.status}` rather than describeFailure(), whose 401/403 wording (deleted service, canceled/lapsed subscription) was written specifically for Ken's September 19 trial but is only used by testKey(). Azure also lacks stt-rest's 250 ms speech floor, so clicks are submitted and billed.

**Evidence.**

```
stt-azure.js:333-335 `if (!res.ok) { if (onStatus) onStatus('error', `http ${res.status}`); return; }`
stt-azure.js:344-355 catch: `onStatus('warning', err && err.name === 'AbortError' ? ... : 'a phrase could not be sent');` (no counter)
stt-azure.js:167-184 describeFailure(...) used only at :239 in testKey
stt-rest.js:208-209 `const fatal = (err && (err.status === 401 || err.status === 403)) || failures >= FAILURES_BEFORE_FATAL;`
stt-rest.js:251 `if (openMs - HANG_MS < MIN_SPEECH_MS) { reset(); return; }`
```

**How it happens.** (a) Azure F0 tier throttles a burst (429): listening switches off mid-conversation with a red wash. (b) Tablet loses Wi-Fi: every phrase logs 'a phrase could not be sent' as a warning, the Listen button stays lit indefinitely, nothing is ever transcribed.

**Suggested fix.** Mirror stt-rest.js in stt-azure.js createSource(): add `let failures = 0;` reset in start(); in submit(), on success set `failures = 0`; on `!res.ok` or a caught error increment `failures` and compute `const fatal = res?.status === 401 || res?.status === 403 || failures >= 3;` report `onStatus('error', describeFailure(status, where))` when fatal (use the HTTP status when there is one, else a 'phrases could not be transcribed' message) and 'warning' otherwise. Add the same speech floor as stt-rest (`if (Math.max(0, now - openedAt) - HANG_MS < 250) { reset-span; return; }` in closeSpan before submitting, but not for the MAX_SPAN cut).

**How to verify the fix.** Extend tests/stt-azure.test.mjs with a fake fetch: one 429 then success -> statuses include 'warning', not 'error'; three rejected fetches -> third status is 'error'; a 401 -> 'error' whose detail contains 'deleted'.

**Do not break.** Keep NoMatch/InitialSilenceTimeout as non-errors (readRecognition). Keep 401/403 immediately fatal. The 'error' detail is written to the error log and weekly report, so do not include the key.

**Design reference.** CLAUDE.md 'HEARING COULD FAIL FOREVER IN SILENCE ...' (three-consecutive-failure rule) and 'A brief noise is no longer transcribed' (250 ms floor)

**Verification notes.** In stt-azure.js submit(), any non-OK HTTP status reports 'error' with `http ${status}`. stt.js handleSourceError treats that as fatal, so a single 429 or 5xx switches listening off. A rejected fetch is always a 'warning', with no counter, so a connection that is completely down listens forever. describeFailure() and its 401/403 text are used only in testKey. stt-rest.js implements the September 30 2026 rule (401/403 fatal at once, otherwise three in a row), and has the 250 ms floor, which Azure lacks. The Azure comment justifies only the transport-failure leniency, and does not make HTTP 429/5xx fatal on purpose. The two backends are inconsistent, and Azure has the 'listening forever, hearing nothing' failure that CLAUDE.md calls the worst one.
