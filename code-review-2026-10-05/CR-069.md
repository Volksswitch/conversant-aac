# CR-069: The background/foreground guard is never set up when the app starts on a paid hearing service

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** design-violation
- **Verdict:** confirmed (skeptic: confirmed; reproducer: reproduced)
- **Location:** `app/js/stt.js:443`
- **Also affects:** `app/js/stt.js:516`; `app/js/stt.js:519`; `app/js/platform.js:211`; `app/js/app.js:519`; `app/js/stt.js:443 (merged duplicate: The backgrounding guard is never registered when the app starts with a paid hearing service)`; `app/js/stt.js:443 (merged duplicate: The background/foreground guard is never registered when the app starts on a paid hearing service)`
- **Source:** stt-03, x-async-08, x-providers-02

**What a user notices.** On an Android tablet or an installed iPad using a paid hearing service, switching to another app and back can leave the app deaf or switch listening off with an error, with nothing done to bring it back - exactly the problem the guard was built to prevent.

**What is wrong.** init() returns at line 443 for any paid source, before `speechCfg = platform.speechConfig()` and before the visibility guard is registered (lines 516-541). The guard registers only from the browser branch. The comment inside the guard says it was extended to cover 'BOTH BACKENDS' because 'the configuration being recommended was the one configuration the guard did not cover', but when the app LAUNCHES with Deepgram/Azure/REST selected (app.js passes `source: usingPaidStt ? sttProvider : 'builtin'`) the listener is never added. It is only added if the app happened to start on the browser recognizer and the user later switched via setSource(). So the paid configurations recommended for Android and required for the iPad Home Screen app have no suspend/resume on backgrounding: the socket/AudioContext are suspended or killed by the OS, Deepgram closes the idle socket after ~10 s (KeepAlive timers are throttled in hidden pages), and the app comes back errored or silently deaf.

**Evidence.**

```
stt.js:413-443 `if (isPaidSource) { ... return; }`
stt.js:452 `speechCfg = platform.speechConfig();` (browser branch only)
stt.js:516 `if (speechCfg.guardVisibility && typeof document !== 'undefined' && !visibilityGuarded) {`
stt.js:519-530 comment: '⚠ BOTH BACKENDS. This used to test `recognition` alone, so with a paid backend selected ... the guard did nothing at all.' / `if (!recognition && !externalSource) return;`
platform.js:234 `return { continuous: true, restartDelayMs: 0, guardVisibility: true };`
```

**How it happens.** Android tablet, Azure selected and keyed; app launched (init runs with source 'azure'). Start listening, press Home for 20 s, return. No visibilitychange handler from stt.js runs suspendSource/openSource; the capture graph may come back suspended and nothing is heard while the button stays lit (or, for Deepgram, the socket closes and listening switches off with a 'closed (code ...)' error).

**Suggested fix.** Move the visibility-guard registration (the whole `if (speechCfg.guardVisibility && ... && !visibilityGuarded) { ... }` block) to a small function `registerVisibilityGuard()` and call it near the top of init(), before the `if (isPaidSource)` branch, after computing `speechCfg = platform.speechConfig();` (also move that line above the branch so paid sources read the same platform config). The listener already handles both `recognition` and `externalSource` via suspendSource()/openSource().

**How to verify the fix.** Add a test in tests/stt.test.mjs: init with `source: 'azure'` (using a fake Azure source or by injecting a fake getUserMedia), call startListening(), dispatch a 'visibilitychange' with document.hidden = true and assert the source's stop() ran; flip hidden to false, dispatch again and assert start() ran. Run the existing suite to confirm only one listener is ever registered after setSource() round trips.

**Do not break.** Keep the 'registered once per page' rule (visibilityGuarded flag) - CLAUDE.md records that a second listener would suspend and resume the microphone twice. Make sure suspendSource()'s stop() of a paid source does not clear listeningIntent (it doesn't today, but see the Deepgram onerror finding: a spurious 'error' during that stop would).

**Design reference.** app/js/platform.js speechConfig() comment 'guardVisibility — ON EVERYWHERE since August 31 2026'; CLAUDE.md 'Android — MEASURED' (backgrounding)

**Verification notes.** init() returns inside `if (isPaidSource)` before `speechCfg = platform.speechConfig()` and before the visibility-guard block. app.js calls stt.init with `source: usingPaidStt ? sttProvider : 'builtin'`, so launching with a paid key never registers the listener. It is registered only when init later runs through the browser branch (for example, starting on builtin and switching with setSource). The guard's own comment says it was meant to cover both backends, so this is not deliberate. What actually happens to a paid source while the app is in the background (a suspended AudioContext, or the socket closing and reporting an error) depends on the platform and was not measured. That is why severity is lowered to medium: the guard is missing for certain, but the exact symptom is uncertain.

**Reproduction (reproduced).** Method: Ran the real stt.js in node (scratchpad exp3.mjs) with a fake document capturing addEventListener, fake getUserMedia/AudioContext, and the Azure source. Two runs: (a) stt.init({source:'azure'}) as app.js:519 does when a paid service is selected at launch; (b) stt.init({source:'builtin'}) then stt.setSource('azure'). In each, startListening, then dispatched visibilitychange with document.hidden=true, then false. (a) launch on paid source: only 1 visibilitychange listener registered (the record-only one at stt.js:99-105, which just counts); tracks stopped on hide 0, streams reopened on return 0, statuses 'listening' only - no suspend/resume happens. (b) started on builtin then switched: 2 listeners; on hide 1 track stopped, on return 1 stream reopened, statuses stopped,listening,stopped,listening - the guard works. Cause confirmed: init() returns at stt.js:443 for a paid source before `speechCfg = platform.speechConfig()` (452) and before the guard block (516); speechCfg also stays at its module default `guardVisibility: false` (stt.js:17) in that case. platform.speechConfig() returns guardVisibility:true on every platform, and app.js:519 passes `source: usingPaidStt ? sttProvider : 'builtin'`, so a launch on a paid service never gets the guard.

<details><summary>Merged duplicate x-async-08: The backgrounding guard is never registered when the app starts with a paid hearing service</summary>

init() returns early from the paid-source branch (line 443) before speechCfg is set and before the visibility-guard block. The guard was explicitly widened to cover external sources (the `!recognition && !externalSource` check), and CLAUDE.md says the paid path 'can just as easily come back deaf', but with a paid source chosen at startup the listener is never added (and speechCfg keeps the default guardVisibility:false). It only appears if the user later switches to the free recognizer via setSource. The test only greps the source text, so it passes.

Fix as proposed by that reviewer: Move `speechCfg = platform.speechConfig();` and the whole visibility-guard registration block (lines 516-541) above the `if (isPaidSource) { ... return; }` branch in init(), so it runs for every source. Keep the `!visibilityGuarded` once-per-page flag.

</details>

<details><summary>Merged duplicate x-providers-02: The background/foreground guard is never registered when the app starts on a paid hearing service</summary>

stt.init() returns early for a paid source (line 443) before reaching the visibilitychange guard registration (lines 516-541) and before speechCfg is set from platform.speechConfig() (line 452). The guard's own comment says it was widened to cover 'BOTH BACKENDS' because the paid path on Android was left unguarded (Aug 31 2026), but the registration itself is still only reachable on the builtin path. So a session that starts on Deepgram/Azure/OpenAI/Google/ElevenLabs never gets suspendSource()/openSource() on hide/show. It only appears if setSource later switches to builtin (then remains registered). Verified with a Node harness: after init({source:'deepgram'}) the visibilitychange listener count stays at 1 (the stats-only listener); after setSource('builtin') it becomes 2.

Fix as proposed by that reviewer: In stt.init(), move `speechCfg = platform.speechConfig();` and the whole visibility-guard registration block (lines 516-541) above the `if (isPaidSource) {...}` branch (or extract it into a `registerVisibilityGuard()` function called at the top of init()). The listener body already handles both `recognition` and `externalSource`, so no change is needed inside it.

</details>
