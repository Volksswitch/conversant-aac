# CR-075: Loading a settings profile or restoring a backup can silently switch automatic reporting back on

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** privacy
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/storage.js:465`
- **Also affects:** `app/js/storage.js:574`; `app/js/storage.js:592`; `app/js/storage.js:733`; `app/js/storage.js:2528`; `app/js/data-transfer.js:424`; `app/js/app.js:442`; `app/js/storage.js:465 (merged duplicate: Restoring a backup or loading a profile can switch automatic usage reporting back on)`
- **Source:** x-security-06, storage-10

**What a user notices.** Someone who turned off the weekly report can have it quietly turned back on, and their usage information sent again, just by loading one of their older settings profiles or restoring a backup someone gave them.

**What is wrong.** weeklySendEnabled (the user's consent to automatic reporting, which also gates on-device event counting) is not in PROFILE_EXCLUDE, so it travels in settings profiles and backups. applySettingsProfile() and applyPortableSettings() REPLACE the whole portable bundle rather than merging; a key absent from the incoming bundle is dropped, and loadWeeklySendEnabled() defaults an absent value to true. So loading any profile saved before the user touched the reporting switch, or importing a backup from another device/person where it was never set, resets this device's choice to ON; importing a backup from someone who had it on also turns it on. No message mentions it. The decision record says the public release must be opt-in and the switch is the user's consent, which should belong to this device's user rather than travel with layout settings.

**Evidence.**

```
app/js/storage.js:465  const PROFILE_EXCLUDE = [...SECRET_KEYS, 'usageInputTokens', ..., 'testerName', 'weeklySendLastAt', 'weeklyInfoHash', 'weeklyEndpoint', 'weeklyErrorMark'];   (no 'weeklySendEnabled')
app/js/storage.js:592-594  for (const k of Object.keys(incoming)) { if (!PROFILE_EXCLUDE.includes(k)) merged[k] = incoming[k]; }  then saveSettings(merged)
app/js/storage.js:2528  export function loadWeeklySendEnabled() { return loadSettings().weeklySendEnabled ?? true; }
app/js/app.js:442  metrics.setEnabled(storage.loadWeeklySendEnabled());
```

**How it happens.** 1. Save a settings profile 'Home' (never having touched the reporting checkbox). 2. Later, Troubleshooting > uncheck automatic weekly reports. 3. Load the 'Home' profile (app reloads). 4. loadWeeklySendEnabled() returns true; counting resumes and the next Start sends a weekly report.

**Suggested fix.** Add 'weeklySendEnabled' to PROFILE_EXCLUDE in storage.js (line 465) so it is neither exported in profiles/backups nor replaced on load/import - the same treatment as testerName and installId. Add a one-line comment saying it is this device user's consent. Consider the same for 'noSaveDefault' only if Ken agrees (it is a privacy default that a stale profile also resets to 'save').

> **Verifier correction to the fix (takes precedence):** Adding 'weeklySendEnabled' to PROFILE_EXCLUDE is right, but note that PROFILE_EXCLUDE also drives the 'unsaved changes' comparison and exportSettingsBundle, so the switch will also stop appearing in profile diffs - acceptable. Check whether reportableSettings() (problem report) relies on PROFILE_EXCLUDE; if so the switch's state would disappear from reports, which may be worth keeping visible.

**How to verify the fix.** Add a test to tests/storage-transcript.test.mjs (which already drives the real profile writer/reader): set weeklySendEnabled false, save a profile, assert the profile file has no weeklySendEnabled key; then write a profile file lacking the key, applySettingsProfile it, and assert loadWeeklySendEnabled() is still false. Repeat with applyPortableSettings({}).

**Do not break.** Keep the switch's default (ON during beta) unchanged for a device that never set it. Do not touch SECRET_KEYS (that list is also used for redaction). The 'What is in a weekly report' disclosure test compares PAYLOAD_FIELDS keys and is unaffected.

**Design reference.** CLAUDE.md 'DEFAULT-ON IS A BETA ARRANGEMENT AND MUST BE REVERSED FOR PUBLIC RELEASE'; the testerName PROFILE_EXCLUDE decision (September 4 2026)

**Verification notes.** PROFILE_EXCLUDE (storage.js:465) does not contain 'weeklySendEnabled'. applySettingsProfile (574-597) and applyPortableSettings (733-743) rebuild settings from the excluded keys plus the incoming bundle, so a key absent from the incoming bundle is dropped, and loadWeeklySendEnabled() returns `?? true`. Loading a profile saved before the switch was ever touched, or importing a backup that lacks the key or has it on, turns automatic reporting back on with no message. CLAUDE.md treats testerName/installId as device-local for exactly this class of reason and calls the switch the user's consent; nothing records weeklySendEnabled travelling as intended.
