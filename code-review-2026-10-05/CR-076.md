# CR-076: "Don't save this conversation" does not stop the app recording which card was chosen afterwards

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** privacy
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/storage.js:2338`
- **Also affects:** `app/js/app.js:2981 (noteUserAction -> finalizeOffer with selectedIndex)`; `app/js/app.js:402-405 (handlePrivacyToggle)`; `app/js/storage.js:2470 (flushLog has no gate)`
- **Source:** storage-03

**What a user notices.** If a person sees the suggestion cards, decides the conversation is getting private, taps "Don't save this conversation" and then taps a card, the saved file still records which card they picked - and the card's words are already in the file, so what they said after going private can be read back.

**What is wrong.** Every conversation writer checks `conversationSaving` except finalizeOffer(). The offer entry (with all card texts) is written while saving is on; when the user then turns privacy on and taps a card, noteUserAction() calls finalizeOffer({ outcome: 'card', selectedIndex, shownMs }), which mutates the entry and calls flushLog(), writing selectedIndex to disk. The same happens for outcome 'composer', 'express', 'regenerate', etc. The User Manual (section 4.5) promises: 'Anything written before you pressed it stays in your data folder, and from that moment nothing more is added.'

**Evidence.**

```
app/js/storage.js:2338-2345:
  export async function finalizeOffer({ outcome, selectedIndex = null, shownMs = null }) {
      if (!pendingOffer) return;
      const entry = pendingOffer;
      pendingOffer = null;
      entry.outcome = outcome || 'superseded';
      if (selectedIndex !== null && selectedIndex !== undefined) entry.selectedIndex = selectedIndex;
      ...
      await flushLog();
Compare app/js/storage.js:2308: if (!conversationSaving) return null;   // logOffer is gated
```

**How it happens.** 1) Saved conversation, AI cards shown (offer written with all four texts). 2) Tap the Command Bar 'Don't save this conversation'. 3) Tap card 2. 4) conversations/<id>.json now shows that offer with outcome 'card' and selectedIndex 2, revealing the reply spoken while private.

**Suggested fix.** At the top of finalizeOffer add `if (!conversationSaving) { pendingOffer = null; return; }` so a set that ends while the conversation is private is closed in memory but nothing is written. Optionally also make setConversationSaving(false) clear pendingOffer.

> **Verifier correction to the fix (takes precedence):** Gating finalizeOffer is right. Also make setConversationSaving(false) drop pendingOffer (pendingOffer = null) so hasPendingOffer() stops reporting a set that can no longer be recorded; otherwise showPalette and clearPalette keep calling finalizeOffer for nothing.

**How to verify the fix.** Add to tests/storage-transcript.test.mjs: startConversationLog, logOffer({options:[a,b]}), setConversationSaving(false), await finalizeOffer({outcome:'card', selectedIndex:1}); read the file and assert the offer's outcome is still null and selectedIndex null.

**Do not break.** Do not change behavior for saved conversations; hasPendingOffer() callers in app.js must keep working (they will simply see no pending offer).

**Design reference.** User Manual section 4.5 'Keeping a Conversation Private'; CLAUDE.md 'Conversation privacy' (log functions no-op when saving is off)

**Verification notes.** Every conversation writer is gated on conversationSaving except finalizeOffer (storage.js:2338), which mutates the pending offer entry and calls flushLog, and flushLog has no gate. handlePrivacyToggle (app.js:402) only calls setConversationSaving and does not clear pendingOffer, so tapping a card after going private makes noteUserAction (app.js:2981) write outcome 'card' and selectedIndex into the saved file, alongside the card texts already written. The User Manual section 4.5 says nothing more is added after the button is pressed. No other in-memory entry is added while private, so the leak is limited to outcome/selectedIndex/shownMs, which still reveals which reply was spoken.
