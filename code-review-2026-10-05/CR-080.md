# CR-080: Switching from one sound button to another clears the new clip's record: it can't be stopped, End conversation can't stop it, and the microphone reopens while it plays

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** race-condition
- **Verdict:** confirmed (skeptic: confirmed; reproducer: reproduced)
- **Location:** `app/js/app.js:5270`
- **Also affects:** `app/js/app.js:5232-5241 (handlePlayAudioItem stops A then synchronously starts B)`; `app/js/app.js:5225-5230 (stopExpressAudio resolves A's `ended` promise)`; `app/js/app.js:5258 (audioPlayer = B)`; `app/js/app.js:5277-5323 (playAudioTurn for A reopens listening with A's wasListening)`; `app/js/app.js:2760 (terminateConversation relies on audioPlayer to stop a clip)`; `app/js/app.js:5237 (merged duplicate: Switching from one sound button to another un-mutes the microphone while the second sound plays)`
- **Source:** x-async-03, app-e-01

**What a user notices.** If the user plays one sound and then taps a different sound button, the second sound's button does not show it playing, tapping it again starts it a second time on top of itself, ending the conversation does not stop it, and the microphone turns back on so the sound is written down as the other person talking and the AI answers it.

**What is wrong.** handlePlayAudioItem calls stopExpressAudio() (which resolves clip A's `ended` promise) and then synchronously calls playAudioTurn(B), whose playClip sets `audioPlayer = B` before its first await. A's continuation then runs as a microtask: it computes `aborted` from `audioPlayer` (now B), then sets `audioPlayer = null` and `speakingUserStatement = false` and redraws - destroying B's record. A's playAudioTurn then commits A's turn and, because A's `wasListening` was true, calls startFreshListening() while B is still playing. Reproduced with a faithful simulation in the scratchpad (clip-race.mjs): 'clip A done; clearing audioPlayer which is B' / 'after switching to B, audioPlayer = null'.

**Evidence.**

```
app.js:5236-5240 `if (audioPlayer && audioPlayer.item.id === item.id) { stopExpressAudio(); return; }
    if (audioPlayer) stopExpressAudio();
    if (!item.file) return;
    resetExpressPaging();
    playAudioTurn(item);`
app.js:5269-5273 `const stopped = await ended;
    const aborted = !!(audioPlayer && audioPlayer.aborted);
    audioPlayer = null;
    speakingUserStatement = false;
    renderExpressPanel();`
app.js:5315 `if (wasListening) { startFreshListening(); return; }`
```

**How it happens.** Listening on. Tap sound button A (mic mutes, clip plays). Before it ends, tap sound button B. B starts; A's continuation sets audioPlayer=null, commits A's turn, and restarts listening (A's wasListening=true) while B plays -> B is transcribed as partner speech and generateOptions runs on it. Tapping B now calls playAudioTurn(B) again (audioPlayer is null), layering a second copy. Pressing End conversation: stopExpressAudio() returns early (audioPlayer null) so B keeps playing, and when B ends its playAudioTurn commits B's turn into the next conversation (aborted is false).

> **Verifier correction to the trigger:** Only happens when B's clip is already primed (no await before audioPlayer=B); if B must be read from disk first, A's continuation runs before B registers and the race does not occur.

**Suggested fix.** In playClip, keep a local reference and only clear state that still belongs to this clip:
```js
const mine = { item, el, finish };
audioPlayer = mine;
...
} catch (err) {
    if (audioPlayer === mine) { audioPlayer = null; speakingUserStatement = false; }
    renderExpressPanel();
    return { played: false, why: ... };
}
const stopped = await ended;
const aborted = !!mine.aborted;
const replaced = !!mine.replaced;
if (audioPlayer === mine) { audioPlayer = null; speakingUserStatement = false; }
renderExpressPanel();
return { played: true, stopped: !!stopped, aborted, replaced };
```
In handlePlayAudioItem, before stopping the old clip when switching, mark it and hand its listening state on: `if (audioPlayer) { audioPlayer.replaced = true; pendingUnmute = pendingUnmute || audioPlayer.wasListening; stopExpressAudio(); }` (store `wasListening` on the audioPlayer record in playAudioTurn, and have the new playAudioTurn use `wasListening = isListening || pendingUnmute` then clear pendingUnmute). In playAudioTurn, when `result.replaced` is true, commit the turn but return before any listening is restored.

**How to verify the fix.** Add a test (tests/express-audio.test.mjs or a new tests/app-audio-race.test.mjs at source level if app.js cannot be imported) asserting playClip only nulls audioPlayer when it still equals its own record. Manually: with listening on, play sound A, then tap sound B; confirm B's button shows playing, a second tap on B stops it, the Listen button stays off until B ends, and End conversation silences B.

**Do not break.** Nothing in the tap path may await before el.play() (iPad gesture rule recorded in CLAUDE.md 'SOUND buttons'). Keep the abort behavior: a clip ended by End conversation must not be recorded.

**Design reference.** CLAUDE.md 'SOUND buttons on the Express Panel (DECIDED + BUILT Ken, September 14 2026)' - a tap MUTES the microphone, a second tap stops it, ending a conversation under a playing clip drops the turn

**Verification notes.** Traced: handlePlayAudioItem calls stopExpressAudio() which resolves A's `ended` promise (queued microtask), then synchronously calls playAudioTurn(B); with the clip primed (the normal case) playClip(B) reaches `audioPlayer = B; speakingUserStatement = true` before its first await. A's continuation then runs, reads aborted from B's record, nulls audioPlayer and clears speakingUserStatement, and A's playAudioTurn commits and calls startFreshListening() (A's wasListening was true; B's is false because A already muted). Result: B unstoppable by a second tap, not stopped by terminateConversation (stopExpressAudio returns early), mic reopened during B. Narrow trigger (switching between sound buttons), so medium.

**Reproduction (reproduced).** Method: Wrote a faithful node simulation (scratchpad/repro-x-async/clip.mjs). It copies the control flow of app.js 5225-5323 (stopExpressAudio, handlePlayAudioItem, playClip, playAudioTurn) verbatim, with a fake Audio whose play() resolves at once, a URL cache already holding both clips (as the render-time preload normally does), and logging stubs for stt/startFreshListening/commit. I checked the result against a line-by-line trace of the real code, including terminateConversation at 2760. Output: 'mic off', 'play blob:a', then on tapping B: 'pause blob:a', 'mic off', 'play blob:b', 'clip A done; clearing audioPlayer which is B', 'commit turn for A (stopped=true)', 'MIC ON (startFreshListening) while audioPlayer=null'. State after the switch: audioPlayer=null, speakingUserStatement=false, isListening=true, and B still playing (it is never paused). End conversation's stopExpressAudio({abort:true}) returned early (audioPlayer is null), so B kept playing. Tapping B again called playAudioTurn(B) a second time ('play blob:b' again), layering a second copy. Mechanism: stopExpressAudio() calls A.finish(true), which resolves A's `ended` promise. handlePlayAudioItem then synchronously calls playAudioTurn(B), and playClip(B) sets audioPlayer = B (5258) before awaiting el.play(). A's continuation (5269-5273) then sets audioPlayer = null and speakingUserStatement = false, discarding B's record, and A's playAudioTurn calls startFreshListening() at 5315 because A's wasListening was true. The race needs B's blob URL to be cached already, so that nothing awaits before 5258. That is the normal case, because clips are read into memory when the panel is drawn.

<details><summary>Merged duplicate app-e-01: Switching from one sound button to another un-mutes the microphone while the second sound plays</summary>

handlePlayAudioItem stops the current clip with stopExpressAudio() and then synchronously starts playAudioTurn(newItem). stopExpressAudio() calls audioPlayer.finish(true), which resolves the FIRST playClip's `ended` promise; its continuation runs as a microtask AFTER the second playClip has already set `audioPlayer` to the new clip (when the clip is cached, nothing is awaited before `audioPlayer = { item, el, finish }`). The first continuation then executes `audioPlayer = null; speakingUserStatement = false;`, wiping the SECOND clip's player record and lifting the placeholder gate while clip 2 plays. Then the first playAudioTurn continues: it commits its turn and, because it captured wasListening=true before the mute, calls startFreshListening() - reopening the microphone during clip 2. Clip 2's playAudioTurn had captured wasListening=false (the first clip had already muted). It also captured raw=heardPartnerText() before startFreshListening reset the recognizer, so when clip 2 ends commitExchange(raw, ...) commits the same partner text a second time. Confirmed with a node simulation of the exact promise structure: log shows 'set A', 'set B', 'clip A ended; clearing audioPlayer which is B', 'turn A restores mic', final audioPlayer=null while B is still playing.

Fix as proposed by that reviewer: Make each playClip own only its own player record and serialize the hand-over. (a) In playClip, keep a local reference `const me = { item, el, finish }; audioPlayer = me;` and after `await ended` only clear shared state if it is still ours: `const aborted = !!me.aborted; if (audioPlayer === me) { audioPlayer = null; speakingUserStatement = false; renderExpressPanel(); }`. Do the same in the play() catch branch. (b) In handlePlayAudioItem, when switching clips, mark the outgoing player as superseded (e.g. `audioPlayer.superseded = true` inside stopExpressAudio when called for a switch) and have playAudioTurn skip the listening restore (and the `wasListening` restart) when its clip was superseded, so only the LAST clip's turn decides whether listening comes back; the new clip's playAudioTurn should inherit the original wasListening (pass it through, e.g. store `audioPlayer.wasListening` and read it when switching). (c) Capture `raw` once: when superseding, clear currentPartnerText / call stt.resetTranscript() after the first turn commits, or pass raw='' to the second clip's commit, so the partner turn is not committed twice.
