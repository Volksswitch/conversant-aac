# CR-081: Problem report can be built, confirmed and sent twice when Send (or the launch-screen report button) is tapped again while it is being assembled

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** race-condition
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:6400`
- **Also affects:** `app/js/app.js:6313`; `app/js/app.js:7088`; `app/js/app.js:610`; `app/js/app.js:6211`; `app/js/confirm-dialog.js:93`
- **Source:** g-misc-overflow-02

**What a user notices.** If a tester taps Send twice because the app seems slow, two identical confirmation boxes stack up. Confirming both sends the report twice; confirming one and dismissing the other leaves a message saying nothing was sent when in fact it was.

**What is wrong.** Neither sendProblemReport() nor sendProblemReportFromStart() has an in-progress guard or disables its button. Both first await buildProblemReportText(), which awaits storage.listConversationLogs() (reads every saved conversation) plus buildErrorReport() (reads conversation files) - seconds on an Android tablet with many conversations. Taps inside Settings are exempt from the two-tap safeguard, so a quick second tap starts a second build. Each build then calls confirmDanger(), which appends a new modal <dialog> every time; two dialogs stack. The page is only inert once the first dialog is shown, so the window is exactly the build time. Outcomes: both confirmed -> two enqueued problem payloads (duplicate Sheet rows and duplicate alert e-mails); one confirmed and the other cancelled -> the later setProblemReportStatus('Not sent. Nothing has left this device.') overwrites 'Sent and received', which is false. Contrast the backup paths, which carry importInProgress/exportInProgress flags for this exact reason.

**How it happens.** 1. Android tablet with ~200 saved conversations. 2. Settings > Troubleshooting, type a note, tap Send; nothing visible happens for a few seconds, so tap Send again. 3. Two 'Send this report?' cards appear one over the other. 4. Tap 'Send it' on the top one -> status 'Sent and received'. 5. The second card is still there; tap 'Not yet' -> status now reads 'Not sent. Nothing has left this device.' although the report was sent. Or tap 'Send it' again -> the report arrives twice and Ken gets two alert e-mails.

**Suggested fix.** Add one module-level flag shared by both senders, next to importInProgress: `let problemReportInProgress = false;`. At the top of sendProblemReport() and sendProblemReportFromStart(): `if (problemReportInProgress) return; problemReportInProgress = true;` and wrap the remainder of each function body in try { ... } finally { problemReportInProgress = false; }. Also set setProblemReportStatus('Preparing the report...') (Settings path) / the button's own say('Preparing the report...') (launch path) before the build so the first tap visibly did something.

> **Verifier correction to the fix (takes precedence):** Fix is right. Put the guard before the build (the window is the build), release it in finally on every exit, and check that the launch-screen button's say() restore timer still works when a second tap is ignored.

**How to verify the fix.** Manual: with many saved conversations (or throttle with a debugger breakpoint in buildUsageText), double-tap Send; exactly one confirmation card must appear, and only one row must arrive in the Sheet. Repeat on the launch-screen 'If something is wrong - send a report' button. Check the status line never reads 'Not sent' after a successful send.

**Do not break.** Do not collapse the see-then-confirm into one tap (standing rule in the comments at app.js:6390-6394). The flag must be released in a finally, including when the user cancels or the build throws, or the button goes dead for the session.

**Design reference.** CLAUDE.md, 'Beta instrumentation and error reporting' (report is previewed then confirmed, two steps); app.js:6460-6466 (one-import-at-a-time guard as the established pattern)

**Verification notes.** Neither sendProblemReport (6400) nor sendProblemReportFromStart (6313) has an in-progress flag, and neither disables its button. Both await buildProblemReportText, which awaits storage.listConversationLogs (reads every file) and buildErrorReport, so there is a real window before the first dialog makes the page inert. confirmDanger (confirm-dialog.js:93-94) creates and showModal()s a new dialog per call, so a second build that resolves later stacks a second card on top. Both outcomes follow: two enqueued payloads, or a 'Not sent. Nothing has left this device.' status overwriting a successful send. The importInProgress/exportInProgress precedent (6466-6467) exists for this reason on the backup path.
