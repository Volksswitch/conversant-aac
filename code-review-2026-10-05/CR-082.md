# CR-082: The "cannot be dismissed" busy and restart modals can be closed by pressing Escape (or Android Back) twice

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** race-condition
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/confirm-dialog.js:146`
- **Also affects:** `app/js/confirm-dialog.js:194`; `app/js/confirm-dialog.js:151`
- **Source:** ui-shell-02

**What a user notices.** During a slow restore, pressing Back or Escape twice can make the 'please wait' box disappear, letting the person press Restore again - which is exactly how a restore ends up importing nothing. The 'the app will now restart' box can vanish the same way, leaving the app running on data it has already replaced.

**What is wrong.** showBusy and showNotice try to make the dialog undismissable only by calling preventDefault() on the 'cancel' event. In current Chromium (dialog close-watcher integration) a cancel event is only cancelable when there has been user activation since the previous close request; a second Escape / Android system Back with no intervening tap fires a non-cancelable cancel (or none) and the dialog closes. Nothing listens for 'close', so showBusy's `open` flag stays true while the dialog is gone (the panel behind becomes live again), and showNotice's promise never resolves because the only path to resolve() is the button that is no longer on screen. The code comments state these dialogs exist precisely to make a second Restore press impossible.

**Evidence.**

```
confirm-dialog.js:146-148
    const block = (e) => e.preventDefault();
    dlg.addEventListener('cancel', block);          // Escape
    dlg.addEventListener('click', block);           // backdrop
confirm-dialog.js:191-195
        // Escape and the backdrop do NOT dismiss: there is one way on from here, and
        // it is the button. ...
        dlg.addEventListener('cancel', (e) => e.preventDefault());
```

**How it happens.** On an Android tablet (or a computer with a keyboard) start Settings > General > Restore selected backup with a large backup. While 'Please wait' shows, press the system Back gesture (or Escape) twice. The modal closes while the import is still running; the Restore button is reachable and pressable again, starting a second import racing the first.

**Suggested fix.** In showBusy: after creating the dialog call `dlg.setAttribute('closedby', 'none');` (Chromium honors it and then ignores Escape/Back entirely) AND add a fallback for browsers without it: `dlg.addEventListener('close', () => { if (open) { try { dlg.showModal(); } catch { /* removed */ } } });`. In showNotice do the same: `dlg.setAttribute('closedby', 'none');` and `dlg.addEventListener('close', () => { if (!settled) { try { dlg.showModal(); } catch { } } });`. Leave confirmDanger alone - there an Escape correctly resolves false.

> **Verifier correction to the fix (takes precedence):** closedby="none" alone was verified to work in Chromium; keep the re-showModal 'close' fallback for engines without it, guarded by `open`/`settled` as described. Note the iPad (WebKit, no Escape key) is not the exposed platform; Windows with a keyboard and Android's system Back are.

**How to verify the fix.** Manual, desktop Chrome: run a restore of a large backup (or temporarily wrap a long await in showBusy from the console), press Escape twice quickly - the modal must stay. Repeat for showNotice: Escape twice must leave the OK button showing, and pressing it must still resolve. Repeat with Android Chrome using the system Back gesture.

**Do not break.** Every caller closes showBusy in a finally; the re-open must check `open` so close() itself (which sets open=false first) does not trigger a re-open. Do not change confirmDanger's cancel-means-false behavior.

**Design reference.** Comment block in confirm-dialog.js (Ken, September 9 2026: busy modal exists so a second Restore press is impossible)

**Verification notes.** Reproduced in the Browser pane (Chrome 152): a modal dialog whose cancel listener calls preventDefault logged 'cancel cancelable=true' on the first Escape, then 'cancel cancelable=false' and 'close' on the second, and d.open became false. showBusy and showNotice rely only on preventDefault of 'cancel' and listen for nothing on 'close', so showBusy's `open` stays true with the dialog gone and showNotice's promise never resolves. Also verified the fix: with closedby="none" set on the dialog, two Escapes fire no cancel event at all and the dialog stays open. Callers are app.js:6502, 6538, 6633, 6661 (restore/import).
