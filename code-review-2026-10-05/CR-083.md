# CR-083: A paid hearing service started twice, or stopped while it is still opening the microphone, leaves a microphone, AudioContext and socket running that nothing owns

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** race-condition
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/stt-deepgram.js:264`
- **Also affects:** `app/js/stt-deepgram.js:357-358 (stop() returns early when !running)`; `app/js/stt-azure.js:420-434, 476-477`; `app/js/stt-rest.js:300-305, 327-328`; `app/js/stt.js:678-687 (openSource fires start() without awaiting)`; `app/js/app.js:1665-1692 (toggleListening relies on isListening, which for Deepgram only turns true on ws.onopen)`; `app/js/stt-deepgram.js:249 (merged duplicate: Paid hearing services can be started twice at once, leaking a live microphone and sending every sound twice)`; `app/js/stt-deepgram.js:249 (merged duplicate: Paid hearing sources can open two microphones, or open one after listening was stopped, because start() has no in-progress guard)`
- **Source:** x-async-04, stt-01, x-providers-04

**What a user notices.** If the user taps Listen twice quickly, or taps it on then off while the paid service is still connecting, the microphone can stay on after the app says listening is off, or the same audio is sent twice and billed twice with a garbled transcript.

**What is wrong.** Each paid source's start() awaits getUserMedia (and AudioContext.resume) with `running` still false. (a) stop() during that window hits `if (!running) return;` and does nothing; start() then resumes, builds the graph and socket and sets running=true, and for Deepgram ws.onopen reports 'listening', so capture runs after the user turned it off. (b) A second start() during the window (isListening stays false until ws.onopen for Deepgram, so a second Listen tap takes the start branch again) runs a second getUserMedia; the module variables stream/audioCtx/processor/ws are overwritten, the first stream and AudioContext are never stopped or closed, and the first processor keeps calling handleFrame, which sends via the module-level `ws` (now the second socket), so every frame is uploaded twice.

**Evidence.**

```
stt-deepgram.js:249-265 `async start() { if (running) {...} ... stream = await navigator.mediaDevices.getUserMedia({...});`
stt-deepgram.js:357-358 `stop() { if (!running) return;`
stt-deepgram.js:353 `running = true;` (set only after all awaits)
stt-deepgram.js:338-341 `processor.onaudioprocess = (e) => { if (!running) return; handleFrame(...); };` and send() uses the shared `ws`.
Same shape: stt-azure.js:421 / 468 / 477, stt-rest.js:301 / 317 / 328.
```

**How it happens.** First Listen of a session on an iPad (permission prompt shows, or getUserMedia takes ~1 s). User taps Listen, sees nothing happen, taps again: two start() calls both pass `if (running)`, two microphones and two sockets open, audio is sent twice. Or: user taps Listen then immediately taps a response card (handleResponseSelected -> stt.stopListening -> stop() no-op); a second later the source comes up and the button turns red with the mic live.

**Suggested fix.** In each of the three sources add `let starting = false; let wanted = false;`. In start(): `if (running || starting) { if (running && onStatus) onStatus('listening'); return true; } wanted = true; starting = true; try { ... } finally { starting = false; }` and after EACH await check `if (!wanted) { stream && stream.getTracks().forEach(t => t.stop()); stream = null; if (audioCtx) { try { audioCtx.close(); } catch {} audioCtx = null; } return false; }`. In stop(): set `wanted = false;` as the first line, before the `if (!running) return;` early exit, so a stop during start is honored.

**How to verify the fix.** Add tests to tests/stt-deepgram.test.mjs (or the existing per-source test file) with a getUserMedia stub that resolves on demand: call start(), call stop() before resolving, resolve, and assert the stub track's stop() was called and onStatus never reported 'listening'; call start() twice before resolving and assert getUserMedia was called once.

**Do not break.** Keep the 're-report listening when already running' behavior (it fixed Ken's drifted button). Do not add any await before getUserMedia that would change gesture timing.

**Design reference.** CLAUDE.md 'Paid speech-to-text - Deepgram' and the August 3 2026 Listen-button notes (WHY THIS IS A WHITELIST)

**Verification notes.** In all three paid sources `running` is set only after the getUserMedia/resume awaits, and stop() returns immediately when !running (stt-deepgram.js:357-358, stt-azure.js:476-477, stt-rest.js:327-328). stt.stopListening during that window clears listeningIntent but the source still comes up and reports 'listening' (Azure/REST at end of start, Deepgram in ws.onopen), which handleSttStatus honors. toggleListening has no in-progress guard and isListening stays false until the source reports, so a second tap re-enters start() and runs a second getUserMedia, orphaning the first stream/context/processor whose handleFrame sends through the shared module-level ws/span. The window is the getUserMedia time, which includes a first-use permission prompt, so it is reachable.

<details><summary>Merged duplicate stt-01: Paid hearing services can be started twice at once, leaking a live microphone and sending every sound twice</summary>

All three paid capture sources guard re-entry with `if (running)`, but `running` is only set to true at the END of start(), after `await navigator.mediaDevices.getUserMedia(...)` (and, for Deepgram/Azure, `await audioCtx.resume()`). A second start() during that window passes the guard and acquires a second MediaStream, AudioContext, ScriptProcessorNode and (Deepgram) WebSocket, overwriting the closure variables. The first processor's onaudioprocess keeps running (it only checks `running`, which becomes true) and feeds the SAME gate/ws/span as the second, so every frame is processed twice: Deepgram receives interleaved duplicate audio at what it believes is the native rate, Azure/REST spans contain each frame twice (half-speed audio). stop() only tears down the second set; the first MediaStream track is never stopped (mic indicator stays on) and the first AudioContext is never closed. For Deepgram the first socket receives no audio or KeepAlive, so the server closes it ~10 s later and its onclose (running is true) reports an error that switches listening off. The mirror case: stop() during the pending start sees `running === false` and returns, then start() resumes and opens the mic after the user stopped; via setSource() the old source object is dropped while still starting, so the resulting capture is orphaned with no way to stop it and its onText still feeds stt.js's shared core. Realistic trigger: the Listen button deliberately does not light until the Deepgram socket opens (stt-deepgram.js:318-326), so a user who sees no response taps again, which takes the start branch again (isListening is still false).

Fix as proposed by that reviewer: In each of the three createSource() factories add a start token: `let startToken = 0; let starting = false;`. At the top of start(): `if (running || starting) { if (onStatus) onStatus('listening'); return true; }` then `starting = true; const mine = ++startToken;`. After EVERY await inside start() (getUserMedia, audioCtx.resume) add `if (mine !== startToken) { release(); starting = false; return false; }` where release() stops the just-acquired stream's tracks and closes the just-created AudioContext. Set `starting = false` wherever start() returns (success or failure; use try/finally). In stop(): if `starting` is true, do `startToken++; starting = false;` (cancels the in-flight start) and emit the stop status, before the existing `if (!running) return;`.

</details>

<details><summary>Merged duplicate x-providers-04: Paid hearing sources can open two microphones, or open one after listening was stopped, because start() has no in-progress guard</summary>

All three paid sources set `running = true` only after awaiting getUserMedia (and, for Deepgram/Azure, audioCtx.resume()). Until then, start() can be entered again (the `if (running)` guard does not fire) and stop() is a no-op (`if (!running) return`). stt.openSource calls externalSource.start() without awaiting, and app.js keeps isListening false until the source reports 'listening', so a second Listen tap takes the start branch again. Consequences: (a) two concurrent starts overwrite stream/audioCtx/processor/ws; the first set is never stopped - its microphone track stays live and, on Deepgram, its keepalive interval and socket leak; the leaked socket's onclose can later fire `running && onStatus('error', 'closed ...')`, killing a later listening session. (b) Stop during start: stop() returns, then start() finishes, opens the mic and reports 'listening', so the button lights with listeningIntent false and audio is captured into the next turn. stt.setSource() relies on the same stop() and has the same hole.

Fix as proposed by that reviewer: In each of the three createSource factories add `let starting = null;` and a `let cancelled = false;` token. In start(): `if (running) {...re-report...} if (starting) return starting; cancelled = false; starting = (async () => { ...existing body...; after each await: if (cancelled) { release stream/audioCtx; return false; } ... })().finally(() => { starting = null; }); return starting;`. In stop(): `if (!running) { if (starting) cancelled = true; return; }`. Releasing means stopping stream tracks and closing audioCtx exactly as stop() does.

</details>
