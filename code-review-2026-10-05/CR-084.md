# CR-084: Every Settings open adds another copy of the key-field and Azure listeners, multiplying saves and network fetches per keystroke

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** resource-leak
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:972`
- **Also affects:** `app/js/app.js:7281 (wireKeyField for apiKeyInput, called inside openSettings)`; `app/js/app.js:7346 (wireKeyField for deepgramKeyInput)`; `app/js/app.js:7429 (wireKeyField for azureKeyInput)`; `app/js/app.js:7917 (wireKeyField for each catalog key, inside the per-service loop)`; `app/js/app.js:7459 (azureKeyInput.addEventListener('input', reflectAzureTestAvailability))`; `app/js/app.js:7462 (azureRegionInput.addEventListener('input', ...))`; `app/js/app.js:7473 (azureRegionInput.addEventListener('blur', ...))`; `app/js/app.js:7934-7937 (catalog Paste saves and refetches a second time after setKeyFieldValue already did)`; `app/js/app.js:972 (merged duplicate: Key-field listeners pile up every time Settings is opened)`; `app/js/app.js:972 (merged duplicate: Every time Settings opens, the key fields gain another set of listeners, so typing a key triggers repeated voice-list downloads)`
- **Source:** app-f-01, app-a-05, x-async-09

**What a user notices.** The more times someone opens Settings in a session, the more times each keystroke in a key or region box is saved and the more times the app asks the speech service for its voice list. After a few visits, pasting one key can fire a burst of identical internet requests and the voice list can flicker or disagree with itself.

**What is wrong.** openSettings() runs every time the Settings button is tapped, and it calls wireKeyField() for six key inputs (Claude, Deepgram, Azure, OpenAI, Google, ElevenLabs). wireKeyField attaches focus, blur and input listeners with addEventListener and a fresh closure every call, so they are never de-duplicated; the same is true of the extra Azure key 'input' listener and the Azure region 'input' and 'blur' listeners. After N opens, one input event runs save() N times and onChange N times. For Azure, onChange is clearAzureVoiceCatalog() + refreshAzureVoices({force:true}); each openSettings call has its own `let azureFetchInFlight` closure flag (7684), so the in-flight guard does not stop the copies from earlier opens and N concurrent voice-catalog fetches go out per keystroke. For OpenAI/Google/ElevenLabs, onChange calls refreshVoices() (no in-flight guard at all), so N fetches per keystroke; the Paste button then calls saveServiceKey and refreshVoices once more on top. Everything else in openSettings uses property handlers (.onclick/.onchange) precisely so re-running is idempotent; these are the exceptions.

**How it happens.** 1. Open and close Settings five times. 2. Open Settings again (6th time), Speech tab, with an Azure key saved. 3. Tap the Azure region box and type 'westus'. Each of the 6 keystrokes runs the region listener 6 times: 36 saves, 36 catalog clears and up to 36 parallel voice-list requests to Azure. Same multiplication for pasting an ElevenLabs or Google key (6 fetches from the listeners plus 1 from the Paste handler).

**Suggested fix.** Make the wiring idempotent. In wireKeyField, return early if the input is already wired and instead update the callbacks it uses: e.g. store the current {load, save, onChange} on the element (input._keyField = {load, save, onChange}) and have listeners read input._keyField; attach the three listeners only when `!input.dataset.keyWired`, then set input.dataset.keyWired = '1'. Do the same for the Azure listeners: replace azureKeyInput.addEventListener('input', reflectAzureTestAvailability) and the two azureRegionInput.addEventListener calls with property handlers (azureRegionInput.oninput = ..., azureRegionInput.onblur = ...), and fold reflectAzureTestAvailability into the Azure wireKeyField onChange. Move `let azureFetchInFlight` to module scope so it guards across opens. In the catalog Paste handler (7930-7941) drop the explicit storage.saveServiceKey and refreshVoices calls, because setKeyFieldValue's dispatched input event already does both.

> **Verifier correction to the fix (takes precedence):** The suggested fix is sound. One addition: when making wireKeyField idempotent, the stored callbacks must be refreshed on every open (input._keyField = {load, save, onChange}), because the onChange closures capture per-open locals such as refreshAzureVoices and showStatus. An alternative that is simpler and matches the precedent at 695-698 is to move all the key/region wiring out of openSettings into a once-only setup function called from initApp. Either way, only drop the explicit save and refresh calls in the catalog Paste handler AFTER the listeners are de-duplicated. Otherwise Paste on a first open would still work, but only because of the dispatched event.

**How to verify the fix.** Add tests/settings-wiring.test.mjs (source-level, like the guards in tests/placeholders.test.mjs): assert wireKeyField contains a once-only guard, and that openSettings contains no `addEventListener(` calls. Manually: open/close Settings 5 times, open the Network panel, paste an ElevenLabs key - exactly one voices request should go out; type a region in the Azure region box - at most one request per keystroke.

**Do not break.** Keep the 'never save the redacted placeholder' check (input.dataset.redacted). Keep focus-reveal and blur-redact behavior. The Close and Escape paths still persist the Claude key via keyFieldValue; do not remove them. The listeners must keep reading the CURRENT load/save (per service id) so the catalog loop still targets the right service.

**Design reference.** CLAUDE.md 'No Save button ... every control applies AND persists immediately'; the openSettings comment 'every control applies and persists' relies on property handlers being replaced on each open.

**Verification notes.** openSettings() (app.js:6883-8438) runs on every Settings tap (ui.onSettingsClick at 649, apiKeyPromptBtn at 601, review openSettingsAt at 882, tap-to-define at 3956). Inside it, wireKeyField is called for the Claude key (7281), Deepgram (7346), Azure (7429) and each catalog service in the loop (7917), and wireKeyField (972-987) uses addEventListener with fresh closures and no once-only guard. The Azure key also gets an extra addEventListener('input', reflectAzureTestAvailability) at 7459 and the region box gets addEventListener 'input' and 'blur' at 7462/7473. `let azureFetchInFlight` is declared inside openSettings (7684), so each open has its own flag and the guard cannot stop copies from earlier opens. The catalog onChange calls refreshVoices with no in-flight guard, and the catalog Paste handler (7930-7941) calls setKeyFieldValue (which dispatches an input event, 953-958) and then saveServiceKey and refreshVoices again. The project has already met this exact shape once: the comment at 695-698 records that the layout pointer listeners 'were briefly wired inside openSettings ... and were added again every time', and were moved to initApp. Nothing else de-duplicates these.

<details><summary>Merged duplicate app-a-05: Key-field listeners pile up every time Settings is opened</summary>

wireKeyField attaches focus, blur and input listeners with addEventListener. It is called from inside openSettings (for the Claude key, Deepgram, Azure and each catalog service), and openSettings runs on every Settings open. Nothing guards against re-wiring, so after N opens each key field has N input listeners, each holding its own closure from its own openSettings call. Each keystroke therefore runs save() N times and onChange N times: refreshDeepgramVoices N times, Azure clearAzureVoiceCatalog + refreshAzureVoices({force:true}) N times (its azureFetchInFlight guard is a `let` local to each openSettings call, so it does not collapse them), and for OpenAI/Google/ElevenLabs N concurrent voice-catalog fetches whose responses race to write the cache and the picker. The rest of openSettings deliberately uses `.onclick =`/`.onchange =` assignment, which replaces rather than accumulates.

Fix as proposed by that reviewer: Make wireKeyField attach its listeners once per element and read the latest handlers from the element: store `input._keyField = { load, save, onChange }` on every call, and only when `!input.dataset.keyWired` add the three listeners (set `input.dataset.keyWired = '1'`), with each listener reading `const h = input._keyField;` and calling `h.load()`, `h.save(...)`, `h.onChange && h.onChange(...)`. Always finish with `showRedactedKey(input, load())` as today.

</details>

<details><summary>Merged duplicate x-async-09: Every time Settings opens, the key fields gain another set of listeners, so typing a key triggers repeated voice-list downloads</summary>

openSettings runs on every open and calls wireKeyField(...) for five key inputs plus two raw addEventListener calls on the Azure key and region inputs. wireKeyField uses addEventListener('focus'|'blur'|'input'), so listeners accumulate: after N opens each input event runs N save() calls and N onChange handlers. For Azure the onChange clears the catalog and calls refreshAzureVoices({force:true}) - and each open's closure has its own azureFetchInFlight flag, so the in-flight guard does not dedupe across them: N parallel catalog fetches per keystroke. Catalog services do the same via refreshVoices(). Stale reflectAzureTestAvailability closures (each with its own azureTestRunning=false) re-enable the Test button during a running test. CLAUDE.md already records this exact mistake for the layout listeners ('added again every time they did') and the rest of openSettings deliberately uses `.onclick =` property assignment for idempotence.

Fix as proposed by that reviewer: Make the wiring idempotent in the style the surrounding code already uses. In wireKeyField replace the three addEventListener calls with property handlers: `input.onfocus = () => {...}; input.onblur = () => showRedactedKey(input, load()); input.oninput = () => {...};`. Fold reflectAzureTestAvailability into the Azure key's onChange instead of `azureKeyInput?.addEventListener('input', ...)`, and change the region box to `azureRegionInput.oninput = ...` and `azureRegionInput.onblur = ...`. Confirm no other code sets oninput/onfocus/onblur on these inputs (grep).

</details>
