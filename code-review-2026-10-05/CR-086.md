# CR-086: Changing or removing the Deepgram key, or switching away from Deepgram, leaves the old connection open and in use

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** resource-leak
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/tts-deepgram.js:217`
- **Also affects:** `app/js/tts-deepgram.js:627-640`; `app/js/tts-deepgram.js:688-692`; `app/js/tts.js:99-110`; `app/js/tts.js:72-97`; `app/js/app.js:7346-7353`; `app/js/app.js:7776-7783`
- **Source:** tts-04

**What a user notices.** If a tester's Deepgram key is replaced or deleted in Settings, the app can keep speaking on the OLD key (and billing that account) for the rest of the session, as long as it keeps talking. If the user switches to another voice service, a connection to Deepgram stays open in the background and keeps pinging every 8 seconds.

**What is wrong.** connect() reuses the open socket whenever `socketModel === model`; the key the socket was authenticated with is never recorded or compared. The keepalive (every 8 s while open and idle) keeps that socket from being closed by the server, so it can live for the whole session. Nothing closes it when the key changes: the key field save (wireKeyField -> storage.saveDeepgramKey) and the provider radio (applyTtsProvider -> tts.setProvider) never touch the backend, and tts.js exposes no way to call the backend's reset() - reset() exists in every backend but is never called anywhere. So: (a) a new or deleted Deepgram key is ignored until the socket happens to drop; (b) after switching provider away from Deepgram the socket and its setInterval keepalive keep running for the session, contradicting the module's own note that the keepalive 'costs nothing when the paid voice is not in use'. The Azure and REST backends read the key per request so they are not affected by (a), but their caches and AudioContexts are also never released.

**Evidence.**

```
tts-deepgram.js:217 `if (socket && socket.readyState === WebSocket.OPEN && socketModel === model) {` (no key check)
tts-deepgram.js:632-639 keepalive `setInterval(... socket.send(JSON.stringify({ type: 'KeepAlive' })) ..., KEEPALIVE_MS)`
tts-deepgram.js:688 `function reset() { cancel(); closeSocket(); cache.clear(); }` (never called)
tts.js:99-110 setProvider only stores readers; it never resets or closes a backend
app.js:7348 `save: (key) => storage.saveDeepgramKey(key),` (no backend notification)
```

**How it happens.** 1. Deepgram voice with key A; speak anything (socket opens). 2. Settings: paste key B (or clear the field) and close Settings without pressing Test. 3. Keep talking: every utterance still goes over the socket opened with key A. Or: 1. Speak with Deepgram. 2. Switch the voice to 'This device'. 3. In DevTools > Network > WS, the Deepgram socket stays open with a KeepAlive frame every 8 s.

**Suggested fix.** In tts-deepgram.js record the key with the socket: add `let socketKey = null;`, set `socketKey = key` in ws.onopen, clear it in closeSocket(), and change the reuse test to `socket && socket.readyState === WebSocket.OPEN && socketModel === model && socketKey === currentKey()`. In tts.js add `export function releaseBackends(except)` that calls `.reset()` (or for Deepgram at least close the socket) on every constructed backend whose name !== the current provider, and call it at the end of setProvider() for the previous provider. Optionally export a `resetBackend(name)` and call it from the Deepgram key field's save handler in app.js.

> **Verifier correction to the fix (takes precedence):** Comparing socketKey to currentKey() in connect() is the essential part. When releasing non-current backends on provider change, closing the Deepgram socket is enough; avoid clearing the caches of other backends unnecessarily (re-billing), and note tts-rest reset() also resets `chain`.

**How to verify the fix.** Add to tests/tts-deepgram.test.mjs: mock WebSocket recording constructor args; speak with getKey returning 'A', change the reader to return 'B', speak again, assert a second WebSocket was created with ['token','B']. Add to tests/tts.test.mjs: setProvider('deepgram'), speak, setProvider('builtin'), assert the Deepgram mock socket was closed and its keepalive interval cleared.

**Do not break.** Do not close the socket on every utterance; reuse is what keeps latency low. A reset must not clear the cache of the provider still in use.

**Design reference.** CLAUDE.md 'The paid voice silently fell back for one sentence ... retry + keepalive' ('tied to the socket's life, not the module's')

**Verification notes.** connect() (217) reuses the open socket on model match only; the key it was opened with is never recorded. currentKey() is read only when opening a new socket. The keepalive (627-640) sends KeepAlive every 8 s while open and idle, so the socket can survive the session. Nothing on the key-field save (app.js:7346-7353, wireKeyField -> storage.saveDeepgramKey, onChange -> refreshDeepgramVoices) or on provider change (app.js:7776-7783 -> applyTtsProvider -> tts.setProvider, which only stores readers and builds a backend) touches the existing Deepgram backend, and no code calls any backend's reset() (grep). Only the Settings Test button closes the socket (676-684). So a replaced or deleted key keeps being used, and after switching away from Deepgram the socket and its keepalive persist.
