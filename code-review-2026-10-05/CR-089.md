# CR-089: In the dark schemes every text field uses the browser's gray field: placeholder text is 2.4:1 and Yellow-on-black fields are white-on-gray

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** ui-inconsistency
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/css/styles.css:2706`
- **Also affects:** `app/css/styles.css:3069-3078 (#composerInput, no background/color)`; `app/css/styles.css:2006-2021 (.composer-overlay #composerInput)`; `app/css/styles.css:1908-1920 (#errorLogView is the only field that sets background/color)`; `app/css/styles.css:2887 (.ee-fields input)`
- **Source:** live-visual-04

**What a user notices.** With Dark, High contrast dark or Yellow on black chosen, every typing box (In my own words, API keys, Express phrase boxes, About Me answers, the problem-report box) is a mid-gray box with white text, and the gray hint text inside empty boxes is very hard to read; in Yellow on black the boxes are not yellow on black at all.

**What is wrong.** Text inputs and textareas declare no background or color, deliberately leaving them to the browser's color-scheme field colors (comment at 2706). Under color-scheme: dark Chrome paints them rgb(59,59,59) with white text and a #757575 placeholder. That placeholder measures about 2.4:1 against the field, failing the 4.5:1 the theme tests require for words, and it carries instructions ('Type here, then Speak it, Reframe…', 'What happened?…', 'How to say it (optional)', 'Topics I'd like to talk about…'). In the Yellow-on-black scheme the fields show white-on-gray instead of the scheme's yellow-on-black, while selects right beside them are themed (rgb(0,0,0) background). The error-log view is the only field given themed colors, so fields are inconsistent with each other too. This is the 'fourth kind of color' CLAUDE.md warns about (a control that declares nothing takes the browser's), not caught by tests/theme.test.mjs because it is not in the stylesheet.

**Evidence.**

```
app/css/styles.css:2706: 'Text inputs are deliberately NOT here: `color-scheme` already gives them a proper dark field'. Measured in Dark and Yellow at 1280x800: composerInput, apiKeyInput, azureKeyInput, ee-input, testerNameInput, problemNoteInput, weeklySendLogView, wv-text all = background rgb(59,59,59), color rgb(255,255,255), ::placeholder rgb(117,117,117); selects = rgb(33,38,41) (Dark) / rgb(0,0,0) (Yellow); errorLogView = rgb(0,0,0) with color rgb(255,212,0) in Yellow.
```

**How it happens.** Settings > Text & Color > Color scheme = 'Yellow on black'. Open 'In my own words': the box is gray with a barely legible gray hint. Settings > Troubleshooting > Report a problem: the hint 'What happened?…' is gray on gray. Any typed text is white rather than yellow.

**Suggested fix.** Add a zero-specificity themed rule for text fields, like the :where(#settingsDialog) button rule at ~2722, but app-wide:
:where(input[type="text"], input[type="password"], input:not([type]), input[type="number"], textarea) {
    background: var(--surface-raised);
    color: var(--ink);
}
:where(input, textarea)::placeholder { color: var(--ink-muted); opacity: 1; }
Then confirm --ink-muted on --surface-raised meets 4.5:1 in all seven palettes (add the pair to the contrast list in tests/theme.test.mjs). Update the 2706 comment to record the reason.

> **Verifier correction to the fix (takes precedence):** Do as suggested, and also: (1) keep the zero-specificity :where() form so the edgeless composer box and the editors' own rules still win; (2) exclude non-text inputs explicitly (range, checkbox, radio, file) so the native controls keep their color-scheme styling; (3) add the (--ink-muted, --surface-raised) pair to the per-scheme contrast list in tests/theme.test.mjs and confirm it reaches 4.5:1 in all seven palettes before shipping; (4) rewrite the 2706 comment to record why the earlier choice was reversed.

**How to verify the fix.** Add the (--ink-muted, --surface-raised) pair to the per-scheme contrast pairs in tests/theme.test.mjs. Manually open the composer and Settings > Speech in Dark, High contrast dark and Yellow and confirm fields match the scheme and hints are readable.

**Do not break.** The composer box must stay edgeless (no border/outline in any state — recorded decision at 2008-2016); only change background/color. Keep color-scheme declarations (they still style scrollbars and native checkboxes). Light scheme should look unchanged (white field, dark text).

**Design reference.** CLAUDE.md UI Layout Rule 23 (schemes; 'a button that declares NO background takes the BROWSER'S'; 58 contrast pairs at 4.5:1 for words).

**Verification notes.** The comment at styles.css:2706 records a deliberate choice to let color-scheme style text fields. That decision does not cover the consequences found here. Measured in headless Chrome under color-scheme: dark, a text input is rgb(59,59,59) with white text and a ::placeholder of rgb(117,117,117), about 2.4:1, which fails the 4.5:1 that Rule 23 requires for words. The stylesheet has no ::placeholder rule anywhere. In Yellow on black the fields therefore cannot follow the scheme, while #errorLogView sets var(--surface-raised)/var(--ink). The fourth-kind-of-color warning in Rule 23 is exactly this case, so the defect is real and not covered by a recorded accepted cost.
