# CR-091: Switching 'What a response card shows' mid-conversation leaves the full wording visible in 'short version' mode

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** ui-inconsistency
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/ui.js:245`
- **Also affects:** `app/js/ui.js:882`; `app/js/ui.js:896`; `app/css/styles.css:2180`; `app/js/app.js:8206`
- **Source:** ui-shell-03

**What a user notices.** If the user changes the card setting to 'The short version' while suggestions are on screen, any card whose full wording was long enough to be trimmed keeps showing the full wording as well as the short one, so the setting looks broken. Switching back the other way can leave long wording cut off mid-word with no ellipsis.

**What is wrong.** fitText() trims overflowing response text by writing INLINE styles on .response-text (display:-webkit-box, -webkit-box-orient, align-items, -webkit-line-clamp). The 'short version only' mode hides the full wording with a stylesheet rule `display: none`, which an inline display always beats. setCardTextMode() only swaps classes on #responseOptions and never re-runs fitCardsAndCommands(), so the inline clamp written under the previous mode persists. The reverse also happens: in condensed mode .response-text has no height so fitText skips it; switching back to a 'both'/'full' mode leaves overflowing text unclamped (cut without ellipsis) until something else re-fits (a resize or the next set of cards). The settings change handler in app.js calls only ui.setCardTextMode.

**How it happens.** Default mode ('Both - full response larger'). Get a set of cards where one response is long enough to be trimmed with an ellipsis. Open Settings > Conversation > 'What a response card shows' and pick 'The short version'. That card still shows its full (trimmed) wording plus the short label; the other cards correctly show only the short label.

**Suggested fix.** At the end of setCardTextMode() in ui.js add `fitCardsAndCommands();`. fitText() already clears the four inline properties first and returns early when the element has no height (the hidden case), so this both removes stale clamps and adds correct ones for the newly visible form.

**How to verify the fix.** Manual: as in the scenario, after the fix the long card shows only its short label in 'short version' mode; switch back to 'Both - full larger' and the long wording ends in an ellipsis. Optionally extend tests/ui-standards.test.mjs (browser test) to switch modes with a long card on screen and assert computed display of .response-text is 'none' on .has-hint cards in condensed mode.

**Do not break.** Paint only - must not change any card's box (Rule 1 keyguard geometry). Never hide .response-text on a card without .has-hint (a card must never come up blank).

**Design reference.** CLAUDE.md Response Option Display ('Every card always CARRIES both forms; the setting is pure CSS... switching re-styles the cards already on screen')

**Verification notes.** fitText (ui.js:882-900) writes inline display:-webkit-box only when the text overflows; the condensed-mode rule at styles.css:2180 is a plain stylesheet `display: none` (no !important), which an inline display beats. setCardTextMode (ui.js:245-248) only toggles classes, and the settings handler at app.js:8201-8207 calls only ui.setCardTextMode. fitCardsAndCommands runs on palette render (ui.js:397), from applyButtonSizing (resize/settings sizing) and from setCommandLabelMode, none of which a card-text-mode change triggers. The reverse case (switching back from condensed leaves overflowing text unclamped) also follows, since fitText skipped elements with clientHeight 0. The stale state clears at the next set of cards or a resize.
