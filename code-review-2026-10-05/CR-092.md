# CR-092: A browser background update can reload the page in the middle of a conversation

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/index.html:1277`
- **Also affects:** `app/sw.js:124`; `app/sw.js:134`
- **Source:** reporting-platform-05

**What a user notices.** If the tablet is left running for a day and a new version has been published, the app can suddenly restart in the middle of a conversation, wiping what the other person was saying and the suggestions on screen.

**What is wrong.** sw.js calls skipWaiting() on install and clients.claim() on activate, and index.html reloads the page unconditionally on 'controllerchange' (only the very first install is excluded). Updates are meant to happen at launch and on Start, but browsers also run a 'soft update' on their own: per the Service Worker spec, any fetch event from a controlled page (including the cross-origin AI and speech requests the worker sees and ignores) triggers an update check once 24 hours have passed since the last one. If a new sw.js has been deployed, it installs, takes control, and the page reloads immediately, whatever the user is doing. AAC tablets are commonly left open all day and overnight, and deploys are frequent.

**Evidence.**

```
app/index.html:1277-1280: `navigator.serviceWorker.addEventListener('controllerchange', () => { if (reloading || !hadController) return; reloading = true; window.location.reload(); });`
app/sw.js:124: `.then(() => self.skipWaiting())`
app/sw.js:134: `.then(() => self.clients.claim())`
```

**How it happens.** 1) Open the app Monday morning and leave it running. 2) A new build is deployed Monday afternoon. 3) Tuesday morning, mid-conversation, the partner speaks; the app asks the AI (a fetch through the controlled page), the browser's 24-hour soft update fires, the new worker activates and claims the page, and the page reloads while the partner is mid-sentence.

> **Verifier correction to the trigger:** The likelier trigger is the update check the app itself starts at launch or Start: a new build is found, the install and precache take several seconds on a slow link, and the reload lands after the user has started talking. The 24-hour soft update is a second route.

**Suggested fix.** Make the reload wait for a safe moment. In index.html, replace the immediate reload with: set `window.__aacUpdateReady = true` and call `window.__aacReloadIfIdle?.()`; in app.js define `window.__aacReloadIfIdle = () => { if (window.__aacUpdateReady && !conversationInProgress()) location.reload(); }` and call it from terminateConversation() and when the Start screen is showing (before Start is pressed). Keep the immediate reload when no conversation has been started (pre-Start). Alternatively, stop calling skipWaiting() in install and have handleStart post a 'SKIP_WAITING' message to a waiting worker, so activation only ever happens on Start.

**How to verify the fix.** Manual: open the app, start a conversation, then in DevTools > Application > Service Workers edit/redeploy sw.js locally (change CACHE_VERSION) and press Update; the page must not reload until End conversation is pressed. Also verify a fresh launch with a new build still reloads once before Start.

**Do not break.** Do not reintroduce a reload loop (keep the `reloading` guard and the first-install exclusion). The launch-time and Start-time update behavior recorded in CLAUDE.md must still work.

**Design reference.** CLAUDE.md 'The app updates itself on launch and on Start (v0.2.10)'

**Verification notes.** index.html reloads unconditionally on controllerchange once a controller existed. sw.js calls skipWaiting() and clients.claim(). Nothing checks whether a conversation is in progress. The 24-hour soft update on fetch events is spec behavior, which I could not exercise here. A more certain trigger the reviewer missed: handleStart calls reg.update() (app.js ~1507) and the page-load script calls it too. On a slow connection the new worker then precaches about 80 files with cache:'reload' before activating, which can take long enough that the user has already begun a conversation when it claims the page and the page reloads. CLAUDE.md records updating 'on launch and on Start' but does not accept a reload in the middle of a conversation. Not run in a browser, so plausible.
