# CR-094: A full browser storage makes every AI suggestion request fail, because saving the usage counter can throw

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/storage.js:403`
- **Also affects:** `app/js/storage.js:2797-2805 addUsageTokens`; `app/js/llm.js:38-41 askDetailed calls onUsageUpdate before returning the reply`; `app/js/app.js:801 llm.onUsage((usage) => storage.addUsageTokens(usage))`; `app/js/storage.js:2845-2851 addTtsCharacters, called from app/js/app.js:1046 via tts-azure.js:397 / tts-deepgram.js:307 / tts-rest.js:222`; `app/js/storage.js:2829-2835 addSttSeconds, called from app/js/app.js:1278 inside stt-deepgram.js:222 audio frame handler`; `app/js/storage.js:2519-2526 loadInstallId, called from app/js/weekly-send.js:308 and :483`; `every other save* settings function in storage.js (68 call sites of saveSettings)`
- **Source:** g-storage-overflow-03

**What a user notices.** If the browser's small settings store fills up (for example several stuck problem reports waiting to send), every request for suggestions fails and the app shows its 'cards could not be fetched' look even though the AI answered. Paid voices also fall back to the device voice on every sentence, and weekly reports and setting changes stop working, with nothing explaining why.

**What is wrong.** saveSettings() calls localStorage.setItem without a try/catch, unlike every other localStorage writer in the app (control-phrases, express-panel, places, relationships, voice, metrics, prediction, the weekly queue and the error log all catch quota errors). localStorage is ~5 MB per origin and is shared with the weekly-report queue (up to 8 payloads; a problem report carries transcripts and the already-reported endpoint bug can leave reports stuck), the 200-entry error ring, the Azure/catalog voice lists, and the worldview/relationships/express caches. When setItem throws QuotaExceededError: (1) addUsageTokens throws inside llm.askDetailed, which calls onUsageUpdate BEFORE returning the text, so a successful, paid AI reply is discarded and generateOptions / regenerate / reframe / openers / repair all reject - the app treats it as a generation failure; (2) addTtsCharacters throws inside the paid-voice synth path (tts-azure.js:397 etc.) so the sentence fails and tts.js falls back to the device voice on every utterance; (3) addSttSeconds throws inside the Deepgram audio frame handler at the gate-close edge; (4) loadInstallId throws on first mint inside weekly-send assembly, so neither the weekly report nor a problem report can be built; (5) every Settings change throws out of its handler.

**Evidence.**

```
app/js/storage.js:398-404
function saveSettings(settings) {
    settings = migrateBundle(settings);
    localStorage.setItem(STORAGE_KEY, JSON.stringify(settings));
}
app/js/llm.js:39-41
    const { text, usage, stopReason } = await provider.complete({ ... });
    if (usage && onUsageUpdate) onUsageUpdate(usage);
    return { text, stopReason: stopReason || null };
app/js/app.js:801  llm.onUsage((usage) => storage.addUsageTokens(usage));
Contrast app/js/storage.js:2592  try { localStorage.setItem(WEEKLY_QUEUE_KEY, JSON.stringify(q)); } catch { /* quota */ }
```

**How it happens.** 1) A tester's problem reports with transcripts sit in the weekly queue (e.g. refused by the endpoint for size) and, with the Azure voice catalog and error ring, localStorage reaches its quota. 2) The partner speaks; the AI request succeeds and returns usage. 3) addUsageTokens -> saveSettings -> setItem throws QuotaExceededError inside askDetailed. 4) generateResponses rejects; the cards never appear and an error is logged on every pause for the rest of the session.

**Suggested fix.** Wrap the write in saveSettings: `try { localStorage.setItem(STORAGE_KEY, JSON.stringify(settings)); } catch (err) { try { console.error('[settings] could not save', err); } catch {} }` and return a boolean (true on success). Do NOT call logError from inside saveSettings (logError writes to localStorage too and could recurse). Additionally make llm.askDetailed robust: `if (usage && onUsageUpdate) { try { onUsageUpdate(usage); } catch { /* a counter must never cost the user their suggestions */ } }`. For user-initiated Settings changes, callers may optionally check the boolean and show their existing status line ('Could not save - device storage is full').

**How to verify the fix.** Add to tests/storage-transcript.test.mjs (or a new tests/storage-quota.test.mjs): replace globalThis.localStorage.setItem with one that throws a QuotaExceededError for 'aac_settings'; assert storage.addUsageTokens({input:5}), addSttSeconds(1), addTtsCharacters(10) and loadInstallId() do not throw. In tests/llm.test.mjs, register an onUsage callback that throws and assert generateResponses still resolves with the parsed options.

**Do not break.** Keep migrateBundle inside saveSettings (it is the single migration choke point per CLAUDE.md). Do not swallow errors in a way that makes a user-visible Settings change appear saved when it was not - returning a boolean lets callers report it. loadInstallId must still return a stable id when the save fails (return the freshly minted one; it will be re-minted next launch, which is acceptable).

**Design reference.** CLAUDE.md 'Prompt caching' section (usage tracking is a cost readout, never on the critical path); weekly-send.js comment 'a diagnostic must never break what it measures'

**Verification notes.** Confirmed in code: saveSettings calls localStorage.setItem with no try/catch, unlike the other localStorage writers. addUsageTokens is called from llm.askDetailed via onUsageUpdate before the reply text is returned (llm.js:39-41), so a throw there discards a successful AI reply. addTtsCharacters runs inside onBilled before the audio bytes are read (tts-azure.js:397), and loadInstallId calls saveSettings on first mint. Whether localStorage can actually reach its roughly 5 MB quota in practice is unproven. The weekly queue is capped at 8 and swallows quota errors, and the error ring is capped at 200. The trigger therefore remains uncertain.
