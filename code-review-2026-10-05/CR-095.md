# CR-095: Endpoint reports failure after it has already written the row, so the app re-sends and the Sheet and inbox get duplicates

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** bug
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `scripts/weekly-report-endpoint.gs:110`
- **Also affects:** `scripts/weekly-report-endpoint.gs:177`; `scripts/weekly-report-endpoint.gs:179`; `scripts/weekly-report-endpoint.gs:197`; `app/js/weekly-send.js:380`; `scripts/weekly-report-endpoint.gs:111 (merged duplicate: A mail failure after the row is written makes the app resend the same report forever)`
- **Source:** reporting-platform-07, x-security-04

**What a user notices.** If the project's email quota runs out or the script loses its mail permission, a tester's problem report is written to the spreadsheet but the app believes it failed, so it sends it again on every launch: duplicate rows, repeated emails, and the tester's later reports stuck behind it.

**What is wrong.** In doPost the Sheet write happens first and the side effects afterwards: for a problem report MailApp.sendEmail runs after appendRow; for a weekly report _writeWeeks (and optionally MailApp) runs after appendRow. Any throw after the row is written (MailApp daily quota exceeded, MailApp authorization lost after an edit, a _writeWeeks error) lands in the outer catch and returns 'error: ...'. The app treats anything but 'ok' as not received and keeps the payload at the head of its queue, so the next launch writes the row again and attempts the mail again, indefinitely, while blocking every later report. There is also no LockService, so two near-simultaneous posts from one device can both append to the weeks tab.

**Evidence.**

```
scripts/weekly-report-endpoint.gs:100-115: `_problemSheet().appendRow([...]); if (ALERT_EMAIL) { MailApp.sendEmail(...); } return _out('ok');`
scripts/weekly-report-endpoint.gs:124/177: `_sheet().appendRow([...]); ... _writeWeeks(p);`
scripts/weekly-report-endpoint.gs:197-198: `} catch (err) { return _out('error: ' + err); }`
app/js/weekly-send.js:380: `if (outcome !== 'sent') { ... return { sent, queued: queue.length }; }`
```

**How it happens.** MailApp quota is exhausted for the day (or the script needs re-authorization after an edit). A tester sends a problem report: the problems row is written, sendEmail throws, the endpoint answers 'error: Exception: Service invoked too many times', the app keeps the report and re-sends it on each launch, writing a new duplicate row each time.

**Suggested fix.** Wrap each post-write side effect in its own try/catch so a successful write always returns 'ok': `try { MailApp.sendEmail(...); } catch (mailErr) { console.error(mailErr); }` for both mail calls, and `try { _writeWeeks(p); } catch (wErr) { console.error(wErr); }`. Optionally wrap doPost's body in `var lock = LockService.getScriptLock(); lock.waitLock(10000); try { ... } finally { lock.releaseLock(); }`. Bump SCRIPT_VERSION and redeploy.

> **Verifier correction to the fix (takes precedence):** Proposed fix is fine. Re-sending a problem report also mails Ken each time a send gets through, so wrap each side effect separately and return 'ok' once the row is written.

**How to verify the fix.** In the Apps Script editor, temporarily set ALERT_EMAIL to an invalid address (so sendEmail throws), POST a probe problem report: the response must be 'ok' and exactly one row added; repeat the POST and confirm the app-side queue would empty (outcome 'sent').

**Do not break.** Problem-report mail must still be sent when possible (Ken wants it). Keep ALERT_ON_WEEKLY_ERRORS false.

**Design reference.** CLAUDE.md 'WEEKLY-REPORT ERRORS NO LONGER MAIL; PROBLEM REPORTS STILL DO' and 'THE ENDPOINT'S REPLY IS READABLE' ('only an accepted report now leaves the queue')

**Verification notes.** The ordering is as described. For problem reports, MailApp.sendEmail runs after appendRow. For weekly reports, _writeWeeks and the optional mail run after appendRow. Any throw lands in the outer catch, which returns 'error: ...'. The app keeps anything that is not 'ok' at the head of the queue and re-sends it on every launch, writing another row each time, while blocking later reports. There is no LockService. The triggers (mail quota exhausted, lost authorization after a script edit, a _writeWeeks exception) are real but rare, and I could not confirm any of them happens in practice.

<details><summary>Merged duplicate x-security-04: A mail failure after the row is written makes the app resend the same report forever</summary>

For a problem report the endpoint appends the row first and then calls MailApp.sendEmail. If sendEmail throws (Apps Script mail quota exhausted - about 100 recipients/day on a consumer account - or a transient mail error), the outer catch returns 'error: ...'. The app reads any non-'ok' reply as a refusal and keeps the payload at the head of the queue (flush), so the next launch posts it again: another identical row is appended and another mail attempted. Because the shared secret is public in the app, anyone can drain the daily mail quota with forged problem reports, which turns every genuine problem report that day into this duplicate/blocked loop. The same ordering exists for the weekly error alert at line 180 (currently disabled by ALERT_ON_WEEKLY_ERRORS=false). There is also no per-install rate limiting.

Fix as proposed by that reviewer: In doPost wrap each MailApp.sendEmail call in its own try/catch so a mail failure is swallowed (optionally logged with console.error) and the function still returns _out('ok') once the row is written: `if (ALERT_EMAIL) { try { MailApp.sendEmail(...); } catch (mailErr) { console.error('alert mail failed: ' + mailErr); } }`. Apply the same at line 180. Optionally add a simple per-install throttle with CacheService (e.g. reject more than 10 problem reports per installId per hour with _out('ok') and no write) to blunt flooding. Bump SCRIPT_VERSION and redeploy via Manage deployments.
