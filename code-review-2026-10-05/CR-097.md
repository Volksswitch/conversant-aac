# CR-097: A failed or partial read of a data file is treated as 'no file', so the browser copy can overwrite the folder copy

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** data-loss
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/storage.js:369`
- **Also affects:** `app/js/worldview.js:193-213 (syncToFolder: null read -> save cache over disk)`; `app/js/relationships.js:114`; `app/js/places.js:163`; `app/js/express-panel.js:250`; `app/js/control-phrases.js:326`; `app/js/placeholder-phrases.js:215`; `app/js/practice-library.js:140`; `app/js/voice.js:246`
- **Source:** storage-07

**What a user notices.** If the app cannot read a data file at the moment it connects to the folder (for example a cloud-only OneDrive file that has not downloaded yet, or a file caught half-way through syncing), it can replace the person's About Me answers, people, places or Express Panel in the folder with the older or empty copy kept in the browser.

**What is wrong.** readFile() returns null for every failure - NotFoundError, NotReadableError, a permission error, an I/O error - so callers cannot tell 'there is no file' from 'the file exists but could not be read'. The sync functions treat null (or unparseable text) as 'no portable file yet' and promote the localStorage cache to disk, overwriting the folder file. That contradicts the v0.2.25 rule that a file in the folder always wins and is never overwritten by the cache. On a second PC (the exact cross-PC scenario the rule was written for) the cache is empty, so the result is an empty profile synced back over the user's real one.

**Evidence.**

```
app/js/storage.js:369-377:
  export async function readFile(filename) {
      if (!dirHandle) return null;
      try { ... return await file.text(); } catch { return null; }
app/js/worldview.js:196-211:
    const raw = await readFile(PROFILE_FILE);
    let disk = null;
    if (raw) { try { disk = JSON.parse(raw); } catch { disk = null; } }
    if (disk) { ... return 'adopted'; }
    profile = normalize(readCache() || profile || defaultProfile());
    await save();
```

**How it happens.** PC2 connects a OneDrive data folder whose worldview.json is a cloud-only placeholder (or is mid-sync and truncated). getFile()/text() throws or returns partial JSON; readFile returns null / JSON.parse fails; syncToFolder writes PC2's empty cache over worldview.json; OneDrive uploads the empty profile.

**Suggested fix.** Change readFile so it returns null ONLY for a missing file: `catch (err) { if (err && err.name === 'NotFoundError') return null; throw err; }`. In each syncToFolder (worldview, relationships, places, express-panel, control-phrases, placeholder-phrases, practice-library, voice) wrap the read in try/catch and return 'noop' (do not write) when it throws; and when the text exists but fails JSON.parse, do not overwrite it - return 'noop' (optionally log an error naming the file). Callers that only load (not sync) can keep treating a throw as 'use the cache'.

> **Verifier correction to the fix (takes precedence):** The direction is right, but readFile has many callers that rely on it never throwing (load paths in every model, practice library, voice, profiles). Rather than changing readFile's contract, add a separate readFileStrict(filename) that returns null only for NotFoundError and throws otherwise, and use it only in the eight syncToFolder functions. Also, a file that exists but fails JSON.parse should be left alone and logged, not overwritten.

**How to verify the fix.** Unit test in tests/worldview.test.mjs (and one per model): mock readFile to throw a NotReadableError and to return '{"trunc'; assert syncToFolder returns 'noop' and writeFile is never called. Mock NotFoundError -> still 'wrote'.

**Do not break.** Keep the cache-promotion path for a genuinely missing file (first folder connection). Do not make the app fail to start when a file is unreadable; just skip the write.

**Design reference.** CLAUDE.md 'Cross-PC copy of worldview.json — bug fixed (June 15 2026), v0.2.25. The file in the folder is the source of truth — full stop.'

**Verification notes.** The mechanism is real: readFile (storage.js:369) returns null for every failure, and worldview.syncToFolder (and relationships.syncToFolder, same shape) treat null or unparseable text as 'no file' and write the cache over the folder file, contradicting the v0.2.25 rule that a file in the folder always wins. What could not be confirmed is the trigger: whether Chrome's File System Access getFile()/text() actually throws or returns a truncated file for a OneDrive cloud-only placeholder or a mid-sync file (Chrome usually hydrates on read). A malformed hand-edited file is a sure trigger but user-caused. Impact if it fires on a fresh PC is an empty profile synced over the real one.
