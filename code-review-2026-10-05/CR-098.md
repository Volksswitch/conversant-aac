# CR-098: A late result from the built-in recognizer after listening stops is added to the cleared buffer

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** race-condition
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/stt.js:457`
- **Also affects:** `app/js/stt.js:724`; `app/js/stt.js:592`; `app/js/app.js:2064`; `app/js/app.js:2071`; `app/js/app.js:2777`; `app/js/app.js:2790`
- **Source:** stt-06

**What a user notices.** After the user answers or ends a conversation, the last few words the other person was saying can reappear afterward: shown again on screen and carried into the next exchange or the next conversation as if just said.

**What is wrong.** recognition.stop() (unlike abort()) makes the browser deliver a final result for audio already captured, asynchronously, before onend. stopListening() sets listeningIntent=false but recognition.onresult does not check it, so that late result is ingested: commitSegment() pushes it into `segments`, onTranscript updates the live partner line, onPartnerActivity fires, and (if the app is not speaking) a silence timer is armed until onend clears it. Callers such as handleResponseSelected() and terminateConversation() call stt.stopListening() and then stt.resetTranscript() synchronously, so the late words land in the freshly cleared buffer and survive. The next heardPartnerText() returns them (re-committed as a partner turn, or kept by resumePartnerCapture()). setSource() has the same shape (stopListening, resetTranscript, then the old recognizer's late result reaches the new service's transcript). TODO.md's 'Silent ... buttons must not cut off a placeholder' entry names this same mechanism as a possible cause of a different symptom (a placeholder being cut off); this finding is the stale-transcript consequence, which is not tracked there.

**Evidence.**

```
stt.js:457-465 `recognition.onresult = (event) => { ... if (ingest(event.results[i][0].transcript, event.results[i].isFinal)) heardPartner = true; ... afterIngest(heardPartner, sawFinal); };` (no listeningIntent check)
stt.js:724-731 `export function stopListening() { ... listeningIntent = false; ... recognition.stop();`
app.js:2064-2071 `stt.stopListening(); ... stt.resetTranscript();`
Experiment (scratchpad exp1.mjs): startListening; emitFinal('Do you want coffee?'); stopListening(); resetTranscript(); emitFinal('or tea') -> getCurrentTranscript() === 'or tea'.
```

**How it happens.** Auto-resume off. Partner: 'Do you want coffee or tea'; user taps a card mid-sentence. Chrome then delivers final 'or tea' after stop(); it is ingested after the reset. Live line shows 'or tea' again. User later taps an Express phrase: 'or tea' is committed as a new partner turn.

**Suggested fix.** In recognition.onresult add as the first line: `if (!listeningIntent && !suspendedForHidden) return;` (a suspend-for-hidden stop keeps listeningIntent true, so its flush is still accepted). Additionally, in setSource() detach the old recognizer's handlers before dropping it: `if (recognition) { recognition.onresult = recognition.onend = recognition.onerror = null; }` before `recognition = null`.

**How to verify the fix.** Add to tests/stt.test.mjs: startListening; emitFinal('a'); stopListening(); resetTranscript(); emitFinal('late'); assert getCurrentTranscript() === '' and no checkpoint fires. Keep the existing pause/resume tests green (resumeListening after a stop must still keep pre-stop text).

**Do not break.** Do not break pause semantics (CLAUDE.md 'Listen stop/start mid-turn is a PAUSE'): words captured BEFORE the stop must stay; only results arriving after the stop are dropped. The interruption capture reads getCurrentTranscript() before stopListening, so it is unaffected.

**Design reference.** CLAUDE.md 'Listen stop/start mid-turn is a PAUSE' and 'Interrupting the partner'; TODO.md 'Silent "get me other options" buttons must not cut off a placeholder' (candidate b)

**Verification notes.** recognition.onresult has no listeningIntent check. In handleResponseSelected and terminateConversation, stopListening() and resetTranscript() run in the same synchronous step, so any onresult delivered after recognition.stop() lands in the cleared buffer. onend then sees listeningIntent=false and leaves the segment in place. With auto-resume off, nothing clears it before the next heardPartnerText(). Whether Chrome/Edge actually deliver a trailing final after stop() with a pending interim depends on the browser, and I did not measure it. TODO.md 'Silent "get me other options" buttons must not cut off a placeholder' (candidate b) names this mechanism and proposes the same fix ('ignore whatever the recognizer delivers after the user has turned listening off'), but for a different symptom, so the stale-transcript consequence is not itself tracked. With auto-resume on, startFreshListening() resets the buffer after the response is spoken, which hides the problem.
