# CR-099: After a Deepgram sentence is stopped, leftover audio from it is glued onto the next sentence and cached that way

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** medium
- **Category:** race-condition
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/tts-deepgram.js:658`
- **Also affects:** `app/js/tts-deepgram.js:255-273`; `app/js/tts-deepgram.js:216-219`; `app/js/tts-deepgram.js:557-563`; `app/js/tts-deepgram.js:661`
- **Source:** tts-03

**What a user notices.** On the Deepgram voice, if a sentence is cut off and another starts right away (for example the user taps a card while a holding phrase is still coming in), the new sentence can begin with a fragment of the old one, or in rare timing be replaced by the end of the old one. Because the result is remembered, the same wrong audio plays every time that phrase is used for the rest of the session.

**What is wrong.** cancel() sets pending to null (failPending), sends {type:'Clear'} on the SAME socket, and keeps the socket for reuse. Audio frames from the cancelled utterance that are already in flight (Deepgram streams at ~2x real time) keep arriving. The next utterance reuses the open socket (connect() returns it when model matches) and sets a new `pending` within milliseconds, so those stale binary frames are pushed into the NEW utterance's chunks and player. If the cancelled utterance's 'Flushed' was already in flight, it is taken as the new utterance's end, resolving it with only stale audio. onmessage does not distinguish utterances (Deepgram's Flushed/Cleared carry a sequence_id that is ignored), and nothing waits for 'Cleared'. The corrupted samples are then stored with remember(key, samples) under the new phrase's text, so the corruption persists for the session.

**Evidence.**

```
tts-deepgram.js:658-661 `if (socket && socket.readyState === WebSocket.OPEN) { try { socket.send(JSON.stringify({ type: 'Clear' })); } ... } failPending('Canceled.');` (socket kept)
tts-deepgram.js:217-218 `if (socket && socket.readyState === WebSocket.OPEN && socketModel === model) { return Promise.resolve(socket); }`
tts-deepgram.js:256 `if (!pending) return;` then 271 `pending.chunks.push(e.data);` (no per-utterance check)
tts-deepgram.js:261-265 any 'Flushed' resolves the current pending
tts-deepgram.js:563 `remember(key, samples);`
Scratch simulation (30 ms one-way latency, server honors Clear): after cancel, 3 chunks of 'Alpha sentence' were delivered after the new pending was set; the cached 'Bravo' replayed with 15 samples instead of its genuine 10.
```

**How it happens.** Deepgram voice. A long AI response (fresh, streaming) is being received; the user taps an Express phrase that has never been spoken this session. speakAsUserTurn -> placeholders.stop() -> tts.cancel() -> tts.speak(phrase). The phrase starts with ~50-150 ms of the cancelled response, and every later tap of that phrase replays the same corrupted audio from cache.

**Suggested fix.** Simplest robust fix: in cancel(), if an utterance was in flight (`pending` non-null or `player` non-null), call closeSocket() instead of sending Clear, so the next utterance opens a fresh connection and no stale frames can reach it. (closeSocket must detach the old socket's handlers - see the separate finding about stale onclose.) Alternative: after sending Clear set `let draining = true`, ignore every message until one with `type === 'Cleared'` arrives, and make synthesize() await that before sending the next Speak. Also, as a guard, never cache samples from an utterance that received a 'Warning' or was preceded by a cancel without a confirmed Cleared.

> **Verifier correction to the fix (takes precedence):** If cancel() is changed to close the socket, it must be combined with detaching the old socket's handlers (see tts-08); otherwise the old socket's late onclose will call failPending on the NEXT utterance's pending and push it to the device voice, trading one fault for another. The 'drain until Cleared' alternative avoids that coupling but must time out if 'Cleared' never arrives.

**How to verify the fix.** Add to tests/tts-deepgram.test.mjs a mock WebSocket that delivers each server message with a delay; call speak('A'), cancel() mid-stream, then speak('B'); assert B's cached sample count equals what the server sent for B only. Manual: on Deepgram, interrupt a long response with a new Express phrase repeatedly and listen for a clipped fragment at the start.

**Do not break.** Closing the socket costs one reconnect (a few hundred ms) only on the cancel path; the ordinary path must keep reusing the connection. Keep failPending('Canceled.') so tts.js still recognizes the cancel and does not fall back.

**Design reference.** CLAUDE.md 'The paid voice silently fell back for one sentence' (connection reuse) and 'THE PAID VOICE STARTS IN A TENTH OF A SECOND' (streaming)

**Verification notes.** Code mechanism is real: cancel() (646-662) sends {type:'Clear'} and failPending('Canceled.') but keeps the socket; connect() reuses an open socket with the same model (217-218); ws.onmessage (255-273) has no per-utterance identity, so once the next synthesize() sets `pending`, any binary frames or a 'Flushed' still in flight from the cancelled utterance are attributed to the new one, and remember(key, samples) (563) caches the result. The next run starts within microtasks of the cancel (chain settles when the cancelled run rejects). Whether Deepgram actually has frames in flight after the cancel depends on network latency and server Clear handling, which cannot be confirmed without the live service; the reviewer's evidence is a simulation with assumed latency. Note most cancelled speech is cached placeholders that do not touch the socket, so the trigger needs a fresh, still-streaming utterance to be interrupted.
