# CR-105: Response-card live region reads out all four (or eight) suggestions on every refresh

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** accessibility
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/index.html:159`
- **Also affects:** `app/js/ui.js:337`; `app/js/ui.js:345`; `app/js/ui.js:275`; `app/js/ui.js:400`; `app/js/ui.js:413`
- **Source:** g-a11y-overflow-02

**What a user notices.** A screen-reader user hears every suggested reply read in full each time the suggestions change, which happens at nearly every pause the other person makes. The reading can run over the conversation, and the spoken suggestions can be heard by the microphone as if the other person said them.

**What is wrong.** #responseOptions has aria-live="polite". showResponses() clears innerHTML and rebuilds every cell and card, each card a button whose aria-label is the full wording (ui.js:275). Every reprompt (about half of all sets are replaced before a selection, per CLAUDE.md 'When the response cards change'), every New N, Reframe, choice chip and context tap therefore queues all four or eight full sentences for announcement. clearResponseOptions() and showResponseError() also replace the whole region. There is no busy signal: setPaletteBusy only toggles a CSS class, so nothing tells a screen reader that the set is about to change. As with the transcript, screen-reader speech is not known to the STT echo filter, so suggestions read through the speaker can be transcribed as partner speech (plausible).

**Evidence.**

```
app/index.html:159  <div id="responseOptions" class="palette-grid" aria-live="polite">
app/js/ui.js:345  responseOptions.innerHTML = '';
app/js/ui.js:275  card.setAttribute('aria-label', response.guessed ? `My best guess: ${text}` : text);
app/js/ui.js:333-335 export function setPaletteBusy(on) { responseOptions.classList.toggle('palette-refreshing', !!on); }
```

**How it happens.** With Narrator or VoiceOver on, let the partner speak with two pauses. At each pause a new set renders and the screen reader reads all four suggested replies end to end; with 'two per category' it reads eight.

**Suggested fix.** Remove aria-live from #responseOptions in index.html. Add a visually hidden status element next to it, e.g. <p id="paletteStatus" class="visually-hidden" role="status" aria-live="polite"></p> (reuse the #statusBar visually-hidden CSS pattern as a class). In showResponses, after building cards, set paletteStatus.textContent to a short message such as 'New suggestions' (or 'New suggestions: 4'), clearing it first so a repeat message is re-announced. In setPaletteBusy(on) also set responseOptions.setAttribute('aria-busy', on ? 'true' : 'false'), and clear aria-busy in showResponses/clearResponseOptions/showResponseError. The cards remain focusable buttons, so a user can move through them to hear each one.

> **Verifier correction to the fix (takes precedence):** Any new status element must be taken out of layout (position:absolute plus a clip-style visually-hidden rule), not just made invisible. #responsesSection is a fixed keyguard footprint, and an in-flow <p> would move the cards. Check this with tests/ui-standards and a rect comparison. No such visually-hidden class exists yet: #statusBar is hidden by an id rule, so a new class is needed.

**How to verify the fix.** Manual: with a screen reader on, trigger two reprompts and confirm only 'New suggestions' is announced each time, and that tabbing onto a card still reads its full wording (and 'My best guess:' when applicable). Optionally a source-level test in tests/ui-standards or tests/styles that index.html's #responseOptions carries no aria-live.

**Do not break.** Do not change card geometry or classes (keyguard). Keep the accessible name = full wording rule (CLAUDE.md Response Option Display). Do not route the message through #statusBar while Settings is open (it is inert then); a sibling status inside #responsesSection is fine.

**Design reference.** CLAUDE.md 'WHEN THE RESPONSE CARDS CHANGE'; 'Response Option Display' (accessible name carries the full wording)

**Verification notes.** #responseOptions has aria-live="polite" (index.html:159). showResponses rebuilds the cells with innerHTML='' (ui.js:345), and each card's aria-label is its full wording (ui.js:275). setPaletteBusy only toggles a CSS class. So every new set of suggestions re-queues every card for announcement. Severity is low for the same reason as finding 01: the target population is sighted direct-select users, and the problem only appears with a screen reader running.
