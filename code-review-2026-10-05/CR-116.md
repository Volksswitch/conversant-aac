# CR-116: Practice tab: every navigation rebuilds the panel and drops keyboard focus to the top of the page

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** accessibility
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/practice-editor.js:87`
- **Also affects:** `app/js/practice-editor.js:36`; `app/js/practice-editor.js:151`; `app/js/practice-editor.js:260`
- **Source:** g-a11y-overflow-08

**What a user notices.** A keyboard or switch user who presses Edit, Done, Cancel, Fill it in yourself or Delete in the Practice tab loses their place: focus jumps back to the start of the page and they have to move all the way back through Settings.

**What is wrong.** goTo() and render() clear the container (container.textContent='') and rebuild it; the button that had focus is destroyed and focus falls to <body>. Only scrollIntoView is done; no element is focused in the new view. Same after Delete (render()). The only focus call is custom.focus() for the behavior field.

**Evidence.**

```
app/js/practice-editor.js:36 container.textContent = '';
app/js/practice-editor.js:87-91 function goTo(next) { view = next; render(); container.scrollIntoView?.({ block: 'start' }); }
app/js/practice-editor.js:151 render();
```

**How it happens.** With a physical keyboard, open Settings > Practice, Tab to 'Edit' on a scenario, press Enter: the form appears but focus is on body; pressing Tab starts again from the Settings header.

**Suggested fix.** In goTo(), after render(), move focus to a sensible target: for edit/create views focus the h3.practice-title (give it tabIndex=-1 in renderForm) or the first input; for the list view focus the first .practice-card (or, after Delete, the next row's card). Use { preventScroll: true } and keep the existing scrollIntoView. Do not focus a text field on touch devices if storage.loadKeyboardMode() is 'onscreen' (it raises the keyboard) - focusing the heading avoids that.

**How to verify the fix.** Manual with a physical keyboard: Edit -> focus on 'Make it your own' heading; Done -> focus on the first scenario card; Delete -> focus on the next card.

**Do not break.** Focusing a text input pops the on-screen keyboard over Settings; prefer the heading. Do not change the view model or saving behavior.

**Design reference.** CLAUDE.md Practice Mode section; UI-Design.docx §13

**Verification notes.** goTo (practice-editor.js:87-91) and render (line 36) clear the container and rebuild it without focusing anything. The button that had focus is destroyed, so focus falls to body. After Delete, confirmDanger hands focus back to the Delete button, and render() then destroys it. This is real for keyboard and switch users only.
