# CR-119: Review state is invisible to assistive technology: whole-conversation re-announcements on every keystroke, and marks not reflected in names

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** accessibility
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/review-ui.js:307`
- **Also affects:** `app/index.html:54 (#transcript aria-live=polite)`; `app/index.html:159 (#responseOptions aria-live=polite)`; `app/js/review-ui.js:390-394 (New 4 marked only by a class)`; `app/js/review-ui.js:375-381 (rewritten card keeps the original wording in aria-label)`; `app/js/review-ui.js:723 (renderPane on every keystroke)`
- **Source:** review-backup-17

**What a user notices.** Someone using a screen reader or switch-access speech hears the entire conversation re-read after every letter they type in review, and cannot tell that New 4 is marked or what a rewritten option now says.

**What is wrong.** renderPane() replaces #transcriptLog.innerHTML (inside the aria-live=polite #transcript) on every render, and afterEdit(true) calls renderPane() per keystroke; renderCards() rebuilds the live-region #responseOptions likewise. The New 4 'I would have asked for a different set' toggle is shown only via the review-want class (no aria-pressed, and its label still says 'New 4 - different options'). A rewritten card shows the new text visually but its aria-label keeps the original wording, though the standing rule is that a card's accessible name carries what would be spoken.

**Evidence.**

```
review-ui.js:307  log.innerHTML = html.join('');
review-ui.js:723  if (textChanged) renderPane();
review-ui.js:393  if (regen) regen.classList.toggle('review-want', !!(e.answer && e.answer.kind === 'more'));
review-ui.js:375-378
        } else if (text && answerIdx === i && e.answer.rewritten) {
            text.textContent = e.answer.text;
        }
        const bits = [card.getAttribute('aria-label') || ''];
```

**How it happens.** With a screen reader, edit a card word in review: each letter re-announces the full transcript.

**Suggested fix.** On enter() set `$('transcript').setAttribute('aria-live','off')` and `$('responseOptions').setAttribute('aria-live','off')`, restoring 'polite' in leave(). In renderNew set `regen.setAttribute('aria-pressed', String(on))` and a review aria-label ('I would have asked for a different set'), restoring via ui.applyControlIcons on leave (already called). In renderCards, when the card is rewritten, start bits from e.answer.text instead of the original aria-label.

**How to verify the fix.** Manual with a screen reader, or a browser check reading aria attributes after each action.

**Do not break.** CLAUDE.md notes blind users are not a target, so keep changes to attributes only; do not change box geometry (keyguard).

**Design reference.** CLAUDE.md UI Layout Rule 4/12 (accessible names), 'What a response card shows' (accessible name carries the full wording)

**Verification notes.** #transcript (index.html:54) and #responseOptions (index.html:159) carry aria-live="polite". renderPane replaces #transcriptLog.innerHTML, and afterEdit(true) calls renderPane on every keystroke, so a polite live region receives a full set of new nodes per keystroke. renderNew shows the New 4 mark only through a class, with no aria-pressed. renderCards starts each card's aria-label from the one ui.showResponses set (the original wording) even when e.answer.rewritten shows new text. Impact is limited for this population (CLAUDE.md treats blind users as out of scope), so low.
