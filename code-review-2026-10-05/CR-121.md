# CR-121: Redrawing the Command Bar faces wipes state-dependent accessible names (privacy shows the wrong tooltip at every launch)

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** accessibility
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/ui.js:1194`
- **Also affects:** `app/js/app.js:686`; `app/js/app.js:690`; `app/js/app.js:8213`; `app/js/ui.js:1050`; `app/js/ui.js:1066`; `app/js/ui.js:1079`; `app/js/ui.js:1272`; `app/js/app.js:8208 (merged duplicate: Changing 'What the command buttons show' resets the accessible name of a latched button to its unlatched wording)`; `app/js/ui.js:1194 (merged duplicate: Changing the command-button labels or leaving Conversation Review resets state-dependent button names (New 8, privacy, latches))`
- **Source:** ui-shell-04, x-rules-02, x-a11y-09

**What a user notices.** For someone whose default is 'Do not save my conversations', the Don't-save button is lit at launch but its tooltip and spoken name invite them to turn saving off, the opposite of its real state. Changing the button-label setting mid-conversation does the same to Wrap up / Start conversation while latched, and makes 'New 8' read 'New 4'.

**What is wrong.** applyControlIcons() unconditionally rewrites aria-label/title of privacyBtn ('Don't save this conversation'), windDownBtn ('Wrap up'), initiateBtn ('Start conversation') and regenerateBtn ('New 4 — different options'), ignoring the state that setPrivacyState / setWrapUpState / setStartConversationState / setRegenerateLabel set. It runs via setCommandLabelMode at startup AFTER applyPrivacyState(), and again whenever the 'On each command button' setting changes. aria-pressed and the fill are kept, so name and state disagree.

**Evidence.**

```
app.js:685-690
    conversationPrivate = storage.loadNoSaveDefault();
    applyPrivacyState();
    ...
    ui.setCommandLabelMode(storage.loadCommandLabels());
ui.js:1205  cmd('privacyBtn', 'noSave', "Don't save this conversation");
ui.js:1211  setIconButton(document.getElementById('regenerateBtn'), 'shuffle', 'New 4 — different options');
ui.js:1055-1057 (setPrivacyState) const label = isPrivate ? 'This conversation is NOT being saved — tap to save' : "Don't save this conversation";
```

**How it happens.** Settings > Conversation > check 'Do not save my conversations'. Reload. Hover (or read with a screen reader) the filled amber Don't-save button: it says "Don't save this conversation" instead of 'This conversation is NOT being saved — tap to save'. Also: set Suggestions per category to 2, then change 'On each command button' to 'A short label': the New button's tooltip now says 'New 4'.

> **Verifier correction to the trigger:** The 'New 8' label is correct at launch (setRegenerateLabel at app.js:744 runs after the icon pass); it reverts to 'New 4' only after the command-label setting is changed during the session. The privacy mislabel happens at every launch when 'Do not save my conversations' is the default, and lasts until the button is toggled or a conversation ends.

**Suggested fix.** In ui.js keep module-level copies of the last state: `let privacyOn = false, wrapUpOn = false, startOn = false, regenCount = null;` assigned inside setPrivacyState/setWrapUpState/setStartConversationState/setRegenerateLabel. At the end of applyControlIcons() (after the cmd(...) calls, before setListenButtonState) call `setPrivacyState(privacyOn); setWrapUpState(wrapUpOn); setStartConversationState(startOn); if (regenCount != null) setRegenerateLabel(regenCount);`.

**How to verify the fix.** Manual: the scenario above shows the correct privacy label after reload and 'New 8' after changing the label mode. A browser check in tests/ui-standards.test.mjs can assert #privacyBtn aria-label matches aria-pressed after setCommandLabelMode.

**Do not break.** restoreConversationScreen (app.js:905-909) calls applyControlIcons then explicitly sets the latches false and re-applies privacy, so the cached values must be updated by those setters (they will be). Do not alter faces set by Conversation Review via setCommandBarFace during review.

**Design reference.** CLAUDE.md UI Layout Rule 6 (sticky action shown as selected) and Rule 21 (accessible name stays the explanatory wording in both modes)

**Verification notes.** At startup app.js:685-686 seeds conversationPrivate from loadNoSaveDefault and calls applyPrivacyState (ui.setPrivacyState sets the 'NOT being saved' label); then app.js:690 calls ui.setCommandLabelMode, which runs applyControlIcons and cmd('privacyBtn', ..., "Don't save this conversation") overwrites aria-label/title while aria-pressed and the private-on fill stay. The wrong name persists until the toggle is pressed or a conversation ends (app.js:2828-2829 re-applies). For New 4/New 8, the startup order is fine (setRegenerateLabel at app.js:744 runs after line 690), so that half only happens when the 'On each command button' setting is changed mid-session, as the reviewer says. Wrap up / Start latches are likewise overwritten only by a label-mode change while latched.

<details><summary>Merged duplicate x-rules-02: Changing 'What the command buttons show' resets the accessible name of a latched button to its unlatched wording</summary>

ui.setCommandLabelMode() calls applyControlIcons(), which redraws every Command Bar button with its fixed default label through setCommandFace() and setIconButton(). Those calls overwrite aria-label and title. For privacyBtn, windDownBtn and initiateBtn, the latched wording is set only by setPrivacyState(), setWrapUpState() and setStartConversationState(). The Settings change handler re-applies only the Listen button's state (applyListenAvailability) and never re-applies the other three. So aria-pressed="true" and the visual latch stay on while the name and tooltip describe the unlatched action. restoreConversationScreen() shows the right order: applyControlIcons first, then the three state setters. The Settings handler lacks the second half.

Fix as proposed by that reviewer: In ui.setCommandLabelMode(), or in the Settings onchange handler at app.js:8208, re-apply the latch states after the redraw. The simplest form follows restoreConversationScreen: in app.js, after ui.setCommandLabelMode(...), call applyPrivacyState() and re-apply the two latches from the current state (for example ui.setWrapUpState(staticBackout?.which === 'wrapUp') and ui.setStartConversationState(... === 'opener'), using whatever variable app.js keeps for the latch at lines ~2895-2925). A more robust option: have ui.js remember the three latch booleans in module variables and have applyControlIcons() call setPrivacyState/setWrapUpState/setStartConversationState with them at its end.

</details>

<details><summary>Merged duplicate x-a11y-09: Changing the command-button labels or leaving Conversation Review resets state-dependent button names (New 8, privacy, latches)</summary>

applyControlIcons() rewrites every Command Bar button's aria-label/title to the static default and sets regenerateBtn's label to the hard-coded 'New 4 — different options', but it does not re-apply state that other functions set: setRegenerateLabel (New 8), setPrivacyState, setWrapUpState, setStartConversationState. restoreConversationScreen() (called when leaving Review) re-applies privacy, wrap-up and start state but never setRegenerateLabel. The commandLabelsInput change handler (app.js:8213) calls setCommandLabelMode -> applyControlIcons and then only applyListenAvailability, so privacy/wrap-up/start labels revert while their aria-pressed stays true, and New 8 reverts to New 4.

Fix as proposed by that reviewer: Make the stateful labels survive a redraw: keep module-level `regenerateCount`, `privacyOn`, `wrapUpOn`, `startOn` in ui.js (set by setRegenerateLabel/setPrivacyState/setWrapUpState/setStartConversationState), and at the end of applyControlIcons() call `setRegenerateLabel(regenerateCount); setPrivacyState(privacyOn); setWrapUpState(wrapUpOn); setStartConversationState(startOn);` after the static faces are drawn.

</details>
