# CR-122: What's new panel: focus lands on Close before the notes, and is lost after Close or Start

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** accessibility
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/whats-new.js:852`
- **Also affects:** `app/js/whats-new.js:822`; `app/js/whats-new.js:841`; `app/js/app.js:1657`; `app/js/app.js:1615`; `app/js/app.js:1646`
- **Source:** g-a11y-overflow-06

**What a user notices.** A screen-reader or keyboard user who presses Start after an update hears only 'Close, button' and is never told there are release notes above it. After closing, and after any start-up notice, the keyboard focus is dropped to the top of the page instead of landing on the conversation controls.

**What is wrong.** renderPanel() builds a heading, a Close button, then the list, and calls okBtn.focus(). The panel has no role/name and the button has no description, so the reader announces just the button; the notes are only reachable by reading-mode navigation. On Close the focused button is destroyed (panel.textContent=''), so focus falls to <body>. The later steps of the start chain (folder notice, API-key notice) show cards without moving focus to them, and finishStart() hides #startBlock (display:none) which contains #startBtn - the element that held focus when no notice was shown - so keyboard focus is left nowhere and the next Tab starts from the top of the document.

**Evidence.**

```
app/js/whats-new.js:830 head.append(h, okBtn);
app/js/whats-new.js:845-846 panel.hidden = true; panel.textContent = '';
app/js/whats-new.js:852 okBtn.focus();
app/js/app.js:1661 document.getElementById('startBlock').classList.add('hidden');
app/css/styles.css:1042-1043 #startBlock.hidden { display: none; }
```

**How it happens.** Update the app, press Start with a screen reader: 'Close, button'. Press Enter: focus goes to body. With no notices pending, press Start with the keyboard: the start block disappears and pressing Tab begins at the first control in document order rather than at the Command Bar.

**Suggested fix.** In renderPanel: give the panel semantics - panel.setAttribute('role','region'); h.id = 'whatsNewTitle'; panel.setAttribute('aria-labelledby','whatsNewTitle'); list.id='whatsNewList'; okBtn.setAttribute('aria-describedby','whatsNewList'); okBtn.type='button'. Keep focusing okBtn (so a stray Enter cannot skip anything else) - the description now reads the notes. In app.js: when afterFolderNotice shows #folderPrompt, focus #folderReconnectBtn; when afterListeningNotice shows #apiKeyPrompt, focus #apiKeyContinueBtn; at the end of finishStart(), if document.activeElement is body or inside #startBlock, focus #listenBtn.

**How to verify the fix.** Manual with a physical keyboard: launch with a pending What's new, Tab/Enter through Close, confirm focus is on the next card's button, then on the Listen button after entering the conversation. With a screen reader confirm the notes are read after 'Close'.

**Do not break.** Do not focus anything inside main while it still has class 'disabled'. Keep the notes inside the transcript region (keyguard opening). The pre-start sequence order must not change.

**Design reference.** CLAUDE.md pre-start sequence notes ('Pre-start sequencing extended to four steps'); 'What's new notes are BUNDLED'

**Verification notes.** In whats-new.js, renderPanel builds the heading and the Close button, then the list, and calls okBtn.focus() (line 852). The panel has no role or name. On Close, panel.textContent='' destroys the focused button, so focus falls to body. The start chain (afterFolderNotice, afterListeningNotice) shows its cards without moving focus to them. finishStart hides #startBlock, which CSS sets to display:none (styles.css:1042), and that block contains #startBtn. So focus is lost after Start, as described. This affects only keyboard and screen-reader users.
