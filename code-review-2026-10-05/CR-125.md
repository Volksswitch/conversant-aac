# CR-125: Recognizer delivery-gap metric includes gaps across microphone stops

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:1222`
- **Also affects:** `app/js/app.js:1218`; `app/js/app.js:1253`; `app/js/stt.js:367`
- **Source:** app-a-07

**What a user notices.** None directly; the weekly report's measure of how unevenly the speech service delivers words is inflated with long, meaningless gaps, which could mislead tuning of the silence setting.

**What is wrong.** handleSpeechResult records metrics.sttGap(now - lastSpeechResultAt) for every transcript update. lastSpeechResultAt is reset only at a silence checkpoint (line 1253). When listening stops without a checkpoint (user interrupts with an Express phrase or composed statement, Pardon, End conversation, a manual stop under pause semantics) and later resumes, the first result records a gap spanning the whole stopped period. stt.js also calls onTranscript for pure-echo ingests (afterIngest calls onTranscript regardless of heardPartner), so gaps that span the app's own speech are counted too. CLAUDE.md defines this metric as the interval between deliveries 'while speech is ongoing', and the long tail is exactly what the metric exists to study.

**Evidence.**

**How it happens.** Partner speaks (results arrive), user taps an Express phrase before any pause (listening stops), a minute later the user presses Listen and the partner speaks: an stt_gap of about 60,000 ms is recorded.

**Suggested fix.** Reset `lastSpeechResultAt = 0` whenever capture stops: in handleSttStatus, inside the branch where status is 'stopped', 'idle' or 'error' (after isListening is set false). Also skip recording when liveText is empty.

> **Verifier correction to the fix (takes precedence):** Reset lastSpeechResultAt in handleSttStatus on stop statuses as suggested, AND do not let echo-only deliveries set it: either have stt.js pass a heardPartner flag to onTranscript and only update the timestamp when it is true, or skip the update while tts.isSpeaking(). Without the second part, gaps spanning the app's own speech are still recorded.

**How to verify the fix.** Manual: with metrics on, interrupt the partner with an Express phrase, resume after 30 s, and check the stored metrics tally has no stt_gap near 30,000 ms.

**Do not break.** Do not reset it on 'capturing' or 'warning' statuses; those occur within an ongoing session.

**Design reference.** CLAUDE.md 'RECOGNITION LATENCY (L)' (delivery-gap distribution while speech is ongoing)

**Verification notes.** lastSpeechResultAt is set in handleSpeechResult (app.js:1218-1223) and reset only at a checkpoint (1253). stt.js afterIngest calls onTranscript for every ingest including pure-echo ones (stt.js:368, outside the heardPartner guard), so echo of the app's own placeholders or the user's statement arriving after a checkpoint re-arms the timestamp; when the mic is then stopped by a selection and reopened, the next partner result records a gap spanning the user's whole turn. That makes the contamination common rather than limited to interruptions. metrics.sttGap (metrics.js:305-308) has no cap, so these land in the tally. Impact is limited because the weekly report summarises stt_gap as a median (weekly-report-endpoint.gs:167), which a minority of long outliers barely moves, but the tail the metric exists to study is polluted. Resetting on 'stopped'/'idle'/'error' in handleSttStatus is safe: the builtin restart loop does not emit 'stopped' (stt.js:486-506).
