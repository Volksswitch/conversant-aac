# CR-127: After a mid-turn 'Repeat what I said', the partner's words are sent to the AI twice

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:1802`
- **Also affects:** `app/js/app.js:348-356 updatePartnerLive updates the promoted history entry`; `app/js/app.js:362-370 flushLivePartnerToHistory`; `app/js/llm.js:632 messages built from history`
- **Source:** app-b-09

**What a user notices.** If the user taps 'Repeat what I said' while the other person is still talking, the next set of suggestions is built from a conversation in which the other person seems to have said the same thing twice, which can make the suggestions odd.

**What is wrong.** When a spoken command (Say again / Ask them to repeat / a 'defers' card) is logged mid-turn, flushLivePartnerToHistory promotes the live partner turn into conversationHistory and sets pendingPartnerHistoryIdx. At the next checkpoint, handleSilencePeriod -> updatePartnerLive writes the full text into that promoted history entry, and generateOptions then builds `history = [...conversationHistory, { role: 'partner', text: partnerText }]`, appending the same text again after the user's command. llm.generateResponses maps every entry to a message, so the model receives partner: 'X Y', assistant: '<repeat>', partner: 'X Y'.

**Evidence.**

```
app/js/app.js:349-351 `if (pendingPartnerHistoryIdx >= 0 && conversationHistory[pendingPartnerHistoryIdx]) {\n        conversationHistory[pendingPartnerHistoryIdx].text = text;`
app/js/app.js:1802 `const history = [...conversationHistory, { role: 'partner', text: partnerText }];`
app/js/llm.js:632-635 `const messages = conversationHistory.map(entry => ({ role: entry.role === 'partner' ? 'user' : 'assistant', content: entry.text }));`
```

**How it happens.** Partner says "So I was thinking..."; user taps Repeat what I said (turn promoted). Partner continues "...we could get lunch Friday" and pauses. The request carries the partner's full sentence both before and after the user's repeat.

**Suggested fix.** In generateOptions, when `pendingPartnerHistoryIdx >= 0`, do not duplicate the full text. Either send only the portion after the promoted prefix (if the promoted entry's text at promotion time was recorded, e.g. store `promotedPrefix` in flushLivePartnerToHistory and append `partnerText.slice(promotedPrefix.length).trim()` when non-empty), or, simpler, build `history` as conversationHistory unchanged when the last entry is the promoted partner turn. Pick the first if the API requires the last message to be the partner's.

**How to verify the fix.** Add a unit-level check by extracting the history-building into conversation-logic.js (pure function, tested in tests/conversation-logic.test.mjs): given a history with a promoted partner entry, assert the partner text appears once. Manual: stub fetch and inspect the request body after the scenario.

**Do not break.** The pane ordering and the in-place update of the promoted entry (CLAUDE.md 'Follow-up — the conversation PANE was out of order') must not change; only the request sent to the AI changes.

**Design reference.** CLAUDE.md 'Transcript mirrors the conversation pane' follow-up on pane ordering.

**Verification notes.** logSpokenUserTurn calls flushLivePartnerToHistory, which pushes the partner turn and sets pendingPartnerHistoryIdx; nothing resets it until a turn boundary. At the next checkpoint updatePartnerLive writes the full text into that promoted entry, and generateOptions builds `[...conversationHistory, { role: 'partner', text: partnerText }]`, so the partner text appears both before and after the user's command; llm.generateResponses maps every entry to a message.
