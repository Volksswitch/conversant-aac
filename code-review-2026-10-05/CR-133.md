# CR-133: Choosing an opener mid-conversation records the opener offer in the OLD conversation file

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:3146`
- **Also affects:** `app/js/app.js:1996`; `app/js/app.js:2048-2055`; `app/js/app.js:2823`; `app/js/app.js:2972-2982`; `app/js/storage.js:2307-2333`
- **Source:** app-c-09

**What a user notices.** Not visible on screen. In the saved conversations, the list of openers offered and which one was picked ends up at the end of the previous conversation, and the new conversation starts with an opener that has no record of what it was chosen from.

**What is wrong.** handleInitiate no longer ends the conversation; renderStaticPalette -> showPalette -> storage.logOffer writes the opener offer into the CURRENT (old) conversation log. When an opener is tapped, handleResponseSelected first calls noteUserAction('card', index), which finalizes that offer (outcome 'card', selectedIndex) in the old file, then runs the deferred terminateConversation() which resets the conversation id; the opener's user turn is written to the NEW file by commitExchange. The offer and its selection therefore live in different files: the old file ends with an opener offer marked chosen but no matching user turn, and the new file has no offer entry for the set the opener was chosen from. This undermines the offer record ('offers are recorded with the correct outcome').

**Evidence.**

```
app/js/app.js:3146 `renderStaticPalette('opener', snap.palette, 'Pick an opener');`
app/js/app.js:1996 `const decideMs = noteUserAction('card', index);`
app/js/app.js:2048-2050 `if (wasOpener && pendingNewConversation) {
        pendingNewConversation = false;
        await terminateConversation();`
app/js/app.js:2981 `storage.finalizeOffer({ outcome: kind, selectedIndex, shownMs: shownSpanMs() });`
```

**How it happens.** With a data folder: hold a conversation (one exchange), press Start conversation, tap an opener. Open the previous conversation JSON: last entry is role 'offer' kind 'opener' outcome 'card'. Open the new conversation JSON: it begins with the opener user turn and no opener offer.

**Suggested fix.** In handleResponseSelected's deferred-ending branch, after `await terminateConversation(); noteConversationStarted();`, re-record the set in the new file: `storage.logOffer({ kind: 'opener', options: shownAtTap }).then(() => storage.finalizeOffer({ outcome: 'card', selectedIndex: index, shownMs: decideMs }));` and, in the old file, change the outcome given to the opener offer by finalizing it as 'start conversation' instead: i.e. when `wasOpener && pendingNewConversation`, call `storage.finalizeOffer({ outcome: 'new conversation', shownMs: shownSpanMs() })` instead of noteUserAction's default (or pass kind 'new conversation' to noteUserAction).

**How to verify the fix.** Extend tests/storage-transcript.test.mjs: logOffer, finalizeOffer, resetConversationId, logOffer+finalizeOffer+logUserResponse, and assert both files read back as intended. Manual check of the two JSON files as in the scenario.

**Do not break.** Respect 'Don't save this conversation' (logOffer already returns early when not saving). Keep the deferred-ending order: terminateConversation must run before `raw` is read.

**Design reference.** CLAUDE.md, 'EVERY SET OF CARDS IS RECORDED, NOT ONLY THE ONES PICKED FROM'; 'Wrap up and Start conversation are TOGGLES'

**Verification notes.** handleInitiate no longer terminates; renderStaticPalette -> showPalette -> storage.logOffer writes the opener offer to the current (old) log as pendingOffer. On tapping an opener, noteUserAction('card', index) runs finalizeOffer against the old file first, then the deferred terminateConversation resets the conversation id (currentLogData = null), and commitExchange writes the opener user turn to the new file. The new file has no offer entry for the set the opener came from.
