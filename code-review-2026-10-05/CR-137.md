# CR-137: The goal stamp can record the wrong source for a lit goal

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:4456`
- **Also affects:** `app/js/app.js:4617 (activeGoals stores the source at tap time)`; `app/js/app.js:4027-4048 (goalButtons dedupes and keeps the more specific source)`
- **Source:** app-d-13

**What a user notices.** A saved conversation can say a goal came from the person being talked to when the user actually switched it on from the general list, which makes reviewing why a goal appeared or vanished misleading.

**What is wrong.** goalStamp() rebuilds the list from goalButtons() and writes g.source - the source of the button as currently composed - rather than the source stored in activeGoals when it was switched on. If a general goal X is lit (stored 'general') and a partner whose list also contains X is then selected, goalButtons now reports X as source 'partner', so every later turn is stamped 'partner' while dropGoalsFrom correctly treats it as general (it will survive a partner change). The stamp exists specifically so 'a goal that vanished at a partner change can be told from one the user switched off'.

**Evidence.**

```
app/js/app.js:4457-4463
  const on = goalButtons().filter((g) => activeGoals.has(g.id));
  ...
  return on.map((g) => ({ id: g.id, text: g.text, source: g.source || 'general' }));
app/js/app.js:4617  if (on) activeGoals.set(item.id, item.source || 'general');
```

**How it happens.** Light general goal 'Make plans together'. Tap partner Mom whose goals include the same goal. Next turn's goals stamp says source 'partner'.

**Suggested fix.** In goalStamp use the stored source: `return on.map((g) => ({ id: g.id, text: g.text, source: activeGoals.get(g.id) || g.source || 'general' }));`.

**How to verify the fix.** Browser: reproduce, then inspect the conversation JSON's goals stamp; source must be 'general'.

**Do not break.** Keep order as composed (goalButtons order is what reached the AI).

**Design reference.** goalStamp JSDoc; CLAUDE.md 'THE TRANSCRIPT NOW RECORDS WHICH GOALS WERE IN FORCE'

**Verification notes.** Traced. goalStamp() rebuilds from goalButtons(), which dedupes by id and keeps the MORE SPECIFIC source; the menu goal ids are shared across the three lists. It writes g.source rather than the source stored in activeGoals at tap time, which is what dropGoalsFrom acts on. A general goal lit before choosing a partner whose list holds the same goal is stamped 'partner', yet it correctly survives a partner change. buildSituationBlock does not use the source, so only the record is wrong.
