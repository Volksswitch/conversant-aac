# CR-140: Problem-report note is never cleared after a successful send, so the next report repeats it

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:6440`
- **Also affects:** `app/js/app.js:6273`; `app/js/app.js:6280`; `app/js/app.js:6429`; `app/js/app.js:7089`; `app/js/app.js:6313`
- **Source:** g-misc-overflow-01

**What a user notices.** After a tester sends a problem report, the description they typed stays in the box. If they later send another report about something else, the old description goes with it as though it described the new problem, and the team reads the wrong complaint.

**What is wrong.** sendProblemReport() reads #problemNoteInput twice (once inside buildProblemReportText for the report body, once for the payload's `note` field) but never empties the textarea after the report is accepted or queued. Nothing else resets it: the only writer is the Clear button handler (7089-7106), and renderTroubleshooting/openSettings never touch it. The textarea is not persisted, so the stale note survives for the rest of the session. The launch-screen path (sendProblemReportFromStart) also calls buildProblemReportText, so if Settings was reached from the pre-start API-key notice and a note typed there, a later launch-screen report carries that stale note in its body even though it passes note: '' in the payload.

**Evidence.**

```
app.js:6273  const noteEl = document.getElementById('problemNoteInput');
app.js:6280      note: noteEl ? noteEl.value : '',
app.js:6428-6433  const res = await weeklySend.sendProblemReport({ note: document.getElementById('problemNoteInput')?.value || '', report: text, ... });
app.js:6440  if (res && res.sent) setProblemReportStatus('Sent and received. Thank you — that is the whole procedure.');
app.js:6441  else if (res && res.queued) setProblemReportStatus('Not sent yet — it is saved and will go by itself ...');
(no line anywhere sets problemNoteInput.value = '' except the Clear button at app.js:7105)
```

**How it happens.** 1. Settings > Troubleshooting, type "Listen did nothing" in Report a problem, tap Send, confirm. Status: Sent and received. 2. The note box still says "Listen did nothing". 3. Later the same session the cards stop appearing; the tester taps Send without noticing the old text (or types a second line under it). 4. The second report arrives with WHAT HAPPENED = "Listen did nothing", and the payload's note column repeats it.

**Suggested fix.** In sendProblemReport(), after weeklySend.sendProblemReport resolves, clear the box when the report has left the tester's hands (sent OR queued): `if (res && (res.sent || res.queued)) { const box = document.getElementById('problemNoteInput'); if (box) box.value = ''; }`. Do not clear when res.blocked (locally served copy) or when the call throws, so nothing typed is lost on a failure. Clearing on `queued` is correct because the note is already saved in the queue payload and will be sent with it.

> **Verifier correction to the fix (takes precedence):** The fix is right. Also clear the box when the launch-screen path sends while Settings holds a note? Not needed: that path sends note:'' in the payload, but its report body does include the box text, so clearing on the Settings path is the only change required. Keep the box untouched on blocked, cancel, and throw.

**How to verify the fix.** Manual: in Settings > Troubleshooting type a note, Send and confirm; the note box must be empty afterwards and the status still reads 'Sent and received'. Repeat with the network off: status says it is saved, and the box is empty. On a locally served copy (blocked) the note must remain. If a DOM test harness is added later, assert problemNoteInput.value === '' after a mocked weeklySend.sendProblemReport returning {sent:1}.

**Do not break.** Must not clear on failure or on the local-origin block, or a tester loses a long note typed on the on-screen keyboard (CLAUDE.md treats a typed report as significant work - that is why Clear asks first). Keep the two-step see-then-confirm flow unchanged.

**Design reference.** CLAUDE.md, 'Beta instrumentation and error reporting' (Report a problem: free-text note) and the 'Confirm before destroying significant work' rule

**Verification notes.** Verified: sendProblemReport (app.js:6400-6450) never writes problemNoteInput; the only writer is the Clear button handler (7089-7106), which empties it after a confirm. weeklySend.sendProblemReport returns {blocked:'local'} for a local origin, {sent}/{queued} otherwise, so the suggested condition is right. The stale note does reach the next report's body via buildProblemReportText and the payload note field. Severity lowered to low because the next send shows the full report text, note included, in the confirmation dialog's preview, so the tester has a chance to see the old note before it leaves.
