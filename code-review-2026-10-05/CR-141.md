# CR-141: Restoring a damaged backup can leave 'Reading…' on screen forever: the restore and file-import handlers have no error handling and summarize() can throw

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:6677`
- **Also affects:** `app/js/app.js:6526`; `app/js/app.js:6529`; `app/js/data-transfer.js:237`; `app/js/app.js:6723`; `app/js/app.js:8475`
- **Source:** g-misc-overflow-03

**What a user notices.** If someone tries to restore a backup file that is slightly damaged, the Restore button shows 'Reading…' and then nothing else happens - no message says the file is bad, and the problem is filed in the error log as a start-up failure.

**What is wrong.** storage.readBackup itself never rejects (it catches everything and returns null), so the rejection named in the review brief does not come from there. It comes one step later: importPackageText() validates with parsePackage() inside a try, but then builds the confirmation body with dataTransfer.summarize(pkg) OUTSIDE any try. summarize() does `profiles.map((x) => x.name)`, which throws a TypeError for a backup whose profiles array holds a null (parsePackage does not check entries). The rejection propagates out of importPackageText into restoreBackupBtn.onclick and fileInput.onchange, neither of which has a try/catch, so it becomes an unhandled rejection. The window 'unhandledrejection' handler logs it as 'startup:promise' (Settings is only reachable after Start, so no card shows) and the backup status line keeps whatever it said last: 'Reading…' on the folder path, blank on the file path. fileInput.onchange also awaits file.text(), which rejects (NotReadableError) if the picked file changed or is a cloud placeholder that cannot be fetched - same unhandled path. Verified in node: summarize(parsePackage('{"kind":"conversant-aac-backup","packageVersion":3,"data":{},"profiles":[null]}')) throws "Cannot read properties of null (reading 'name')"; a profile with no name renders as '1 saved profile: ' (empty name).

**How it happens.** 1. Put a backup in <data folder>/backups whose JSON has "profiles": [null] (hand-edited, or truncated/merged by a sync tool). 2. Settings > Backup, choose it, tap Restore selected backup. 3. Status shows 'Reading…' and stays there; no confirmation card appears; the error log gains a 'startup:promise' entry and the transcript turns faintly red.

**Suggested fix.** (a) Make summarize() tolerant: in data-transfer.js:234-238 filter to valid entries: `const profiles = (pkg && Array.isArray(pkg.profiles)) ? pkg.profiles.filter((x) => x && typeof x.name === 'string' && x.name.trim()) : [];`. (b) In importPackageText, compute the summary inside the existing parse try (e.g. `let lines; try { pkg = dataTransfer.parsePackage(text); lines = dataTransfer.summarize(pkg); } catch (err) { setBackupStatus(err.message || 'That backup could not be read.'); return; }`) and use `lines` in the confirm body. (c) Wrap the bodies of restoreBackupBtn.onclick and fileInput.onchange in try/catch that calls storage.logError('import', msg) and setBackupStatus('Could not read that backup: ' + msg), mirroring the export handler at app.js:6666-6668.

> **Verifier correction to the fix (takes precedence):** The three parts are right. Also handle the showOpenFilePicker path (app.js:6698-6712): its bare catch swallows a summarize/file.text failure with no message, so move the importPackageText call out of that try (catch only the picker's own AbortError/refusal) or give it the same status-line handling.

**How to verify the fix.** Unit test in tests/ (data-transfer test file): summarize(parsePackage(JSON with profiles:[null, {}, {name:'A'}])) returns a profiles line naming only 'A' and does not throw. Manual: restore the damaged file above; a legible status line must appear and no 'startup:promise' entry is logged.

**Do not break.** Keep the confirmation before any write (confirmDanger standing rule). importSettingsProfiles already skips null profiles, so do not change the import itself. Do not touch the importInProgress guard ordering.

**Design reference.** data-transfer.js header ('this is the one place a user can hand the app an arbitrary file, so the failure has to be legible'); CLAUDE.md 'Startup failures must be VISIBLE' (startup handler is for start-up, not mid-session)

**Verification notes.** Verified in node: summarize(parsePackage('{"kind":"conversant-aac-backup","packageVersion":3,"data":{},"profiles":[null]}')) throws "Cannot read properties of null (reading 'name')". parsePackage does not validate profile entries. In importPackageText, summarize runs inside the confirmDanger argument, outside the parse try. restoreBackupBtn.onclick (6677-6688), fileInput.onchange (6723-6727) have no try/catch. The rejection goes to the window unhandledrejection handler, which logs 'startup:promise' (and shows the startup card only if the pre-start block is still visible, which it is when Settings was opened from the pre-start API-key notice). The status stays 'Reading…' on the folder path. The showOpenFilePicker path is protected by its own catch, but that catch silently swallows the same error, so the user sees nothing at all there either. The trigger needs a damaged or hand-edited file, so it is narrow.
