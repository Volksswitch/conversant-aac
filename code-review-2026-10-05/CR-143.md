# CR-143: Side-dock layout is never pulled back above the transcript floor, so a smaller usable height pushes the response cards off the bottom

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/conv-layout.js:148`
- **Also affects:** `app/js/app.js:4788`; `app/css/styles.css:1281`
- **Source:** ui-shell-06

**What a user notices.** With the keyboard on the side, after the user has made the response area large, making the usable screen shorter (a bigger screen-edge margin, leaving full screen, or loading the settings on a smaller tablet) leaves the conversation area squashed below its minimum, and the bottom of the response cards is pushed off the screen - so keyguard openings no longer line up.

**What is wrong.** normalize() exists to force a stored layout back inside its limits when something other than a drag changes the sums (a different screen). For dock==='side' it clamps command and response individually and returns before ever checking the transcript floor (1 - command - response >= floorT). Simulated: side layout dragged to the limits on a 1000px-tall area gives transcript 0.048; at 560px floorT is 0.0857 but normalize/solve still return transcript 0.048 (27px), while the CSS enforces min-height: var(--conv-transcript-floor) (48px), so the column overflows by ~21px. The bottom-dock path trims correctly in the same simulation.

**Evidence.**

```
conv-layout.js:145-148
    for (const k of ['command', 'response', 'dock']) {
        next[k] = clamp(num(next[k], DEFAULTS[ctx.dock][k]), lim[k].lo, lim[k].hi);
    }
    if (ctx.dock === 'side') return next;   // the keyboard is on the other axis
styles.css:1281  min-height: var(--conv-transcript-floor, 3rem);
```

**How it happens.** Side dock. Settings > Screen Layout > 'Let me drag the borders', drag the command/response border up as far as it goes. Then Settings > Keyguard Design > Screen edge margin to maximum (or turn off full screen / load the profile on a shorter screen). The response region now extends past the bottom of the screen.

**Suggested fix.** In normalize(), replace the early return with the same trimming loop used for the bottom dock but excluding the dock: `const parts = ctx.dock === 'side' ? ['response', 'command'] : ['dock', 'response', 'command']; const order = parts.filter((k) => k !== next.last); if (next.last && parts.includes(next.last)) order.push(next.last); for (const k of order) { const used = next.command + next.response + (ctx.dock === 'side' ? 0 : next.dock); const owe = lim.floorT - (1 - used); if (owe <= 0) break; next[k] = Math.max(lim[k].lo, next[k] - owe); }`.

**How to verify the fix.** Add a test to tests/conv-layout.test.mjs: side ctx height 1000, setRegion response 0.99 then command 0.99; then normalize with height 560 and assert solve(...).transcript >= limits(ctx).floorT - 1e-9.

**Do not break.** normalize must stay a no-op after a legal drag (setRegion already stops there); the side dock's width (dock) must not be trimmed for a vertical shortfall.

**Design reference.** conv-layout.js header ('normalize() exists only for... a different screen... which can raise a floor'); CLAUDE.md UI Layout Rule 1 (static geometry) and Rule 16 (screen edge margin)

**Verification notes.** conv-layout.js normalize() returns early for the side dock (line 148) without checking the transcript floor. Verified with a node script: a side layout dragged to its limits at height 1000 gives transcript 0.048. Normalized and solved at height 560, transcript is still 0.048 against a floorT of 0.0857. app.js:4788-4791 feeds normalize/solve output straight into --conv-command-h and --conv-response-h in pixels, while CSS keeps a min-height transcript floor, so the column overflows. The overflow is a few to a few dozen pixels depending on how much the usable height shrinks (the maximum screen-edge margin alone costs about 5 px at a 1000 px height).
