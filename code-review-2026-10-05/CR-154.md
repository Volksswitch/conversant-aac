# CR-154: A profile whose file name has an accent, period or apostrophe cannot be loaded, updated or deleted

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/storage.js:503`
- **Also affects:** `app/js/storage.js:548`; `app/js/storage.js:574`; `app/js/storage.js:708`; `app/js/app.js:7157`; `app/js/app.js:7179`; `app/js/app.js:7198`; `app/js/storage.js:708 (merged duplicate: Choosing or deleting a settings profile whose name cleans up to nothing reads or deletes a file called '.json')`
- **Source:** x-security-08, g-storage-overflow-05

**What a user notices.** If someone copies a settings file named, for example, "José.json" or "Mom's tablet.json" into the settings folder, it appears in the list, but Load says it cannot read it, Update creates a second, differently named copy, and Delete says it worked while the file stays.

**What is wrong.** listSettingsProfiles() returns raw file names, but applySettingsProfile(), deleteSettingsProfile() and saveSettingsProfile() first pass the name through sanitizeProfileName(), which strips every character outside [A-Za-z0-9 _-()]. A listed name containing any other character therefore resolves to a different file: Load throws 'Could not read that profile.', Update writes '<stripped>.json' and leaves the original, and Delete removes nothing (the error is swallowed) yet reports 'Deleted'. Copying profile files between devices through the data folder is an explicitly intended workflow (CLAUDE.md: settings profiles travel with the folder), and users name files in their file manager.

**Evidence.**

```
app/js/storage.js:503-505  function sanitizeProfileName(name) { return String(name || '').trim().replace(/[^A-Za-z0-9 _\-()]/g, '')... }
app/js/storage.js:554-555  names.push(entryName.slice(0, -5));   (unsanitized)
app/js/storage.js:575-581  const clean = sanitizeProfileName(name); ... const fh = await dir.getFileHandle(`${clean}.json`); ... catch { throw new Error('Could not read that profile.'); }
app/js/storage.js:708-712  deleteSettingsProfile: const clean = sanitizeProfileName(name); ... try { await dir.removeEntry(`${clean}.json`); } catch { /* already gone */ }
app/js/app.js:7207  setProfileStatus(`Deleted “${name}”.`);
```

**How it happens.** 1. Copy a profile file into <data folder>/settings and rename it 'José.json'. 2. Open Settings: 'José' is listed. 3. Tap Load: 'Could not read that profile.' 4. Tap Delete and confirm: status says Deleted “José” but the list still shows it.

**Suggested fix.** Use the exact listed name for operations on an existing file: in applySettingsProfile and deleteSettingsProfile, try `${name}.json` first (the raw name as listed) and fall back to the sanitized name only if that is not found; validate the raw name only by rejecting path separators (FSA already rejects '/' and '\'). For Update (saveSettingsProfile called with an existing listed name), write to the raw existing name when a file with that exact name exists. Keep sanitizeProfileName for NEW names the user types.

**How to verify the fix.** Extend tests/storage-transcript.test.mjs (real OPFS-shim storage): create a settings/José.json profile file directly, assert listSettingsProfiles() includes 'José', applySettingsProfile('José') succeeds, deleteSettingsProfile('José') removes it.

**Do not break.** Do not loosen the sanitizer for newly typed names. importSettingsProfiles' collision renaming must keep working.

**Design reference.** CLAUDE.md 'DECIDED — named settings profiles ARE the settings-persistence and transfer mechanism'

**Verification notes.** listSettingsProfiles returns raw names (storage.js:554-555) while applySettingsProfile, deleteSettingsProfile and saveSettingsProfile all pass the name through sanitizeProfileName, which strips everything outside [A-Za-z0-9 _-()]. 'José' becomes 'Jos', so Load throws 'Could not read that profile.', Delete silently removes nothing (error swallowed) while the caller reports success, and Update writes a second file. Trigger requires a file the user named or copied in by hand, which is narrow.

<details><summary>Merged duplicate g-storage-overflow-05: Choosing or deleting a settings profile whose name cleans up to nothing reads or deletes a file called '.json'</summary>

listSettingsProfiles() lists every *.json in the settings folder under its raw name, so a hand-copied file such as 'Профиль.json' or '日本.json' appears in the picker. applySettingsProfile() and deleteSettingsProfile() run the selected name through sanitizeProfileName(), which strips every character outside [A-Za-z0-9 _-()] and can return ''. Neither function checks for an empty result (saveSettingsProfile does: 'Please enter a profile name.'), so they operate on `${''}.json` = '.json'. Load then fails with 'Could not read that profile.', Delete swallows the not-found error and the app reports 'Deleted …' although the real file is untouched; if a file literally named '.json' exists (it is itself listed as a profile with an empty name), Delete of the other profile removes it. This is the empty-result edge of the already-reported 'accent, period or apostrophe cannot be loaded, updated or deleted' finding at storage.js:503 and should be fixed with it.

Fix as proposed by that reviewer: Stop sanitizing names that came FROM the folder: in applySettingsProfile, deleteSettingsProfile and activeProfileUnsaved, use the exact listed name when it is one of `await listSettingsProfiles()` (compare exactly, then case-insensitively), and only fall back to sanitizeProfileName for names typed by the user. Then add a guard in both: `if (!clean) throw new Error('That profile name cannot be used.');` (deleteSettingsProfile should throw too, and the app.js Delete handler should wrap the call in try/catch and show err.message via setProfileStatus instead of always reporting 'Deleted').

</details>
