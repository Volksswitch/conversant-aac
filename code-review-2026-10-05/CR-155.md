# CR-155: One stored setting ('<id>Model') serves as both the speaking model and the hearing model for OpenAI, Google Cloud and ElevenLabs

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/storage.js:1197`
- **Also affects:** `app/js/storage.js:1201-1205 (saveServiceModel - no caller anywhere)`; `app/js/app.js:533-534 (hearing reader: getRestModel)`; `app/js/app.js:1070 (speaking reader at startup)`; `app/js/app.js:8008, app/js/app.js:8025, app/js/app.js:8060 (speaking readers in Settings)`; `app/js/speech-catalog.js:61, 114, 163 (TTS defaultModel: gpt-4o-mini-tts, '', eleven_multilingual_v2)`; `app/js/speech-catalog.js:208, 226, 263 (STT defaultModel: gpt-4o-transcribe, latest_long, scribe_v2)`; `app/js/storage.js:627 and 664 (backup/profile import copies any settings key verbatim)`
- **Source:** g-stt-overflow-04

**What a user notices.** Nothing goes wrong today. But the first time the app (or a restored backup) stores a model choice for one of these services, the same choice would be sent to the other half - for example asking OpenAI to transcribe speech with a voice model - and either hearing or speaking for that service would stop working.

**What is wrong.** loadServiceModel(id) reads settings[id + 'Model'] and is used by BOTH the text-to-speech catalog readers (TTS_PROVIDERS ids openai/google/elevenlabs) and the speech-to-text reader (STT_PROVIDERS ids, which are the SAME strings openai/google/elevenlabs). The function's own comment shows the conflation: 'OpenAI's tts model, ElevenLabs' model_id, Google's recognizer' - two speaking models and one hearing model under one key. The two halves need different, incompatible values (OpenAI: gpt-4o-mini-tts vs gpt-4o-transcribe; ElevenLabs: eleven_multilingual_v2 vs scribe_v2; Google: '' vs latest_long). Confirmed by grep: nothing in app/, scripts/ or tests/ calls saveServiceModel or writes '<id>Model', so it is latent and every reader currently falls through to the right defaultModel. It becomes live if (a) a model picker is added (CLAUDE.md records a planned model-tier setting), or (b) a settings bundle carrying e.g. 'openaiModel' is imported - backup restore and profile load copy any non-excluded key verbatim, so such a bundle from a future version would cross-wire an older install.

**Evidence.**

```
app/js/storage.js:1196-1205
/** The model (OpenAI's tts model, ElevenLabs' model_id, Google's recognizer). */
export function loadServiceModel(id) {
    return loadSettings()[id + 'Model'] || null;
}
export function saveServiceModel(id, model) { ... settings[id + 'Model'] = model; ...
app/js/app.js:533-534  getRestModel: (id) => storage.loadServiceModel(id)
                || (STT_PROVIDERS[id] && STT_PROVIDERS[id].defaultModel) || '',
app/js/app.js:1070  getModel: () => storage.loadServiceModel(id) || TTS_PROVIDERS[id].defaultModel,
app/js/speech-catalog.js:61 defaultModel: 'gpt-4o-mini-tts'  vs  208 defaultModel: 'gpt-4o-transcribe'
```

**How it happens.** A later release adds a 'speaking model' picker that calls saveServiceModel('openai', 'gpt-4o-mini-tts'). From then on stt-rest sends model=gpt-4o-mini-tts to https://api.openai.com/v1/audio/transcriptions; every phrase is refused, three in a row trip the fatal path and listening switches off. Same if a user restores a backup made by such a release onto this version.

**Suggested fix.** Split the key by direction before anything writes it. In storage.js replace the pair with
    export function loadServiceTtsModel(id) { return loadSettings()[id + 'TtsModel'] || null; }
    export function saveServiceTtsModel(id, model) { const s = loadSettings(); s[id + 'TtsModel'] = model; saveSettings(s); }
    export function loadServiceSttModel(id) { return loadSettings()[id + 'SttModel'] || null; }
    export function saveServiceSttModel(id, model) { const s = loadSettings(); s[id + 'SttModel'] = model; saveSettings(s); }
Update app.js:533 to loadServiceSttModel and app.js:1070, 8008, 8025, 8060 to loadServiceTtsModel. Delete loadServiceModel/saveServiceModel (no other caller). Fix the doc comment so each names only its own direction. No migration is needed because nothing has ever written the old key.

**How to verify the fix.** Add to tests/storage-transcript.test.mjs (or a storage test): save a TTS model for 'openai' and assert loadServiceSttModel('openai') is still null, and vice versa. grep -rn "loadServiceModel" app/ must return nothing afterwards. Run npm test.

**Do not break.** Keep the defaultModel fallbacks exactly as now (the readers currently rely on them). The new keys are ordinary settings and should travel in profiles/backups (not PROFILE_EXCLUDE); they are not secrets.

**Design reference.** CLAUDE.md 'Five paid speech services, and the catalog that makes a sixth cheap' (providers are data; hearing and speaking mixable per service)

**Verification notes.** Verified: loadServiceModel(id) reads settings[id+'Model']. The hearing reader (app.js:533) and the speaking readers (app.js:1070, 8008, 8025, 8060) both call it with the same ids: openai, google and elevenlabs. Those services need different defaults for each direction (speech-catalog.js 61/114/163 against 208/226/263). saveServiceModel has no caller anywhere in app/, scripts/ or tests/, so the fault is latent today and every reader falls back to the correct default. The defect in the key design is real, and nothing user-visible happens until something writes the key.
