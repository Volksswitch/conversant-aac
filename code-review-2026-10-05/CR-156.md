# CR-156: metrics.log flush can strand buffered lines with no timer (and skips them at page-hide)

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/storage.js:2749`
- **Also affects:** `app/js/storage.js:2737-2746 appendMetricsFile`; `app/js/storage.js:2755 the metricsWriting early return`; `app/js/metrics.js:235-239 flush() calls storage.flushMetricsFile`; `app/js/app.js:451-454 pagehide and visibilitychange-hidden call metrics.flush()`
- **Source:** g-storage-overflow-04

**What a user notices.** Some usage events may never reach the detailed usage log on the device, typically the last few seconds before the tablet is put down or the app is closed. Nothing the user sees changes; the weekly report's totals are not affected.

**What is wrong.** flushMetricsFile() clears metricsTimer FIRST and only then checks `if (metricsWriting) return;`. While a write is in flight, appendMetricsFile() pushes new lines and (because metricsTimer was nulled by the in-flight flush) schedules a fresh 10 s timer. Any second flush call that arrives during the write - the visibilitychange-hidden / pagehide handler via metrics.flush(), the fresh timer firing, or the 40-line threshold - clears that new timer and returns early. The lines are left in metricsBuffer with no timer, and the in-flight write's finally block does not re-check the buffer. They are written only when the next event arrives; if none arrives (app backgrounded and then discarded by the OS, or closed), they are lost. The page-hide flush itself is a no-op whenever it lands during a write.

**Evidence.**

```
app/js/storage.js:2748-2756
export async function flushMetricsFile() {
    if (metricsTimer) { try { clearTimeout(metricsTimer); } catch {} metricsTimer = null; }
    if (!dirHandle || !metricsBuffer.length) return;
    ...
    if (metricsWriting) return;
app/js/storage.js:2768-2770
    } finally {
        metricsWriting = false;
    }
```

**How it happens.** 1) A timed flush starts writing metrics.log. 2) A Command Bar tap records an event; appendMetricsFile buffers it and schedules a 10 s timer. 3) The user switches away from the app before the write finishes; visibilitychange-hidden calls metrics.flush() -> flushMetricsFile(), which cancels the timer and returns because a write is running. 4) The write finishes; nothing re-schedules. 5) The OS discards the backgrounded tab: the buffered line(s) are never written.

**Suggested fix.** In flushMetricsFile, move the `if (metricsWriting) { ...; return; }` check ABOVE the timer clear, and when returning early mark that another pass is wanted: `if (metricsWriting) { metricsFlushAgain = true; return; }` (new module flag). In the finally block, after `metricsWriting = false;`, add: `if (metricsFlushAgain || metricsBuffer.length >= METRICS_FLUSH_LINES) { metricsFlushAgain = false; flushMetricsFile(); } else if (metricsBuffer.length && !metricsTimer) { metricsTimer = setTimeout(flushMetricsFile, METRICS_FLUSH_MS); }`.

**How to verify the fix.** New test in tests/storage-transcript.test.mjs (or tests/metrics.test.mjs) using the in-memory directory with a createWritable whose write() awaits a manually-resolved promise: call appendMetricsFile once and flushMetricsFile (write now blocked), append a second entry, call flushMetricsFile again, resolve the blocked write, await a tick, and assert metrics.log eventually contains both lines (or that a timer/second flush is pending) without any further append.

**Do not break.** Keep the write serialized (two concurrent appends seek to a stale length). Keep the 'put lines back on failure' behavior. Do not make flushes recursive without a guard.

**Design reference.** storage.js comment block 'Metrics log (August 16 2026)'; CLAUDE.md 'Beta instrumentation and error reporting' (write continuously so a lockup still leaves a file)

**Verification notes.** Traced flushMetricsFile. It clears metricsTimer before checking metricsWriting. A flush in flight sets metricsBuffer=[] and leaves metricsTimer null, so appendMetricsFile during the write schedules a fresh timer. A second flushMetricsFile call during the write cancels that timer and returns early. The finally block only resets metricsWriting and never reschedules, so lines stay buffered with no timer until the next event. The pagehide/visibilitychange-hidden handler (app.js:451-454, via metrics.flush) can be that second call. The failure path that puts lines back on the buffer also reschedules nothing. The impact is limited to metrics.log lines on the device; the weekly tally is persisted separately.
