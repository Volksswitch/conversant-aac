# CR-157: Azure's last-phrase submission when listening stops is paid for and then always thrown away

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/stt-azure.js:482`
- **Also affects:** `app/js/stt-azure.js:483`; `app/js/stt-azure.js:332`; `app/js/stt-azure.js:482 (merged duplicate: Azure hearing: the 'submit the last words before stopping' step is always thrown away (but still billed))`; `app/js/stt-azure.js:482 (merged duplicate: Stopping Azure hearing pays to transcribe the last phrase and then throws the result away)`
- **Source:** stt-13, x-async-11, x-providers-10

**What a user notices.** Each time listening stops while the other person is mid-sentence, Azure is sent (and charges for) a clip whose words are never used.

**What is wrong.** stop() calls `closeSpan(Date.now(), generation)` to 'submit whatever is in hand', then synchronously does `generation++`. submit() is async and its first await is fetch, so by the time the response arrives `mine !== generation` and the text is discarded. The request is still made and billed. The comment claims the partner's last words are preserved; they never are (and delivering them after stop would pollute the next turn anyway).

**Evidence.**

```
stt-azure.js:479-483 `// Submit whatever is in hand before tearing down ... if (gate && gate.isOpen()) closeSpan(Date.now(), generation); generation++;`
stt-azure.js:332 `if (mine !== generation) return;    // listening stopped while this was in flight`
Experiment (scratchpad exp2.mjs): 10 loud frames then stop() -> fetches 1, texts delivered [].
```

**How it happens.** Partner is talking; user taps a response card. Azure source stop() posts the open span; the reply is dropped.

**Suggested fix.** Replace line 482 with dropping the span without submitting: `if (gate && gate.isOpen()) { span = []; spanSamples = 0; }` (and do not add to billedMs), and update the comment. The interruption path already captures what was heard via stt.getCurrentTranscript() before stopping.

**How to verify the fix.** tests/stt-azure.test.mjs: feed loud frames, call stop(); assert fetch was not called and onText not called.

**Do not break.** None beyond keeping generation++ so in-flight earlier phrases are still discarded.

**Design reference.** none

**Verification notes.** stop() calls closeSpan(Date.now(), generation), which starts the async submit(). The very next statement is `generation++`. When fetch resolves, `mine !== generation` and the text is discarded, but the request has already been made and billed. The comment promising the partner's last words are kept is wrong. Dropping the span instead is right, because text delivered after a stop would land in the next turn's buffer (the same family as stt-06).

<details><summary>Merged duplicate x-async-11: Azure hearing: the 'submit the last words before stopping' step is always thrown away (but still billed)</summary>

stop() calls closeSpan(Date.now(), generation), which bills the span and starts an async submit() tagged with the current generation, then immediately does `generation++`. When the response arrives, submit checks `mine !== generation` and returns, so the result is always discarded. The comment above says the purpose is that 'the partner's last words ... are not lost'. Note that simply delivering it would be wrong in another way: after a card selection stt.resetTranscript has already run, so late text would leak into the next turn.

Fix as proposed by that reviewer: Choose one behavior explicitly. Recommended (matches the REST source, which abandons in-flight work on stop): remove the closeSpan call from stop() so nothing is uploaded or billed for a result that is discarded, and update the comment. If delivering the tail is wanted for the manual-pause case, instead pass a dedicated tag (`closeSpan(now, generation + 1)` then `generation++`) AND have stt.js ignore text arriving after resetTranscript (e.g., a transcript epoch in stt.js bumped by resetTranscript and captured per source start).

</details>

<details><summary>Merged duplicate x-providers-10: Stopping Azure hearing pays to transcribe the last phrase and then throws the result away</summary>

stop() calls closeSpan(Date.now(), generation), which bills the span and starts submit() with mine = current generation, then immediately increments generation. When the response arrives, submit() checks `mine !== generation` and returns, discarding the text. The comment claims the opposite ('Submit whatever is in hand ... dropping them would look exactly like a mishearing'). stt-rest.js's stop() does not submit the open span at all, so the two phrase-at-a-time backends disagree.

Fix as proposed by that reviewer: Decide one behavior and make both backends match. Simplest and consistent with stt-rest: in stt-azure stop(), replace the closeSpan call with nothing (just drop the span) and update the comment. If the last words are wanted, instead pass a special token and deliver them only when the app has not already committed the turn - that is a larger design change and should not be done silently.

</details>
