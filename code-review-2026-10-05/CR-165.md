# CR-165: Cancelling the About Me folder picker throws on a null event target, leaves the button disabled and logs a false start-up error

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/worldview-ui.js:157`
- **Also affects:** `app/js/app.js:8453-8475 (unhandledrejection -> reportStartupFailure -> storage.logError('startup:promise', ...))`; `app/js/storage.js:2677 (logError dispatches aac-error-logged, which drives the transcript red wash)`
- **Source:** worldview-03

**What a user notices.** If the user taps 'Choose data folder' on the About Me page and then cancels the folder window, the button stays greyed out so they cannot try again, and the app records an error that makes the conversation transcript flash red and shows up in the weekly report as a start-up failure.

**What is wrong.** Inside the async onclick, e.currentTarget is read in the catch block after an await. The DOM sets Event.currentTarget to null once dispatch finishes, so after `await storage.pickDataFolder()` rejects (AbortError when the user cancels), `e.currentTarget.disabled = false` throws TypeError. The async handler's promise rejects unhandled, reaching the window 'unhandledrejection' listener, which calls reportStartupFailure -> storage.logError('startup:promise', ...). The button was disabled synchronously at line 149 and is never re-enabled. Verified in headless Chromium: currentTarget is non-null before await and null after.

**Evidence.**

```
app/js/worldview-ui.js:148-158:
    onclick: async (e) => {
        e.currentTarget.disabled = true;
        try {
            await storage.pickDataFolder();
            ...
        } catch (err) {
            e.currentTarget.disabled = false;   // AbortError = user cancelled
        }
app/js/app.js:8475: window.addEventListener('unhandledrejection', (e) => reportStartupFailure('promise', e.reason));
app/js/app.js:8456: try { storage.logError('startup:' + where, msg); } catch {}
Puppeteer: {"before":true,"after":null}
```

**How it happens.** No data folder connected. Settings > About Me > tap 'Choose data folder' > press Cancel in the browser's folder window. The button remains disabled; the error log gains 'startup:promise TypeError: Cannot set properties of null (setting 'disabled')'; the next conversation transcript shows the red error wash.

**Suggested fix.** Capture the button before the first await: `onclick: async (e) => { const btn = e.currentTarget; btn.disabled = true; try { ... } catch (err) { btn.disabled = false; } }`. Optionally only treat AbortError silently and log other errors via storage.logError with a meaningful context such as 'aboutme:pickFolder'.

> **Verifier correction to the fix (takes precedence):** Capture `const btn = e.currentTarget;` before the first await and use btn in both branches. Keep pickDataFolder as the first await.

**How to verify the fix.** Manual: cancel the picker from the banner; the button must become tappable again and Settings > Troubleshooting > Error log must show no new entry. A source guard in tests/ can assert no `e.currentTarget` read appears after an `await` inside worldview-ui.js handlers.

**Do not break.** Keep pickDataFolder as the first await so the user gesture is still valid for showDirectoryPicker.

**Design reference.** CLAUDE.md 'Error reporting — audited against expectation' and the reportStartupFailure comment (a rejection during a session belongs in the error log only when it is real).

**Verification notes.** Verified in headless Chromium: e.currentTarget is non-null before an await and null after. When the user cancels showDirectoryPicker, the catch block does e.currentTarget.disabled = false, which throws a TypeError. The async handler's promise rejects unhandled, and app.js:8475 routes it to reportStartupFailure, which calls storage.logError('startup:promise', ...), which in turn dispatches aac-error-logged (red wash) and puts an entry in the error log and weekly report. The startup card does not show because startBlock is hidden by then. The button stays disabled until About Me is re-rendered, for example by leaving and returning, so it is recoverable. That makes it low rather than medium.
