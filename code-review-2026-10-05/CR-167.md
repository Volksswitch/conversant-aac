# CR-167: Person/place auto-save name guard restores a stale name and silently drops other edits

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/worldview-ui.js:1188`
- **Also affects:** `app/js/worldview-ui.js:1190 (name: name || existing.name)`; `app/js/worldview-ui.js:1482-1486 (commitPlaceNow uses the same stale existing.name fallback)`; `app/js/relationships.js:157-182 (listPeople returns a snapshot copy, so existing.name never updates)`
- **Source:** worldview-05

**What a user notices.** If someone renames a person, then later clears the name box while editing, the person silently goes back to their original name. If a person has no relationship set and the name box is empty, checking 'Private' or changing anything else is not saved.

**What is wrong.** commitNow captures `existing` (a snapshot from rel.listPeople() taken when the form was drawn). (a) The blank-name guard falls back to existing.name, which is the name at render time, not the latest committed one; after a rename in the same form, blanking the box writes the pre-rename name back. (b) `if (!name && !relationship) return;` returns before ANY field is written, so while the name box is empty and no relationship is selected, edits to Private, Lives with me, about, topics and the partner profile are discarded without notice (Done also calls commitNow, so it does not rescue them). Toggling Private is a privacy choice. commitPlaceNow has the same stale-name fallback.

**How it happens.** (a) Edit person 'Bob', change name to 'Robert', tap another field (saved). Clear the name box and tap the Private checkbox: updatePerson is called with name 'Bob'. Done shows 'Bob'. (b) Person 'Tyler' with no relationship: clear the name box (intending to retype), check Private, press Done: Private is not saved.

**Suggested fix.** Keep a mutable `let lastName = existing ? existing.name : '';` in buildPersonForm; after a successful updatePerson set `lastName = name || lastName`. Use `name: name || lastName` and change the guard to `if (!(name || lastName) && !relationship) return;`. Apply the same `lastName` pattern in buildPlaceForm/commitPlaceNow.

**How to verify the fix.** Manual: the two scenarios above must end with 'Robert' and with Tyler marked Private. If the form logic is extracted, add a unit test in tests/relationships.test.mjs.

**Do not break.** Must still never write an empty name (CLAUDE.md: auto-save must not blank a name).

**Design reference.** CLAUDE.md 'A LIST THAT SHOWS AN ITEM AS ADDED HAS PROMISED IT IS SAVED': 'AUTO-SAVE MUST NOT BE ABLE TO BLANK A NAME... A rename still works'.

**Verification notes.** `existing` is a snapshot object from rel.listPeople(), which builds fresh objects, and the form is not re-rendered after commitNow. So existing.name stays the render-time name, and after a rename in the same form, blanking the box writes the old name back. The guard `if (!name && !relationship) return;` exits before any field is written. With an empty name box and no relationship, edits to Private and the other fields are dropped, Done included. commitPlaceNow uses the same stale existing.name fallback, though it has no early-return guard.
