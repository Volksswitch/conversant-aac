# CR-173: Two conversations started in the same second share one file name, and the second one erases the first

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** data-loss
- **Verdict:** confirmed (skeptic: plausible; reproducer: reproduced)
- **Location:** `app/js/storage.js:2069`
- **Also affects:** `app/js/storage.js:2120-2146 (startConversationLog opens the existing file with create:true and flushes over it)`; `app/js/storage.js:2074-2088 (resetConversationId)`; `app/js/storage.js:2661 (logError calls ensureConversationId, so a stray error mints the colliding id)`; `app/js/storage.js:2687-2701 (logErrorToConversation starts a log)`; `app/js/app.js:2823 (terminateConversation resets the id)`; `app/js/app.js:1730 (startFreshListening starts a log)`; `app/js/app.js:2048-2051 (choosing an opener mid-conversation tears down and the opener turn then starts a new log)`
- **Source:** g-storage-overflow-01

**What a user notices.** If a new conversation (or even a stray error) begins within the same second that the previous one ended, the earlier conversation's saved record is wiped and replaced by the new one. The person loses that conversation from review, usage figures and problem reports, with no warning.

**What is wrong.** Conversation ids are the ISO timestamp truncated to whole seconds: `new Date().toISOString().replace(/[:.]/g,'-').slice(0,19)` gives e.g. 2026-10-05T18-06-08. resetConversationId() clears currentConversationId and currentLogData, so the next ensureConversationId() mints a fresh id from the clock. If that happens in the same wall-clock second as the previous conversation's id was created... no - in the same second as the reset when the previous id was also minted in that second is not required; what matters is that the NEW id equals the OLD id string, which happens whenever the old conversation was started in second S and the new one is started in second S. More commonly: any two conversations whose starts fall in the same second. startConversationLog then calls dir.getFileHandle(`${id}.json`, {create:true}), which returns the EXISTING file, and flushLog() calls createWritable() (no keepExistingData), truncating it and writing the new conversation's data. The old file is gone. The same collision also makes logError entries of the two conversations share one id, and a `<id>.review.json` attaches to the wrong conversation. Measured with the real storage.js on an in-memory folder: start a log, write two user turns, resetConversationId(), logError('stt','connection closed') in the same second -> id1 === id2 === '2026-10-05T18-06-08', one file in conversations/, and its exchanges are ['error'] - both user turns lost. Note that the first conversation's id was minted when it started, so the collision needs the old conversation to have STARTED in the same second as the new one; in practice this is: (a) a very short conversation (e.g. an opener card chosen, then End, then Listen), (b) the error path - logError right after terminateConversation mints an id, and if the previous conversation was itself created lazily by an error moments earlier... Correction for precision: the decisive case measured is any new log whose id equals an existing file name; because ids encode the START second, two conversations collide when their starts are in the same second. A late error after End (already reported separately as creating a fake conversation) and a quick End -> Listen after a conversation that only just began are the realistic triggers; choosing an opener mid-conversation creates the new conversation only after the opener is spoken, so it collides only if the old conversation began in that same second.

**Evidence.**

```

app/js/storage.js:2127  const id = ensureConversationId();     // shared with the error log

Scratch run (real storage.js): { id1: '2026-10-05T18-06-08', id2: '2026-10-05T18-06-08', files: ['2026-10-05T18-06-08.json'], firstConversationTurnsLeft: 0, roles: ['error'] }
```

**How it happens.** 1) Press Listen (conversation file 12:00:05.json is created at 12:00:05.2). 2) Within the same second press End conversation (or the app ends it) and the deepgram 'stopped while connecting' error, or an immediate Listen tap, starts a new log at 12:00:05.8. 3) The new log gets id 12:00:05 again, opens the same file and overwrites it. Generally: any time two conversation logs are started inside one wall-clock second, the earlier file is replaced. Reproduced in node with the real module (see evidence).

> **Verifier correction to the trigger:** The overwrite only happens when two conversation ids are minted in the same second. The old id is minted when that conversation begins, so the earlier conversation must have begun, and ended, within that same second. Example: press Listen and then End conversation within one second, after which a late logError or another Listen starts a new log. What is lost is an essentially empty file holding the start context and perhaps a 'listen on' event, not a conversation with turns.

**Suggested fix.** Make ids unique and never reuse an existing file. In ensureConversationId(), keep the human-readable second-resolution stem but add milliseconds: `new Date().toISOString().replace(/[:.]/g, '-').slice(0, 23)` (gives 2026-10-05T18-06-08-123). Keep a module-level `lastIssuedId`; if the new id equals it, append `-2`, `-3`, ... In startConversationLog(), before `getFileHandle(currentLogName, {create:true})`, probe with `getFileHandle(currentLogName)` (no create) and if it already exists (and currentLogData is a fresh object, i.e. this is a new conversation), add a numeric suffix until a free name is found. Check every reader that parses the id back into a date (grep for `getConversationId`, `listConversationLogs`, review-ui sorting/'last week' filtering by file-name prefix, usage-summary) and make sure a longer id still parses - the 'last week' filter reads the date from the start of the name, which is unchanged.

> **Verifier correction to the fix (takes precedence):** The suggested fix (millisecond suffix plus a probe for an existing name) is fine as hardening, but treat it as low priority. Also check every reader that parses the id, including review-file pairing, before lengthening it.

**How to verify the fix.** Add to tests/storage-transcript.test.mjs: start a log, log two user turns, call resetConversationId(), then immediately startConversationLog() (and separately logError) in the same tick; assert two distinct files exist in conversations/ and the first still has both user turns. Also assert getConversationId() differs before and after the reset.

**Do not break.** The id is also the error-log correlation key and the review file stem (`<id>.review.json`); both must keep using the exact same string. Do not change the date prefix format, because the Conversation Review list skips old files by the date at the start of the name without opening them. Existing files on disk keep their old names and must still be listed and opened.

**Design reference.** CLAUDE.md 'Transcript mirrors the conversation pane' and 'THE STANDARD FOR THE RECORD IS CAN IT BE RECREATED TO THE SECOND'; storage.js comment at 2058-2065 (one id per conversation, shared with the error log)

**Verification notes.** The mechanism is real: ids are second-resolution, startConversationLog opens `${id}.json` with create:true and flushLog truncates it. But a collision needs the NEW id to equal the OLD one, and the old id is minted when the old conversation began (startFreshListening/startConversationLog or the first logError), never later. So the earlier conversation must have STARTED in the same wall-clock second as the new one, which means the whole earlier conversation lasted under a second. The reviewer's node proof wrote two user turns and reset inside one tick, which cannot happen in real use: each user turn is spoken aloud and takes seconds. In the reachable case (Listen, then End within the same second, then a late error or a fresh start mints the same id), the file being overwritten holds only the time-zero context entry and perhaps a 'listen on' event. A conversation created lazily by an error after End is not reset either, so a quick Listen merges into it instead of overwriting it. The data-loss impact claimed (losing a real conversation) is effectively unreachable.

**Reproduction (reproduced).** Method: Ran the real app/js/storage.js in node 24 (scratchpad repro.mjs and real.mjs). I used the in-memory directory handle and the browser shims from tests/storage-transcript.test.mjs: no showDirectoryPicker, and navigator.storage.getDirectory returns the fake root, so restoreDataFolder() adopts device storage. In the deterministic run I pinned Date to 18:06:08.200 and moved it forward with an offset. A second run used the real clock with no pinning. Each run called startConversationLog, logUserResponse, resetConversationId (what terminateConversation calls), then startConversationLog or logError again. Afterwards I read the bytes left in conversations/<id>.json. Scenario A (End, then a new log in the same second): conversation 1 was written with two user turns, 'Hi there' and 'How are you?', to 2026-10-05T18-06-08.json. After resetConversationId(), with the clock at 18:06:08.800, startConversationLog() produced id2 '2026-10-05T18-06-08', the same as id1. conversations/ still held only that one file, and its exchanges array was now [], so both earlier turns were gone. The cause runs through four lines. storage.js:2069 builds the id at whole-second resolution (slice(0,19)). Line 2139 calls getFileHandle(name,{create:true}), which returns the existing file. Line 2144 calls flushLog(). Line 2473 calls createWritable() without keepExistingData, which truncates the file and writes the new, empty log over it.

Scenario B (the error path): conversation 2026-10-05T18-06-13 with user turn 'Bye' was reset. Then logError('stt','connection closed') ran in the same second. It called ensureConversationId() (line 2661), which minted '2026-10-05T18-06-13' again. logErrorToConversation (lines 2687-2701) then started a log over that same file, and the file now holds only ['error']. The 'Bye' turn is lost, and the error is filed under the old conversation's id.

Real clock, no pinning: start, one user turn, reset, start again back to back gave id1 = id2 = '2026-10-05T18-10-41'. There was one file with 0 exchanges, so the earlier turn was erased.

Control: starts in different seconds (offsets 9000 and 10500 ms) produced separate files, 18-06-17.json and 18-06-18.json. That confirms the clash comes purely from the two starts falling in the same second.

I did not trace the app.js call sites (terminateConversation, startFreshListening, the opener path) step by step. The storage-level defect stands regardless: any two log starts inside one wall-clock second share an id and the later one truncates the earlier file.
