# CR-178: activeProfileUnsaved is dead code, and would report unsaved changes forever for a profile saved before the September layout migration

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** dead-code
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/storage.js:689`
- **Also affects:** `app/js/storage.js:1766-1816 migrateBundle (removes minGapPos/buttonSizePos only from the LIVE bundle)`; `tests/backup-folder.test.mjs:258-271 the only callers`; `git a29e692 removed the app.js callers (the 'offer to fold unsaved changes into the current profile' export flow)`
- **Source:** g-storage-overflow-07

**What a user notices.** None today, because nothing in the app calls it. If it were reconnected as it stands, anyone who saved a settings profile before September 2026 would be told forever that they had unsaved changes.

**What is wrong.** activeProfileUnsaved() has no caller in app/ (grep finds it only in storage.js and tests/backup-folder.test.mjs); its two app.js callers were removed in commit a29e692 ('One backup again, filtered at import by a device signature', September 9 2026) together with the export-time 'fold unsaved changes into the current profile' prompt. It is also wrong as written: it compares the RAW settings stored in the profile file against exportSettingsBundle(), which reads the live bundle that saveSettings has already passed through migrateBundle. A profile file saved before September 2026 still carries minGapPos and/or buttonSizePos and lacks the migrated buttonGapPos/convLayout values, so `differs` is true even immediately after loading that very profile, until the user re-saves it.

**Evidence.**

```
app/js/storage.js:701-705
    const a = (saved && saved.settings) || {};
    const b = exportSettingsBundle();
    const keys = [...new Set([...Object.keys(a), ...Object.keys(b)])].sort();
    const differs = keys.some((k) => JSON.stringify(a[k]) !== JSON.stringify(b[k]));
app/js/storage.js:1776  delete out.minGapPos;   and :1813  delete out.buttonSizePos;   (live bundle only)
`grep -rn activeProfileUnsaved app/` -> only app/js/storage.js:689
```

**How it happens.** Not reachable in the shipped app. If reconnected: load a profile file containing "buttonSizePos": 70 -> applySettingsProfile -> saveSettings migrates it (deletes buttonSizePos, writes convLayout) -> activeProfileUnsaved() compares file (has buttonSizePos, no convLayout) to live (no buttonSizePos, has convLayout) -> differs: true forever.

**Suggested fix.** Delete activeProfileUnsaved() and its test block in tests/backup-folder.test.mjs (the 'unsaved changes to the current profile are detectable before an export' test), since the feature it served was removed on purpose. If it is kept for a future staleness indicator (CLAUDE.md lists one as deferred), compare like with like: `const a = migrateBundle({ ...((saved && saved.settings) || {}) });` then strip PROFILE_EXCLUDE keys from `a` before the key comparison.

**How to verify the fix.** After deleting: `grep -rn activeProfileUnsaved app tests` returns nothing and `npm test` passes. If fixing instead: add a test that writes a profile file containing buttonSizePos: 70 and minGapPos: 40, applies it, then asserts activeProfileUnsaved().differs === false.

**Do not break.** The deferred 'settings-profile staleness indicator' in CLAUDE.md (Open Questions) would reuse this logic; if kept, it must migrate the saved side. Do not remove migrateBundle.

**Design reference.** CLAUDE.md Open Questions 'TO DO - decide whether the settings-profile STALENESS INDICATOR is worth its UI cost'; storage.js 'CARRYING A REMOVED SETTING FORWARD'

**Verification notes.** grep shows activeProfileUnsaved is defined at storage.js:689 and called only in tests/backup-folder.test.mjs, so it is dead code in the shipped app (commit a29e692 'One backup again, filtered at import by a device signature' exists). It also compares the profile file's raw settings against the live bundle, which has passed through migrateBundle in saveSettings. A file holding removed keys (minGapPos/buttonSizePos) would therefore always differ. There is no user impact today.
