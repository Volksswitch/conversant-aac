# CR-182: The launch-screen report button is wired after the code most likely to throw, and the failure card points to unreachable Settings

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** design-violation
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:609`
- **Also affects:** `app/js/app.js:437`; `app/js/app.js:465`; `app/js/app.js:514-537`; `app/index.html:80`
- **Source:** app-a-06

**What a user notices.** If the app fails while starting up, the 'send a report' link on the opening screen may do nothing, and the error message tells the person to use Settings, which cannot be opened before Start - so they have no way to report the problem from the device.

**What is wrong.** CLAUDE.md records that the pre-start report button's listener 'is attached early in initApp, before anything that can throw, because the tester who most needs it is the one whose app did not finish starting', and the code comment repeats that claim. In fact it is wired at line 609-610, after storage.migrateStoredSettings (which can call localStorage.setItem without a try/catch), metrics setup, viewport.init(), platform checks, stt.init (which constructs a SpeechRecognition or a paid source) and several hook registrations. A throw in any of those leaves the button inert. The startup-failure card's text (index.html:80) says 'Settings -> About -> Reload the app is worth trying first', but Settings is unreachable before Start (main.disabled) and, if initApp threw before line 597, Start itself is not wired either.

**Evidence.**

```
app/js/app.js:604-610
    // Reporting from the launch screen. Wired here, early in init, ON PURPOSE: the
    // tester who most needs it is the one whose app did not finish starting, so this
    // listener must be attached before anything that could throw. ...
    const startReportBtn = document.getElementById('startReportBtn');
    if (startReportBtn) startReportBtn.addEventListener('click', () => sendProblemReportFromStart());

app/js/app.js:437  storage.migrateStoredSettings();
app/js/app.js:519  stt.init({ ... });
app/index.html:80  <p class="setting-hint">Settings → About → Reload the app is worth trying first. ...</p>
```

**How it happens.** Any exception thrown in initApp before line 609 (for example localStorage.setItem raising QuotaExceededError during migrateStoredSettings on a full device, or a paid source constructor failing in stt.init): the startup-failure card appears, the 'If something is wrong — send a report' link does nothing, and the card's advice cannot be followed because Settings cannot be opened.

**Suggested fix.** Move the two lines that wire startReportBtn to the very top of initApp (before storage.setAppVersion), wrapped in their own try/catch so they can never be the thing that throws. Change the startup-error hint in index.html to advice that is reachable from that screen (e.g. 'Close the app completely and open it again. If it keeps happening, tap the report link below - this text is included.').

> **Verifier correction to the fix (takes precedence):** Moving the wiring to the top of initApp is right. sendProblemReportFromStart is a function declaration so hoisting is fine, but check it does not depend on anything initApp sets up later (e.g. metrics.setEnabled or storage.setAppVersion) - if it does, have it tolerate that state rather than reorder those calls after the listener.

**How to verify the fix.** Manual: temporarily throw at the top of viewport.init in a local build, load the app, confirm the failure card shows and the report link still opens its preview dialog. Revert the throw.

**Do not break.** The report must keep its preview-then-confirm step (the tester sees the exact text before sending). Do not let report wiring depend on Settings or storage being healthy.

**Design reference.** CLAUDE.md 'Beta instrumentation and error reporting - AS BUILT items 1 and 2' (pre-start affordance wired early, before anything that can throw)

**Verification notes.** The code comment at app.js:604-608 (and CLAUDE.md's AS BUILT note) says the launch-screen report listener is attached before anything that could throw, but it is wired at app.js:609-610, after storage.migrateStoredSettings (storage.js:1820-1824 -> saveSettings at 398-404, an unguarded localStorage.setItem), metrics setup, viewport.init, stt.init (which constructs SpeechRecognition or a paid source) and several hook registrations. A throw anywhere there is caught at app.js:8483-8487 and the card shown, but the report link is then inert. The card's text (index.html:80) recommends Settings -> About -> Reload, and #settingsBtn sits inside #listenControls under <main class="disabled">, which has pointer-events: none (styles.css:1103-1105) until Start completes; if initApp threw before line 597 Start is not wired either. Low likelihood of a throw in practice, hence low severity.
