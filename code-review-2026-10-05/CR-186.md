# CR-186: Choosing OpenAI, Google Cloud or ElevenLabs as the speaking voice with no key gives no warning

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** design-violation
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:7788`
- **Also affects:** `app/js/app.js:7381-7391 (the hearing-service radio does check all five services)`; `app/js/app.js:7790 (merged duplicate: Choosing a catalog speaking voice with no key gives no warning, unlike Deepgram and Azure)`; `app/js/app.js:7790 (merged duplicate: Choosing an OpenAI, Google Cloud or ElevenLabs voice without a key gives no warning)`
- **Source:** app-f-04, x-contracts-11, x-providers-07

**What a user notices.** Picking a paid voice from three of the five services without having entered its key looks like it worked, but every sentence then falls back to the device voice; only Deepgram and Azure tell the user to add a key.

**What is wrong.** The ttsProvider radio handler explains that choosing a paid voice with no key is the commonest way to end up silently falling back, and warns - but only for 'deepgram' and 'azure'. The three catalog services fall through with no message. This is the exact two-service if/else-meets-five-services shape CLAUDE.md warns about; the sttProvider handler right above already handles all five via storage.loadServiceKey.

**Evidence.**

```
app/js/app.js:7784-7794
  // Choosing a paid voice with no key is the commonest way to end up with a
  // setting that looks applied and silently falls back on every utterance, ...
  showAuraStatus('own', null, ''); showAzureVoiceStatus('own', null, '');
  if (radio.value === 'deepgram' && !(storage.loadDeepgramKey() || '').trim()) { showAuraStatus('own','warn', ...); }
  else if (radio.value === 'azure' && !(storage.loadAzureKey() || '').trim()) { showAzureVoiceStatus('own','warn', ...); }
```

**How it happens.** With no ElevenLabs key saved: Settings > Speech > speaking voice: ElevenLabs. No message appears; the user closes Settings and every utterance comes out in the device voice (logged as a fallback error).

**Suggested fix.** Add a third branch: `else if (TTS_PROVIDERS[radio.value] && !(storage.loadServiceKey(radio.value) || '').trim()) { setStatusLine(radio.value + 'VoiceStatus', 'warn', `Add your ${TTS_PROVIDERS[radio.value].label} key above, then tap Test.`); }` and clear each catalog service's VoiceStatus at the top alongside the Aura/Azure clears.

**How to verify the fix.** Manual: with no ElevenLabs key, select ElevenLabs as the speaking voice - a warning appears under its voice picker; add the key and it clears (see the stale-status finding).

**Do not break.** Use the existing `${id}VoiceStatus` element (shown by showVoiceStatus in the catalog loop) so no new per-control hint text is added (Rule 14 allows live status).

**Design reference.** CLAUDE.md 'A two-service if/else met five services' (September 30 2026); UI Layout Rule 14 (live status allowed).

**Verification notes.** The ttsProvider onchange handler (app.js:7777-7796) clears and sets the add-a-key warning only for 'deepgram' and 'azure'. The catalog services (openai/google/elevenlabs) fall through with no message, even though each has its own `${id}VoiceStatus` element in index.html (673/681/689) and the sttProvider handler just above (7381-7384) already checks all five via loadServiceKey. CLAUDE.md records this same two-branch-meets-five-services shape as a known trap.

<details><summary>Merged duplicate x-contracts-11: Choosing a catalog speaking voice with no key gives no warning, unlike Deepgram and Azure</summary>

The ttsProvider radio handler shows the 'Add your ... key above, then tap Test' warning only for 'deepgram' and 'azure'. <details><summary>Merged duplicate x-providers-07: Choosing an OpenAI, Google Cloud or ElevenLabs voice without a key gives no warning</summary>

The speaking-voice radio handler warns about a missing key only for Deepgram and Azure. For the catalog services there is no check, although the comment above says the warning exists because 'choosing a paid voice with no key is the commonest way to end up with a setting that looks applied and silently falls back on every utterance'. It also clears only the Aura and Azure status lines, so a stale status on an OpenAI/Google/ElevenLabs voice row is left behind.

Fix as proposed by that reviewer: After the Azure branch add: `else if (TTS_PROVIDERS[radio.value] && !serviceKeyFor(radio.value)) { setStatusLine(radio.value + 'VoiceStatus', 'warn', `Add your ${TTS_PROVIDERS[radio.value].label} key above, then tap Test.`); }`, and before the checks clear every catalog voice status: `for (const id of Object.keys(TTS_PROVIDERS)) setStatusLine(id + 'VoiceStatus', null, '');`.

</details>
