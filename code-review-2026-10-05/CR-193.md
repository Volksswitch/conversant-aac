# CR-193: errors.log gets fancy punctuation through the error's extra detail, breaking the plain-ASCII log rule

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** design-violation
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/storage.js:2708`
- **Also affects:** `app/js/storage.js:2635-2639 (asciiForLog)`; `app/js/storage.js:2665 (extra stored raw in the ring buffer)`; `app/js/app.js:1944-1947 (extra.reply holds up to 400 characters of AI output)`; `app/js/storage.js:2707 (merged duplicate: errors.log lines can carry non-ASCII punctuation through the error's extra detail)`
- **Source:** storage-06, x-rules-07

**What a user notices.** Lines in the error file can show garbled characters when opened in a text editor or pasted into an email, which is what the plain-text rule exists to prevent.

**What is wrong.** logError passes context and message through asciiForLog, but appendErrorFile appends `JSON.stringify(entry.extra)` unsanitized. extra.reply carries the AI's unreadable reply (frequently containing em dashes and curly quotes) and extra.partner carries recognizer text, so typographic characters reach errors.log. CLAUDE.md states the rule applies so 'the same scrubbed text reaches all four sinks'. Reproduced: an extra of {reply:'He said — “hi”…'} appeared verbatim in errors.log.

**Evidence.**

```
app/js/storage.js:2707-2708:
        const line = `${entry.ts} v${entry.version} conv=${entry.conversation} [${entry.context}] ${entry.message}`
            + (entry.extra ? ` | ${JSON.stringify(entry.extra)}` : '') + '\n';
```

**How it happens.** Generation returns an unparseable reply containing an em dash; logError('generateOptions', ..., { reply }) writes the em dash into errors.log.

**Suggested fix.** In logError, after the privacy strip, sanitize string values of extra: `if (extra && typeof extra === 'object') { extra = Object.fromEntries(Object.entries(extra).map(([k, v]) => [k, typeof v === 'string' ? asciiForLog(v) : v])); }`. That covers all sinks (ring buffer, errors.log, conversation file). asciiForLog maps punctuation only, so accented letters survive.

**How to verify the fix.** Add a test (tests/storage-transcript.test.mjs or a new tests/storage-errorlog.test.mjs): logError('x','y',{reply:'a — “b”…', partner:'José'}); read errors.log and the ring buffer; assert no characters from the LOG_ASCII map remain and 'José' is intact.

**Do not break.** Punctuation-only mapping: never strip non-ASCII letters (CLAUDE.md is explicit about 'José'). Keep the privacy strip before this.

**Design reference.** CLAUDE.md 'Logs are ASCII, and a permission prompt is not a hang'

**Verification notes.** logError maps only context and message through asciiForLog; appendErrorFile appends JSON.stringify(entry.extra) unchanged (storage.js:2707-2708), and JSON.stringify does not escape non-ASCII characters. extra.reply (up to 400 characters of AI output, app.js:1944-1947) and extra.partner routinely carry em dashes and curly quotes, so they reach errors.log, the ring buffer and the conversation file. CLAUDE.md states log text is plain ASCII and that the scrub reaches all sinks; extra.reply was added later and was never covered.
