# CR-195: An Express phrase's respelling is announced to the echo filter and 'now playing' line instead of its display text

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** design-violation
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/tts.js:337`
- **Also affects:** `app/js/app.js:3718`; `app/js/app.js:5187`; `app/js/express-editor.js:284-287`; `app/js/app.js:575-582`
- **Source:** tts-11

**What a user notices.** For an Express button with a 'how to say it' respelling, the app tells its own speech-filter the made-up spelling rather than the real words, so the filter is less able to recognize the app's own voice if the microphone hears it; in Settings the playing line shows the respelling.

**What is wrong.** tts.speak(text) announces `text` and speaks `pronounce(text)`, which is correct for names in the lexicon. But Express phrases carry their own respelling (item.speak) and the app passes THAT as `text`: speakAsUserTurn(phrase.text, phrase.speak || phrase.text) -> speakUserStatement(spokenText) -> tts.speak(spokenText). So notifySpeaking receives the respelling, which stt.noteSpokenStart uses for echo matching, and ui.setNowPlaying shows when not suppressed (e.g. the editor's 🔊 button). CLAUDE.md states the DISPLAY form must be what is announced, since speech-to-text normalizes a respelling back to the real word.

**Evidence.**

```
tts.js:337-338 `notifySpeaking(text); const said = pronounce(text);`
app.js:5187 `await speakAsUserTurn(phrase.text, phrase.speak || phrase.text, 'express');`
app.js:3718 `await speakUserStatement(spokenText);`
app.js:580-582 `tts.onSpeakingChange((speaking, text) => { if (speaking) stt.noteSpokenStart(text); ...`
express-editor.js:286-287 `const said = (inputs[1] && inputs[1].value.trim()) || ...; if (said) tts.speak(said);`
```

**How it happens.** Express phrase 'Volksswitch' with respelling 'Folks-switch'. Tap it, listening resumes; a delayed recognizer result 'Volkswitch' arrives within the echo window; it is compared against 'folks switch' and may not be recognized as the app's own speech, so it is filed as partner speech.

**Suggested fix.** Add an optional display override to tts.speak: `export function speak(text, opts = {})` -> announce `opts.display || text`, keep `said = pronounce(text)`. In app.js speakUserStatement accept and forward a display string, and pass `historyText` from speakAsUserTurn: `await speakUserStatement(spokenText, { display: historyText })`. In express-editor.js pass `{ display: inputs[0].value.trim() }`.

**How to verify the fix.** Add to tests/tts.test.mjs: register onSpeakingChange, call speak('Folks-switch', { display: 'Volksswitch' }) and assert the listener received 'Volksswitch' while the synthesizer (mock speechSynthesis) received 'Folks-switch'.

**Do not break.** The conversation record must keep both fields as today (selectedText = display, spokenText = what was said). The respelling must not reach the transcript or LLM.

**Design reference.** CLAUDE.md 'Display text vs. spoken text' ('THE SEAM IS ONE LINE IN tts.speak ... notifySpeaking(text) keeps the DISPLAY form')

**Verification notes.** handleSpeakExpressItem passes phrase.speak || phrase.text as spokenText (app.js:5187); speakAsUserTurn calls speakUserStatement(spokenText) (3718), which calls tts.speak(text) (268), and tts.speak announces its argument via notifySpeaking (337) to the echo filter (app.js:580-582 -> stt.noteSpokenStart). So for an Express phrase with a respelling, the echo filter and now-playing listeners get the respelling, against the CLAUDE.md rule that the display form is announced. Same in express-editor.js:286-287. Impact is small: the mic is stopped during the user statement, so only a late recognizer result inside the echo match window is affected, and the fuzzy matcher tolerates small edits.
