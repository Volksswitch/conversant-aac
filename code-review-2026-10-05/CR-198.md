# CR-198: Installed-app manifest allows any orientation although the app is landscape-only

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** design-violation
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/manifest.webmanifest:9`
- **Source:** reporting-platform-15

**What a user notices.** On an Android tablet or phone where the app is installed, turning the device sideways switches the app to a portrait layout it was never designed for, which moves every button out from under a keyguard.

**What is wrong.** UI Layout Rule 2 makes the app landscape-only and Rule 1 requires static geometry for keyguards, but the manifest declares orientation 'any', so an installed app on Android (which honors the manifest) rotates to portrait.

**Evidence.**

```
app/manifest.webmanifest:9: `"orientation": "any",`
```

**How it happens.** Install the app on an Android tablet, start it, rotate to portrait: the layout reflows into an unplanned portrait arrangement.

**Suggested fix.** Change to `"orientation": "landscape"` (iPadOS ignores it; Android installed apps lock to landscape).

**How to verify the fix.** Install on an Android device, rotate; the app must stay in landscape.

**Do not break.** If Ken has intentionally allowed portrait for phones, confirm with him before changing; CLAUDE.md does not record such a decision.

**Design reference.** CLAUDE.md UI Layout Rules 1 and 2

**Verification notes.** manifest.webmanifest:9 declares "orientation": "any". UI Layout Rule 2 makes the app landscape-only and Rule 1 requires fixed geometry for keyguards. Nothing in CLAUDE.md or TODO.md records allowing portrait, and no code locks orientation. Installed Android web apps honor the manifest orientation, so the device can rotate into an unplanned portrait layout. iPadOS ignores the field, as the reviewer says. The cautions are right: Android phones were measured too, so confirm the change with Ken.
