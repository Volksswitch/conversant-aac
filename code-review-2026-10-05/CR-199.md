# CR-199: repromoteSettingsOverFullscreen comment says the Settings dialog has no 'close' listener; help-mode registers one

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** doc-mismatch
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:5578`
- **Also affects:** `app/js/help-mode.js:287`; `app/js/help-mode.js:288`; `app/js/app.js:5587`
- **Source:** g-misc-overflow-07

**What a user notices.** Nothing visible today. The risk is that a future change relies on this comment and adds work to the dialog's close event, which would then run every time the user turns on 'Use the whole screen' from inside Settings.

**What is wrong.** The safety argument for calling dlg.close() then dlg.showModal() in repromoteSettingsOverFullscreen states there is no 'close' listener and the only listener is 'cancel'. help-mode.js init() registers both `dialog.addEventListener('close', reset)` and `dialog.addEventListener('cancel', reset)` on the same #settingsDialog, so every re-promotion fires help-mode's reset(), disarming spoken help and cancelling any help speech. Today that is harmless in practice (an armed tap is swallowed, so the fullscreen checkbox cannot be toggled while help is armed, and a same-group tap during speech already stops speech before it acts), but the comment's premise is false and the 'close' event is now a hidden side channel of the fullscreen toggle. (The separate finding that help-mode relies on the 'close' event at all is already reported against help-mode.js:287; this item is only the false premise in app.js.)

**Evidence.**

```
app.js:5578-5579  // Safe to close() here: there is no 'close' listener (the one listener is 'cancel', // which close() does not fire -- it is Escape only)
app.js:5587-5588  dlg.close(); dlg.showModal();
help-mode.js:287-288  dialog.addEventListener('close', reset); dialog.addEventListener('cancel', reset);
app.js:278-279  helpMode.init({ dialog: document.getElementById('settingsDialog'), ...
```

**How it happens.** Read the comment, then grep for listeners on #settingsDialog: help-mode.js registers a 'close' listener. Turning on 'Use the whole screen' from Settings (General) fires fullscreenchange -> repromoteSettingsOverFullscreen -> dlg.close() -> help-mode reset().

**Suggested fix.** Correct the comment to: "Safe to close() here: the only 'close' listener on this dialog is help-mode's reset(), which merely disarms spoken help - harmless, because an armed tap cannot reach the fullscreen checkbox. Any NEW close listener on #settingsDialog will also run on every fullscreen re-promotion, so do not add one (CLAUDE.md: dialog cleanup runs explicitly in the Close handler, never on 'close')." No code change is required; if help-mode's 'close' listener is later removed per its own finding, update this comment again.

**How to verify the fix.** Code review only: grep -n "addEventListener('close'" app/js/*.js and confirm the comment matches the result.

**Do not break.** Do not change the close()/showModal() re-promotion itself; it is the fix for fullscreen painting over Settings (Rule 19).

**Design reference.** CLAUDE.md UI Layout Rule 19 ('Use the whole screen') and Standing findings: 'The <dialog> close event is unreliable here (v0.2.17)'

**Verification notes.** The comment at app.js:5578-5579 says #settingsDialog has no 'close' listener. help-mode.js:287 registers dialog.addEventListener('close', reset) on the same dialog (passed in at app.js:278). So repromoteSettingsOverFullscreen's dlg.close() fires help-mode's reset() on every fullscreen re-promotion. As the reviewer says, this is harmless today. The defect is a false premise in a comment. A grep finds no other close listener or onclose on the dialog.
