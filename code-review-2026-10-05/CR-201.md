# CR-201: Display diagnostics label the visual viewport as the layout viewport (contrary to UI Rule 13)

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** doc-mismatch
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/viewport.js:30`
- **Also affects:** `app/js/viewport.js:32`; `app/js/viewport.js:57`; `app/js/viewport.js:69`; `app/js/diagnostics.js:97`
- **Source:** g-a11y-overflow-09

**What a user notices.** Nothing changes on screen, but a problem report from a zoomed iPad shows the wrong screen size under the heading meant to diagnose exactly that, so a keyguard misalignment caused by zoom could be misdiagnosed.

**What is wrong.** getMetrics() reports window.innerWidth/innerHeight as 'layoutViewport' and comments it as 'the number that matters', and labels documentElement.clientWidth/Height 'Same, minus scrollbars'. CLAUDE.md UI Rule 13 records that in Safari innerWidth/innerHeight are the VISUAL viewport (they shrink under pinch zoom) and that the layout viewport is documentElement.clientWidth/Height (app.js layoutVW/layoutVH). The 'aspect' field and the console log line ('layout WxH') are also computed from innerWidth/innerHeight. Nothing decides layout or keyguard output from these values - the only consumer is diagnostics.js (info.display, shown in the DISPLAY block of the problem report) - so this is a mislabelled diagnostic, but it is wrong in the one situation it exists for: under zoom 'layoutViewport' and 'visualViewport' read the same, hiding the layout-vs-visual difference.

**Evidence.**

```
app/js/viewport.js:29-30 // The box our page actually lays out against (the number that matters).
        layoutViewport: { w: window.innerWidth, h: window.innerHeight },
app/js/viewport.js:31-35 // Same, minus scrollbars. clientBox: { w: document.documentElement.clientWidth, h: document.documentElement.clientHeight },
app/js/viewport.js:57-58 aspect: window.innerHeight ? +(window.innerWidth / window.innerHeight).toFixed(3) : null,
app/js/app.js:4699 const layoutVW = () => document.documentElement.clientWidth || window.innerWidth;
```

**How it happens.** On an iPad in a Safari tab, pinch-zoom to 2x and send a problem report: DISPLAY shows layoutViewport ~half the real width, matching visualViewport, while the app actually lays out against clientBox.

> **Verifier correction to the trigger:** Pinch-zoom is blocked by blockZoomGestures, so the example (pinch to 2x in a Safari tab) is mostly unreachable. The mislabel shows only if that blocking is bypassed, for example by an OS accessibility zoom on iPadOS Safari. In Chromium the two numbers are equal.

**Suggested fix.** In getMetrics: set layoutViewport to { w: document.documentElement.clientWidth || window.innerWidth, h: document.documentElement.clientHeight || window.innerHeight } (same expression as app.js layoutVW/layoutVH); rename the current innerWidth/innerHeight pair to innerWindow with comment 'window.innerWidth/Height - equals the visual viewport in Safari under zoom'; drop clientBox (now identical) or keep it with a corrected comment; compute aspect from layoutViewport. Update the log() line to use the corrected layoutViewport.

**How to verify the fix.** Add tests/viewport.test.mjs stubbing globalThis.window/document/screen with innerWidth 600 and documentElement.clientWidth 1180 and assert getMetrics().layoutViewport.w === 1180.

**Do not break.** Any report reader (scripts/report-eval, evaluate-beta) that reads display.layoutViewport keys - grep scripts/ before renaming fields; keep 'layoutViewport' as the key name so readers keep working.

**Design reference.** CLAUDE.md UI Layout Rule 13 (No zoom; measure from the layout viewport)

**Verification notes.** viewport.js:29-30 reports window.innerWidth/innerHeight as 'layoutViewport' and calls it 'the number that matters', while app.js (layoutVW/layoutVH) lays out against documentElement.clientWidth/Height, as UI Rule 13 requires. The label is wrong. The impact is narrower than stated. In Chromium, innerWidth is the layout viewport even under pinch, so the two values agree there. They differ only in Safari under pinch-zoom, and blockZoomGestures (app.js:4719) blocks pinch-zoom. visualViewport.scale is also in the report, so a zoom state is still visible. Note that scripts/report-eval/analyze.mjs:229 reads layoutViewport.w to compare against screen.w ('running in a small window'), so the key name must stay.
