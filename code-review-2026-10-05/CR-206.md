# CR-206: Every uncaught error during a conversation is logged as a 'startup' failure

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** other
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:8456`
- **Also affects:** `app/js/app.js:8474-8475 (session-long window error/unhandledrejection listeners)`; `app/js/app.js:7198-7212 (deleteSettingsProfile not caught, so a failure only surfaces here)`; `app/js/app.js:8456 (merged duplicate: Mid-conversation crashes are logged as 'startup:promise' errors)`
- **Source:** app-f-09, live-runtime-10

**What a user notices.** Problems that happen mid-conversation are filed in the error log and the weekly report as start-up failures, which points anyone reading the reports at the wrong part of the app.

**What is wrong.** The window 'error' and 'unhandledrejection' listeners stay attached for the whole session (the comment acknowledges this), and reportStartupFailure always logs with context 'startup:script' or 'startup:promise' before it checks whether the pre-start screen is still up. So a runtime rejection (for example the uncaught await storage.deleteSettingsProfile at 7206, or a rejected tts.speak from a Test button) is recorded as a startup failure. The weekly report and 'evaluate beta' group errors by context, so these are miscounted as startup problems. The profile Delete handler also shows no status message when deletion fails.

**Evidence.**

```
app/js/app.js:8456 try { storage.logError('startup:' + where, msg); } catch { ... }
app/js/app.js:8464-8465 const startBlock = ...; if (!startBlock || startBlock.classList.contains('hidden')) return;   // checked AFTER logging
app/js/app.js:7206 await storage.deleteSettingsProfile(name);   // no try/catch
```

**How it happens.** After Start, with the data folder permission revoked, Settings > About > select a profile > Delete > confirm. The rejection reaches unhandledrejection and is logged as 'startup:promise'; the Settings status line says nothing.

> **Verifier correction to the trigger:** A clearer trigger: after Start, any unhandled rejection (for example Promise.reject(new Error('x')) in devtools, or a rejected promise from a Test button) is logged as 'startup:promise'. For Delete profile, only a throw from getSettingsDir reaches the global handler, because removeEntry errors are swallowed inside storage.

**Suggested fix.** In reportStartupFailure compute `const started = !startBlock || startBlock.classList.contains('hidden');` first and log with context `(started ? 'uncaught:' : 'startup:') + where`. Wrap the Delete handler body in try/catch and call setProfileStatus(err.message || 'Could not delete the profile.') on failure.

**How to verify the fix.** Manual: throw a test rejection after Start (devtools: Promise.reject(new Error('x'))) and check the error log context reads 'uncaught:promise'.

**Do not break.** Keep 'first failure wins' and keep logging wrapped so the handler can never throw.

**Design reference.** app.js reportStartupFailure header comment; CLAUDE.md 'Error reporting — audited against expectation'.

**Verification notes.** reportStartupFailure (app.js:8453-8472) logs with context 'startup:'+where before it checks whether the pre-start block is still visible. The window 'error' and 'unhandledrejection' listeners (8474-8475) stay attached for the whole session. The function's own comment says a mid-conversation rejection 'is not a startup failure — it belongs in the error log', yet it is filed under a 'startup:' context. The suggested fix is correct. The Delete-profile example is weak: storage.deleteSettingsProfile (storage.js:708-713) swallows removeEntry errors, so only a throw from getSettingsDir would escape it.

The global 'error' and 'unhandledrejection' listeners stay attached for the whole session and call reportStartupFailure, which always logs with context 'startup:' + where, even though its own comment says a rejection during a conversation 'is not a startup failure - it belongs in the error log'. The context should reflect whether the pre-start screen was still up.

Fix as proposed by that reviewer: In reportStartupFailure compute `const atStartup = startBlock && !startBlock.classList.contains('hidden');` before logging and use `storage.logError((atStartup ? 'startup:' : 'runtime:') + where, msg)`.
