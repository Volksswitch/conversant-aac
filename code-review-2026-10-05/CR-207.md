# CR-207: No test ties Settings text fields to the on-screen keyboard's scope list

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** other
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/keyboard.js:38`
- **Also affects:** `app/index.html:517`; `app/index.html:527`; `app/index.html:555`; `app/index.html:565`; `app/index.html:588`; `app/index.html:1015`; `app/index.html:1023`; `app/index.html:1108`; `app/index.html:1160`; `tests/ui-standards.test.mjs:173`
- **Source:** g-test-suite-05

**What a user notices.** When a new text box is added to Settings, nothing checks whether the app's own keyboard serves it, so on a touch tablet the system keyboard can pop up over the panel instead.

**What is wrong.** IN_SCOPE is a hand-maintained selector of ids. Of the editable inputs in index.html's Settings, azureKeyInput, azureRegionInput, openaiKeyInput, googleKeyInput, elevenlabsKeyInput, testerNameInput, and the number inputs bandContextInput, bandFlexInput and titleBarHeightInput are not matched (the key/region/tester gaps are already reported as a bug). The gap is that no test compares the two, so each new field repeats the omission. A deliberate exclusion (for example read-only report textareas) should be recorded in the test rather than discovered.

**Evidence.**

```
app/js/keyboard.js:38: const IN_SCOPE = '#composerInput, #reviewWordInput, .wv-text, #apiKeyInput, #deepgramKeyInput, #controlEditor input, #expressEditor input, #settingsProfileNameInput, #problemNoteInput, #practicePanel input[type="text"], #practicePanel textarea';
app/index.html:517: <input type="text" id="azureKeyInput" ...>  app/index.html:1160: <input type="text" id="testerNameInput" ...>  app/index.html:1015: <input type="number" id="bandContextInput" ...>
```

**How it happens.** 1) Add a new <input type="text"> to a Settings tab. 2) npm test passes. 3) With Settings > keyboard set to on-screen on a Windows tablet, focus the field: the Windows touch keyboard appears over the panel instead of the app keyboard.

**Suggested fix.** Export IN_SCOPE from keyboard.js (export const IN_SCOPE = ...). Add to tests/ui-standards.test.mjs a test that walks every Settings tab (and the About Me screens it already visits), collects every visible input of type text/search/number/password and every non-readonly textarea, and asserts el.matches(IN_SCOPE) unless the id is in an ALLOWED_OUTSIDE list where each entry carries its reason (same DELIBERATE pattern the file already uses).

**How to verify the fix.** The new test must fail today listing the fields above; after the separately reported scope fix (or adding reasoned exclusions for the number inputs) it passes. Mutation: remove '#apiKeyInput' from IN_SCOPE and confirm failure.

**Do not break.** Read-only textareas (weeklyReportContents, usageSummaryView, errorLogView, systemInfoView, weeklySendLogView) must not be forced into scope. Exporting the constant must not change its value.

**Design reference.** CLAUDE.md 'In My Own Words — keyboard-selection design' (onscreen mode suppresses the OS keyboard on in-scope fields) and UI Layout Rule 24 (control standards enforced by a browser test).

**Verification notes.** IN_SCOPE in keyboard.js:38 names apiKeyInput and deepgramKeyInput. It does not name the other text inputs in Settings: azureKeyInput, openaiKeyInput, testerNameInput and others. Those are type=text in index.html, so they fall outside the app keyboard. No test compares the Settings inputs with IN_SCOPE, so a new field can repeat the omission. The number inputs may be deliberately out of scope, and the proposed allowlist handles that.
