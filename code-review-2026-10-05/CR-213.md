# CR-213: Voice caches are capped by count only and store every unique AI sentence, which can use hundreds of megabytes

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** performance
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/tts-azure.js:474`
- **Also affects:** `app/js/tts-azure.js:56`; `app/js/tts-deepgram.js:71`; `app/js/tts-deepgram.js:563`; `app/js/tts-rest.js:56`; `app/js/tts-rest.js:291`
- **Source:** tts-06

**What a user notices.** During a long day of conversation with a paid voice, the app keeps every sentence it has said in memory, which on an iPad can make the browser reload the page unexpectedly.

**What is wrong.** Each backend caches up to 300 entries, justified as 'entries are short phrases' that repeat (placeholders, Express buttons). But remember() is called for every fresh utterance, including every one-off AI response and composed statement, which never repeat. Azure/REST cache decoded AudioBuffers at the AudioContext's sample rate (commonly 48 kHz, 4 bytes/sample): a 4 s sentence is ~770 KB, so 300 entries approach ~200 MB per backend; Deepgram caches Float32 at 24 kHz (~380 KB per 4 s). Each backend that has been used (including via Settings Test) holds its own cache and its own AudioContext, and none is ever released (reset() is never called).

**Evidence.**

```
tts-azure.js:56 `const MAX_CACHE_ENTRIES = 300;`
tts-azure.js:474 `remember(key, buffer);      // so the next time this phrase is said, it is instant`
tts-deepgram.js:563 `remember(key, samples);`
tts-rest.js:291 `remember(k, buffer);`
tts-deepgram.js:46-51 comment justifying the cache by repeated short phrases
```

**How it happens.** Use Azure for several hours of conversation; each AI response is unique; memory grows by roughly the decoded size of every sentence spoken until 300 are held. On an iPad 10th gen (4 GB) combined with the rest of the page this risks a tab reload mid-conversation.

**Suggested fix.** Cap by size, not just count: track total samples (Deepgram: samples.length; Azure/REST: buffer.length * buffer.numberOfChannels) in a running total and evict oldest until under a budget (e.g. 20 million samples ≈ 80 MB, or smaller). Simpler alternative matching the stated purpose: only cache when the text is short (e.g. `trimmed.length <= 80`).

**How to verify the fix.** Add a unit test per backend that speaks 400 distinct long texts against mocks and asserts the cached total stays under the budget, and that a short phrase spoken twice is still served from cache the second time (no second fetch/socket send).

**Do not break.** Repeated short phrases (placeholders, Express buttons, control phrases) must stay cached, since the cache is what keeps those instant and unbilled.

**Design reference.** tts-deepgram.js 'WHY THE CACHE IS NOT AN OPTIMIZATION' comment

**Verification notes.** remember() is called for every fresh utterance in all three backends (tts-azure.js:474, tts-rest.js:291, tts-deepgram.js:563), with a count-only cap of 300 (tts-azure.js:56, tts-deepgram.js:71, tts-rest.js:56). Unique AI responses and composed statements are therefore cached even though they never repeat, contrary to the stated justification that entries are short repeated phrases. Azure/REST store decoded AudioBuffers at the context rate, so memory can reach the hundreds of MB the reviewer estimates after many unique utterances. Whether this actually triggers a tab reload on a tablet is not demonstrated, so low severity.
