# CR-215: The Start button stays tappable for up to 14 seconds with no feedback, and a second tap runs the start-up twice

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** race-condition
- **Verdict:** confirmed (skeptic: plausible)
- **Location:** `app/js/app.js:1518`
- **Also affects:** `app/js/app.js:597 startBtn click -> handleStart`; `app/js/app.js:1600 afterFolderNotice awaits settleRestore up to FOLDER_ANSWER_GRACE_MS`; `app/js/app.js:1523 engine.reset()`; `app/js/app.js:1475 (merged duplicate: The Start button stays live during the storage warm-up, so a second tap runs the whole start-up sequence twice)`
- **Source:** app-b-12, x-async-12

**What a user notices.** On a slow device (Android with a data folder), tapping Start can appear to do nothing for many seconds; tapping it again starts everything a second time, which can reset the conversation state after the user has already begun.

**What is wrong.** handleStart awaits warmUpStorage for up to STORAGE_WARMUP_MS (6s); when there is no What's new notice, afterFolderNotice then awaits settleRestore for up to FOLDER_ANSWER_GRACE_MS (8s). During both waits the Start button is visible, enabled and unchanged. A second tap runs handleStart again: a second warmUpStorage (concurrent load/syncToFolder of every data file), a second pre-start chain, and a second engine.reset() that can land after the first chain already entered the conversation.

**Evidence.**

```
app/js/app.js:597 `document.getElementById('startBtn').addEventListener('click', handleStart);`
app/js/app.js:1518 `await withTimeout(warmUpStorage(), STORAGE_WARMUP_MS, 'storage warm-up');`
app/js/app.js:1523 `engine.reset();`
app/js/app.js:1600 `try { await storage.settleRestore(FOLDER_ANSWER_GRACE_MS); } catch { /* decide anyway */ }`
```

**How it happens.** Android, folder remembered, slow restore. Tap Start: nothing visible. Tap again 3 s later. First chain finishes and the user taps an Express phrase; the second chain's warm-up then completes and calls engine.reset(), discarding the sequence stack mid-conversation.

**Suggested fix.** Add a module-level `let startInProgress = false;`. At the top of handleStart: `if (startInProgress) return; startInProgress = true;` and disable the button visually (`startBtn.disabled = true` plus a status/label such as 'Starting…'). Reset `startInProgress = false` and re-enable in finishStart() (and if any pre-start step returns the user to the start block). Keep the synchronous gesture-bound calls (chime.unlock, tts.unlockAudio, requestFolderPermissionNow, requestAppFullscreen) above the first await.

**How to verify the fix.** Manual: throttle storage (or add a temporary delay in restoreDataFolder in a scratch build), double-tap Start, confirm handleStart runs once and the button shows it is working.

**Do not break.** Do not add any await before requestFolderPermissionNow/requestAppFullscreen; user activation must not be spent. The startup-failure card must still be reachable.

**Design reference.** CLAUDE.md 'Android — MEASURED' (request on the Start tap) and the pre-start sequence notes in handleStart.

**Verification notes.** handleStart has no re-entry guard and does not disable the Start button before awaiting warmUpStorage (up to 6s) and the later folder grace wait; a second tap would rerun warm-up, requestFolderPermissionNow and engine.reset(). The mechanism is real, but on most devices warm-up completes in milliseconds, and whether a second chain's engine.reset can actually land after the first chain has entered a conversation depends on timing I could not confirm.

<details><summary>Merged duplicate x-async-12: The Start button stays live during the storage warm-up, so a second tap runs the whole start-up sequence twice</summary>

handleStart awaits warmUpStorage for up to 6 s (CLAUDE.md records that Android regularly reaches the deadline) and does not hide or disable the Start button until after that await. A second tap re-enters handleStart: requestFolderPermissionNow again, a second concurrent warmUpStorage (concurrent load/syncToFolder on worldview, relationships, places, express panel, control phrases...), engine.reset twice, and two pre-start chains (two afterFolderNotice runs when no What's-new notes).

Fix as proposed by that reviewer: Add `let startInProgress = false;` In handleStart, as the first line: `if (startInProgress) return; startInProgress = true; document.getElementById('startBtn').disabled = true;` (still above every await, after which the gesture-bound calls stay where they are). In finishStart re-enable: `startInProgress = false; document.getElementById('startBtn').disabled = false;`.

</details>
