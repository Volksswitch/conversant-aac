# CR-216: Two errors close together: one line is lost from errors.log

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** race-condition
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/storage.js:2704`
- **Also affects:** `app/js/storage.js:2748-2771 (flushMetricsFile already serializes the same pattern)`; `app/js/app.js:1338-1343 (stt errors that can fire together)`
- **Source:** storage-05

**What a user notices.** The error file kept in the data folder can silently miss problems that happened at nearly the same moment, which makes a reported problem harder to diagnose.

**What is wrong.** appendErrorFile is fire-and-forget and unserialized. Each call opens createWritable({ keepExistingData: true }), which copies the file, seeks to the current size and writes its line; the last close wins, so when two logError calls overlap both copies start from the same content and the first line is discarded. metrics.log has an explicit metricsWriting guard for exactly this reason; errors.log does not. Reproduced in Node against the real storage.js: two back-to-back logError calls left only the second line in errors.log.

**Evidence.**

```
app/js/storage.js:2709-2714:
        const fh = await dirHandle.getFileHandle('errors.log', { create: true });
        const writable = await fh.createWritable({ keepExistingData: true });
        const file = await fh.getFile();
        await writable.seek(file.size);   // append
        await writable.write(line);
        await writable.close();
```

**How it happens.** A generation failure logs 'generateOptions' and the empty-palette tripwire logs a second error in the same tick (or two stt errors arrive together): errors.log ends up with only one of the two lines.

**Suggested fix.** Serialize appends with a promise chain: add `let errorFileChain = Promise.resolve();`, rename the current body to `async function writeErrorLine(entry)`, and make `function appendErrorFile(entry) { errorFileChain = errorFileChain.then(() => writeErrorLine(entry)).catch(() => {}); return errorFileChain; }`.

> **Verifier correction to the fix (takes precedence):** The promise-chain fix is right; note that appendErrorFile is called without await from logError, so keep logError synchronous and just chain inside appendErrorFile.

**How to verify the fix.** Add to tests/storage-transcript.test.mjs (with a fake createWritable that delays 5 ms): call logError twice without awaiting, wait 50 ms, assert errors.log contains both messages in order.

**Do not break.** logError must stay synchronous and never throw; keep the ring buffer and conversation-file sinks unchanged.

**Design reference.** CLAUDE.md 'Logs are ASCII, and a permission prompt is not a hang' (errors.log as the permanent record)

**Verification notes.** appendErrorFile (storage.js:2704) is fire-and-forget and unserialized, opening createWritable({keepExistingData:true}) per call; in Chrome each writable works on its own swap copy and the last close wins. Reproduced in Node with a fake whose createWritable and close each take 5 ms: two back-to-back logError calls left only the second line in errors.log. The same file's metrics flush carries a guard written for exactly this race (storage.js:2752-2760), and errors genuinely arrive close together (e.g. repeated stt errors when the network drops).
