# CR-217: Stopping speech does not stop a sentence already waiting in a paid voice's queue; it plays afterwards unannounced

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** race-condition
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/tts-azure.js:459`
- **Also affects:** `app/js/tts-azure.js:478`; `app/js/tts-azure.js:482-489`; `app/js/tts-rest.js:276`; `app/js/tts-rest.js:295`; `app/js/tts-rest.js:299-306`; `app/js/tts-deepgram.js:526-529`; `app/js/tts-deepgram.js:568`; `app/js/tts-deepgram.js:646-662`; `app/js/tts.js:268`; `app/js/tts.js:364`; `app/js/tts.js:401-412`; `app/js/app.js:2707`; `app/js/app.js:2680`
- **Source:** tts-02

**What a user notices.** With a paid voice, if the app has a second sentence lined up behind the one being spoken and something stops speech (End conversation, Hold on, a card tap), the first sentence stops but the lined-up one is still spoken a moment later, and the app does not treat it as its own speech. With the device voice the same situation behaves differently: a new sentence interrupts the old one instead of waiting.

**What is wrong.** All three paid backends serialize utterances with `chain = chain.then(run, run)`. Each run takes its cancellation token only when it STARTS (`const mine = ++playToken`). cancel() bumps playToken and stops the playing nodes, but a run that is queued behind the current one has not captured a token yet, so when the cancelled run settles, the queued run starts with a fresh token and plays in full. Meanwhile tts.cancel() has already set speaking=false and called notifySpeaking(null), so the STT echo filter's phrase for that utterance expires ECHO_MATCH_MS after the cancel and the 'app is speaking' checkpoint gate is open while the queued audio is playing. A second, related inconsistency: speakBuiltin cancels any current browser utterance before starting a new one (`if (synth.speaking) synth.cancel()`), but the paid backends queue, so the same app code behaves differently per voice (e.g. the controls tour's hint, which is spoken without awaiting while an instruction is playing, interrupts on the device voice but queues on a paid voice).

**Evidence.**

```
tts-azure.js:458-459 `const c = audioContext(); const mine = ++playToken;` (token taken at run start)
tts-azure.js:478 `chain = chain.then(run, run);`
tts-azure.js:482-483 `function cancel() { playToken++; ...` (nothing marks queued runs)
Same pattern: tts-rest.js:276/295/299-300, tts-deepgram.js:529/568/646-647.
tts.js:268 `if (synth.speaking) synth.cancel();` (builtin preempts)
Scratch simulation of tts-azure with mocked fetch/AudioContext: speak('first'); speak('second (queued)'); cancel() during 'first' -> output `played after cancel: [ 'first', 'second (queued)' ]`.
```

**How it happens.** Paid voice (Azure, OpenAI, etc.). Practice > controls tour. While an instruction is being spoken, tap a wrong button (hintWhere speaks the hint without awaiting -> queued). Then tap a control that calls placeholders.stop()/tts.cancel() (e.g. Hold on). The instruction stops, then the stale hint plays, and the user's own Hold on statement is delayed until the hint finishes. Same for two quick taps on the Settings 🔊 'Hear this phrase' buttons followed by closing Settings.

**Suggested fix.** In each backend's createVoice add `let cancelGen = 0;`. In speak(), capture it at CALL time: `const gen = cancelGen;` (outside `run`), and as the first line of `run` add `if (gen !== cancelGen) return;`. In cancel() add `cancelGen++;` beside `playToken++`. Do this in tts-azure.js, tts-rest.js and tts-deepgram.js (in Deepgram also check `gen` before `await play(cached)`). Separately, decide one policy for a new speak() while one is playing; the minimal consistent change is to leave queuing alone but make cancel() drain the queue as above.

> **Verifier correction to the fix (takes precedence):** The cancel-generation approach is correct. In tts-rest.js also note reset() replaces `chain`, so the generation counter must be bumped there too (reset already calls cancel(), so bumping in cancel() suffices).

**How to verify the fix.** Add to tests/tts-azure.test.mjs, tests/tts-rest.test.mjs and tests/tts-deepgram.test.mjs: mock AudioContext/fetch (or WebSocket), call speak('a'), speak('b'), then cancel() while 'a' plays, and assert 'b' never reaches node.start(). Manual: on Azure, in the tour, reproduce the scenario above and confirm nothing is spoken after the cancel.

**Do not break.** Do not break the serialization that stops two utterances sharing one Deepgram socket. Keep `chain.then(run, run)` so one failure never wedges the queue. A speak() issued AFTER a cancel() must still play.

**Design reference.** tts.js header comment (superseded-utterance token); CLAUDE.md 'The TTS-echo defense is TWO layers'

**Verification notes.** tts-azure.js speak() (453-479) and tts-rest.js speak() (270-297) take `mine = ++playToken` only when `run` starts, and chain runs with chain.then(run, run); cancel() (482-489 / 299-306) bumps playToken and stops current nodes but nothing marks runs still queued, so a run queued behind the cancelled one starts afterwards with a fresh token and plays in full. Deepgram's speak() has the same shape (529, 568). In tts.js the queued utterance's speakToken is already stale after cancel(), so its .then never reports speaking, and cancel() has already called notifySpeaking(null) - the echo filter/checkpoint gate is open while it plays. Overlapping speak() calls without an intervening cancel do occur (hintWhere at app.js:2707 is not awaited while a tour instruction may be playing; express-editor.js:287 and placeholder-editor.js:99 🔊 buttons), and speakBuiltin preempts (tts.js:268) while paid backends queue, so behavior differs by voice. Severity lowered to low: the triggers are the practice tour and Settings preview buttons, not the main conversation loop.
