# CR-218: Played sound files are never released from memory

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** resource-leak
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:5207`
- **Also affects:** `app/js/app.js:5210-5221 (primeExpressAudio)`; `app/js/app.js:5246-5252 (playClip re-reads while priming is in flight)`; `app/js/app.js:5216 (merged duplicate: Sound clip memory is never released when a clip is replaced or deleted)`
- **Source:** app-e-13, tts-13

**What a user notices.** Each sound file the panel has ever loaded stays in the device's memory until the app is closed, so trying out several large music files while setting up buttons can slow a tablet down.

**What is wrong.** audioUrls maps stored clip names to URL.createObjectURL(blob) and nothing ever calls URL.revokeObjectURL or deletes entries. Clip names are fresh stamps each time a new file is chosen, so every replaced or deleted sound button leaves its blob (up to 10 MB) pinned. Additionally, when a tap arrives while priming is still in flight (value null), playClip reads the file again and stores a second object URL; the priming promise then overwrites it, leaking one URL.

**Evidence.**

```
app/js/app.js:5207 const audioUrls = new Map();
app/js/app.js:5216 if (blob) audioUrls.set(item.file, URL.createObjectURL(blob));
app/js/app.js:5250-5251 url = URL.createObjectURL(blob); audioUrls.set(item.file, url);
(no revokeObjectURL anywhere in app.js)
```

**How it happens.** In Settings > Express, choose five different 8 MB songs for one sound button in turn; about 40 MB of blobs remain referenced for the rest of the session.

**Suggested fix.** In primeExpressAudio (called with the current composed items), revoke and delete any audioUrls entry whose name is not among the current items: `const live = new Set(items.filter(i => i && i.type === 'audio' && i.file).map(i => i.file)); for (const [name, url] of audioUrls) if (!live.has(name) && (!audioPlayer || audioPlayer.item.file !== name)) { if (url) URL.revokeObjectURL(url); audioUrls.delete(name); }`. In the priming .then, if an entry already holds a URL, revoke the new one instead of overwriting.

**How to verify the fix.** Manual: replace a sound file several times and check in DevTools Memory that old blobs are released; the playing clip must keep playing.

**Do not break.** Never revoke the URL of a clip that is currently playing.

**Design reference.** none

**Verification notes.** app.js never calls URL.revokeObjectURL; the only calls are in data-transfer.js and express-editor.js. primeExpressAudio and playClip store object URLs in audioUrls and never delete them, and choosing a new file creates a new stamped name. So each replaced or deleted clip's blob stays referenced for the rest of the session. If a tap arrives while priming is still in flight (the entry is null), playClip reads the file and stores its own URL. The priming .then then overwrites it, leaking one URL.

<details><summary>Merged duplicate tts-13: Sound clip memory is never released when a clip is replaced or deleted</summary>

audioUrls maps stored clip names to object URLs created by URL.createObjectURL and is never pruned or revoked. Choosing a new file for a button writes a new name (fresh stamp) and deletes the old file, but the old name's object URL (and the blob it pins) remains in audioUrls for the session. There is also a race: playClip creates its own object URL when the primed entry is still null (loading), and primeExpressAudio's pending read later overwrites the map entry with a second object URL, leaking the first.

Fix as proposed by that reviewer: In primeExpressAudio(items), after the loop, revoke and delete any audioUrls entry whose name is not the `file` of some current audio item: `const live = new Set(items.filter(i => i && i.type === 'audio' && i.file).map(i => i.file)); for (const [name, url] of audioUrls) if (!live.has(name)) { if (url) URL.revokeObjectURL(url); audioUrls.delete(name); }` (skip the clip currently playing: `audioPlayer && audioPlayer.item.file === name`). In the primeExpressAudio .then, if the entry is already a non-null URL (set by playClip), revoke the new one instead of overwriting.
