# CR-221: File names from the data folder are inserted into the page as HTML in the backup and profile lists

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** security
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:6598`
- **Also affects:** `app/js/app.js:6758 (renderSettingsProfiles)`; `app/js/storage.js:548-556 (listSettingsProfiles lists any .json, unsanitized)`; `app/js/storage.js:845-858 (listBackups lists any .json)`; `app/js/app.js:6758 (merged duplicate: Settings-profile and backup file names are inserted into the page as unescaped HTML)`; `app/js/app.js:6596 (merged duplicate: Backup list builds its options with innerHTML from raw file names)`
- **Source:** app-e-08, x-security-07, review-backup-16

**What a user notices.** A file with a specially crafted name placed in the data folder (for example by a shared or synced folder) could run code inside the app, which could read the stored API keys. Ordinary names with characters like quotes or '&' can also make Restore or Load act on the wrong name.

**What is wrong.** renderBackupList and renderSettingsProfiles build <option> elements by string interpolation into innerHTML using names read straight from the data folder: listBackups returns every .json in backups/ 'whatever its name', and listSettingsProfiles returns every .json in settings/ without passing it through sanitizeProfileName. On macOS, ChromeOS/Linux and Android storage, file names may contain <, >, ", and &, so a name such as `x"><img src=x onerror=...>.json` executes script in the app origin (where the Anthropic and speech keys live in localStorage). Names containing `&amp;`-style sequences or quotes also round-trip wrongly through the value attribute, so readBackup/loadSettingsProfile get a different name. ui.js already has escapeHtml for the same purpose elsewhere.

**How it happens.** On a Mac running Chrome, the user's data folder is a shared cloud folder. Someone places a file named `a"><img src=x onerror=alert(localStorage.getItem('aac_settings'))>.json` in its backups subfolder. When the user opens Settings (or connects the folder), renderBackupList runs and the script executes, with access to the saved API keys.

**Suggested fix.** Build the options with DOM APIs instead of innerHTML: `select.replaceChildren(...backups.map((b) => { const o = document.createElement('option'); o.value = b.name; o.textContent = `${when} — ${b.name} (${b.sizeKB} KB)`; return o; }));` and the same for profile names (`o.value = n; o.textContent = n;`). The constant placeholder options ('— No backups ... —') can stay as they are.

**How to verify the fix.** Add a test (e.g. tests/backup-folder.test.mjs) or a manual check: create a file named `a"<b>x</b>.json` in backups/ on a platform that allows it (or stub storage.listBackups), open Settings, and confirm the option shows the literal name and Restore reads that exact file. Grep app/js/app.js for innerHTML with `${` and folder-derived values.

**Do not break.** Keep option ordering and the disabled states; keep the empty-state placeholder text.

**Design reference.** Conversant AAC Security Review.docx (SEC-1 shared-origin key exposure; SEC-8 innerHTML hygiene); CLAUDE.md SEC-3 (no CSP yet, so escaping is the only defence).

**Verification notes.** renderBackupList (app.js:6596-6599) and renderSettingsProfiles (6758) put names from listBackups and listSettingsProfiles straight into innerHTML, unescaped, both as the attribute value and as text. Those functions (storage.js:548-556, 845-858) accept any .json entry in the folder without sanitizing it. On platforms whose file names allow < > " (macOS, ChromeOS/Linux, Android), a crafted name injects markup into the app origin, where the API keys are stored. On Windows, '<', '>' and '"' are illegal in file names, so the risk there is limited to names containing & sequences that resolve to a different value. The trigger needs somebody else to write files into the user's folder. The Security Review's SEC-8 covers a different innerHTML helper, so this is not tracked.

<details><summary>Merged duplicate x-security-07: Settings-profile and backup file names are inserted into the page as unescaped HTML</summary>

renderSettingsProfiles builds the profile picker with select.innerHTML from raw directory entry names, and renderBackupList does the same with backup file names. listSettingsProfiles() and listBackups() return whatever file names are in the folder - not only names the app wrote through sanitizeProfileName - so any file a user, another device, or a cloud-sync peer drops into <data folder>/settings or <data folder>/backups is interpolated verbatim into both the value attribute and the option text. Windows forbids < > " in file names, but macOS, ChromeOS, Android internal storage and Google Drive (all supported) allow them. Current Chromium's relaxed <select> parser accepts arbitrary elements inside a select, so a name like `<img src=x onerror=...>.json` can execute script in the app's origin, which holds the API keys in localStorage; at minimum a '"' breaks out of the value attribute. Every other dynamic string in the app goes through escapeHtml/esc or textContent.

Fix as proposed by that reviewer: Build the options with DOM APIs instead of innerHTML: `select.innerHTML = ''; for (const n of names) { const o = document.createElement('option'); o.value = n; o.textContent = n; select.appendChild(o); }` in renderSettingsProfiles, and likewise in renderBackupList (o.value = b.name; o.textContent = `${when} — ${b.name} (${b.sizeKB} KB)`). The static placeholder strings can stay as they are.
