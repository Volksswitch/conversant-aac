# CR-222: No guard against unescaped interpolation into innerHTML in app source

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** security
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:6758`
- **Also affects:** `app/js/app.js:6596`; `app/js/ui.js:17`; `app/js/review-ui.js:65`; `tests/source-hygiene.test.mjs:67`
- **Source:** g-test-suite-08

**What a user notices.** A name taken from a file can be shown as page markup instead of plain text, and nothing in the checks stops a new case from being added.

**What is wrong.** Most innerHTML templates in app/js pass every interpolated value through escapeHtml (ui.js) or esc (review-ui.js), but the settings-profile and backup lists interpolate raw file names (already reported). There is no source-level test that flags a template literal assigned to innerHTML whose ${...} is not wrapped in an escape helper, so the pattern can recur. A grep-based test is cheap: of the ~20 innerHTML template sites, only the two already-reported ones fail the rule.

**Evidence.**

```
app/js/app.js:6758: select.innerHTML = names.map((n) => `<option value="${n}">${n}</option>`).join('');
app/js/ui.js:566: b.innerHTML = `<span class="ep-text">${escapeHtml(label)}</span>`;  (the escaped norm elsewhere)
```

**How it happens.** 1) A developer adds `el.innerHTML = `<b>${person.name}</b>`` in a new editor. 2) npm test passes. 3) A person named '<img src=x onerror=...>' (e.g. via an imported backup) injects markup.

**Suggested fix.** Add a test to tests/source-hygiene.test.mjs (or a new tests/no-raw-html.test.mjs): for each app/js/*.js, find statements matching /\.innerHTML\s*\+?=\s*[^;]*`[\s\S]*?`/ and, inside each template, every ${...} expression; fail unless the expression starts with escapeHtml(, esc(, or is on a small reasoned ALLOW list (e.g. ui.js:727 'Choice button #${slot}', a number). Fix the two reported sites to use option elements built with textContent (or escapeHtml).

**How to verify the fix.** The test fails today naming app.js:6596 and app.js:6758; after those are fixed it passes. Mutation: remove escapeHtml from one ui.js site and confirm failure.

**Do not break.** Keep icons.js (static SVG constants) and literal-only assignments out of scope; do not flag innerHTML = '' resets.

**Design reference.** Documents/Conversant AAC Security Review.docx (escaping discipline); CLAUDE.md SEC-3/SEC-8 notes.

**Verification notes.** app.js:6596 (the backup list) and app.js:6758 (the settings-profile list) put file names into option markup through innerHTML with no escaping. No test flags an unescaped ${...} in an innerHTML template. The Security Review records escapeHtml discipline as the primary control, with CSP (SEC-3) as the planned backstop, but no source-level guard is tracked. Exploitability is limited: Windows file names cannot contain < > or quote characters, and the select parser drops most tags. That keeps severity low, but the missing guard is real.
