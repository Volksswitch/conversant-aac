# CR-223: Imported conversation ids are not validated, so a backup can write arbitrary files into the conversations folder (including review files)

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** security
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/data-transfer.js:442`
- **Also affects:** `app/js/storage.js:1005-1018 (writeConversationLog uses `${id}.json`)`; `app/js/data-transfer.js:451 (audio names ARE validated with isSafeAudioName)`
- **Source:** review-backup-12

**What a user notices.** A doctored backup file could put oddly named files among the saved conversations or overwrite the notes made while reviewing a conversation.

**What is wrong.** applyPackage passes the untrusted `c.id` straight to writeConversationLog, which writes `${id}.json` in the conversations folder; `c.data` and `c.review` are also not type-checked. Sound files are protected by isSafeAudioName for exactly this reason ('a backup is a file somebody could hand the app from anywhere'), but conversations are not. An id ending in '.review' writes `<x>.review.json`, which listConversationLogs treats as the review of conversation <x>; a non-object `data` (e.g. missing) creates an empty/invalid conversation file because getFileHandle(create:true) runs before the write throws.

**Evidence.**

```
data-transfer.js:441-444
    for (const c of convos) {
        if (!c || !c.id) { step('conversations'); continue; }
        if (await storage.writeConversationLog(c.id, c.data, c.review || null)) restored.conversations++;
storage.js:1009-1011
        const fh = await dir.getFileHandle(`${id}.json`, { create: true });
        const w = await fh.createWritable();
        await w.write(JSON.stringify(data, null, 2));
```

**How it happens.** A backup with conversations: [{ id: '2026-10-01_120000.review', data: {...} }] overwrites the user's review of conversation 2026-10-01_120000; [{ id: 'x' }] (no data) leaves an empty x.json.

**Suggested fix.** In applyPackage skip any conversation where `typeof c.id !== 'string' || !/^[A-Za-z0-9_\-:.]+$/.test(c.id) || c.id.toLowerCase().endsWith('.review') || !c.data || typeof c.data !== 'object' || Array.isArray(c.data)`, and only pass `c.review` when it is a plain object. Match the actual id format storage uses (check startConversationLog's id generator and mirror it).

> **Verifier correction to the fix (takes precedence):** Current ids come from new Date().toISOString().replace(/[:.]/g,'-').slice(0,19) (storage.js ~2069), for example 2026-10-01T12-00-00. Before tightening a pattern, check older ids in tests/fixtures and the user's folder. The essential checks are: id is a non-empty string; id does not end in '.review' (case-insensitive); id has no '/' or '\\'; and data is a plain object.

**How to verify the fix.** Unit test in tests/ (OPFS shim, as tests/storage-transcript.test.mjs): applyPackage with the two bad entries above writes neither file and counts 0 conversations.

**Do not break.** Must still accept every id the app has ever written (check older id formats in existing test fixtures before tightening the pattern).

**Design reference.** CLAUDE.md 'SOUND buttons' (a name the app did not write is refused on import)

**Verification notes.** applyPackage passes c.id unchecked to writeConversationLog, which writes `${id}.json`. Path traversal is not possible: getFileHandle rejects '/', '\\' and '..'. An id ending in '.review' does overwrite that conversation's review file, and an entry with no data leaves an empty file, because getFileHandle(create:true) creates it before the write throws. listConversationLogs skips the empty file. The 'security' framing overstates it: a legitimate backup can already replace any review through a conversation's own `review` field, and a same-id conversation is overwritten by design, so a doctored file gains nothing new. This is input validation and robustness, not a vulnerability.
