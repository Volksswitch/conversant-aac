# CR-224: A partner, place or recognizer label of "__proto__" pollutes Object.prototype during the usage summary

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** security
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/usage-summary.js:287`
- **Also affects:** `app/js/usage-summary.js:292`; `app/js/usage-summary.js:295`; `app/js/usage-summary.js:150`; `app/js/usage-summary.js:152`; `app/js/data-transfer.js:443`
- **Source:** x-security-10

**What a user notices.** A backup or conversation file with a deliberately odd name in it can make the usage summary, problem reports and weekly reports show nonsense numbers and may disturb other parts of the app until it is restarted.

**What is wrong.** summarize() aggregates per partner, per place and per recognizer into plain object literals indexed by values read from conversation files (e.partner.label, e.place.label, e.stt). For the key '__proto__', `out.hearingByPartner[who]` returns Object.prototype (truthy), so the `if (!...)` guard does not create a row and addHearing() then increments `turns`, `flagged`, `words` and `flaggedWords` on Object.prototype, giving every object in the page inherited NaN-valued properties. Conversation files arrive from backup import with no shape or key validation (applyPackage writes c.data as-is), and partner labels come from user-entered names. Verified with node: after summarize() of one turn whose partner label is '__proto__', `({}).turns` is NaN.

**Evidence.**

```
app/js/usage-summary.js:287  if (!out.hearingByPartner[who]) out.hearingByPartner[who] = hearingRow();
app/js/usage-summary.js:288  addHearing(out.hearingByPartner[who], e);
app/js/usage-summary.js:152-157  function addHearing(row, turn) { row.turns++; ... row.words += ...; row.flaggedWords += flags; }
app/js/data-transfer.js:443  if (await storage.writeConversationLog(c.id, c.data, c.review || null)) restored.conversations++;
```

**How it happens.** 1. Import a backup whose conversations contain a partner turn with partner {label:'__proto__'} and an `uncertain` array. 2. Open Settings > Troubleshooting (or let the weekly report run). 3. summarize() mutates Object.prototype; ({}).turns is now NaN for the rest of the session.

**Suggested fix.** Create the three maps with a null prototype so no key reaches Object.prototype: in the `out` object initializer use `hearingByPartner: Object.create(null), hearingByPlace: Object.create(null), hearingByRecognizer: Object.create(null)`, and do the same for any other object keyed by data (sourceCounts, slotCounts, errorContexts, voiceByProvider, byRecognizer) - or guard with `Object.prototype.hasOwnProperty.call(map, key)` before reading. JSON.stringify of null-prototype objects works normally.

**How to verify the fix.** Add a test to tests/usage-summary.test.mjs (or the existing summary test file): summarize a log whose partner label is '__proto__' and assert `({}).turns === undefined` afterwards and that hearingByPartner['__proto__'].turns === 1 as an own property.

**Do not break.** The weekly payload and the Troubleshooting text read these objects with Object.entries/Object.keys - both work with null-prototype objects. Combine with the partner-name redaction finding if done together.

**Design reference.** none

**Verification notes.** Ran summarize() in node on a log whose partner label is '__proto__': afterwards ({}).turns is NaN. out.hearingByPartner['__proto__'] returns Object.prototype, the !guard skips creating a row, and addHearing increments properties on Object.prototype. Same for hearingByPlace and hearingByRecognizer. Trigger requires a person or place literally named '__proto__' or a crafted backup, so impact is low.
