# CR-228: Disabled Load / Update / Delete profile buttons look exactly like enabled ones

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** ui-inconsistency
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/css/styles.css:2722`
- **Also affects:** `app/js/app.js:6741-6743 (setActionsEnabled)`; `app/index.html:271 (loadSettingsProfileBtn)`; `app/css/styles.css:3577 (.key-row button:disabled has a style)`; `app/css/styles.css:2897 (.ee-tools button:disabled has a style)`
- **Source:** live-visual-07

**What a user notices.** On Settings > General > Settings profiles with no profile saved, the Load, Update and Delete buttons look normal but do nothing when tapped, with no sign they are unavailable.

**What is wrong.** renderSettingsProfiles() disables all three when there is no folder or no saved profile, but the generic Settings button rule (:where(#settingsDialog) button) has no :disabled appearance and the browser's default disabled styling is overridden, so they keep full opacity, normal text color and a pointer cursor. Other families (.key-row, .ee-tools, .wv-icon-btn) do dim when disabled, so disabled state is shown inconsistently across the panel.

**Evidence.**

```
app/js/app.js:6741-6743:
    const setActionsEnabled = (on) => {
        loadBtn.disabled = delBtn.disabled = updBtn.disabled = !on;
    };
Measured with no profiles: loadSettingsProfileBtn disabled=true, opacity 1, color rgb(26,26,26), cursor pointer — identical to the enabled 'Save as a new profile'. testAzureKeyBtn (disabled) shows opacity 0.6 via .key-row rule.
```

**How it happens.** Fresh install with a data folder and no profiles: Settings > General > Settings profiles shows '— No saved profiles —' and three normal-looking buttons; tapping Load does nothing.

**Suggested fix.** Add a zero-specificity disabled look next to the rule at 2722:
:where(#settingsDialog button:disabled) { opacity: 0.45; cursor: default; }
(keeps existing family-specific disabled rules winning).

**How to verify the fix.** Browser check in tests/ui-standards.test.mjs: every visible disabled button in Settings has computed opacity < 1. Manually confirm the three buttons dim when there are no profiles and brighten after saving one.

**Do not break.** Use :where() so no deliberate button style is outranked (see the comment at 2699-2704).

**Design reference.** UI-Design.docx §13 'Settings action button — ONE APPEARANCE'.

**Verification notes.** renderSettingsProfiles disables Load, Update and Delete together (app.js:6741-6743). The author-origin rule :where(#settingsDialog) button sets color: var(--ink) and a background, which overrides the browser's disabled styling whatever the specificity. No generic :disabled rule exists for Settings buttons. Only the family rules at 2897, 3577, 4166, 4339, 4900 and 5447 dim a disabled button, so these three look enabled.
