# CR-229: Credential key fields are too narrow: every paid-service placeholder is clipped mid-word on the Speech tab

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** ui-inconsistency
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/css/styles.css:3522`
- **Also affects:** `app/css/styles.css:3550 (.key-row .key-field { flex: 0 1 9rem; })`; `app/index.html:517 (azureKeyInput placeholder 'Your Azure Speech key')`; `app/index.html:555 (openaiKeyInput)`; `app/index.html:565 (googleKeyInput)`; `app/index.html:575 (deepgramKeyInput)`; `app/index.html:588 (elevenlabsKeyInput)`; `app/index.html:232 (apiKeyInput, General tab - same rule, placeholder 'sk-ant-...' fits)`
- **Source:** g-visual-consistency-01

**What a user notices.** When someone sets up a speech service, the empty key boxes read 'Your Azure Speec', 'Your OpenAI API k', 'Your Google Clou' and so on - cut off mid-word, on the setup step people already find hardest.

**What is wrong.** All credential inputs inside .key-row take `flex: 0 1 9rem` (and the Azure key's wrapper .key-field likewise). 9rem resolves to ~131px (box) / ~114px of text area at the default 1280x800 Settings size. The placeholder strings are 10-11.9rem wide, so all five paid-service placeholders overflow the box and are clipped. The rows themselves are far wider than the box (641-1171px measured), so the narrowness is not forced by available space - it is the flex-basis. The basis was presumably chosen for the redacted stored-key form 'sk-ant-…4f2a' (6.6rem in monospace), which does fit; the empty state, which is what a new user sees, does not.

**Evidence.**

```
app/css/styles.css:3522-3526
.key-row input[type="text"] {
    flex: 0 1 9rem;
    width: auto;
    min-width: 0;
}
app/css/styles.css:3550  .key-row .key-field { flex: 0 1 9rem; }
app/index.html:565  <input type="text" id="googleKeyInput" placeholder="Your Google Cloud API key" ...>

Measured in headless Chrome (real app, Settings > Speech, all sections open):
- bottom dock 1280x800: box 131px, text area 114px; placeholder widths Azure 146, OpenAI 133, Google 173, Deepgram 152, ElevenLabs 155 -> all clipped; row width 1096px
- side dock 1280x800: same box, row 712px -> all clipped
- bottom/side 1180x820 (iPad size): box 134/inner 117; placeholders 136-177px -> all clipped; side row 641px
- 1366x1024: box 164/inner 144; placeholders 165-215px -> all clipped
Placeholder widths in rem: 'Your Google Cloud API key' 11.85rem, 'Your Azure Speech key' 10.02rem; input padding 0.5rem each side + 1px border.
Screenshot of the OpenAI row at side dock 1180 shows 'Your OpenAI API k' then Paste / Test.
```

**How it happens.** Open Settings > Speech > 'Keys for paid services' with no keys stored, either dock, any of 1180x820 / 1280x800 / 1366x1024. Every empty key box shows a clipped placeholder.

**Suggested fix.** In app/css/styles.css change both rules from 9rem to 14rem: `.key-row input[type="text"] { flex: 0 1 14rem; ... }` and `.key-row .key-field { flex: 0 1 14rem; }`. Leave `.key-row .region-input` / `.region-field` at 7rem (the region placeholder 'e.g. eastus' fits). 14rem leaves ~12.9rem of text area, which fits the longest placeholder (11.85rem) with margin for font differences on iPad; the widest row (Azure: key 14 + Paste + region 7 + Paste + Test + gaps ≈ 37rem) still fits the narrowest measured row (side dock at 1180, ~43rem), and `.key-row.wrap` already lets it wrap below that. Because flex-shrink stays 1 and min-width 0, a very narrow panel still shrinks instead of overflowing. Alternative if the row must stay compact: shorten every placeholder to a service-neutral 'Paste your key' (6.4rem, fits the current 9rem) - the label above each box already names the service. Do not change the class approach: style by .key-row, never by id (§13).

> **Verifier correction to the fix (takes precedence):** The suggested 14rem is fine. One check to add: the same rule also sizes the General tab's #apiKeyInput (placeholder 'sk-ant-...'), which was the original reason for 9rem. Confirm the General row still looks right, or leave that row narrower with a scoped `#apiKeyRow`... no - per §13 do not style by id. Prefer the class-wide change, or the alternative of shortening the placeholders to 'Paste your key'. Shortening also avoids reopening the 9rem decision.

**How to verify the fix.** Add a check to tests/ui-standards.test.mjs (it already walks every Settings tab in a browser): for each `.key-row input[placeholder]`, measure the placeholder with a canvas using the input's computed font and assert it is <= clientWidth minus padding, at 1280x800 in both docks. Manually: Settings > Speech, open 'Keys for paid services', confirm all five placeholders read in full in bottom and side dock; paste a key, blur, confirm the redacted 'sk-ant-…4f2a' form still shows in monospace and the Azure row (Key, Paste, Region, Paste, Test) stays on one line at 1280x800 side dock.

**Do not break.** Keep the styling on the .key-row class (UI-Design §13 credential row: 'styled by class and never by service name'; CLAUDE.md Rule 18b). Settings is a supporter overlay, not keyguard geometry, so no keyguard hole moves. Do not floor min-width - the pathological side-dock/max-button case (Settings content ~84px wide) must still shrink.

**Design reference.** Conversant AAC UI-Design.docx §13 'Credential row' and 'Text input' (house font, same minimum height; width not floored); CLAUDE.md UI Layout Rule 18b (one section for credentials).

**Verification notes.** styles.css:3522 gives every .key-row text input `flex: 0 1 9rem` (grow 0) and :3550 does the same for .key-field. At 1280x800 the root size is ~14.6px, so the box is ~131px. 'Your Google Cloud API key' at that font is ~180px, so all five paid-service placeholders (index.html 517/555/565/575/588) are clipped. The 9rem came from commit dff5f94 (June 29 2026): 'the key is masked to dots... so the Paste button shows fully and the General tab's two columns don't crowd.' That reason has lapsed now that Settings tabs are one column (Rule 18), and the empty-placeholder state was never considered. No CSS or test guards against it.
