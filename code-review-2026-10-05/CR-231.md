# CR-231: Command Bar and response-card "armed" ring is mostly hidden at the default gap of 0

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** ui-inconsistency
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/css/styles.css:5492`
- **Also affects:** `app/css/styles.css:1159 (#mainArea overflow: clip)`; `app/js/storage.js:1703 (DEFAULT_BTN_GAP_POS = 0)`; `app/js/app.js:853-867 (tapGuard rules using the default tap-armed class)`
- **Source:** css-04

**What a user notices.** In two-tap mode, the blue ring that tells the person their first tap on a Command Bar button, New 4 or a response card was received is mostly hidden behind neighbouring buttons, so it looks as if the tap did nothing.

**What is wrong.** `.tap-armed` draws an OUTER 4px box-shadow. The default button gap is 0 (storage DEFAULT_BTN_GAP_POS = 0 maps to --grid-gap 0). Flex and grid items paint atomically in document order, so the next sibling's background covers the ring on the right/bottom, and #mainArea's `overflow: clip` with padding = gap = 0 clips it on the outer edges. Measured in headless Chrome with the real stylesheet: for the first response card and the Listen button the ring survived only along the top edge; right and bottom samples were the neighbour's colours.

**Evidence.**

```
styles.css:5492 `.tap-armed { box-shadow: 0 0 0 4px var(--info) !important; }`
styles.css:1159 `overflow: clip;` (#mainArea)
storage.js:1703 `const DEFAULT_BTN_GAP_POS = 0;     // → gap 0 (flush by default)`
```

**How it happens.** Default spacing, two-tap mode on, tap Wrap up once (or a response card once): only a thin blue line along one edge appears; the person taps again too late and re-arms.

> **Verifier correction to the trigger:** The ring is not lost on every side for every control: a button that is not first in its row still shows the ring on its LEFT edge (it paints over the earlier neighbour), and #listenControls has margin-top 0.5rem so its top edge shows. For the first button or card, only the top edge is visible. So it is partly hidden, worst on the first control in a row.

**Suggested fix.** Draw the ring inside the box: `.tap-armed { box-shadow: inset 0 0 0 4px var(--info) !important; }`. (In review, #listenBtn uses an inset shadow as its border; while armed the armed ring replaces it, which is acceptable.)

**How to verify the fix.** Manual at default spacing: two-tap mode, tap each Command Bar button, New 4 and a card once; the full ring is visible on all four sides. Confirm button rects are unchanged.

**Do not break.** Must stay paint only (no border/padding), so no keyguard hole moves. Review's card outlines (outline 4px offset -4px) also sit inside the card; check both read clearly together.

**Design reference.** CLAUDE.md UI Layout Rule 10 (One tap or two) and tap-guard.js header

**Verification notes.** .tap-armed draws an outer 4px box-shadow (styles.css:5492). Default gap is 0 (storage.js:1703), Command Bar buttons and response cells are non-positioned flex/grid items painted in document order, so a later sibling's background covers the ring on its right and lower sides, and #mainArea has overflow: clip with padding equal to the gap (0). An inset shadow avoids both and stays paint only.
