# CR-234: In review, any non-answer tap (Undo, Hear it, Next Word, a card being edited) throws the Express Panel back to its first page

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** ui-inconsistency
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:669`
- **Also affects:** `app/js/review-ui.js:431-438 (reveal suppressed while userPaged)`; `app/js/review-ui.js:518-530, 532-535`
- **Source:** review-backup-09

**What a user notices.** While reviewing, someone pages through their buttons with More to find a phrase; pressing Hear it or Undo jumps the panel back to the first page, which is neither where they were nor where the exchange's button is.

**What is wrong.** app.js installs a document capture-phase click listener that resets expressPaging on ANY button tap (except More and Hold on) and redraws. In review the response cards and all Command Bar buttons are <button>s. review-ui sets userPaged=true on More, which suppresses `reveal`; only change()/goTo() clear userPaged. So after paging, a tap on Undo/Redo/Hear it/Prev Word/Next Word resets the paging (global listener) while userPaged stays true, and renderPanel draws page 1 with no reveal - the user's page and the turn's own button are both lost. This contradicts review-ui's stated rule ('True while the user is turning the panel's pages themselves').

**Evidence.**

```
app.js:669-677
    document.addEventListener('click', (e) => {
        if (!expressPaging) return;
        const btn = e.target && e.target.closest ? e.target.closest('button') : null;
        ...
        resetExpressPaging();
        setTimeout(renderExpressPanel, 0);
    }, true);
review-ui.js:431-432
        reveal: userPaged ? null : [{ id: wantId }, { id: usedId, text: usedText }],
        onMore: () => { userPaged = true; },
```

**How it happens.** In review, tap More twice to reach page 3 of Always; tap Hear it. Panel returns to page 1.

**Suggested fix.** In the app.js global listener add `if (reviewUI.isActive()) return;` (review manages its own paging and resets it at turn changes and answers), OR in review-ui stepHistory/hear and the prev/nextWord cases leave paging alone by skipping. The first is simpler and matches review's own comment.

> **Verifier correction to the fix (takes precedence):** Adding `if (reviewUI.isActive()) return;` to the app.js listener is fine, but restoreConversationScreen must then call resetExpressPaging() so the live panel is not left on a review page after leaving. Opening or closing Settings is documented as resetting paging, so check that path still does.

**How to verify the fix.** Manual: in review, page with More, press Hear it / Undo / Next Word - the panel stays on the same page; press Next Turn - it returns to the turn's button.

**Do not break.** Do not change the live-conversation rule (any button tap puts the panel back, Ken Sept 14 2026). Leaving review via Settings must still end with the live panel unpaged (restoreConversationScreen should call resetExpressPaging() if the global listener no longer does it in review).

**Design reference.** CLAUDE.md 'A band that overflows gets a MORE button'; Conversation Review.docx §6 (panel opens on the page that shows the turn's button; once the user pages...)

**Verification notes.** The app's paging-reset listener is on document in the capture phase (app.js ~669); review's onBarClick/onCardsClick are capture listeners on descendant elements, so the document listener runs first, and stopImmediatePropagation in review cannot stop it. expressPaging is the same module variable drawReviewPanel/composedPanel use. A tap on Hear it, Undo or Redo after paging with More resets expressPaging; userPaged stays true, so renderPanel passes reveal: null and the panel is drawn on page 1. Prev/Next Word only work while editing, when the keyboard covers the panel, so those cases are invisible; Hear it and Undo/Redo show it.
