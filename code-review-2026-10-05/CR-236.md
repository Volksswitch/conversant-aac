# CR-236: The 'cards may change' look can stay on forever after a failed repair prefetch or a failed practice-partner line

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** ui-inconsistency
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:2163`
- **Also affects:** `app/js/app.js:2159 (setPaletteBusy(true))`; `app/js/app.js:2168-2169 (bail paths without clearing)`; `app/js/app.js:2605 and 2612-2617 (advancePracticePartner sets busy and its catch returns without clearing)`; `app/js/ui.js:328-335 (busy is only cleared by the next render)`; `app/js/app.js:2159 (merged duplicate: The 'cards may change' look can stay on forever after a repair-options request fails or is overtaken)`; `app/js/app.js:2163 (merged duplicate: Repair prefetch failure leaves the "cards may change" stripe on with nothing running)`
- **Source:** x-async-13, app-b-10, llm-engine-09

**What a user notices.** After certain failures the reply cards keep dimming and showing the moving stripe that means 'new suggestions are on the way', even though nothing is coming.

**What is wrong.** ui.setPaletteBusy is documented as cleared by whatever renders next, on the assumption that a bail-out means a newer request is still running. prefetchRepairOptions sets busy on, and on an AI error (or when the mode has already left REPAIR_OF_SELF) returns without rendering and without any newer request in flight; advancePracticePartner's catch does the same. The repair cards stay in the provisional look until some unrelated render.

**Evidence.**

```
app.js:2159-2166 `ui.setPaletteBusy(true); let opts; try { opts = await llm.repairOptions(last, conversationHistory); } catch (err) { storage.logError('repairOptions', err.message); return; }`
app.js:2612-2617 catch block in advancePracticePartner returns after setStatus/setListenButtonState with no setPaletteBusy(false).
```

**How it happens.** Partner says 'What?'; repair cards appear; the prefetch request fails (rate limit). The three repair cards keep the refreshing animation indefinitely while the user reads them.

> **Verifier correction to the trigger:** The stuck look comes from the two catch paths (repair prefetch failure, practice partner line failure); the 'mode already left repair' bail is normally cleared by the render that accompanied leaving the mode.

**Suggested fix.** In prefetchRepairOptions: in the catch add `if (token === generationToken) ui.setPaletteBusy(false);` before return, and change the mode bail to `if (engine.getMode() !== engine.MODE.REPAIR_OF_SELF) { ui.setPaletteBusy(false); return; }`. In advancePracticePartner's catch add `ui.setPaletteBusy(false);`.

**How to verify the fix.** Manual with an invalid API key in Practice Mode: tap Listen; after the error the cards must not show the refreshing stripe.

**Do not break.** Do not clear busy on the superseded (token mismatch) path - a newer request is running there.

**Design reference.** ui.js setPaletteBusy comment (look-only, cleared by the next render)

**Verification notes.** prefetchRepairOptions sets setPaletteBusy(true) and its catch returns without clearing; advancePracticePartner's catch likewise returns after setPaletteBusy(true). setPaletteBusy is only undone by showResponses/clearResponseOptions, so the provisional look persists until the next unrelated render. The mode-bail path is mostly harmless because the action that leaves REPAIR_OF_SELF (a card tap, clearPalette) already strips palette-refreshing via clearResponseOptions; the catch paths are the real defect.

<details><summary>Merged duplicate app-b-10: The 'cards may change' look can stay on forever after a repair-options request fails or is overtaken</summary>

prefetchRepairOptions turns on the provisional palette look with ui.setPaletteBusy(true) and only turns it off implicitly via ui.showResponses on success. The catch path, the superseded-token return and the left-repair-mode return all exit with the class 'palette-refreshing' still on the response region. The busy state persists until some other render clears it.

Fix as proposed by that reviewer: Wrap the body after setPaletteBusy(true) in try/finally, or call `ui.setPaletteBusy(false)` before each early return in the catch and mode-check paths. For the superseded-token path, clear it only if no newer generation is running (the newer generation sets its own busy state), e.g. `if (token !== generationToken) return;` stays as is, but add `ui.setPaletteBusy(false)` in catch and in the mode-check return.

</details>

<details><summary>Merged duplicate llm-engine-09: Repair prefetch failure leaves the "cards may change" stripe on with nothing running</summary>

prefetchRepairOptions turns the busy look on, and on a thrown error just logs and returns. ui.setPaletteBusy's contract is that 'whatever renders next' clears it, which holds for superseded requests (a newer one is running) but not here: no newer request is running and nothing renders, so the stripe persists until the user acts.

Fix as proposed by that reviewer: In the catch block, before `return`, add `if (token === generationToken) ui.setPaletteBusy(false);`. Also clear it on the `engine.getMode() !== REPAIR_OF_SELF` bail only if token still matches.

</details>
