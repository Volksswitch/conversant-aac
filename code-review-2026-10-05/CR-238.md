# CR-238: Layout handles can stay visible and swallow taps after a conversation begins via Start conversation

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** ui-inconsistency
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:4903`
- **Also affects:** `app/js/app.js:4871-4878 (noteConversationStarted is the only conversation-start relock hook)`; `app/js/app.js:3125-3147 (handleInitiate does not call refreshLayoutMode)`; `app/js/app.js:5014-5016 (onHandlePointerDown returns without passing the press through)`; `app/css/styles.css:1369-1376 (handles z-index 900, shown by body.layout-unlocked)`
- **Source:** app-d-12

**What a user notices.** If the layout was left unlocked and the person presses Start conversation, the round drag handles can stay on screen; a tap that lands on one does nothing instead of pressing the button underneath.

**What is wrong.** body.layout-unlocked (which displays the 10mm handles at z-index 900) is only recomputed by refreshLayoutMode, called from applyButtonSizing and noteConversationStarted. conversationInProgress() becomes true when openers appear (currentStatic.kind) without either running, so layoutDraggable() is false (the handle's pointerdown returns early) but the circle is still displayed and still the hit target, so the press never reaches the Command Bar button or card beneath it. The CSS comment claims the class is toggled by refreshLayoutMode 'which a conversation starting already calls', which is not true for this path. Unverified whether some other code in renderStaticPalette happens to re-run applyButtonSizing.

**Evidence.**

```
app/js/app.js:4903-4906
  function refreshLayoutMode() {
      document.body.classList.toggle('layout-unlocked', layoutDraggable());
      positionLayoutHandles();
  }
app/js/app.js:5016  if (!layoutDraggable()) return;
```

**How it happens.** Unlock the layout, close Settings, press Start conversation. If the handles remain visible, tap the top edge of the middle Command Bar button under the command-bar handle: nothing happens.

**Suggested fix.** Call refreshLayoutMode() at the end of handleInitiate and of handleWindDown (and anywhere currentStatic.kind is set), or more robustly call it from showPalette/renderStaticPalette. Alternatively make the handles pointer-events:none unless body.layout-unlocked is accurate by having onHandlePointerDown, when the gate is false, call refreshLayoutMode() to hide them.

**How to verify the fix.** Manual: unlock layout, press Start conversation, confirm the circles disappear immediately and Command Bar buttons under their former positions respond.

**Do not break.** Practice Mode must keep the handles (realConversationInProgress excludes practice).

**Design reference.** app/css/styles.css comment at 1336-1342; CLAUDE.md layout drag notes

**Verification notes.** Traced. body.layout-unlocked is toggled only by refreshLayoutMode, which runs from applyButtonSizing, noteConversationStarted and the unlock checkbox. handleInitiate, overlayEnter, renderStaticPalette and showPalette call none of them, and there is no resize or mutation observer. Once the openers set currentStatic.kind, layoutDraggable() is false but the circles stay displayed at z-index 900. onHandlePointerDown returns early without passing the press on, so a tap on a circle does nothing, including a tap on an opener card under it. The circles disappear at the next applyButtonSizing, for example a redraw of the Express Panel. The CSS comment saying a conversation starting already calls refreshLayoutMode is wrong for this path.
