# CR-239: Keyguard 'Generate Screen Openings' reports through native browser alert boxes

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** ui-inconsistency
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:5438`
- **Also affects:** `app/js/app.js:5378`; `app/js/app.js:5388`; `app/js/app.js:5445`; `app/js/app.js:5448`; `app/js/confirm-dialog.js:169 (showNotice)`
- **Source:** live-runtime-11

**What a user notices.** The result of generating keyguard openings appears in a plain browser pop-up that looks like a website warning rather than the app's own message card, and on a tablet it says 'Choose Save to Files' even on browsers where no such sheet appears.

**What is wrong.** generateScreenOpenings uses window.alert for all five outcomes while every other Settings outcome uses the app's showNotice/confirmDanger cards (top-layer, styled, Cancel focused). The no-picker branch's wording ('Choose "Save to Files" in the sheet that appears') is iPad-specific but is shown on any browser without showDirectoryPicker.

**Evidence.**

```
app/js/app.js:5437-5440
        dataTransfer.downloadText('Screen Openings.txt', text, 'text/plain');
        window.alert(`"Screen Openings.txt" (${lines.length} controls) is ready to save. ` +
            'Choose "Save to Files" in the sheet that appears, then attach it to an email.\n\n' + expected);
Runtime: DIALOG alert: "Screen Openings.txt" (48 controls) is ready to save. Choose "Save to Files"...
```

**How it happens.** Settings > Keyguard Design > Generate Screen Openings: a native alert appears.

**Suggested fix.** Replace each window.alert with `await showNotice({ title: 'Screen openings', body: ..., buttonLabel: 'OK' })` (import from confirm-dialog.js is already used in app.js). Reword the no-picker text to 'Your browser will save or share the file - keep it and attach it to an email.' unless platform.isIOS().

**How to verify the fix.** Manual: generate openings with and without a folder; the app's notice card appears and closes with OK; no window.alert remains (grep 'window.alert' app/js).

**Do not break.** The measurement must still be taken BEFORE any dialog opens (the notice card covers controls). Keep the zoom refusal.

**Design reference.** UI-Design.docx §13 control standards; CLAUDE.md 'Confirm before destroying significant work' (native dialogs read as routine)

**Verification notes.** generateScreenOpenings uses window.alert for all five outcomes (5378, 5388, 5438, 5445, 5448), while app.js elsewhere uses showNotice/confirmDanger from confirm-dialog.js (already imported at line 58). The no-picker branch is chosen by capability (!supportsUserChosenFolder), which also covers desktop Safari and Firefox, so its 'Choose "Save to Files" in the sheet that appears' wording is iPad-specific. No written standard bans alert outright (the CLAUDE.md native-dialog ban is about confirm() for destructive actions), so this is a consistency issue, not a rule violation.
