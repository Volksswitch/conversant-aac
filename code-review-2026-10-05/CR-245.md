# CR-245: Tapping Copy twice quickly leaves the button permanently labeled 'Copied ✓'

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** ui-inconsistency
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:7063`
- **Also affects:** `app/js/app.js:7048-7049 (copyErrorLogBtn has the same pattern)`
- **Source:** app-f-06

**What a user notices.** If a tester taps a Copy button again within a second and a half, the button keeps saying 'Copied ✓' (or 'Copy blocked') for the rest of the session instead of going back to 'Copy'.

**What is wrong.** flash() reads btn.textContent at click time as the label to restore. A second click inside the 1.5 s window captures 'Copied ✓' as the original, and its timer restores to that, so the real label is lost. The launch-screen report button already avoids this by keeping the label in btn.dataset.label.

**Evidence.**

```
app/js/app.js:7063-7067
  const flash = (btn, word = 'Copied ✓') => {
      const orig = btn.textContent;
      btn.textContent = word;
      setTimeout(() => { btn.textContent = orig; }, 1500);
  };
app/js/app.js:7048 const orig = btn.textContent; btn.textContent = 'Copied ✓';
```

**How it happens.** Settings > Troubleshooting > Copy (usage summary): tap, then tap again within 1.5 s. After both timers fire the button reads 'Copied ✓' permanently (this population taps imprecisely and often double-taps).

**Suggested fix.** Store the original once: `const orig = btn.dataset.label || (btn.dataset.label = btn.textContent);` in flash, and route copyErrorLogBtn through flash(btn) instead of its own inline copy.

**How to verify the fix.** Manual: double-tap a Copy button; after 1.5 s it reads 'Copy' again.

**Do not break.** none

**Design reference.** none

**Verification notes.** flash() (app.js:7063-7067) reads btn.textContent when it is called, and copyFrom calls it after awaiting writeText. A second tap within 1.5 s therefore captures 'Copied ✓' as the label to restore. The first timer restores 'Copy', then the second timer sets 'Copied ✓', and the label stays wrong. copyErrorLogBtn (7044-7051) has the same inline pattern. Taps inside Settings are exempt from the double-tap safeguard, so a quick second tap goes straight through, and openSettings does not reset the labels.
