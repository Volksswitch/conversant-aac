# CR-246: Warnings and test results in Settings stay on screen after they stop being true

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** ui-inconsistency
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/app.js:7386`
- **Also affects:** `app/js/app.js:7791 (Aura 'Add your Deepgram key' warning is never cleared when a key is typed)`; `app/js/app.js:7339-7354 (reflectSttProvider on open does not clear sttProviderStatus)`; `app/js/app.js:7269 (partnerVoiceStatus 'Auto chose X' survives own-voice changes and reopening)`; `app/js/app.js:7924 (catalog key onChange clears only its own KeyStatus)`
- **Source:** app-f-05

**What a user notices.** Settings can keep saying 'this service needs a key before it can hear anything' after the key has been added, or keep naming a practice voice Auto no longer picks, which makes a working setup look broken.

**What is wrong.** Several status lines are written once and only cleared by the same control that wrote them. sttProviderStatus is set when the hearing radio changes (warn if the chosen service has no key) but nothing clears or re-evaluates it when a key is then pasted, and openSettings does not reset it, so the stale warning persists across opens. The Deepgram voice warning 'Add your Deepgram key above, then tap Test.' is not cleared by refreshDeepgramVoices when the key arrives. The builtin partner status 'Auto chose <name>.' is left in place when the user's own voice changes (which changes what Auto picks) and when Settings is reopened. CLAUDE.md notes 'an uncleared status line reads as a message about whatever the user did NEXT'.

**Evidence.**

```
app/js/app.js:7386-7391 setStatusLine('sttProviderStatus', haveKey ? 'ok' : 'warn', ... 'Saved, and in use now — but this service needs a key before it can hear anything. Add one below.');
app/js/app.js:7651-7661 refreshDeepgramVoices() never calls showAuraStatus
app/js/app.js:7339-7345 reflectSttProvider() only re-checks the radio
```

**How it happens.** Settings > Speech > hearing service: OpenAI (no key yet) -> warning 'needs a key'. Paste an OpenAI key below. The warning stays. Close and reopen Settings: still there.

**Suggested fix.** (1) Extract the haveKey/status computation in the sttProvider handler into a function reflectSttProviderStatus() and call it from reflectSttProvider() (so it runs on every open) and from every key field's onChange (Deepgram, Azure, catalog). (2) In refreshDeepgramVoices, when a key is present call showAuraStatus('own', null, '') if the current text is the add-key warning. (3) In voiceSelect.onchange and at openSettings, hide partnerVoiceStatus (showPartnerVoiceNote('')).

**How to verify the fix.** Manual steps above; the warning disappears once the key is entered and reappears only if the key is removed.

**Do not break.** Do not add explanatory per-control text (Rule 14); only update live status lines.

**Design reference.** app.js setStatusLine comment (lines 991-994); UI Layout Rule 14 (live status regions).

**Verification notes.** sttProviderStatus is written only at app.js:7386, in the sttProvider radio handler, and nothing else clears or re-evaluates it. reflectSttProvider (7339-7345) only re-checks the radio, and openSettings does not reset the line, so the 'needs a key' warning (or 'Saved, and in use now') stays after a key is pasted and across later opens. refreshDeepgramVoices (7651-7661) never touches showAuraStatus, so the Deepgram add-key warning set at 7791 stays until the provider radio or the voice/Test path (8077) is used. partnerVoiceStatus 'Auto chose X' (7255-7270) is cleared by voiceSelect.onchange only when releasePartnerIfNowSameAsOwn is true (8163-8169).
