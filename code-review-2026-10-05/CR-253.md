# CR-253: With spoken help armed, tapping the Settings Close button silently disarms help and swallows the tap

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** ui-inconsistency
- **Verdict:** confirmed (skeptic: confirmed)
- **Location:** `app/js/help-mode.js:201`
- **Also affects:** `app/js/help-mode.js:128`; `app/js/help-mode.js:63`; `app/js/app.js:293`; `settings-help.json`
- **Source:** x-rules-05

**What a user notices.** If the person arms the '?' and then taps the X to close Settings, nothing happens and nothing is said. The '?' quietly turns itself off, so the panel looks briefly broken and the person has to tap X again.

**What is wrong.** resolveTap() returns key 'control:closeSettingsBtn' for the X because it is a button with an id, so decideTap() returns SPEAK and the tap is prevented. say() looks the key up (there is no entry for closeSettingsBtn in settings-help.json) and falls back to labelFor(). The X has no <label for> and sits outside any .setting-group, so labelFor returns ''. say() then disarms (armed=false) and returns without speaking. The result is a swallowed tap with no feedback and a silently disarmed help mode. CLAUDE.md says a swallowed tap must read as 'still talking' rather than broken. A related gap: the same-target pass-through compares tap.groupEl with speakingGroup, so for any control outside a .setting-group (groupEl null) a second tap is always swallowed rather than passed through.

**Evidence.**

```
app/js/help-mode.js:197-205: async function say(key, groupEl) { const text = lookup(key) || labelFor(key, groupEl); armed = false; if (!text) { render(); return; } ...
app/js/app.js:293-298 labelFor: const own = id && document.querySelector(`#settingsContent label[for=...]`); const label = own || (groupEl && groupEl.querySelector('label')); return label ? label.textContent.trim() : '';
settings-help.json: no 'closeSettingsBtn' entry (grep returns nothing).
app/js/help-mode.js:228: sameGroup: !!(tap.groupEl && tap.groupEl === speakingGroup)
```

**How it happens.** Open Settings, tap '?', then tap X. Settings stays open, nothing is spoken, and the '?' is no longer armed.

**Suggested fix.** Either (a) add a 'closeSettingsBtn' entry under controls in settings-help.json (for example 'Closes Settings and goes back to the conversation.'), regenerate app/js/settings-help.js with scripts/apply-settings-help.mjs, and extend the coverage test to include the header buttons. Or (b) in help-mode.js handle(), treat a tap on #closeSettingsBtn as ALLOW (reset help and let the close happen), because closing is never a value change the user needs protecting from. Also, in say(), when text is empty, keep armed=true (render and return without changing armed) so a tap on something with no phrase behaves like SWALLOW rather than silently disarming.

> **Verifier correction to the fix (takes precedence):** Prefer option (b), or do both. In say(), an empty text should leave armed unchanged so it matches decideTap's intent. If option (a) is chosen, note that the coverage test in tests/settings-help.test.mjs scans #settingsContent controls; the header buttons sit outside #settingsContent and would need to be added explicitly.

**How to verify the fix.** Manual: arm '?', tap X. Either Settings closes, or the X's purpose is spoken. Unit test in tests/help-mode.test.mjs: decideTap with armed and the close key. If option (a) is used, tests/settings-help.test.mjs should fail when the header button lacks an entry.

**Do not break.** Keep the load-bearing property that an armed tap never changes a control's value. Header buttons are 56px-square per Rule 15; no layout change.

**Design reference.** CLAUDE.md UI Layout Rule 17 (spoken help; swallowed tap must not read as broken; same-target pass-through)

**Verification notes.** resolveTap: the X (#closeSettingsBtn, index.html:207) matches target.closest('button') and has an id, so key='control:closeSettingsBtn'. groupEl is null because the header is not inside a .setting-group. decideTap with armed and a key returns SPEAK, so the tap is prevented. In say(), lookup has no entry (no closeSettings key in settings-help.json or settings-help.js). The labelFor fallback (app.js:293-298) finds no label[for] and has no groupEl, so it returns ''. say() then sets armed=false and returns without speaking. The tap is swallowed silently and help disarms. decideTap's own comment says a tap with nothing explainable should SWALLOW and stay armed, because disarming 'would look like a failure', and say() contradicts that. The sameGroup observation is also correct: sameGroup requires a non-null groupEl.
