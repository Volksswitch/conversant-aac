# CR-269: Collapsible Settings sections have no heading semantics, so screen-reader users cannot jump between them

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** accessibility
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/sections.js:111`
- **Also affects:** `app/js/sections.js:95`; `app/js/sections.js:117`
- **Source:** g-a11y-overflow-10

**What a user notices.** In Settings, a screen-reader user cannot use 'next heading' to skip from section to section; they must step through every collapsed section and control one at a time.

**What is wrong.** build() turns each group heading into a <span class="wv-disclosure-title"> inside a <summary>. The native summary exposes expanded/collapsed correctly (no aria-expanded is needed), but the sections carry no heading role or level, and the tab panels contain almost no h2/h3 elements, so heading navigation finds nothing in most tabs. Nested sub-sections are also indistinguishable from top-level ones to assistive technology.

**Evidence.**

```
app/js/sections.js:95-98 const title = document.createElement('span'); title.className = 'wv-disclosure-title'; ... title.textContent = heading.textContent.trim();
app/js/sections.js:111-117 const details = document.createElement('details'); const summary = document.createElement('summary'); ... summary.append(mark, title);
```

**How it happens.** Open Settings > Speech with NVDA or VoiceOver and press H (next heading): nothing is found, although the tab has several sections.

**Suggested fix.** Give each section a heading wrapper around the summary contents without breaking the summary's button role: create `const h = document.createElement('span'); h.setAttribute('role','heading'); h.setAttribute('aria-level', String(depth));` where depth is 3 for top-level groups and 4 for sub-sections (pass a depth parameter through build(); start at 3 and use depth+1 in the recursive call at line 131), and append the title span inside h, then summary.append(mark, h). Keep the summary as the clickable element.

> **Verifier correction to the fix (takes precedence):** Do not rely on a role=heading span inside <summary>, because Chromium flattens the children of a summary. To get heading navigation, use the disclosure pattern <hN><button aria-expanded aria-controls=bodyId>title</button></hN> with a body div, instead of details/summary. That is a rebuild of sections.js. It must keep: the one-open-at-a-time behavior (closeSiblings), the openSections memory, the rule that a section already holding a section is skipped, the mark element, the CSS classes used by help-mode.js and the stylesheet, and the existing heading measurements. Test it in NVDA with Chrome and in VoiceOver on iPad before shipping. Given the low value for this population, it is reasonable to leave this as is.

**How to verify the fix.** Manual with NVDA (Chrome) and VoiceOver (iPad Safari): heading navigation lands on each section title and announces it collapsed/expanded. Confirm tapping the words still toggles the section (the CLAUDE.md label-in-summary trap does not apply to a span).

**Do not break.** CLAUDE.md Rule 18: the heading must NOT be a <label> (it would stop the words toggling the section). Do not change classes used by CSS or help-mode.js. Verify in Chrome that a role=heading span inside summary is exposed; if a browser flattens it, fall back to aria-describedby or leave as is.

**Design reference.** CLAUDE.md UI Layout Rule 18 (collapsible sections)

**Verification notes.** The missing heading semantics are real. sections.js builds <summary><span mark/><span title/></summary> with no heading role or level, so heading navigation finds nothing in most Settings tabs. However, Chromium exposes <summary> as a button-like element whose children are presentational. A role=heading span inside it is usually flattened, and many screen readers will still not reach it by heading navigation. The suggested fix may therefore do nothing, and the reviewer's own confidence is low.
