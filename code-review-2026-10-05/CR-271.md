# CR-271: Import from the backups folder silently does nothing on any picker failure and never falls back

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/app.js:6713`
- **Also affects:** `app/js/app.js:6702-6721 (importDataBtn handler)`
- **Source:** app-e-10

**What a user notices.** If the browser's file chooser fails for any reason other than the person closing it, tapping 'Import' does nothing at all and keeps doing nothing, with no message, so the person cannot restore their backup from this button.

**What is wrong.** When showOpenFilePicker and primedBackupsDir exist, every error - including a SecurityError/NotAllowedError (e.g. the tap no longer counts as recent, or the primed handle lost permission), a TypeError from startIn, or a read failure from handle.getFile()/file.text() - is swallowed and the handler returns without trying the hidden <input> fallback. The comment says 'the plain input is still there', but the code returns before reaching it, and a permanent failure repeats on every tap.

**Evidence.**

```
app/js/app.js:6704-6718
        if (window.showOpenFilePicker && primedBackupsDir) {
            try {
                const [handle] = await window.showOpenFilePicker({ startIn: primedBackupsDir, ... });
                ...
            } catch {
                // The user closed the picker, or the browser refused it. Neither is an
                // error worth reporting, and the plain input is still there.
            }
            return;
        }
```

**How it happens.** A browser that exposes showOpenFilePicker but rejects the `startIn` handle (or a handle whose permission was revoked between rendering the list and the tap) throws a non-Abort error on every tap; the Import button appears dead.

**Suggested fix.** Distinguish cancellation: `catch (err) { if (err && err.name === 'AbortError') return; setBackupStatus('Could not open the file chooser: ' + (err && err.message || 'unknown error')); }` and for non-Abort errors fall through to the input path instead of returning (move `return` into the success branch and the AbortError branch). Note the fallback `fileInput.click()` may itself be refused if the gesture was spent, so also show the status line.

**How to verify the fix.** Manual: temporarily make primedBackupsDir an invalid object in the console and tap Import: a status message appears (or the plain picker opens). Cancel the picker normally: nothing is reported.

**Do not break.** Do not await anything before showOpenFilePicker (the gesture rule in the comment above it).

**Design reference.** Comment at app.js:6690-6701 (picker opens in backups folder; hidden input is the fallback).

**Verification notes.** The catch at app.js:6713-6718 swallows every error, including non-Abort failures from showOpenFilePicker, handle.getFile() and file.text(), and then returns without reaching the hidden-input fallback. The comment's 'the plain input is still there' is also misleading, because that input is hidden. Whether a real browser throws a non-Abort error for a stale startIn handle, rather than quietly opening the default folder, was not verified. The reachability of a permanently 'dead' button is therefore uncertain. A read failure after the user picks a file does, however, fail silently.
