# CR-272: Copy on the error log fails silently, likely always on an iPad

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/app.js:7044`
- **Also affects:** `app/js/app.js:7068-7075 (copyFrom shows 'Copy blocked' instead)`
- **Source:** app-f-07

**What a user notices.** Tapping Copy under the error log may do nothing at all on an iPad, with no message, so a tester trying to send us their errors thinks the button is broken.

**What is wrong.** The error-log Copy handler awaits buildErrorReport() (which reads saved conversations from storage) before calling navigator.clipboard.writeText. Safari only allows clipboard writes while the tap still counts as recent; a slow await spends that, so writeText rejects - and the catch swallows it with no feedback, unlike the Troubleshooting copy buttons which flash 'Copy blocked'.

**Evidence.**

```
app/js/app.js:7044-7051
  document.getElementById('copyErrorLogBtn').onclick = async () => {
      try {
          await navigator.clipboard.writeText(await buildErrorReport());
          ...
      } catch { /* clipboard blocked/denied */ }
  };
```

**How it happens.** iPad Safari, with saved conversations in storage: Settings > About > error log > Copy. buildErrorReport takes time, writeText is rejected (NotAllowedError), nothing visible happens.

**Suggested fix.** At minimum, show feedback in the catch (use flash(btn, 'Copy blocked')). Better: on WebKit, use `navigator.clipboard.write([new ClipboardItem({ 'text/plain': buildErrorReport().then(t => new Blob([t], { type: 'text/plain' })) })])`, which is called synchronously in the tap and accepts a promise, falling back to writeText where ClipboardItem is missing.

> **Verifier correction to the fix (takes precedence):** At minimum, route the handler through flash() so a failure shows 'Copy blocked' (and the label bug in app-f-06 is fixed at the same time). The ClipboardItem-with-a-promise approach is a reasonable WebKit improvement, but test it on a device before relying on it.

**How to verify the fix.** Manual on an iPad: Copy the error log and paste into Notes. Desktop Chrome still copies.

**Do not break.** The report must keep withholding private-conversation transcripts (SEC-2) - do not change buildErrorReport.

**Design reference.** CLAUDE.md iPad section (Paste button: 'Every outcome is reported').

**Verification notes.** The silent catch is real: the copyErrorLogBtn handler (app.js:7044-7051) swallows any clipboard failure with no feedback, unlike copyFrom, which shows 'Copy blocked'. buildErrorReport does genuine async disk reads before writeText is called (errorsFromDisk and readConversationLog, around 6837 and 6856). Whether Safari on an iPad actually rejects writeText after those awaits was not measured, so 'likely always on an iPad' is unconfirmed. Note that the Troubleshooting copy buttons await their text the same way, and they report failure rather than failing silently.
