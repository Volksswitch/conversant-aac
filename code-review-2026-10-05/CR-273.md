# CR-273: The once-per-conversation listening chime is used up even when it made no sound

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/chime.js:46`
- **Also affects:** `app/js/chime.js:62-65`; `app/js/chime.js:69`; `app/js/ui.js:1107`; `app/js/chime.js:46 (merged duplicate: The start-of-listening chime is counted as played even when the audio system was asleep and nothing sounded)`
- **Source:** tts-09, x-async-14

**What a user notices.** With 'resume listening automatically' on, if the audio was not ready at the moment listening started (common on an iPad), the partner never hears the start-of-listening tone for the whole conversation.

**What is wrong.** playListenChime() sets `playedThisConversation = true` before it knows whether the notes will sound. If the context is not 'running' (WebKit suspended or 'interrupted' context, which the comment says is expected on iPad because this is called from the recognizer's async start event), the function returns without playing, and if Web Audio throws it also returns true. In once-per-conversation mode (auto-resume on) every later capture start in that conversation is then suppressed, so the partner-awareness cue (SEC-7) never sounds.

**Evidence.**

```
chime.js:45-46 `if (oncePerConversation && playedThisConversation) return false; playedThisConversation = true;`
chime.js:62-65 `if (ctx.state !== 'running') { ctx.resume().catch(...); return true; }` (no sound, latch already set)
chime.js:69 `} catch { /* audio unavailable ... */ }` then `return true;`
```

**How it happens.** iPad, auto-resume on, chime on. Tap Start; the first Listen's recognizer 'start' event arrives while the chime's AudioContext is still not running; no tone; after each exchange the mic restarts and the chime is skipped every time for the rest of the conversation.

**Suggested fix.** Only set the latch when the cue was actually scheduled, except where the device has no Web Audio at all (keep that case latched so tests in Node still pass): move `playedThisConversation = true;` to (a) inside the `if (!AudioCtx)` branch before `return true`, and (b) after the two playNote(...) calls. Leave the `ctx.state !== 'running'` branch and the catch branch NOT latched, so the next capture start in the conversation tries again.

**How to verify the fix.** Extend tests/chime.test.mjs: stub window.AudioContext with a class whose state is 'suspended' and resume() resolves; with setOncePerConversation(true) call playListenChime() twice and assert createOscillator was not called the first time and the second call still attempts to play (does not return false). Keep the existing tests passing (no-window case still latches).

**Do not break.** Do not reintroduce chiming on every exchange when auto-resume is on once a chime has actually sounded; do not schedule notes on a non-running context (the July 30 2026 'chime from the End conversation button' bug).

**Design reference.** CLAUDE.md SEC-7 'The chime is once per CONVERSATION when auto-resume is on (Ken, July 27 2026)'

**Verification notes.** playListenChime() sets playedThisConversation = true (46) before knowing whether sound will play; when the context is not 'running' it returns true without playing (62-65), and a thrown error also leaves the latch set. In once-per-conversation mode every later capture start is then suppressed. The code fact is certain, but the trigger requires the context not to be running at the first capture start even though chime.unlock() is called on the Start and Listen taps (app.js:1480, 1666) before the recognizer's start event; that this happens in practice on an iPad is not demonstrated.

<details><summary>Merged duplicate x-async-14: The start-of-listening chime is counted as played even when the audio system was asleep and nothing sounded</summary>

playListenChime sets playedThisConversation = true before checking the AudioContext. If the context is not 'running' (iOS interruption after the recognizer or getUserMedia changes the audio session, or an idle-suspended context), it calls resume() and returns without scheduling the notes. In once-per-conversation mode no later chime is allowed, so the conversation has no audible disclosure at all.

Fix as proposed by that reviewer: In the not-running branch, play once the resume completes: `ctx.resume().then(() => { const t = ctx.currentTime; playNote(t, 660, 0.20); playNote(t + 0.17, 880, 0.26); }).catch(() => { playedThisConversation = false; }); return true;` so a refused resume lets the next Listen try again.


Verifier correction: Do NOT play the notes in ctx.resume().then(...): on WebKit resume() resolves on the next user gesture, which reintroduces the July 30 2026 bug (the chime sounding out of the End conversation button). Instead, in the not-running branch just reset `playedThisConversation = false;` before returning, so the next capture start in the conversation tries again with a running context.
