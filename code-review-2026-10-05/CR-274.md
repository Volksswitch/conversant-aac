# CR-274: Lead-mode statements: a non-JSON reply is split into lines and offered as speakable cards

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/llm.js:810`
- **Also affects:** `app/js/llm.js:792-797 (generateStatements ask without schema)`; `app/js/llm.js:838-842 (repairSelf returns raw text, spoken as the user)`
- **Source:** llm-engine-06

**What a user notices.** When the user types a direction and taps Reframe with no question pending, the cards can occasionally contain the AI's own chatter, such as "Sure! Here are some ways to bring it up:", which the user could tap and have spoken in their own voice.

**What is wrong.** generateStatements sends a single user message (the steer) with no output schema, and parseStatements' last resort turns ANY reply into cards by splitting lines and stripping list markers. CLAUDE.md records that Sonnet 5.5 sometimes answers conversationally instead of returning JSON (4 of 6 on a real replay) and fixed it with a schema for generateResponses only. Here the failure mode is worse than an error: prose lines become user statements. repairSelf has the same exposure in a smaller form: whatever text comes back is spoken directly as the user's rephrase.

**Evidence.**

```
llm.js:809-813:
    if (!Array.isArray(list)) {
        // Last resort: non-empty lines, stripped of list markers/quotes.
        list = text.split('\n').map(s => s.replace(/^\s*[-*\d.]*\s*/, '').replace(/^["']|["']$/g, '').trim()).filter(Boolean);
    }
llm.js:792-796: `const text = await ask({ system: systemPrompt, messages: [{ role: 'user', content: steer }], maxTokens: 600 });` (no schema)
```

**How it happens.** Model replies: "Sure! Here are four ways you could raise it:\n1. ...\n2. ...". Card 1 reads "Sure! Here are four ways you could raise it:".

**Suggested fix.** Add a schema and drop the line fallback: define `const STATEMENTS_SCHEMA = { type:'object', additionalProperties:false, required:['statements'], properties:{ statements:{ type:'array', items:{ type:'string' } } } };`, change the prompt to 'Return ONLY a JSON object {"statements": [...]}', call `askDetailed({ ..., schema: STATEMENTS_SCHEMA })`, and in parseStatements read `parsed.statements` (still accept a bare array), throwing 'Could not parse statements from API' instead of splitting lines. Optionally do the same for repairSelf with `{ text: string }`.

**How to verify the fix.** tests/llm.test.mjs: stub the provider to return 'Sure! Here are some:\n1. A\n2. B' and assert generateStatements rejects; stub a valid {"statements":["A","B"]} and assert two STATEMENT responses; assert the request body carries output_config.format.

**Do not break.** Keep generateStatements uncached (it is not the hot path). Keep the NO_OUTSIDE_KNOWLEDGE and NO_VULGARITY blocks in the prompt.

**Design reference.** CLAUDE.md 'THE SERVICE ENFORCES THE SHAPE OF A SET OF SUGGESTIONS' ('Add a schema to another call if it ever shows the same failure').

**Verification notes.** Confirmed in code: generateStatements (llm.js ~765) asks with no schema and a single user message containing the steer. parseStatements (llm.js:810) falls back to splitting any non-JSON reply into lines, and those lines become STATEMENT cards. repairSelf returns raw text that is spoken. Prose around a JSON array is already handled by the bracket regex, so only a reply that is entirely prose reaches the line split. That failure is documented for generateResponses' multi-turn case, not measured for this single-message call, so the trigger frequency is unknown.
