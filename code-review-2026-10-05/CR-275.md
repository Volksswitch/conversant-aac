# CR-275: A failed save of a practice scenario makes buttons silently do nothing and is logged as a start-up failure

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/practice-library.js:135`
- **Also affects:** `app/js/practice-editor.js:118-121`; `app/js/practice-editor.js:138-141`; `app/js/practice-editor.js:197-202`; `app/js/practice-editor.js:224`; `app/js/practice-editor.js:304-313`; `app/js/app.js:8475`; `app/js/storage.js:380-386`
- **Source:** phrases-practice-09

**What a user notices.** If the data folder cannot be written at that moment, tapping Make a copy, Done or Practice this appears to do nothing. The error is then recorded as a startup failure, which points anyone reading the log in the wrong direction.

**What is wrong.** practice-library.save() awaits storage.writeFile, which throws on any file-system error when a folder is connected (createWritable / write rejections). Unlike control-phrases and placeholder-phrases, which catch disk errors (`writeDisk(...).catch(() => {})`), every practice-library mutation propagates the rejection. practice-editor awaits these inside click/change handlers with no try/catch, so goTo / hooks.onStart never run, and the rejection reaches window 'unhandledrejection', which logs it as 'startup:promise'. The cache was already updated before the throw, so a retry of Make a copy creates a second copy.

**Evidence.**

```
practice-library.js:132-136 `async function save() { model.updated = ...; writeCache(model); await writeFile(FILE, JSON.stringify(model, null, 2)); }`
practice-editor.js:119-120 `const id = await library.copyScenario(s); if (id) goTo({ mode: 'edit', id });`
app.js:8475 `window.addEventListener('unhandledrejection', (e) => reportStartupFailure('promise', e.reason));`
control-phrases.js:210-211 `writeFile(...).catch(() => { /* best-effort */ });`
```

**How it happens.** With a data folder connected, make the folder unwritable (e.g. revoke the browser's folder permission in site settings mid-session, or a OneDrive lock on practice-scenarios.json), then tap Make a copy: no navigation; tap again: a second copy exists in the cache; the error log shows 'startup:promise'.

**Suggested fix.** In practice-library.save(), wrap the disk write like the other models: `try { await writeFile(...); } catch (e) { storage.logError?.('practice-library', e.message || String(e)); }` (import logError from storage.js), so the cache stays the working copy and callers continue. Alternatively wrap each await in practice-editor in try/catch and show the error in the `note` status line.

**How to verify the fix.** Unit test in tests/ with a writeFile that rejects: copyScenario resolves to an id and the scenario is in listScenarios(). Manual: as in the scenario, confirm the editor moves on and the error is logged under 'practice-library', not 'startup:promise'.

**Do not break.** Keep 'file in the connected folder wins' reconciliation unchanged.

**Design reference.** none

**Verification notes.** The mechanism is real. practice-library.save() awaits storage.writeFile, which does not catch errors from getFileHandle, createWritable or write (storage.js:380-386). The editor's async click and change handlers have no try/catch, and an unhandled rejection is logged by reportStartupFailure as 'startup:promise' (app.js:8456; the card only shows before Start, but the log entry is always written). The cache is written before the disk write, so a retry duplicates the scenario. The trigger, a folder write failing mid-session, could not be confirmed as a common occurrence.
