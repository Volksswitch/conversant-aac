# CR-276: OpenAI, Google and ElevenLabs hearing never wakes its audio engine and is wired straight to the speakers

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/stt-rest.js:307`
- **Also affects:** `app/js/stt-rest.js:323`; `app/js/stt-deepgram.js:282`; `app/js/stt-deepgram.js:346`; `app/js/stt-azure.js:438`; `app/js/stt-azure.js:464`
- **Source:** stt-12

**What a user notices.** On some tablets, choosing OpenAI, Google Cloud or ElevenLabs for hearing may leave the microphone lit while nothing is ever heard, particularly when listening restarts on its own after returning to the app.

**What is wrong.** Deepgram and Azure both call `audioCtx.resume()` when the new AudioContext is not 'running' (it is created after an await, so outside the tap's activation, and on iOS a context created outside a gesture starts suspended), and both route the ScriptProcessor through a zero-gain node with the comment that wiring the microphone toward the speakers 'would howl'. stt-rest.js does neither: no resume (so onaudioprocess may never fire and the source silently hears nothing while reporting 'listening'), and `processor.connect(audioCtx.destination)` directly (relies on the engine zero-filling an unwritten output buffer). Also requests `{ audio: true }` without the explicit echoCancellation/noiseSuppression the other two request.

**Evidence.**

```
stt-rest.js:307 `audioCtx = new Ctor();` (no resume)
stt-rest.js:323 `processor.connect(audioCtx.destination);`
stt-azure.js:438-440 `if (audioCtx.state !== 'running') { try { await audioCtx.resume(); } catch {} }`
stt-azure.js:464-466 `const mute = audioCtx.createGain(); mute.gain.value = 0; processor.connect(mute).connect(audioCtx.destination);`
```

**How it happens.** Installed iPad app, OpenAI hearing, listening auto-restarted from a timer or the visibility guard (no fresh tap): the context stays 'suspended', no frames arrive, nothing is transcribed, no error is reported.

**Suggested fix.** In stt-rest.js start(), after creating the context: `if (audioCtx.state !== 'running') { try { await audioCtx.resume(); } catch { /* gesture needed */ } }` (re-check the start token from the start-race fix after this await), request audio with `{ echoCancellation: true, noiseSuppression: true, autoGainControl: true }`, and replace line 323 with the muted-gain routing used by stt-azure.js (lines 464-466).

**How to verify the fix.** tests/stt-rest.test.mjs: a fake AudioContext whose state is 'suspended' must have resume() called; assert processor is connected to a gain node with gain 0. Manual check on an iPad Home Screen app with an OpenAI key.

**Do not break.** Do not route the microphone audibly to the speakers. Keep 'listening' emitted only once capture is up.

**Design reference.** Comments in stt-deepgram.js/stt-azure.js on ScriptProcessorNode routing and resume()

**Verification notes.** Confirmed: stt-rest.js never calls audioCtx.resume() and connects the processor straight to audioCtx.destination, while Deepgram and Azure resume the context and route through a zero-gain node. The impact is uncertain. An unwritten ScriptProcessor output buffer is silent in practice, so 'howl' is not a real risk. Deepgram and Azure also call resume() only after an await, outside the tap, so whether the context comes up suspended on iOS while a capture stream is active, and whether resume() rescues it, was not established.
