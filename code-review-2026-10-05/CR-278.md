# CR-278: Backgrounding the app loses the words the partner was in the middle of saying

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/stt.js:474`
- **Also affects:** `app/js/stt.js:487`; `app/js/stt.js:505`; `app/js/stt.js:673`; `app/js/platform.js:219`
- **Source:** stt-14

**What a user notices.** If the app is sent to the background while the other person is mid-sentence, the words shown on screen but not yet settled can disappear when they continue after the user comes back.

**What is wrong.** recognition.onend flushes currentInterim into segments only inside `if (listeningIntent && !suspendedForHidden)`. When the visibility guard suspends (suspendedForHidden = true), onend falls through to the else-branch, which neither commits nor clears currentInterim. After return, openSource() restarts recognition and the next interim result overwrites currentInterim, losing the earlier unsettled words. platform.js asserts the opposite ('stt.js flushes the pending interim on the way out, so nothing heard is lost'). The suspend also emits 'stopped', which logs a 'listen off' event in the conversation record for a trip to the home screen.

**Evidence.**

```
stt.js:474 `if (listeningIntent && !suspendedForHidden) {` ... :487 `if (currentInterim.trim()) commitSegment(currentInterim);`
stt.js:505-506 `clearSilenceTimer(); if (onStatusChange) onStatusChange('stopped');`
platform.js:219-220 'stt.js flushes the pending interim on the way out, so nothing heard is lost.'
```

**How it happens.** iPad (non-continuous recognizer). Partner mid-sentence: interim 'I was going to the'. User presses Home; iOS ends the session without a final. Return: partner continues 'store later'; the interim becomes 'store later' and 'I was going to the' is gone.

**Suggested fix.** In onend, before the `if (listeningIntent && !suspendedForHidden)` test, flush whenever the intent survives: `if (listeningIntent && currentInterim.trim()) { commitSegment(currentInterim); currentInterim = ''; }`, then keep the existing restart branch for the not-suspended case (remove the now-duplicate flush inside it).

**How to verify the fix.** tests/stt.test.mjs: startListening; emitInterim('I was going to the'); dispatch visibilitychange hidden (document.hidden true) so suspendSource runs; let onend fire; dispatch visible; emitInterim('store later'); assert getCurrentTranscript() === 'I was going to the store later'.

**Do not break.** commitSegment (not a bare push) must be used so the Android re-send rule still collapses a later fuller final.

**Design reference.** app/js/platform.js speechConfig() guardVisibility comment

**Verification notes.** recognition.onend flushes currentInterim only inside `if (listeningIntent && !suspendedForHidden)`. On a suspend-for-hidden, the else branch neither commits nor clears it, and the first interim of the restarted session overwrites it. This contradicts platform.js's claim that the interim is flushed on the way out. It only loses words if the browser does not deliver a final for the pending interim on recognition.stop(). Chrome usually does deliver one, and that final is ingested because listeningIntent stays true. Whether iOS ends without a final here was not measured.
