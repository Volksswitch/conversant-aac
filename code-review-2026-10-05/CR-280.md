# CR-280: A stuck audio wake-up can leave the paid voice 'speaking' forever and block every later sentence

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/tts-azure.js:463`
- **Also affects:** `app/js/tts-rest.js:280`; `app/js/tts-deepgram.js:533`; `app/js/tts-deepgram.js:337`; `app/js/tts.js:364-370`
- **Source:** tts-05

**What a user notices.** On an iPad with a paid voice, after a quiet spell the app may go silent: a holding phrase never plays, later sentences never play, and new suggestions stop appearing when the other person talks, until the user taps something.

**What is wrong.** Every paid backend awaits `c.resume()` when the AudioContext is 'suspended', with no time limit. On WebKit a resume() requested outside a user gesture can stay pending until the next tap. Placeholders fire on timers, so a timer-driven tts.speak() can hang inside `await c.resume()`. While it hangs: the backend's promise never settles, so tts.js never reports the end (speaking stays true, which the STT layer uses to suppress silence checkpoints), there is no error so no fallback to the device voice, and the backend's `chain` is wedged so every later speak() queues behind it. The state only clears when some user action calls tts.cancel(). The code also only resumes on 'suspended'; on iOS the context can be 'interrupted', in which case start() is called on a non-running context and onended may never fire, with the same latch. This is distinct from the known open speakBuiltin watchdog item (browser voice); this is the paid path.

**Evidence.**

```
tts-azure.js:460-464 `if (c.state === 'suspended') { try { await c.resume(); } catch { } if (mine !== playToken) return; }`
tts-rest.js:277-281 identical
tts-deepgram.js:530-535 identical; tts-deepgram.js:333-341 in play()
tts.js:364-370 the end is only reported when paid.speak() settles
```

**How it happens.** iPad, Azure voice. Start a conversation, leave the app quiet long enough for the browser to suspend its audio, then the partner speaks; the first placeholder fires from a timer, its resume() never settles, the 'speaking' flag stays on, and the partner's next pause produces no new cards until the user taps a button. (Platform behavior needs confirming on a device.)

**Suggested fix.** Add a small helper in each backend: `async function wake(c) { if (c.state === 'running') return; try { await Promise.race([c.resume(), new Promise((r) => setTimeout(r, 1500))]); } catch {} if (c.state !== 'running') throw new Error('Audio could not start on this device.'); }` and use it in place of the bare `await c.resume()` blocks (keep the playToken check after it). Treat 'interrupted' the same as 'suspended'. The thrown error makes tts.js fall back to the device voice, which is the documented behavior for any paid failure.

**How to verify the fix.** Add to tests/tts-azure.test.mjs (and tts-rest, tts-deepgram): a mock AudioContext with state 'suspended' whose resume() returns a never-settling promise; assert speak() rejects within ~2 s with the new message. Manual on iPad: leave the app idle several minutes with a paid voice, then let a placeholder fire and confirm either it plays or the device voice speaks it.

**Do not break.** The resume must still be awaited before any audio starts (the September 2 2026 dropped-first-word fix). Do not throw when resume() succeeds slowly within the limit.

**Design reference.** tts-deepgram.js comment block at 311-330 (resume must be awaited); CLAUDE.md 'The TTS-echo defense is TWO layers'

**Verification notes.** All three paid backends await c.resume() with no timeout when state is 'suspended' (tts-azure.js:460-464, tts-rest.js:277-281, tts-deepgram.js:530-535 and play() 333-341), and only check 'suspended', not 'interrupted'. If resume() never settles, the run never settles, tts.js never reports the end (speaking stays true, suppressing checkpoints) and `chain` wedges. But whether WebKit actually leaves resume() pending indefinitely outside a gesture is unverified; the app unlocks audio on Start and Listen taps (app.js:1480, 1666 and tts unlockAudio), which normally makes the context running before timer-driven speech. Reviewer marked low confidence; impact would be serious if real but the trigger is unconfirmed.
