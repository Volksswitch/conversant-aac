# CR-281: A Deepgram retry reuses the same player, so the failed attempt's first fragment plays before the retried sentence

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/tts-deepgram.js:606`
- **Also affects:** `app/js/tts-deepgram.js:537-542`; `app/js/tts-deepgram.js:454-465`
- **Source:** tts-07

**What a user notices.** Occasionally, when the Deepgram connection drops right as a sentence starts, the retried sentence begins with a short stutter of its own first syllable.

**What is wrong.** speak() creates one stream player and passes `(buf) => p.push(buf)` to synthesizeWithRetry, which passes the same onChunk to both attempts. The no-retry guard is hasStarted(), which is only true once 300 ms of audio has been scheduled. If the first attempt delivered some audio (< 300 ms, queued but not yet started) and then failed with a retryable error ('closed', 'took too long', 'refused the connection'), the retry pushes the new attempt's full audio onto the SAME queue behind the old partial audio, so playback starts with the first attempt's opening fragment followed by the complete sentence.

**Evidence.**

```
tts-deepgram.js:541-542 `chunks = await synthesizeWithRetry(model, trimmed, (buf) => p.push(buf), p.hasStarted);`
tts-deepgram.js:602 `if (hasStarted && hasStarted()) throw err;`
tts-deepgram.js:606 `return synthesize(model, text, onChunk);` (same onChunk, same player)
tts-deepgram.js:460-462 nothing plays until queued >= leadInSamples()
```

**How it happens.** Deepgram voice on flaky wifi: the socket closes after 2-5 chunks (80-200 ms of audio) arrive; the retry succeeds; the user hears e.g. 'I wa- I want to go now'.

**Suggested fix.** Give the retry a clean queue: add a `reset()` method to the object returned by createStreamPlayer that does `queue = []; queued = 0;` only when `!started`, and in synthesizeWithRetry accept an `onRetry` callback invoked just before the second synthesize(); pass `() => p.reset()` from speak(). Alternatively treat 'any chunk received' (not just 'started') as the no-retry condition.

**How to verify the fix.** Add to tests/tts-deepgram.test.mjs: mock socket that sends 3 chunks then closes on the first connection and sends 10 tagged chunks + Flushed on the second; assert the scheduled audio length equals the second attempt's only.

**Do not break.** Keep 'never retry once the user has heard audio'. The retry for an idle-closed socket (no chunks received) must still work.

**Design reference.** CLAUDE.md 'The paid voice silently fell back for one sentence ... retry + keepalive'

**Verification notes.** speak() creates one stream player and passes the same onChunk to both attempts (541-542, 606); hasStarted() is only true after 300 ms of audio is queued (460-462). If an attempt received some chunks (<300 ms) and then failed with a retryable message, the retry's audio is appended behind the stale partial audio in the same queue, so playback would begin with the failed attempt's fragment. The code path is certain given that condition, but the condition (a retryable close or timeout after only a few chunks have arrived) is a narrow timing case not demonstrated.
