# CR-282: Per-file network timeout can mix old cached modules with new ones right after a deploy

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** bug
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/sw.js:151`
- **Also affects:** `app/sw.js:184`
- **Source:** reporting-platform-14

**What a user notices.** On a slow connection right after an update, the app can occasionally fail to start once, until it reloads.

**What is wrong.** networkFirst decides per request: a module that takes longer than 6 s is served from the (previous build's) cache while faster modules come fresh from the network. After a deploy that changes exports between modules, the page can load a mix of old and new files, causing a module-link error ('does not provide an export named ...') and a startup failure. It self-heals when the new worker installs and controllerchange reloads, but the first launch can fail.

**Evidence.**

```
app/sw.js:151: `const NETWORK_TIMEOUT_MS = 6000;`
app/sw.js:157: `setTimeout(() => { timedOut = true; controller.abort(); }, NETWORK_TIMEOUT_MS);`
app/sw.js:184-185: `const cached = await caches.match(request); if (cached) return cached;`
```

**How it happens.** Deploy changes app.js (large) and ui.js together. On a slow cellular link the old worker fetches ui.js new within 6 s but app.js times out and is served from cache; app.js imports a name only the old ui.js exported; the app shows its startup failure card.

**Suggested fix.** Apply the timeout only to navigation requests (`request.mode === 'navigate'`) and let subresource fetches wait for the network once the navigation itself came from the network, or exempt './js/' requests from the timeout. A simpler alternative: when a navigation is served from cache because of the timeout, serve all subsequent same-origin requests for that client from cache too (track by event.clientId / resultingClientId).

**How to verify the fix.** Manual with DevTools throttling ('Slow 3G') and two locally built versions whose modules disagree on an export; launch after switching versions and confirm no link error.

**Do not break.** Keep the fallback that protects a launch against a reachable-but-sick server.

**Design reference.** sw.js networkFirst comments; CLAUDE.md 'LOCALLY, THE SERVICE WORKER SERVES A STALE APP'

**Verification notes.** networkFirst applies its 6-second deadline to each request and falls back to the cached copy per file, so after a deploy a slow module can come from the old cache while others are fresh. A mismatched export would then break module linking. That needs one module to exceed 6 s while its siblings do not, right after a deploy that changed exports between modules. Not demonstrated, and it self-heals on the next launch.
