# CR-287: Spoken-help cleanup depends on the Settings dialog 'close' event, against the standing rule

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** design-violation
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/help-mode.js:287`
- **Also affects:** `app/js/app.js:278`; `app/js/app.js:8418`; `app/js/app.js:879`; `app/js/app.js:2529`; `app/js/app.js:2553`; `app/js/app.js:5578`; `app/js/app.js:6883`
- **Source:** x-rules-04

**What a user notices.** If the browser does not deliver the dialog's close notice, closing Settings while the '?' is armed or speaking can leave help armed or the explanation still talking. The next time Settings opens, the '?' may already be lit and the first tap explains a control instead of acting on it.

**What is wrong.** help-mode.init() relies on dialog.addEventListener('close', reset) to disarm and stop speech when Settings is left by a route other than Escape. CLAUDE.md records that the <dialog> close event was unreliable here and that dialog cleanup must run explicitly in the Close handler (plus a cancel listener). The app's own Close handler (app.js:8418) and the programmatic closes in reviewUI.closeSettings, Practice onEnd and startPractice call dialog.close() without resetting help. The object returned by helpMode.init() is discarded at app.js:278, so app.js has no way to call reset(). openSettings() does not reset help either. There is also a contradiction: repromoteSettingsOverFullscreen() states as a safety premise that 'there is no close listener', but help-mode added one, so that close/reopen now also resets help.

**Evidence.**

```
app/js/help-mode.js:287-288: dialog.addEventListener('close', reset); dialog.addEventListener('cancel', reset);
app/js/app.js:278: helpMode.init({ ... });   (return value not stored)
app/js/app.js:8418-8437 closeSettingsBtn.onclick: ... keyboard.hideKeyboard(); hostExpressPanel(false); dialog.close();   (no help reset)
app/js/app.js:5578: // Safe to close() here: there is no 'close' listener (the one listener is 'cancel', ...
```

**How it happens.** On a browser where close does not fire for a programmatic close (the condition CLAUDE.md v0.2.17 recorded): open Settings, arm '?', then start a practice scenario from the Practice tab (startPractice closes the dialog programmatically). Reopen Settings: the '?' is still armed, and the next tap speaks instead of acting.

**Suggested fix.** Store the return value: const spokenHelp = helpMode.init({...}) in initSpokenHelp() (module-level let). Call spokenHelp?.reset() explicitly in every path that closes Settings: the closeSettingsBtn handler before dialog.close(), reviewUI's closeSettings dep, Practice onEnd, startPractice, and openSettings() as a belt-and-braces reset on open. The existing 'cancel' listener can stay. Remove the 'close' listener from help-mode.js, or keep it only as a redundant backstop. Update the comment at app.js:5578 to say what actually listens.

**How to verify the fix.** Manual: arm '?', close Settings with X, reopen and check that '?' is not armed. Arm '?', tap a control so it speaks, start a practice scenario before the speech ends, and check that the speech stops. Unit test in tests/help-mode.test.mjs (if present): init() returns an object with reset() that disarms.

**Do not break.** Do not disarm help on the fullscreen re-promotion close/reopen if that is not wanted; it is harmless either way. Keep the one-shot behavior.

**Design reference.** CLAUDE.md Standing findings: 'The <dialog> close event is unreliable here (v0.2.17)'; UI Layout Rule 17 (spoken help)

**Verification notes.** The mechanism is real. help-mode.js:287 relies on dialog 'close' (plus 'cancel') to reset help. app.js:278 discards init's return value, so no explicit reset() is possible. The closeSettingsBtn handler (app.js:8418-8437) calls dialog.close() without resetting help. The comment at app.js:5578 is stale: it says no 'close' listener exists, but help-mode adds one. Per spec and in current Chromium, though, programmatic close() does fire 'close'. The v0.2.17 note in CLAUDE.md about unreliability is old and was never re-measured, and I could not confirm that the event actually fails to fire on any target browser. The fix (store the handle and call reset() explicitly) is still cheap and consistent with the standing rule.
