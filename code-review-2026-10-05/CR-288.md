# CR-288: Changing or forgetting the data folder mid-conversation keeps writing the conversation into the old folder

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** design-violation
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/storage.js:93`
- **Also affects:** `app/js/storage.js:310-320 (clearDataFolder)`; `app/js/storage.js:295-303 (pickDataFolder)`; `app/js/storage.js:2049-2051 (currentLogHandle/currentLogData)`
- **Source:** storage-09

**What a user notices.** If someone chooses a different data folder, or presses "Forget this folder", while a conversation is going on, the rest of that conversation keeps being saved into the folder they just moved away from or asked the app to forget.

**What is wrong.** setRoot() explicitly invalidates the cached conversations directory because 'a handle from the old root must never leak into the new one', but it leaves currentLogHandle/currentLogData pointing at the file in the old root. flushLog uses currentLogHandle directly, so every later turn is written to the old folder, including after clearDataFolder (dirHandle null) - the 'forgotten' folder keeps receiving writes until the conversation ends.

**Evidence.**

```
app/js/storage.js:93-97:
  function setRoot(handle, kind) {
      dirHandle = handle;
      backend = handle ? kind : BACKEND.NONE;
      conversationDirHandle = null;   // cached from the OLD root — must not leak across
  }
app/js/storage.js:2471: if (!currentLogHandle || !currentLogData) return;  // never checks dirHandle
```

**How it happens.** During a conversation open Settings > Forget this folder (or Choose Folder and pick another); go back and keep talking; the old folder's conversations/<id>.json keeps growing.

> **Verifier correction to the trigger:** Only the 'choose a different folder' path is reachable; clearDataFolder is not called from any UI code, so 'Forget this folder' cannot trigger this.

**Suggested fix.** In setRoot, when `handle !== dirHandle`, also set `currentLogHandle = null; currentLogData = null; currentLogName = null; pendingPartnerTurn = null; pendingOffer = null;` (keep currentConversationId so errors still correlate). With a new root the next write lazily starts the same-id file in the new folder; with no root nothing more is written.

> **Verifier correction to the fix (takes precedence):** Nulling currentLogData in setRoot would make the next write start a new same-id file in the new folder holding only the later turns, splitting the conversation. If the behavior is to change, carry the in-memory conversation across instead: in setRoot, when the root changes and currentLogData exists, reopen currentLogHandle under the new root's conversations folder with the same name and flush the whole currentLogData there, so the new folder gets the complete conversation.

**How to verify the fix.** Add to tests/storage-transcript.test.mjs: start a log under one fake root, call pickDataFolder/setRoot equivalent via a second restore with a different root (or clearDataFolder on the FOLDER backend with a stubbed idbDelete), then logUserResponse; assert the first root's file did not change.

**Do not break.** Do not reset currentConversationId (error correlation). Make sure the flush fix (snapshotting handle at call time) still applies.

**Design reference.** storage.js comment at 11-15 and 92-97

**Verification notes.** setRoot (storage.js:93) clears conversationDirHandle but not currentLogHandle/currentLogData, and flushLog never consults dirHandle, so after choosing a different folder mid-conversation (Settings > Choose Folder, app.js:7006, reachable mid-conversation) the rest of the conversation keeps going to the old folder's file. However clearDataFolder ('Forget this folder') has no caller anywhere in app/js, so that half of the scenario is unreachable. Whether continuing to write the conversation where it began is a defect is debatable: it keeps the record whole, while the suggested fix would split one conversation across two folders.
