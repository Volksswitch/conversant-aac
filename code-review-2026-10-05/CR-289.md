# CR-289: logEvent lets a caller field overwrite the entry's role, timestamp or kind (latent - no current caller does)

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** other
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/storage.js:2204`
- **Also affects:** `app/js/app.js:572 logEvent('generation requested', { reason })`; `app/js/app.js:1328 logEvent('listen on'|'listen off')`; `app/js/app.js:3481 logEvent('reframe', { text })`; `app/js/app.js:3753 logEvent('composer opened')`; `app/js/app.js:3856 logEvent('composer canceled', { text })`
- **Source:** g-storage-overflow-08

**What a user notices.** None today. If a future recording passes a detail named 'role' or 'timestamp', that entry would be filed as the wrong kind of record (for example as a user turn) or out of time order in the saved conversation and in review.

**What is wrong.** logEvent builds `{ timestamp, role: 'event', kind, ...extra }`. Because the spread comes last, any key in `extra` named timestamp, role or kind replaces the authoritative value. Every reader filters conversation entries positively by role (usage-summary, review, voice harvest), so `{ role: 'user' }` in extra would make an event count as a user turn, and a caller-supplied timestamp would break the time ordering the record relies on. All five current callers pass only `reason` or `text`, so no wrong entry is produced today; this is a latent hazard at the one generic entry builder (the other builders - pushContext, logPlaceholder, logOffer, logErrorToConversation - use fixed fields or nest extra under its own key).

**Evidence.**

```
app/js/storage.js:2200-2205
    currentLogData.exchanges.push({
        timestamp: new Date().toISOString(),
        role: 'event',
        kind,
        ...extra,
    });
compare app/js/storage.js:2698  ...(entry.extra != null ? { extra: entry.extra } : {}),   (nested, safe)
```

**How it happens.** A future call such as storage.logEvent('tour step', { role: 'user', text: 'Wrap up' }) writes an entry whose role is 'user'; usage-summary and the voice harvest then treat the tour step as something the user said.

**Suggested fix.** Put the authoritative fields after the spread: `currentLogData.exchanges.push({ ...extra, timestamp: new Date().toISOString(), role: 'event', kind });` (or strip those three keys from extra first). Keep the existing field names so current files are unchanged.

**How to verify the fix.** Add to tests/storage-transcript.test.mjs: start a log, call storage.logEvent('x', { role: 'user', timestamp: '1970-01-01T00:00:00Z', kind: 'y', text: 'hi' }), read the file back and assert the last entry has role 'event', kind 'x', a current timestamp, and text 'hi'.

**Do not break.** Do not nest existing fields (reason, text) under a new key - readers and the Ken-facing record expect them at the top level of the event entry.

**Design reference.** storage.js comment above logEvent ('ONE ENTRY TYPE RATHER THAN A ROLE PER GESTURE'); CLAUDE.md 'THE STANDARD FOR THE RECORD IS CAN IT BE RECREATED TO THE SECOND'

**Verification notes.** Code matches the quote: `{ timestamp, role:'event', kind, ...extra }`, so extra keys would override the three fields. All five callers pass only {reason} or {text} or nothing, so no wrong entry is written today. This is a latent hazard, not an observed defect. Moving the spread first is a harmless hardening.
