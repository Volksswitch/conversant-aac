# CR-290: metrics.log and errors.log grow without limit, and every append rewrites the whole file

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** performance
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/storage.js:2761`
- **Also affects:** `app/js/storage.js:2709-2714 appendErrorFile uses the same keepExistingData+seek append`; `app/js/storage.js:2731-2732 METRICS_FLUSH_LINES / METRICS_FLUSH_MS`
- **Source:** g-storage-overflow-09

**What a user notices.** Over months of use the detailed usage log in the data folder keeps getting bigger, and each save of it copies the whole file, so the background saves during conversations slowly get heavier. On a OneDrive folder, each save uploads the entire file again.

**What is wrong.** flushMetricsFile appends by opening createWritable({ keepExistingData: true }), seeking to the end and writing. With the File System Access API (and OPFS's async writable) a keepExistingData writable starts as a copy of the whole existing file in a swap file, and close() replaces the original - so each append costs the full file size, not the new lines. metrics.log is written up to every 10 s (or every 40 events) during conversations and has no rotation, size cap or pruning anywhere in the app; errors.log likewise. Cost per flush therefore rises linearly with the lifetime of the install. Not measured on a device; the mechanism is the documented behaviour of keepExistingData writables.

**Evidence.**

```
app/js/storage.js:2760-2765
        const fh = await dirHandle.getFileHandle('metrics.log', { create: true });
        const writable = await fh.createWritable({ keepExistingData: true });
        const file = await fh.getFile();
        await writable.seek(file.size);   // append
        await writable.write(lines.join('\n') + '\n');
        await writable.close();
`grep -rn 'metrics.log' app/js` shows no rotation or truncation.
```

**How it happens.** A tester uses the app daily for several months; metrics.log reaches several MB. Every 10 seconds of conversation the browser copies the multi-MB file to append a few hundred bytes, and OneDrive re-uploads it.

**Suggested fix.** Rotate by size: before appending in flushMetricsFile, if `file.size > 1_000_000`, rename/replace by writing the current contents to 'metrics.1.log' (overwriting any previous one, via getFileHandle('metrics.1.log',{create:true}).createWritable() then write(await file.text())) and start 'metrics.log' fresh with createWritable() (no keepExistingData). Apply the same helper to appendErrorFile with a smaller threshold (e.g. 256 KB). Keep the one-previous-file so recent history survives a rotation.

> **Verifier correction to the fix (takes precedence):** Do not rotate to a single 'metrics.1.log' that each later rotation overwrites. That discards the permanent history metrics.js says this file exists to keep. If the cost matters, roll over to new files named by date or sequence (metrics-2026-10.log, …) and never delete older ones, so each append copies only the current small file. Any reader that wants history should read all of them.

**How to verify the fix.** In tests/storage-transcript.test.mjs, pre-fill the in-memory metrics.log with 1.1 MB, call appendMetricsFile + flushMetricsFile, and assert metrics.1.log holds the old content and metrics.log holds only the new line.

**Do not break.** Any reader of metrics.log/errors.log (problem report, Troubleshooting) should read both files if it needs history. Keep the write serialized (metricsWriting).

**Design reference.** storage.js 'Metrics log (August 16 2026)' comment ('opening a writable handle inside the speech path would be a real cost on a tablet')

**Verification notes.** Confirmed that metrics.log and errors.log are appended with createWritable({keepExistingData:true}) + seek and have no rotation or cap anywhere in app/. The per-append cost of copying the whole file is the documented swap-file behavior of File System Access writables, but it is not measured on a device, and the flush rate is buffered (40 lines or 10 s). metrics.js describes metrics.log as 'the permanent detailed record' for offline analysis, so unbounded growth is intended. Only the cost per append is in question.
