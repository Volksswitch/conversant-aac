# CR-291: Typing an Azure key or region fetches the voice list on every keystroke and can end on a stale failure

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** race-condition
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/app.js:7719`
- **Also affects:** `app/js/app.js:7432-7439 (Azure key onChange forces a refetch per keystroke)`; `app/js/app.js:7462-7470 (region input forces a refetch per keystroke)`; `app/js/app.js:7924 (catalog services: refetch per keystroke, no in-flight guard)`
- **Source:** app-f-11

**What a user notices.** Typing an Azure key or region by hand can leave Settings saying the full voice list could not be loaded, even though the final key and region are right, until Settings is closed and reopened.

**What is wrong.** Each keystroke clears the cached Azure catalog and calls refreshAzureVoices({force:true}). While one fetch (made with a partial key/region) is in flight, later calls return early on azureFetchInFlight. If the last keystroke lands during that window, no fetch is ever made with the final value; the in-flight partial request fails and leaves the 'Showing a few voices only' warning and an empty cache. Pasting (one event) avoids it, but typing on the on-screen keyboard does not.

**Evidence.**

```
app/js/app.js:7718-7721
  if (cached && !force) return;
  if (azureFetchInFlight) return;
  azureFetchInFlight = true;
app/js/app.js:7468-7469 storage.clearAzureVoiceCatalog(); refreshAzureVoices({ force: true });
```

**How it happens.** Type 'eastus' into the region box with a valid key: the fetch for 'eastu' is in flight when 's' is typed; the final refresh is dropped; the 'eastu' request fails; the warning stays.

**Suggested fix.** Debounce the refetch (e.g. 600 ms after the last input) and, instead of dropping a request while one is in flight, set a `azureRefetchPending = true` flag that triggers one more fetch with the current key/region when the in-flight one finishes; ignore a response whose key/region no longer match storage. Apply the same debounce to the catalog services' onChange.

> **Verifier correction to the fix (takes precedence):** Fix together with app-f-01. When the in-flight guard moves to module scope, add a 'pending refetch' flag (or a debounce) so a request dropped during flight is re-issued once with the current key and region. Also discard any response whose key and region no longer match storage.

**How to verify the fix.** Manual: type a region character by character with throttled network in DevTools; final state shows 'N English voices available'.

**Do not break.** Keep 'draw the cache first' behavior and the per-key catalog invalidation.

**Design reference.** app.js comment at 7672-7683 ('A failed fetch ... says so on the status line').

**Verification notes.** The mechanism is real. Every keystroke clears the catalog and calls refreshAzureVoices({force:true}). While a fetch is in flight, later calls return at `if (azureFetchInFlight) return` (app.js:7719), and the finally block does not re-run with the newest key or region. If the last keystroke lands while an earlier partial-value request is in flight, no request is ever made with the final value, and the earlier request's failure leaves the 'Showing a few voices only' warning with an empty cache. The next open of Settings refetches, which recovers. Whether this happens in practice depends on how long a partial-region or partial-key request takes against typing speed, which was not measured. Note that the duplicate listeners from app-f-01 currently mask this race after the first open, because each extra copy of the wiring has its own in-flight flag. Fixing app-f-01 alone would make this race more likely, so the two fixes should land together.
