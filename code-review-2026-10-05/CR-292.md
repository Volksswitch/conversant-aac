# CR-292: The panel file is written to disk on every keystroke with no ordering, so the saved copy can end up behind

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** race-condition
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/express-panel.js:123`
- **Also affects:** `app/js/express-panel.js:161-173`; `app/js/express-editor.js:246-249`; `app/js/express-editor.js:261-267`; `app/js/storage.js:380-386`
- **Source:** express-11

**What a user notices.** While typing a phrase in the editor, the app saves the whole panel file once per letter. If those saves finish out of order, the copy in the data folder can be missing the last letters typed, and because the folder copy wins on the next launch, the phrase comes back slightly wrong.

**What is wrong.** Each keystroke in a phrase/label box calls saveBand -> setModel -> writeDisk, which fires storage.writeFile (getFileHandle, createWritable, write, close) without awaiting or serializing. Several writes to the same express-panel.json are in flight at once; with File System Access each createWritable writes a swap file that replaces the target on close(), so the last close() to complete wins, which is not guaranteed to be the last keystroke (especially on OneDrive-synced folders where close can be delayed or fail and is swallowed by `.catch(() => {})`). The localStorage cache is correct, but load()/syncToFolder treat the folder file as the source of truth, so a stale disk copy overrides the cache next session. CLAUDE.md elsewhere notes that per-keystroke whole-file writes were avoided for People/Places for this cost.

**Evidence.**

```
express-panel.js:123-127 `function writeDisk(m) { writeFile(FILE, JSON.stringify({...})).catch(() => {}); }` called from setModel :171 on every edit
express-editor.js:248 `i.addEventListener('input', () => oninput(i.value));` -> :266 `saveBand(band, list);`
```

**How it happens.** Type 'Thanks a lot' quickly into a new Always phrase with a data folder on OneDrive; 12 overlapping writes are issued. If an earlier write's close() completes last, express-panel.json holds 'Thanks a l'. Relaunch: the folder file wins and the button reads 'Thanks a l'.

**Suggested fix.** Serialize and coalesce disk writes in express-panel.js: keep `let writing = null, pending = null;` and in writeDisk set `pending = m`; if a write is running, return; otherwise loop: take pending, set it null, await writeFile(...), repeat while pending is non-null. This guarantees the last model is written last and collapses bursts into at most two writes. Optionally debounce by ~300 ms.

> **Verifier correction to the fix (takes precedence):** The serialize-and-coalesce queue is sound. Route syncToFolder's and resetItems' writes through the same queue, and keep the localStorage cache write synchronous.

**How to verify the fix.** Unit test in tests/express-panel-store.test.mjs with a fake directory whose close() resolves in reverse order (or with random delays): call setModel 10 times with increasing text and assert the final file content equals the last text.

**Do not break.** Keep writes best-effort and non-blocking for the UI; keep writeCache synchronous. syncToFolder and resetItems should go through the same queue.

**Design reference.** CLAUDE.md 'A LIST THAT SHOWS AN ITEM AS ADDED HAS PROMISED IT IS SAVED' (typed fields commit on leave, not per keystroke, for People/Places); v0.2.25 'file in folder wins'

**Verification notes.** The mechanism is real: each keystroke runs setModel -> writeDisk -> storage.writeFile (getFileHandle, createWritable, write, close) with no await or serialization, so several writes to express-panel.json overlap and errors are swallowed. Whether close() calls actually complete out of order on Chromium's FSA or OPFS was not demonstrated, and the same unserialized pattern exists in the other stores. The impact is uncertain.
