# CR-295: Review save: an in-flight write is not awaited on leave, and re-entering uses the list's stale copy of the review, which can roll back answers

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** race-condition
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/review-ui.js:465`
- **Also affects:** `app/js/review-ui.js:145-160 (enter uses entry.review from the list)`; `app/js/review-ui.js:174-192 (leave)`; `app/js/review-ui.js:871 (rows carry c.review captured at list time)`
- **Source:** review-backup-07

**What a user notices.** On a slow tablet, if someone leaves a review just as it is saving and immediately reopens the same conversation, their last answer can disappear.

**What is wrong.** scheduleSave() fires writeNow() after 400 ms; flushSave() only writes if the timer is still pending, it does not await a writeNow() that has already started. leave() therefore can reach openSettingsAt('review') -> renderList() while the write is still in progress, so listConversationLogs reads the previous review file. If the user taps that row, enter() uses `entry.review` (defined, so no fresh read) and immediately schedules a save of that stale review (markReached + scheduleSave), overwriting the newer file once the first write completes. Answers made shortly before leaving and `reached` can be lost.

**Evidence.**

```
review-ui.js:465-467
async function flushSave() {
    if (saveTimer) { clearTimeout(saveTimer); saveTimer = null; await writeNow(); }
}
review-ui.js:463  saveTimer = setTimeout(() => { saveTimer = null; void writeNow(); }, 400);
review-ui.js:149
    const raw = entry.review !== undefined ? entry.review : await storage.readReview(entry.id);
review-ui.js:158-159
    review = model.markReached(review, 0);
    scheduleSave();
```

**How it happens.** Android tablet: mark a card, wait ~450 ms (timer fired, write in progress), tap Settings, tap the same row again. The review opens without the mark and saves that state.

**Suggested fix.** Track the write promise: `let writing = null;` in writeNow set `writing = storage.writeReview(...)` and await it; in flushSave `if (saveTimer) {...} if (writing) await writing;`. In enter(), always read the review fresh: `const raw = await storage.readReview(entry.id);` (ignore entry.review), which also removes any staleness from an old list render.

**How to verify the fix.** Unit test in tests/review.test.mjs is hard (DOM); manual check with a throttled write, or a small test of a promise-tracking helper. Confirm the list still renders quickly (enter() reading one file is cheap).

**Do not break.** The conversation file must still never be written by review. Keep 'reached' monotonic.

**Design reference.** Conversant AAC Conversation Review.docx §5 (stores what they write as they write it)

**Verification notes.** flushSave() awaits only when saveTimer is still pending; once the 400 ms timer has fired, writeNow() is running and leave() does not wait for it. renderList then reads review files through listConversationLogs, and enter() uses entry.review captured at list time, then markReached + scheduleSave writes that copy back. If the list read the review file before the in-flight write closed, the stale copy can overwrite it. The list has to read every conversation first, which usually takes longer than one small write, so the window is narrow and was not reproduced.
