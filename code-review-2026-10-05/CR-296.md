# CR-296: Two log writers arriving together each start the conversation file, duplicating the start entry

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** race-condition
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/storage.js:2120`
- **Also affects:** `app/js/app.js:1730 (startConversationLog not awaited)`; `app/js/app.js:2246-2249 (finalizePartnerTurn and logUserResponse not awaited)`; `app/js/storage.js:2313 (logOffer lazy start)`; `app/js/storage.js:2384 (logUserResponse lazy start)`
- **Source:** storage-08

**What a user notices.** A saved conversation can list its starting situation (who, where, how you felt) two or three times at the top, which confuses Conversation Review and any later replay.

**What is wrong.** startConversationLog checks `if (currentLogData) return` and then awaits getConversationsDir() before assigning currentLogData. Two callers entering in the same tick (e.g. app.js startFreshListening's unawaited startConversationLog() alongside an unawaited logUserResponse/logOffer that starts the log lazily) both pass the check; each replaces currentLogData, resets pendingPartnerTurn/pendingOffer, and pushes its own 'context start' entry. Reproduced in Node against the real storage.js: three concurrent starts produced ['context','context','context','user','offer'].

**Evidence.**

```
app/js/storage.js:2122-2134:
    if (currentLogData) return currentLogName; // already started for this conversation
    const dir = await getConversationsDir();
    ...
    currentLogData = { id, started: now.toISOString(), exchanges: [] };
    pendingPartnerTurn = null;
    pendingOffer = null;
```

**How it happens.** First action of a session is an Express phrase with auto-listen re-arming: speakAsUserTurn logs the user turn (lazy start) while startFreshListening calls startConversationLog(); both start the log and the file gets two 'context start' entries (and a pendingOffer recorded by one may be nulled by the other).

**Suggested fix.** Memoize the in-flight start: add `let logStarting = null;`, rename the body to `async function doStartConversationLog()`, and export `export function startConversationLog() { if (!conversationSaving) return Promise.resolve(null); if (currentLogData) return Promise.resolve(currentLogName); if (!logStarting) logStarting = doStartConversationLog().finally(() => { logStarting = null; }); return logStarting; }`. Also set `logStarting = null` in resetConversationId.

**How to verify the fix.** Add to tests/storage-transcript.test.mjs: with a context provider set, call startConversationLog(), logUserResponse(...), logOffer(...) without awaiting, await all, and assert exactly one 'context' entry with trigger 'start'.

**Do not break.** The context snapshot must still be entry number one of every conversation; private conversations must still create nothing.

**Design reference.** storage.js comment at 2209-2226 (time zero snapshot is entry number one by construction)

**Verification notes.** startConversationLog (storage.js:2120) checks currentLogData, then awaits getConversationsDir() before assigning it, so two callers in the same window both pass the check, each pushes a 'context start' entry and resets pendingPartnerTurn/pendingOffer. The reachable concurrent pairs are narrow: in speakAsUserTurn an opening Express phrase calls logUserResponse unawaited inside commitExchange and then, after several microtasks, startFreshListening calls startConversationLog; whether the first call has passed its await by then depends on whether conversationDirHandle is cached (one microtask) or needs real I/O (first conversation after connecting). The reviewer's reproduction used three artificially simultaneous calls, not an app path. Not confirmed reachable.
