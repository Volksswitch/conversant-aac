# CR-297: On iPad, a delayed recognizer restart ignores a backgrounding that happened during the delay

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** race-condition
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/stt.js:494`
- **Also affects:** `app/js/stt.js:531-535 (visibility guard sets suspendedForHidden and stops)`
- **Source:** x-async-16

**What a user notices.** On an iPad, switching away from the app at just the wrong moment can restart speech recognition in the background, which can leave the microphone button lit but deaf when the user returns.

**What is wrong.** With restartDelayMs 200 on iOS, onend schedules recognition.start() in a setTimeout that only checks listeningIntent. If the page is hidden in those 200 ms, the guard sets suspendedForHidden=true and stops (nothing is running), then the timer starts recognition while hidden - exactly what the guard exists to prevent (the stats even count 'restartsWhileHidden').

**Evidence.**

```
stt.js:494-498 `setTimeout(() => { if (!listeningIntent) return;      // stopped while we waited
                    noteListen('sessions');
                    try { recognition.start(); } catch { } }, speechCfg.restartDelayMs);`
```

**How it happens.** iPad Safari tab, listening: a non-continuous session ends; within 200 ms the user presses the Home button. The delayed start runs while hidden.

> **Verifier correction to the trigger:** The likely visible effect is a recognizer start (or failed start) while hidden and a 'stopped' status flicker, after which the visibility guard reopens on return; a permanently deaf lit button was not demonstrated.

**Suggested fix.** Change the timer's check to `if (!listeningIntent || suspendedForHidden) return;`.

**How to verify the fix.** Add to tests/stt.test.mjs: with iOS speechConfig, trigger onend, set suspendedForHidden via a hidden visibilitychange before advancing timers, assert recognition.start was not called.

**Do not break.** None.

**Design reference.** stt.js visibility-guard comment; CLAUDE.md iPad probe findings (recognition stops when backgrounded)

**Verification notes.** The restart setTimeout (stt.js:494-498) checks only listeningIntent, not suspendedForHidden, so if the page is hidden within the 200 ms iOS restart delay the guard marks suspendedForHidden and the timer still calls recognition.start() while hidden. Mechanism is real, but the claimed 'lit but deaf' outcome is uncertain: a session that ends while hidden hits onend's else branch (suspendedForHidden true -> 'stopped'), and on return the guard reopens the source. The one-line guard fix is still correct.
