# CR-298: setSource() abandons the old built-in recognizer with its handlers still attached, so its late events act on the newly chosen service

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** race-condition
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/stt.js:584`
- **Also affects:** `app/js/stt.js:457-465 (onresult)`; `app/js/stt.js:467-507 (onend, incl. the restartDelayMs setTimeout that calls the module-level recognition.start())`; `app/js/stt.js:543-552 (onerror -> handleSourceError -> listeningIntent = false)`; `app/js/stt.js:660-663 (handleSourceError)`; `app/js/app.js:7368 (only caller)`
- **Source:** g-stt-overflow-03

**What a user notices.** Rarely, right after the hearing service is changed in Settings and listening is started straight away, the Listen button can switch itself off while the new service is still listening, or words heard by the old service can appear in the new turn.

**What is wrong.** setSource() calls stopListening() (which calls recognition.stop(), an asynchronous stop) and then sets `recognition = null` and re-runs init(). The old SpeechRecognition object keeps its onresult/onend/onerror handlers, and those handlers close over MODULE-level state (listeningIntent, segments, currentInterim, silenceTimer, onStatusChange, and the module-level `recognition` variable), not state belonging to the old object. Chrome delivers a final onresult for audio captured before stop(), then onend, and can deliver onerror (e.g. 'network') late. If the user has meanwhile started listening on the new service: (1) a late old onerror with a non-ignored error runs handleSourceError -> listeningIntent = false and onStatusChange('error') -> app sets isListening = false, the Listen button goes dark and an 'stt' error is logged, while the new paid source keeps capturing; (2) a late old onend sees listeningIntent === true and takes the restart branch: it commits the NEW service's currentInterim into segments and calls recognition.start() on whatever `recognition` now is (null for a paid source -> caught throw; noteListen('sessions') miscounts); (3) a late old onresult ingests the old service's words into the buffer that setSource() just cleared, contradicting setSource's own comment that the words do not cross the switch, and arms the silence timer. Settings is modal, so the window requires closing Settings and tapping Listen before the old recognizer finishes stopping (a few hundred ms in Chrome; the iPad restart-delay path adds 200 ms) - hence low severity and low confidence on reachability. Paid sources are not affected: stt-rest/stt-azure guard with a generation counter and the Deepgram socket stops dispatching after close().

**How it happens.** 1. Built-in hearing, partner mid-sentence, user opens Settings -> Speech and picks OpenAI (or Deepgram). 2. setSource stops the browser recognizer (async) and builds the OpenAI source. 3. User closes Settings and taps Listen at once (listeningIntent = true, OpenAI source starting). 4. The old recognizer's final onresult arrives: its words are added to the new, supposedly empty turn and a silence checkpoint is scheduled; or its onerror('network') arrives: the Listen button turns off and the transcript red-washes while OpenAI is still capturing.

**Suggested fix.** In setSource(), before `recognition = null;`, detach and abort the old recognizer:
    if (recognition) {
        const old = recognition;
        old.onresult = null; old.onend = null; old.onerror = null;
        try { old.abort(); } catch { /* not running */ }
    }
(abort() discards pending results instead of delivering them, which is what a service switch wants.) Also make the onend restart branch use a captured reference rather than the module variable: in init(), `const rec = recognition;` and inside the restart setTimeout and the immediate path use `if (!listeningIntent || recognition !== rec) return; rec.start();` so a stale timer cannot touch a newer source.

**How to verify the fix.** In tests/stt.test.mjs add: `stt.startListening(); const old = rec; stt.setSource('openai'); stt.resumeListening();` then call `old.onerror && old.onerror({ error: 'network' })` and `old.onresult && old.onresult(...)` (or use the fake's emitFinal) and assert statuses has no 'error' after the switch and getCurrentTranscript() === ''. Check the fake in tests/env.mjs supports abort(); add a no-op abort if not.

**Do not break.** stopListening() must still be called first so the user's intent is cleared (setSource comment). Do not remove the existing 'switching away stops the service that was listening' test expectations. The built-in path's own restart-on-end behavior during normal listening must be unchanged.

**Design reference.** stt.js setSource comments (Sept 30 2026: 'THE OLD SOURCE IS TORN DOWN FIRST', 'The words heard by the previous service belong to the previous service'); CLAUDE.md '⚠ HEARING COULD FAIL FOREVER IN SILENCE, AND THE SERVICE COULD NOT BE CHANGED WITHOUT A RESTART'

**Verification notes.** The mechanism is real. setSource() calls stopListening(), which calls recognition.stop(). stop() is asynchronous, and Chrome still delivers a final onresult and then onend. setSource() then sets recognition=null, resets the transcript and re-inits, but leaves the old object's handlers attached. Those handlers act on module-level state. A late onresult is not checked against listeningIntent, so its words can land in the freshly cleared buffer. That needs no fast Listen tap, only that the browser recognizer was hearing speech when the service was changed in Settings. The following onend (with listeningIntent false) clears the silence timer, so no checkpoint fires. But the stray words stay in the buffer and would make the next Listen tap take the resume path and keep them. The error and restart cases need the user to restart listening before the old recognizer finishes stopping, which Settings being modal makes unlikely. Could not confirm Chrome's timing, so plausible.
