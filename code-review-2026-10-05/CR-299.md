# CR-299: A closed Deepgram socket's leftover handlers can fail the next sentence on the new connection

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** race-condition
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/tts-deepgram.js:197`
- **Also affects:** `app/js/tts-deepgram.js:274-286`; `app/js/tts-deepgram.js:220`; `app/js/tts-deepgram.js:605`; `app/js/tts-deepgram.js:677`
- **Source:** tts-08

**What a user notices.** Rarely, right after a voice change, a retry or a Settings voice test, the next sentence switches unexpectedly to the device voice.

**What is wrong.** closeSocket() calls socket.close() and nulls the reference but leaves the old WebSocket's onclose/onerror handlers attached. The close event arrives asynchronously (after the closing handshake, which can be slow on a bad network - exactly when retries happen). Its handler calls failPending('The connection to the voice service closed.') unconditionally, which rejects whatever `pending` exists at that moment - by then possibly the NEW utterance on the NEW socket. The `socket === ws` check guards only the bookkeeping, not failPending. onerror likewise calls failPending unconditionally.

**Evidence.**

```
tts-deepgram.js:197-203 `function closeSocket() { stopKeepAlive(); if (!socket) return; try { socket.close(); } ... socket = null; socketModel = null; }` (handlers not detached)
tts-deepgram.js:281-285 `ws.onclose = () => { ... if (socket === ws) { ... } failPending('The connection to the voice service closed.'); ...`
tts-deepgram.js:274-279 onerror also calls failPending unconditionally
```

**How it happens.** Deepgram, slow network: a synthesis times out ('took too long', no audio yet), synthesizeWithRetry calls closeSocket() and opens a new socket; the new socket opens and the retry's pending is set before the old socket's close event arrives; the late close event rejects the retry, and tts.js falls back to the device voice.

**Suggested fix.** In both ws.onerror and ws.onclose, only touch pending when this socket is the current one or is the one still connecting: e.g. capture `let mineActive = true;` and in closeSocket() detach handlers before closing: `const old = socket; old.onopen = old.onmessage = old.onerror = old.onclose = null; try { old.close(); } catch {}`. Keep the connect-phase reject path working by leaving handlers on a socket that has not opened yet (closeSocket only deals with an opened `socket`).

**How to verify the fix.** Add to tests/tts-deepgram.test.mjs: mock WebSocket whose close() fires onclose 200 ms later; first synth times out (use fake timers), retry opens a second socket that streams normally; assert speak() resolves.

**Do not break.** The connect-time failure paths (onerror/onclose before open) must still reject connect() so the fallback happens promptly.

**Design reference.** none

**Verification notes.** closeSocket() (197-203) nulls the reference and calls close() without detaching handlers; the old ws.onclose (281-286) and onerror (274-279) call failPending unconditionally (the `socket === ws` check guards only bookkeeping). In synthesizeWithRetry (597-608) the dead socket is closed and a new one opened immediately; if the new socket opens and sets `pending` before the old socket's close event fires, the late event rejects the retry and tts.js falls back to the device voice. This is a real race in the code, but whether the old close event commonly arrives after the new socket is open and pending is set depends on network timing that was not demonstrated.
