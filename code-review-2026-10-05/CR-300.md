# CR-300: Two report sends can run at the same time and overwrite each other's queue, sending duplicates or dropping a report

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** race-condition
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/weekly-send.js:355`
- **Also affects:** `app/js/weekly-send.js:489`; `app/js/weekly-send.js:413`; `app/js/app.js:8514`
- **Source:** reporting-platform-10

**What a user notices.** A problem report sent from the launch screen just before pressing Start can arrive twice, and in a bad network moment a report can be silently dropped.

**What is wrong.** flush() reads the queue into a local variable, awaits the network, then writes back `queue.slice(1)`. It has no in-progress guard. sendProblemReport() (launch screen or Troubleshooting) and maybeSend() (3 s after Start) each enqueue and call flush() independently. If they overlap, the second flush posts the same head payload again (duplicate row/email), and the first flush's `saveWeeklyQueue(queue.slice(1))` overwrites the queue the second call just saved, so an item enqueued in between can vanish if the second flush then stops on a failure.

**Evidence.**

```
app/js/weekly-send.js:356-386: `let queue = storage.loadWeeklyQueue(); ... outcome = await post(payload); ... queue = queue.slice(1); storage.saveWeeklyQueue(queue);`
app/js/weekly-send.js:489-490: `storage.saveWeeklyQueue(enqueue(storage.loadWeeklyQueue(), payload)); return await flush();`
```

**How it happens.** Tester presses 'Report a problem' on the launch screen and confirms; the Apps Script answers slowly (cold start, several seconds). They press Start; 3 s later maybeSend enqueues the weekly report and starts a second flush, which re-posts the problem report. Result: the problem report row and email appear twice.

> **Verifier correction to the trigger:** No weekly report needs to be due. maybeSend calls flush() on every Start, about 3 seconds in, even when shouldSend is false, so pressing 'Report a problem' on the launch screen and then Start within a few seconds is enough to post the same problem report twice while the first post is still waiting.

**Suggested fix.** Serialize flushes with a module-level promise: `let flushing = null; export function flush() { if (flushing) return flushing.then(() => flushImpl()); flushing = flushImpl().finally(() => { flushing = null; }); return flushing; }` (rename the current body flushImpl), and inside flushImpl re-read the queue from storage after each post and remove the sent item by identity (e.g. match `sentAt` + `installId` + `kind`) rather than writing back a stale slice.

**How to verify the fix.** Add to tests/weekly-send-delivery.test.mjs: stub fetch with a delayed 'ok', call sendProblemReport and maybeSend concurrently, and assert fetch was called exactly once per payload and the queue ends empty.

**Do not break.** Keep the 'only an accepted report leaves the queue' rule. flush must still never throw.

**Design reference.** CLAUDE.md 'THE ENDPOINT'S REPLY IS READABLE' (queue semantics)

**Verification notes.** flush() has no re-entry guard. It reads the queue, awaits post(), then saves a slice of its own stale copy. sendProblemReport and maybeSend both call flush independently. The race is real if the Apps Script reply takes several seconds (cold starts do). I did not run it.
