# CR-301: A layout drag that loses its pointerup leaves the whole app unclickable

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** resource-leak
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/app.js:5089`
- **Also affects:** `app/js/app.js:5034-5036 and 5076-5078 (window listeners added)`; `app/js/app.js:5122-5130 (endLayoutDrag is the only cleanup)`; `app/css/styles.css:1404 (body.layout-dragging * { pointer-events: none !important; })`
- **Source:** app-d-10

**What a user notices.** Rarely, if a border drag is interrupted (for example the mouse button is released outside the window), every button stops responding and moving the mouse keeps resizing the screen until the next click.

**What is wrong.** The drag is ended only by a pointerup/pointercancel reaching window. No setPointerCapture is used and onLayoutDrag never checks e.buttons, so if the release is not delivered (window loses focus mid-drag via Alt-Tab, release outside the browser window, a system dialog), body keeps class layout-dragging - which sets pointer-events:none on every element - and every subsequent pointermove keeps rewriting the layout even though no button is pressed.

**Evidence.**

```
app/js/app.js:5089-5090
  function onLayoutDrag(e) {
      if (!layoutDrag) return;
app/css/styles.css:1404  body.layout-dragging * { pointer-events: none !important; }
```

**How it happens.** Desktop, layout unlocked: start dragging a border with the mouse, press Alt-Tab while holding the button, release, switch back. Moving the mouse resizes the region with no button held; Command Bar buttons ignore clicks until a click somewhere ends the drag.

**Suggested fix.** At the top of onLayoutDrag add `if (e.pointerType === 'mouse' && e.buttons === 0) { endLayoutDrag(); return; }`. Also add `window.addEventListener('blur', endLayoutDrag);` alongside the pointerup/pointercancel listeners in both onHandlePointerDown and onLayoutPointerDown, and remove it in endLayoutDrag.

**How to verify the fix.** Manual reproduction above: after the fix, the first mouse move with no button held ends the drag and buttons respond.

**Do not break.** Do not end touch drags on buttons===0 checks (touch pointermove reports buttons=1 while down; keep the pointerType guard).

**Design reference.** none

**Verification notes.** The mechanism is real: the drag ends only on pointerup or pointercancel reaching window, there is no pointer capture and no e.buttons check, and body.layout-dragging sets pointer-events:none on everything. Whether a release outside the window or an Alt-Tab actually loses the pointerup is browser-dependent; Chromium usually delivers mouseup for a press that began in the page, even outside the window. Not reproduced.
