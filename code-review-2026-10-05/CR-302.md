# CR-302: IndexedDB helpers open a new database connection on every call and never close it

Part of the [October 5, 2026 code review](README.md). Read its instructions before fixing.

- **Severity:** low
- **Category:** resource-leak
- **Verdict:** plausible (skeptic: plausible)
- **Location:** `app/js/storage.js:19`
- **Also affects:** `app/js/storage.js:28-56 idbGet/idbPut/idbDelete`; `app/js/storage.js:138 hasRememberedFolder`; `app/js/storage.js:155 page-load prime`; `app/js/storage.js:241 restoreDataFolderInner`; `app/js/storage.js:298 pickDataFolder`; `app/js/storage.js:319 clearDataFolder`; `app/js/worldview-ui.js:109 restoreDataFolder on every About Me open`; `app/js/app.js:621, 1430, 1602 callers`
- **Source:** g-storage-overflow-06

**What a user notices.** Nothing visible today. Each check of the remembered data folder leaves an open database connection behind; if the app ever needs to change that small database's layout, an already-open copy of the app (another tab, or the same page) would block the change and the folder lookup would hang instead of failing.

**What is wrong.** idbOpen() calls indexedDB.open(IDB_NAME, 1) each time, and idbGet/idbPut/idbDelete never call db.close(). The connection outlives the transaction and stays open until the page unloads (the IDBDatabase is kept alive by the browser while open). restoreDataFolder() runs at page load (prime), at Start, on every About Me open (worldview-ui.js:109) and from the reconnect card, so connections accumulate per session. idbOpen also has no onblocked handler: open connections prevent any future versionchange, and an open() that is blocked neither resolves nor rejects, so a later schema bump would hang hasRememberedFolder/restoreDataFolder (which the Start sequence awaits behind a timeout) rather than fail cleanly. No onversionchange handler closes the old connection either.

**Evidence.**

```
app/js/storage.js:19-25
function idbOpen() {
    return new Promise((resolve, reject) => {
        const req = indexedDB.open(IDB_NAME, 1);
        req.onupgradeneeded = () => req.result.createObjectStore(IDB_STORE);
        req.onsuccess = () => resolve(req.result);
        req.onerror = () => reject(req.error);
    });
}
app/js/storage.js:28-35  const db = await idbOpen(); ... tx.objectStore(IDB_STORE).get(key) ... resolve(req.result)   // db never closed
```

**How it happens.** Open About Me ten times in a session: ten connections to 'aac-db' remain open. If a future release opens 'aac-db' at version 2 while a second tab of the old build is open, the upgrade is blocked and the folder restore never settles.

**Suggested fix.** Cache one connection: `let dbPromise = null; function idbOpen() { if (!dbPromise) { dbPromise = new Promise((resolve, reject) => { const req = indexedDB.open(IDB_NAME, 1); req.onupgradeneeded = () => req.result.createObjectStore(IDB_STORE); req.onsuccess = () => { const db = req.result; db.onversionchange = () => { db.close(); dbPromise = null; }; resolve(db); }; req.onerror = () => { dbPromise = null; reject(req.error); }; req.onblocked = () => { dbPromise = null; reject(new Error('IndexedDB open blocked')); }; }); } return dbPromise; }`. idbGet/idbPut/idbDelete stay as they are (they reuse the shared connection).

**How to verify the fix.** Manual: in Chrome DevTools > Application > IndexedDB, open About Me several times and confirm only one connection (or run in node with fake-indexeddb, if added, counting open() calls). Unit: in a test that stubs globalThis.indexedDB, call storage.hasRememberedFolder() three times and assert indexedDB.open was called once.

**Do not break.** The stored value is a FileSystemDirectoryHandle; do not change the store name, key or version. Every caller already wraps these in try/catch; keep rejections (not hangs) as the failure mode.

**Design reference.** none

**Verification notes.** idbOpen does open a new connection on every idbGet/idbPut/idbDelete and nothing calls db.close(). However, the IDB spec lets a connection object with no versionchange/abort/error listeners be garbage-collected and closed, so the claim that open connections accumulate is not established. The blocked-upgrade hang needs a future schema-version bump that does not exist, and onblocked does not cause a hang by itself (the open waits until other connections close). The impact is hypothetical; caching one connection with an onversionchange handler is reasonable hardening.
