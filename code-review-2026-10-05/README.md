# Code Review Findings: October 5, 2026

This is a review of the Conversant AAC code as of commit `dbeb4d5` (version 0.13.5 in development). It lists problems found in the app: bugs, places where the screen behaves inconsistently, security and privacy weaknesses, and code that does not do what CLAUDE.md or a design document says it should.

Each item is in its own file in this folder (`CR-001.md`, `CR-002.md` and so on), so a working session can be handed one item and fix it without having seen the rest of the review. Every item starts with a plain sentence saying what a person using the app would notice. The rest of each item is for the engineer.

## How the review was done

Twenty-eight reviewers each read one part of the code, or looked at one concern across all of it: security, data passed between parts of the app, CLAUDE.md's standing rules, timing problems, the six speech services, settings defaults, accessibility, and two that ran the real app in a headless browser. Seven more then wrote up what the first round had found but run out of room to describe, and covered the gaps the first round left.

Every finding then went to a skeptic who tried to disprove it. Each high or critical finding also went to a second checker, who tried to make the problem actually happen without seeing anyone else's verdict. Findings that did not survive were dropped. Findings that turned out to be a recorded decision, or were already open in TODO.md, are listed in the appendices instead of the main list. Findings that described the same root cause were merged.

The checkers disproved very few findings. That reflects how the reviewers worked (each one traced a path before reporting), but it also means a "confirmed" item still deserves a second look at the code before it is changed.

## Where to start

The first thirteen items (one critical, twelve high) are where the real harm is: a saved conversation that can be overwritten, a paid hearing service that is quietly swapped for the free one after every restart, a repair card that crashes, edits typed with the on-screen keyboard that are never saved, and three ways private information leaves the device or outlives a "Don't save" conversation. Fix those first, in order.

Most of the low items are small and independent. Several "medium" and "low" items are about tests that would have caught the high ones (CR-072, CR-073); they are cheap and worth doing right after the bugs they describe.

## Instructions for the session that fixes these

- **Re-read the code before changing it.** Line numbers are as of `dbeb4d5` and will drift as fixes land. Search for the quoted code rather than trusting the number.
- **"Confirmed"** means a checker traced the problem end to end, or made it happen. **"Plausible"** means the mechanism is real but nobody could prove the trigger is reachable. Confirm a plausible item yourself before changing code for it, and drop it if it does not hold up.
- **Where a verifier correction appears under an item, it takes precedence** over the original suggested fix.
- **Work one item at a time, most severe first.** Commit each fix to local `main` on its own, and do not push: a push to `main` deploys the app to every tester.
- **Run `npm test` after each fix**, and add the test the item suggests. A fix that crosses layers needs one check that crosses all of them (CLAUDE.md, Working Guidelines).
- **A fix a user would notice gets a plain-English bullet** under `## Unreleased (next release)` in `CHANGELOG.md`, in the same commit. A problem that only existed inside the current development cycle is not a "fix" for users (CLAUDE.md, Versioning).
- **If a fix would contradict a decision recorded in CLAUDE.md, stop and ask Ken.** Some findings question a decision rather than a slip; those are Ken's call.
- **Watch the traps CLAUDE.md records:** keyguard geometry must not move (no padding, border, or margin changes on grid cells); "Don't save this conversation" must be honored by every writer; API keys never go into any export, report, or log; partner speech never leaves the device automatically.
- **When an item is done**, change its Status in the table below from "open" to "fixed (commit)", or "dropped" with a one-line reason, so the next session does not redo it.
